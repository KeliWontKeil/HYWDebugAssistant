# ADR-0053：**叠加层的两个信息维度 + 角色自身信息 + 线的端点与流向**（第三十四轮观感修正）

> **状态**：**Accepted + 已落地**（用户第三十四轮复验反馈 5 条，逐条落实；2026-09）。
>
> **关联**：修订 **ADR-0052**（角色方块的内容与信息落点）· 修订 **ADR-0049**（D14 线的端点、D15 断口、D17 信息卡 → 改为角色信息文字）·
> 沿用 ADR-0045（灰玻璃遮罩 / 层级 / 共享 20Hz 时钟 / 中点色）与 ADR-0044（方向语义色）。
>
> **性质**：**观感与信息设计**修订（不改角色语义、不改建网与判定口径）。

---

## 1. 用户原话（本轮唯一依据）

> "首先是几个 UI 问题：
> **1. 各种错位**，连线错位/文本框错位，同时我希望**连线从角色方块中心出发**，以及**虚线的流动方向有问题**，现在输入/输出均为**中心块向外**；
> **2. 中心块太大了**观感不好，建议使用**文本自适应宽度**；
> **3. 我希望信息表示更接近我给你的示意图，不显式绘制文本框**，其大致位置位于**角色方块周围/上方**，
> 这些信息表达的**不是"数据通路信息"，而是"角色本身速率信息"**，也就是说**每一个角色块显示其自身的信息**。
> **4. 网络标签上缺少速率显示**，这才是"**数据通路速率**"，可能实际底层实现读取与叠加层的信息相同，
> 但是**用户感知到的不是一个维度的信息**。
> **5. 我认为从 UI 表现上，仍然没有区分两个不同的信息维度**，之前说的**网络标签不高亮**也没有做，
> 可能文档写明了，但是似乎并没有落实。
> 也就是说，我认为'**两处观感问题仍等你定方向**'这两个问题从设计上不成立。**数据包类型表暂缓，先完善叠加层观感**。"

**归纳成一句**：**角色维度**（"这块功能自己在跑多快"）画在**角色方块**上；**通路维度**（"这条网络在跑多快"）画在**端口标记（网络标签）**上；
两个维度在视觉上必须**一眼可分**（角色高亮、接口层降权），而不是把两件事都堆在"线上的一个文本框"里。

## 2. 逐条落地（D1–D5）

### D1. 线的端点 = **两个角色方块中心**；绘制方向 = **数据流方向**

| 项 | 决定 |
|---|---|
| **几何端点** | 一条线 = **本端角色方块中心 ↔ 对端角色方块中心**（`ConnectionOverlay.LinkSegment`，纯函数） |
| **绘制裁剪** | 画出来的那一段 = 该线段**落在本窗内**、**且在本端方块之外**的部分 ⇒ 起点/终点落在**方块边界**（朝对端那一点）。⇒ 视觉上"从方块中心方向出发"，又**不会在方块里留一道淡线**、也不会横穿方块（旧实现按"左/右接口侧中点"取端点，对端在反方向时线会从方块另一侧出发并穿过方块 —— 用户说的"连线错位"） |
| **两侧共线** | 两端都用**同一个** `LayoutRoles` + `LinkSegment` 算 ⇒ 两窗各画的那段落在同一条直线上（相邻无缝、未拼接恰好缺两窗之间那段） |
| **箭头** | 画在**指向本模块的那一端**（发送 ⇒ 朝窗外；接收 ⇒ 朝本端方块） |
| **断口 + 对端名** | 未拼接时画在**窗口边界那一端** |

### D2. 虚线**沿数据流方向**流动（并修正了一个真正的"方向反了"）

- **约定（实测得出，不靠文档）**：`DashStyle.Offset` **增大 ⇒ 虚线图案整体朝几何起点移动**；
  且它的**单位是笔宽的倍数**（不是 DIP）—— 由渲染实测确认（笔宽 2、偏移 +2 ⇒ 实测位移 **4 DIP**）。
- **修法**：线的几何**恒按数据流方向**绘制（D1）⇒ 两侧取**同一个偏移量** = `-相位 ÷ 线宽`
  （`OverlayAnimationClock.DashOffset`）；取负 ⇒ 图案沿绘制方向**从起点向终点**前进；
  除以线宽 ⇒ "20Hz × 1.2 DIP/秒"的相位约定真的成立（否则速度会随线宽变化）。
- **为什么之前反了**：上一版按"两侧各自把方块中心当起点"给两侧取了**相反数**（发送 `-相位`、接收 `+相位`）。
  在**新几何**下接收侧那一段的起点是**窗口边界**，"朝起点移动"就表现为**向外** ⇒ 用户看到的"输入/输出均为中心块向外"。
  ⇒ 现在两侧同号，配合 D1 的绘制方向，**发送向外、接收向内**。

### D3. 角色方块**宽度随文本自适应**（去掉"固定 128 + 缩小档"）

- 宽度由 **`RoleTextMetrics.BoxWidth`** 估算（CJK 一个字宽 ≈ 字号、拉丁 ≈ 0.6 字号，留 5% 余量），
  夹在 **[64, 176]** 之间；块高统一 **34**（原 42）。
- **必须是确定性纯函数**：宽度同时被**两端**用来算连线锚点 ⇒ 不能依赖渲染期排版（字体缺失/主题差异会让两侧不一致 ⇒ 线又错位）。
- **阶梯简化**：放不下 ⇒ 只画得下的 + 底部 **`+K`**（如实报出）；原"先缩方块再隐藏"的中间档**删除**（文字自适应后已无意义）。

### D4. 角色信息 = **方块周围/上方的纯文字**（不画文本框）

| 行 | 内容 | 字号 | 来源（框架口径，UI 只格式化） |
|---|---|---|---|
| ① | **该角色自身的速率**（无流量 `---`） | 11px · 叠层主色 | `RoleView.RateBytesPerSecond` = 该角色**产出侧**承载网络的 `BusByteRate` 之和 |
| ② | `投递 … · 丢弃 …` | 10px · 叠层次色 | `RoleView.Delivered` / `Dropped`（同口径聚合；丢弃 = **传输丢弃**） |
| ③ | 类型语义 · 标称速率 | 10px · 叠层次色 | `RoleView.SemanticText` / `NominalRateHz`（未声明 ⇒ 不占位） |

- **位置**：默认在方块**上方**（居中，间隙 5）；上方放不下（会压到左上身份/出窗）⇒ 自动改到**下方**；
  一律留在 `Gutter` 以内。
- **口径**（"角色自身"到底指什么）：**产出侧优先** —— 有输出口 ⇒ 聚合它的**输出网络**；纯汇分块 ⇒ 聚合它的**输入网络**。
  **不把入/出两侧相加**：那是多条不同通路的和，会被读成"这块功能的总吞吐"（口径不清）。
- **删除**：`RoleLinkViewModel` 上的 `RateText`/`TrafficText`/`MetaText`（连同 `DrawCard` 与 `OverlayCard` 令牌）——
  线**不再承载任何文字**。

### D5. 网络标签：**显示通路速率** + **叠加层里降权（不高亮）**

| 项 | 决定 |
|---|---|
| **通路速率** | 标记上显示 **`RateText`**（该口所在网络的搬运字节速率；未入网/无流量 = `---`）；字号 **10**（比名称小一号）。〔**§5 D7 修订**：**常驻**显示，与叠加层开关**解耦**〕 |
| **降权** | 〔**§5 D6 修订：本行已作废**〕原做法是"叠加层开启时给标记加 `overlay` 类（中性边框 / 名称变暗 / 箭头降透明度 + 不透明度 0.88）" ——
用户明确否决："网络标签不高亮**指的不是在上面覆盖一层**，我的意思是**做减法**，将网络标签也**埋入灰色玻璃下方**" ⇒ 改为**层级**实现，样式整体删除 |
| **为什么** | 用户："网络标签是**数据接口的抽象**……不该在叠加视图里高亮" + "仍然没有区分两个不同的信息维度" ⇒ 视觉上必须"**接口层沉下去、角色层浮上来**" |
| **两个维度各自的出处** | 角色维度 ⇒ **角色方块**（D4）；通路维度 ⇒ **端口标记**（本 D5）。二者读**同一份**框架诊断，但**表达对象不同**（用户明确：不能因为底层同源就当作一个维度） |

## 4. 渲染自检结论（`%TEMP%\hyw-overlay-snapshot\*.png`，逐张放大看过）

- ✅ 方块明显变小（宽度贴文字：`发送` ≈ 64、`显示` ≈ 64），不再"太大";
- ✅ 信息在方块**上方、左对齐、无边框**（大字 `---` + `输入 0 / 输出 1`），随方块走；
- ✅ 连线从**方块边界朝对端方向**出发（汇集于方块下边两点），不再横穿方块、不再与文本框错位（**没有文本框了**）；
- ✅ **端口标记沉在灰玻璃之下**（做减法）：`bus`/速率的文字、箭头、灯都变暗，不再抢眼；未入网时灯是空心（正确）；
- ⚠️ **一处仍可再调**：虚线会从角色信息文字上穿过（文字画在线上层，仍可读）——若你觉得碍眼，我可以给信息文字加一层极淡的底衬（或让线绕开信息块）。

## 5. 二次修正（用户手工实测后 3 条裁定 · D6–D8）

> 本节是**二次修正**的裁定条目所在（裁定见文末修订记录第 2 行）。为避免同一事实写两遍，
> 三条裁定的**结论文本**就地写在 §2 的对应条目里，本节 D6/D7/D8 给出条目定位与一句话结论。

### D6. "网络标签不高亮" = **做减法**

见 **§2 D5** 表「**降权**」行：标记层排到**遮罩之前**（被灰玻璃压暗），**删除**上一版给标记加的降权样式（那是做加法）。

### D7. 通路速率**常驻**标记

见 **§2 D5** 表「**通路速率**」行：`RateText` **常驻**显示（与叠加层开关**解耦**），字号比名称小一号。

### D8. **坐标系唯一事实源**

见 **§2 D5 / §5.1**：叠加层画布尺寸统一为 `ModuleViewViewModel.CanvasWidth/CanvasHeight`（**DIP**，= `Width/Height ÷ Scale`），`Bounds` 只兜底。
本条当时把"两端连不齐"归因到 **`Bounds` 比窗口客户区小 2 DIP**；**§5.1** 复测后确认那只是**次要项**，真根因是**单位混用**（模型几何 = 物理像素、叠加层 = DIP）。

### 5.1 补记：**单位统一**（D9 · 用户复测"线仍然没有对齐"之后的真根因）

> 用户复测："**线仍然没有对齐。在线完全水平/垂直的情况下，均有肉眼可见的偏移**" ⇒ §5 D8 的"`Bounds` 差 2 DIP"只是**次要项**。

| 项 | 定稿 |
|---|---|
| **真根因：单位混用** | 模型几何（`X/Y/Width/Height`）的单位是**物理像素**（窗口位置本身就是 `PixelPoint`，见 `ModuleWindowManager`），而叠加层是 Avalonia 控件、绘制单位是 **DIP** ⇒ 缩放 ≠ 100% 时两者差一个**缩放因子**；把 px 增量当 DIP 用，**完全水平/垂直的线也会错位**（整体按比例放大/缩小） |
| **口径** | **叠加层几何一律 DIP**：`ModuleViewViewModel.CanvasWidth/CanvasHeight = Width/Height ÷ Scale`（叠加层经同名属性接收，`Bounds` 只兜底）；世界增量经 `ToDip(...)` 换算。**换算只发生在这两处**，别处不许再乘除缩放 |
| **画布贴边** | 叠加层加 **`Margin="-1"`** 抵消 `Frame` 的 1px 边框 ⇒ 画布**正好等于窗口客户区**，连线因此画到窗口真正的外沿 ⇒ 两窗拼接处两段严丝合缝（此前停在离外沿 1px 处） |
| **遮罩浓度** | 用户裁定"**遮罩浓度降到 0.6 我同意**" ⇒ `OverlayScrim` **0.85 → 0.60**（浅/深两套都改）：网络标签已改为**沉到遮罩之下**，0.85 会把它压得读不出通路速率 |
| **回归网** | 上述用例 + 新增断言"叠加层的**实际画布 = 窗口客户区**（负边距抵消边框）"与 `CanvasWidth == Width / Scale` |
| **说明** | 无头环境的渲染缩放恒为 1，**无法在测试里复现缩放 ≠100% 的场景** ⇒ 该条由用户**手动复验**（用户："这两个改完后无需测试和改文档，我直接手动测"）；本条为**事实源补记**（原 §5 D8 把根因只归到 `Bounds`，不完整） |
