# ADR-0003 概念框架：组合件 / 内容-核心三分 / 保存单元

> 状态：Accepted（用户裁决，批次 1）
> 关联批次：批次 1（框架层）
> 关联主文档章节：§3.3、§4.1、§4.2、§6、§9、术语表
> 取代：无（构成后续点状裁决的支点框架）
> 被取代：部分条目（"保存单元 = Workspace"表述）被 ADR-0016 取代

## 问题

批次 1 点状裁决（Composition 所有权、Project、Definition 组成、ID 等）逐一悬空，缺乏统一的上层框架。用户反馈："缺少某种上层的框架定义，导致许多问题无法定夺"。需要先立三条框架之梁，再重审点状问题。

## 背景

- 用户心智类比链：积木 / 电路拼接 / 工厂建设游戏"蓝图"（模块=工厂，统一标准数据=产物，连接=传送带/机械臂，Core=游戏本体只维护标准与管理、可加载 mod；类比不覆盖实际功能、不可生搬硬套，仅提炼思想）。
- 已冻结：P1/P2/P3/P10/P12/P13/P16/P17、AC-1、ADR-0001（Application 构成/Workspace 去容器化）、ADR-0002（Definition 发布物与同形）、无全局 Run/Stop（§7.1）。

## 决策

### 梁 1：组合件（Composite）——组合可作为标准件复用

- 平台支持"**组合即件**"：用户拼出的 Composition 可**物化为 Composite（组合件/蓝图）**——命名、保存、加载、复用，并可像模块一样被实例化/拼入其他组合。
- 模块（Definition）的**实现来源**可包括：原生代码、脚本定义、或 Composite 定义（来源机制 Gate：批次 8）。
- **递归嵌套机制（组合含组合的展开/防环规则）不属于当前设计阶段裁决**（Gate：后续阶段）；本层只确立组合的可物化性。

### 梁 2：内容—核心三分边界

- **Core = 框架机制**（对一切模块与契约中立）：宿主、标准维护、模块生命周期、Workspace 文档管理、"组合→运行时"通用解释、Interface 兼容判定（通用规则）、点对点绑定执行、资源与错误管理。
- **业务功能**（数据获取/处理/呈现/分析……）= 内容，全部由模块承担。
- **编排/拓扑决策**（何时分/合、路由到哪、聚合语义——Splitter/Router/Merger 等）= 内容，由结构块模块承担；Core 不做编排决策。
- 宿主固有 UI（窗口框架/全局 UI，§3.2）除外（非内容）。
- 本三分允许在技术架构阶段做职责细分/分块实现/重新表述，**不改变顶层边界**。

### 梁 3：保存与复用单元

- **不引入 Project 概念**：保存/恢复单元 = Workspace 文档（无 UI 容器，ADR-0001）。
- 组合可**另存为 Composite 件**（进入组合库/Registry），供跨工作区加载复用。
- 工作流围绕"拼装 → 加载 → 复用组合"展开。

## 最终选择

三梁如上（用户逐项确认：梁 1 支持但递归机制 Gate；梁 2 三分确认且保留后续细分空间；梁 3 采纳）。

## 影响

- 主文档：§3.3 增职责三分注记；§4.1 概念表增 Composite 行；§4.2 对象图增物化关系；§6 记组合件；§9 保存单元（无 Project）；术语表增"Composite/组合件"。
- 点状重审：Composition 所有权=Workspace 文档持有（编辑态）+ Composite（物化态）；PQ-DM-08（Project）关闭；PQ-DM-02（ID）降级为属性级（格式 Gate）；PQ-DM-01（Definition 组成）纳入"实现来源槽"。
- 未来若组合引用成环规则等递归细节进入设计，需新 ADR（本 ADR 不预判）。
