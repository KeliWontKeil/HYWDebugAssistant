# 1. 产品定位与总体目标 【冻结 · 基线】

## 1.1 产品定位

本软件定位为：

> **面向工程人员的模块化数据处理、通信与可视化工作台。**

软件最初由 FOC 项目衍生，但平台本身不定义为 FOC 专用软件。FOC、串口、TCP、协议解析、示波器、数据处理等均应作为平台上的专业功能模块。

## 1.2 长期目标

建立稳定、通用、可扩展的架构，使新的功能能够主要通过新增 Module 实现，而不需要持续修改 Core。核心目标：

- 模块化
- 可组合
- 可扩展
- 可维护
- 可持久化
- 运行时可管理
- 用户使用方式统一
- 核心架构不随业务功能增长而持续膨胀

## 1.3 明确不属于产品核心目标的内容

**结论**：通用数据流编程 / 面向开发者的数据流编辑器 / 消息总线管理工具 / 路由表编辑器 / 通信拓扑编辑器 / LabVIEW / Node-RED 类通用流程编程器**均不属产品核心目标**；**完整边界裁剪（产品层 / 结构层 / 机制层 / 安全层）的正文见 §18.4**，本节不再复述。

## 1.4 v1 范围政策 【Gate · 顶层完成后（产品范围）】

- 平台不绑定具体业务（§1.1），因此"v1 交付哪些业务模块"不属于顶层裁决，推迟到 Concrete Module 阶段。
- 顶层阶段以**架构能力判据（§14.1）** 与**架构验证参考组合（§14.2）** 验收架构，不以业务闭环验收架构（§14.3，三分法 批次0冻结）。
- v1 产品验收场景（业务闭环，如真实串口/FOC 链路）在顶层冻结后定义，只用于**业务正确性**验收。

# 2. 用户模型与心智 【冻结 · 基线 + 批次0冻结】

## 2.1 目标用户

> **工程人员 / 使用者**，而不是软件开发者。

## 2.2 权威心智类比：模块拼接（积木 / 电路）【冻结】

用户应以"**拼接积木 / 搭建电路**"的心智理解平台（该类比由用户提出，用于指导 Interface 与结构块的设计直觉）：

```text
每一个承载功能的模块 = 一个"积木块"（类比芯片/元件，如 MCU）
模块的输入输出数据接口 = 元件的 IO（类比芯片引脚）
```

模块按职责与输入输出数据分类，粗略分为两类：

- **功能块**：负责具体的数据处理与呈现（类比承担功能的具体器件）；
- **结构块**：负责数据分配/组合（类比分线/汇线结构）。**注**：该术语与分类**已被 ADR-0010/0018 取代**——框架不设"结构块"类；无状态分/合由**网络成员关系**表达，带逻辑的分/合是普通内容模块。此处保留为用户侧直觉（区分"器件"与"连接形态"）。

拼接示例（电路设计直觉）：

```text
单设备直连：MCU ──点对点── I2C 设备        → "模块直接拼接"
多设备挂载：MCU ── 分线/总线(结构块) ── 多个 I2C 设备
→ 组成的整个系统 = "使用结构块拼接出的工作区"
```

即：**点对点即模块直接拼接；一对多/多对一需要一个"结构块"介入**——这就是结构块（Splitter/Distributor/Merger…）在用户心智中的存在意义。

## 2.3 类比边界（防止机械套用）【冻结】

该类比**不完善**，仅服务"连接拓扑 + 模块职责"的直观，不得套用到实现机制：

- 硬件拼接后是静态的；软件模块拼接后可各自独立配置、可热插拔、可在线调整。
- 软件模块间传递的是**结构化、有类型、可校验的数据**，不是物理信号（电压/电流/时序）。
- 结构块不只是"导线"，它承载分配/组合/同步等语义。
- 不存在硬件的"电气规则"（阻抗/驱动能力）；软件侧的连接规则来自 Interface Contract 的兼容性判定。
- 类比的用途是用户心智与设计直觉，**不用于论证运行机制**（运行机制见 §7，另行论证）。

## 2.4 用户核心心智模型

用户应理解：

```text
选择模块 → 放入工作区 → 配置模块 → 拼接模块 → 模块即插即用
```

（批次0冻结：基线原为"运行工程"，依"全在线变更 / 即插即用"裁决改为"模块加入工作区即开始工作"，无全局"运行/停止"。）

用户**不应该**需要理解：

> Message、Channel、Queue、Subscription、Routing、Thread、Task、Runtime Binding 等底层实现概念。

## 2.5 用户操作模型 【重构 · ADR-0018】

核心交互方式为 **Module Assembly（模块组合/拼接）**。用户可：添加模块、移动模块、配置模块、拖拽模块、靠近模块**（位置对齐）**、删除模块、启用/禁用模块、**建立/断开网络**、**保存组合件、加载组合件**（ADR-0016）。

**几何与连接解耦（ADR-0018，Supersede 基线 P9 语义）**：
- **吸附/拼接 = 仅位置排列与对齐**（排版与美学），不承担连接语义；
- **连接完全由"网络（Network）"承担**：直连 = 匿名网络，标签 = 命名网络；网络表现依附于**口**（口上显示网络名/方向标识/连接状态）；
- **建网**：**网络标签同名即连**（命名网络）＋ **接触且对齐即连**（未打标签的口，匿名直连）（规则见 §6.2）；**打标签的口只参与命名网络**，**拖开即自动断开**；
- 用户界面呈现的是组合关系（网络），不暴露独立的"数据流"编辑层（跨层不变式 P10）。

# 3. 系统级结构 【冻结 · ADR-0001/0004】

## 3.1 总体结构（批次1 裁决 · ADR-0001）

```text
┌─ 用户可感知层 ───────────────────────────────────────────────┐
│ Application（平台整体）                                        │
│   UI 构成（术语：Shell）：主窗口 / 全局 UI / 命令 / 模块区       │
│     ┌─────┐   ┌─────┐        ┌─────┐                          │
│     │ M1  │───│ M2  │────────│ M3  │   ← 模块视图直接拼挂      │
│     └─────┘   └─────┘        └─────┘   （无 Workspace 容器）   │
└────────────────────────────────────────────────────────────────┘
┌─ 语义层（不可见）─────────────────────────────────────────────┐
│ Core 构成（语义内核）：Registry / 模块宿主 / 运行时 /           │
│   Composition→Runtime 解释 / 工作现场内容管理 / 系统状态         │
└────────────────────────────────────────────────────────────────┘
抽象的 Workspace = 当前会话整体（Core + 模块 + 拓扑 + 布局）
                 = 文档聚合单元（保存/恢复），无 UI 容器语义
```

模块内部结构视图（基线保留）：

```text
Module
   │
   └── Interface
          │
          └── Composition
```

## 3.2 Application 的构成（ADR-0001：Shell/Core 不再是平级领域对象）

Application 是平台整体，含两个**逻辑构成面**（非独立对象：同生命周期、双向引用）：

- **UI 构成（术语"Shell"）**：主窗口、全局菜单/工具栏、命令入口、**模块视图宿主（模块区，自由拼接）**、应用级 UI。框架自身 UI（Core UI）不作为普通 Module。
- **Core 构成（语义内核）**：见 §3.3。

早期基线中"Application Shell / Core Runtime 平级顶层对象"的表述作废（ADR-0001）；"Shell"仅作为 UI 构成面的实现术语保留。

### 3.2.1 注记：表现层 / 语义层分离（为什么分、分什么、不分什么）

- **本质**（与"是否有数据库"无关）：在"用户看到并操作的（表现）"与"规则/数据/状态/能力（语义）"两类演化对象之间放置稳定的契约边界，使两边可独立修改/测试/替换，一个语义可对应多种表现。数据库只是历史上最常见的触发场景，不是判据。
- **本项目落点**：UI 构成与模块视图 = 表现层；Core 构成与模块业务能力 = 语义层。分离决策已冻结（ADR-0001；§10.1 视图与运行解耦）。
- **嵌入式类比**：等同"应用层与驱动层之间插入 HAL"——变化率不同的两部分以稳定契约解耦；即"界面逻辑与业务逻辑分离"的同构思想。
- **术语选择**：本项目称"表现层/语义层"（同进程契约分离），**不采用"前端/后端"**——后者暗示网络边界，会引入无关议题（API 服务、数据库等）。
- **边界**：不分离的是模块内部实现与性能关键路径内聚；分离的具体机制（视图 API 形态、线程、UI 框架）属批次 2/7 与 Gate（技术选型后）。

## 3.3 Core 构成（语义内核）职责（基线 Core Runtime 职责，保留）

Core = **Module Host + Runtime Environment + System Management Layer**。职责：Module discovery、Module loading、Module lifecycle、工作现场内容（Module Instance + Composition）管理、Interface compatibility 判断、Runtime 构建、Runtime 资源管理、系统级状态管理、系统级错误管理。（持久化载体=组合件，ADR-0016/§9.2。）

Core **不应**：承担具体业务逻辑、成为所有业务数据的中央交换机、理解 FOC/UART/TCP/Plotter 等具体业务、为每种业务写特殊分支、成为 God Object。

### 3.3.1 职责三分注记（ADR-0003）

- Core 只持 **①框架机制**（对模块与契约中立：宿主/标准/通用解释/点对点绑定执行）；**②业务功能**与 **③编排/拓扑决策**（Splitter/Router/Merger 等的分合/路由语义）全部由**内容模块**承担；宿主固有 UI 除外。
- 此三分允许在技术架构阶段做职责细分/分块实现/重新表述，**不改变顶层边界**（ADR-0003）。

## 3.4 装配链（批次1 已裁决 · ADR-0001）

- 启动序：Application 初始化 → 创建 **Core 构成**（含 Module Registry）→ 创建 **UI 构成**（引用 Core）。
- **抽象工作区**：无容器、无多开（§9.1）；其内容（Instance + Composition + Layout）由 **Core 管理**；**持久化载体 = 组合件**（ADR-0016/§9.2）；UI 构成只承载各模块视图（挂载于模块区，随 Instance 派生，可独立开关/重排，§10.1）。
- 模块入口/目录（UI 侧）→ 查询 Core 的 Module Registry（§4.2）。

运行时关系视图（基线，供理解）：

```text
用户拼接声明（抽象工作区内容）
        ↓
Composition
        ↓
Core 构成
        ↓
Runtime Binding
        ↓
```

## 4.3 Module 分类 【修订 · ADR-0010（Supersede P5/P6 域结论）】

- **框架只维护一种"内容模块"**，不再设 Functional/Structural 框架分类（P5/P6 原表述 Supersede，ADR-0010）。
- "功能/结构"仅作**用户侧角色描述**（§2.2 心智：功能块=处理与呈现；分线/汇线=结构直觉），**不构成框架机制**；模块按作者定义的角色与契约自然呈现，框架不维护业务分类。
- 无状态拓扑（分线/汇线 1:N / N:1）→ **网络成员关系 + 绑定机制多播**（§6.3/ADR-0018）；带逻辑的结构操作（缓冲/同步/聚合/条件路由）→ **普通内容模块**，按功能命名（如"缓冲模块"）。
- Core 不理解"这是 Splitter/Router"，只理解其 Interface / Composition Contract（基线保留）。

## 4.4 Module Definition 【冻结（ADR-0002/0005/0008）】

表示模块提供者发布的**不可变能力发布物**（示例：Serial/Parser/Plotter Module）；携带**唯一、不可变的接口标准**；用户不可修改、不感知底层实现；内置与外部模块共用同一模型（ADR-0002）。

**对外声明（最小组成，6 项）**：① 身份与版本标识；② 目录/用户元数据；③ 对外契约声明（Interface 集合，ADR-0008）；④ 可配置项声明（Configuration Schema，语言 Gate）；⑤ 可选视图声明（ADR-0019）；⑥ 宿主/生命周期能力声明（ADR-0014）。

**边界**：原语层/行为层构成模块实现域（SDK，技术选型后），**不进入 Definition 对外语义**；Composite 属组合复用层，与 Definition 并列不混（ADR-0003）；**Definition 不携带业务数据类型声明**——模块间交换为契约化载荷，Core 对具体类型无知（P16/ADR-0005）。

## 4.5 Module Instance 【冻结（ADR-0005/0016/0017）】

表示当前工作现场中实际使用的实例（Serial #1、Serial #2…）。**归属原则（ADR-0005/0016）**：Configuration = Instance 持有、**随组合件保存**（Schema 在 Definition）；Runtime State = 运行期数据、通常重建（模块需"记忆"则入 Configuration）；Presentation = 运行期由 Instance 派生的视图、不持久化（视图偏好可入 Configuration/Layout）；布局数据**随组合件保存**（加载可忽略）。实例集合构成抽象工作区的内容。

## 4.6 Interface 与接口实例（端口）【冻结（ADR-0005/0007/0008）】

Interface 是系统架构层面的 **Module Composition Contract**，不等同于 C# `interface`。**接口实例（端口）**：实例化后模块上存在具名/编号的端口级端点（Interface Instance）；Connection 两端锚定**端口**而非 Definition 的契约声明；多同型接口由此可区分（命名/编号/契约匹配细化批次 2）。

## 4.8 模块—框架运行顶层机制（批次1c 冻结 · ADR-0004）

> 图景：Core = 统一框架（仿真器）；Module Definition = 可加载模型；内置 = 预装库。本机制**不预设**容器类承载（工作区仅抽象；持久化载体=组合件，ADR-0016/§9.2）。

**A1 用户行为视角**（用户做什么 → 框架响应什么）：
① 从目录选择模块 → 框架依其模型在会话中产生模块实例；
② 配置模块 → 框架把配置交给实例（配置内容模块自定，框架不解释）；
③ 拼接两模块接口 → 框架校验契约兼容并建立连接（连接 = 用户声明的组合关系）；
④ 改配置 / 改拼接 / 增删模块 → 变更即时生效（§7.1），受影响局部重建；
⑤ 保存 / 恢复 → 保存用户声明的整套内容（聚合机制批次 6）；恢复 = 重新产生实例并按声明重建连接。

**A2 模块运行行为视角**：
① 实例被框架驱动运行（活动方式见 C）；
② 数据经已建立连接**直接**流到下游模块输入接口——**不经 Core 中转**（§7.2，P2/E1）；
③ 模块只与框架运行环境交互（生命周期/配置/上报），**不知其他模块存在**，实现**不引用另一具体模块**（P12 澄清语义）；
④ 模块业务状态与行为自管；框架只管宿主级状态（存在/激活/错误标记）与连接/绑定生命周期。

**B 边界契约**（顶层轮廓，实现 Gate）：
- 框架供给模块：生命周期驱动（批次 5）；连接的建立/拆除服务（数据模块间直通）；配置读写；状态/错误上报（批次 5）；视图宿主（可选，批次 7）；活动承载。
- 模块承诺框架：业务语义自负（框架不解释业务）；经契约（接口）互联——实现不引用另一具体模块（P12）；错误经受控通道上报。

**C 活动方式（裁决：不分类）**：**不预设"被动变换/自治源"分类**——模块是否需要自发活动视为模块**自身属性**（实现层差异），不属顶层约束，不提前分类；具体表达随 PQ-DM-01 回审与批次 4（ADR-0004）。

## 4.10 模块机制（核心专题 · ADR-0006）

> 定位：模块结构 / 生命周期 / 通信机制是本项目最重要的顶层设计，并决定技术栈。本专题横切领域模型与后续批次；口（Interface）设计是其子问题。用户裁决：**应用层近似统一，非重量级框架对象系统**（参考 WinForms Window/Control 启示：机制同路径、实现各异）。
>
> **【ADR-0046 顶层补充】**（用户第十六～二十轮："顶层设计没有对齐和细化"）—— 模块机制补三条**语义层**条款，原三分模型与成员路径不变：
> ① **类型注册**：类型由模块**声明并注册**（标识 + 版本 + 尺寸 + 传输语义 + 计量块 + **解码器**），框架只持**机械镜像**（见 §5.4.1）；
> ② **解析三段式**：声明期读取（框架必做）· 传输期零解析（框架不读数据内容）· **呈现期解码由模块注册的解码器执行**（框架只回调；`Ui/Runtime/SampleCodec` 降级为参考实现）；
> ③ **角色分层**（**两层都在用户感知层**；仅呈现，不参与判定）—— 定义见下；**开发期如何用它判"模块粒度 / 角色数"** 见 `docs/implementation/06-module-standard-and-development-process.md` §A/§B：
>    - **功能角色**（层① = "这个模块是什么/干什么"）：**一个模块只有一个**，用**一个名字**指代它（模块清单 / 模块自身 UI / 帮助）。框架**不维护业务分类**（§4.3），载体 = 目录展示元数据（`DisplayName` / `Description` / `Tags`）。
>    - **数据角色**（层② = "模块内部有哪几块处理功能"）：**一个模块可多个**，**由模块自己声明**（`DeclareRole` / `DeclareFlow`），框架**不派生、不发明**；显示在**叠加层**与拓扑。
> **【ADR-0052 · 已落地】数据角色 = 模块声明的「功能分块」**（**不是框架派生量**）：**一个角色 = 一种数据类型 + 输入口 / 输出口**（口数**不设上限**；&gt;2 口只在 **SDK 自检**的独立建议通道 `Advisories` 给一条**可忽略的建议**，不进 `Problems`、运行期不报）；**方块两行 = 功能名**（无则类型短名）+ **`m/n`** = 输入 / 输出侧连接的**对端角色数**（去重键 =（对端实例, 对端角色）），**由框架从网络成员关系派生、模块不得自报**；红线 = **框架不发明角色**（未声明 ⇒ 不画方块 + 一句可执行的事实；**不做兼容回退**），**零口 ⇒ 不画方块**；**只呈现** —— **不参与**建网 / 兼容判定 / 停流 / 投递 / 计量，且**不进组合件**。**声明面与校验的正文见 `docs/architecture/02-module-sdk.md` §「扩展声明面」（`DeclareRole`）· §「角色两侧同型（α）」；画法、层级与颜色映射的正文见 `docs/architecture/07-overlay-and-visual-baseline.md` §「叠加信息层：语义、开关、层级」· §「两个信息维度（角色维度 vs 通路维度）」· §「角色方块（角色维度）」· §「类型 → 颜色：色板、覆盖、调色板窗口」。**
> **【2026-09 补充裁定 · 角色两侧同型（α）】** **一个角色的输入口与输出口承载同一种数据类型**（= 该角色的 `Type`）。依据：ADR-0052 已裁"**一个角色只有一种数据类型**"，本次裁的是它**没裁的那半** —— **两侧是否同型**。⇒ **类型转换 = 两个数据角色**（"收 A"的角色 + "发 B"的角色）+ `DeclareFlow` 表达先后；叠加层上表现为**两个方块**、各按自己的类型色。**推论**：同一路输入要喂给两个角色 ⇒ **需要两个接收口**，由上游一个发送口按 **1→N 广播**（§6.3 ①）投递。
> **【ADR-0048 的口径已作废】** "数据角色 =（方向 × 类型身份）的**纯派生**量、在模块内聚合"**已被 ADR-0052 取代**，不再作为实现依据；原文与论证留在 `docs/archive/adr/ADR-0048-module-data-role-model.md`。

### 4.10.2 成员统一路径（应用层近似：路径一致、实现各异）

**框架通用面**（对一切模块中立，§3.3.1 ①）：生命周期驱动、成员实例管理、绑定（连接建立/拆除，数据直通不中转 §7.2）、状态/错误上报。

### 4.10.3 口 = 成员机制首个实例（ADR-0006）

- 口是带**方向两态（发送 / 接收）**与**契约形状**的通信成员（IF-A；**双向=两个口，ADR-0022**）；
- 口类型目录由平台提供（受控）；模块声明口成员、框架实例化通信端点；
- Definition"6 项声明"中口/配置/视图声明是**成员声明集**的特例（不推翻 ADR-0005，表述可后续收敛）。

# 5. Interface 模型 【批次 2 已冻结】

## 5.1 总体目标（基线）

Interface 必须：统一、抽象、可扩展、与业务模块解耦、与具体通信媒介解耦、能表达组合关系、能支持未知的未来数据类型、不要求 Core 理解具体业务。

## 5.2 数据与通信媒介解耦（基线）

Interface 不应绑定 Serial/TCP/CAN/USB/Ethernet。示例：

```text
Serial → Parser   （成立的原因）
不是 SerialType == ParserType
而是 Output Contract compatible with Input Contract
```

## 5.3 兼容性（**修订 · ADR-0018**）

组合规则由 Interface Contract 决定（Interface Compatibility）；**兼容判定发生在建立网络时**，结果以口上网络标记与 Issue 呈现（吸附仅为**几何对齐**、不再承担连接语义，§2.5/§6.2）——**兼容规则正文（判定矩阵 / 逐 (源,宿) 对判定 / 作废项 P9）见 `docs/architecture/03-data-protocol-and-typing.md` §7。**

## 5.4 批次 2 冻结裁决（ADR-0007）

**结论**：口只有**两态方向（发送 / 接收）**（双向 = 两个口）；**网络严格单向**（源 = 发送口，宿 = 接收口）；两个发送口相接 = 连接存在但无数据流（合法组合 + UI 标注）；**网络允许多对多（N:M）**，投递与兼容判定**逐 (源,宿) 对**；数据面载体 = 统一的**定长数据报**（流 / 消息 / 事件 = 契约层的传递语义标注）；**分发（1:N）由网络成员关系表达**（绑定机制直接多播，**无运行时转发对象、无独立视觉件**）——契约与口身份见 `docs/architecture/03-data-protocol-and-typing.md` §5–§8；网络口径与派发见 `docs/architecture/05-network-semantics.md` §1–§4。

## 5.4.1 兼容规则与契约能力（ADR-0008）

**结论**：契约能力 = **传递语义标注**（流 / 消息 / 事件）· **受控基础形状原语目录** · **组合与签名**；**兼容判据 = 传递语义一致 + 形状完全一致**（字段名 / 原语 / 长度 / 顺序 / 数量全同；**形状比较必须走结构比较 `ContractShape.AreSame`**）；**同标识不同版本 ⇒ 不兼容**（按破坏性变更处理）；**不同标识 ⇒ 默认不兼容**（框架无资格判定是否同一种量），用户**显式确认**后可强连、**仍要求形状完全一致**；任一方未声明类型则只按形状完全一致判定；**不自动转换**（转换 = 用户显式插入转换模块）；**类型由模块声明并注册**（标识 + 版本 + 尺寸 + 传输语义 + 兼容声明 + 计量块 + 解码器），框架只持**机械镜像**；**v1 数据单元只定长**（批量 = 定长数组 `T[N]`，不做框架自动合并）；**解析三段式** = 声明期读取 · 传输期零解析 · 呈现期由模块注册的解码器执行。

正文见 `docs/architecture/03-data-protocol-and-typing.md` §2（解析三段式）· §5（契约形状 `ContractShape`）· §6（类型注册与机械镜像）· §7（兼容规则：形状完全一致）· §8（类型身份、命名与演进）· §9（单位与语义元数据）。

## 5.4.2 数据面边界（ADR-0022）

**结论**：框架**不往数据单元附加任何元数据**（时间戳 / 序号 / 来源标识）——**投递字节 == 模块产出字节**（字节守恒）、无每单元构造开销；**数据包不自描述**（不带类型标签，框架按**声明**路由）；框架侧**只做统计**（投递计数 · 最后数据时间 · 间隔统计；**"序号" = 框架侧累计计数，不写入单元**）；模块需要"采集时刻 / 序号" ⇒ **自行在契约形状里声明字段**；**契约不含单位 / 量纲语义**（语义元数据可随类型声明供**展示**，但**禁参与任何框架判定**——可声明 ≠ 可判定）。

正文见 `docs/architecture/03-data-protocol-and-typing.md` §4（统计 vs 附加）· §9（单位与语义元数据）；**计量分档**（四档速率 / 三类丢弃 / 队列水位）与**顺序保证等级**见 `docs/architecture/05-network-semantics.md` §9 / §6。
  - **明确不做**（三条）：**进程内不换真 UDP socket**（实测完整投递 **54 ns** / 三跳 **1.8 µs**，走环回内核栈为 µs 级、约 **20–100× 慢**）· **不变长 / 不分片**（保持定长）· **模块远程化不属本轮**（登记为未来能力：跨进程 / 跨机用真 UDP/TCP/共享内存，**同一语义契约**）；**与真实设备通信由模块承担**（`ModuleCapability.Network/SerialPort` 已存在）——框架数据面是**模块之间的织物**。
- **【ADR-0050 R2/R3 落地精化】**（**源集合两态** `Sources` / `UnresolvedSources` · **`IsStalled` 是派生量** · 停流/悬空 Issue **只由锚定路径报一次** · `AnchorNetwork` 加载与重锚**共用同一套规则** · 网络身份键用**声明的源**）与 **【2026-09 实测澄清 · 无需融合器时的链路语义】**（**1 源 → N 宿** = 广播，每宿各得**一份独立拷贝**；**N 源 → 同一个宿口** = **匿名多路复用**（按到达顺序、不排序 / 不去重 / 不仲裁 / 不告知来源），**推荐一源一口**或应用自带来源字段；**不同尺寸的源不可能连到同一宿口**）——**正文见 `docs/architecture/05-network-semantics.md` §3（多对多成员与两态）· §7（两种连线形态的现行语义）· §10（停流 / 悬空 / 未建网）。**

# 6. Composition 模型 【批次 3 已冻结】

## 6.1 定位（冻结 · ADR-0003/0016/0018）

Composition = **用户在当前工作现场中声明的模块组合关系**（A → B）。Composition ≠ Runtime Binding：前者是用户声明，后者是运行时实现。

```text
用户拼接声明 → Composition → Runtime Construction → Binding
```

**组合件 = 持久化/复用唯一载体（ADR-0016，修订 ADR-0003）**：用户选择"一组实例 + 连接（+ 配置 + 布局）"保存为一个**组合件**（1 文件 1 组合件），可加载实例化进当前工作区、可参与拼接。当前工作区内的组合（编辑态）由 Core 管理（删除 Instance 时原子级联删除其连接）；组合件（物化态）是持久化产物，由用户保存/加载（§9.2）。

## 6.2 组合操作集与建网规则（ADR-0011/0018/0037/0050/0051）

**操作集**：建立网络 / 加入网络 / 退出网络 / 断开网络 / Add Module / Remove Module / Enable / Disable（原 Connect/Disconnect 重述为网络操作，ADR-0018）；依"全在线变更"裁决，这些操作**作用于常驻运行中的系统**，Core 在线增量生效（§7.2）。

**建网规则（现行 · ADR-0037；兼容条件经 ADR-0051 修订 · 多源语义经 ADR-0050 修订）—— 结论**：**两条机制互不混用**：① **命名网络**（口打**网络标签**，**同名即连**；**同名标签上的多个发送端 = 一条多对多网络**——多对多是常规形态，不提示、不报 Issue；**0 发送端 / 不兼容 ⇒ 提示或 Issue**）② **对齐网络（匿名直连）**（**双方均未打标签**的口，**接触且标记对齐**即连，**拖开即自动断开**；打标签的口只参与命名网络）。**判定只有一份实现**（`DockRule`，拖动预览与实际建网必然一致；UI 只经 `Core.Api` 预览查询，**实际建网只发生在布局提交之后**）；**网络在每次变更提交后整体重算**（不做增量、无隐藏状态；**组合件加载与用户显式建立的网络一律不动**）；**可建投递 = 传递语义一致 + 形状完全一致**（逐 (源,宿) 对判定，**不兼容者不建投递**、保留声明 + Issue，**不自动转换**）。

**完整规则**（"接触且对齐"七条判据与 px 容差 · 重算时机 · 提示 · 开关 `alignAutoNetwork` 与旧键兼容）见 `docs/architecture/05-network-semantics.md` §2–§4；**原子性**（单操作原子 / 多步复合 = 一次 **ChangeSet**：整体校验 → 一次性应用与增量重建 → 任一步失败整体拒绝；无全局事务与锁）见 `docs/architecture/04-runtime-mechanisms.md` §ChangeSet 原子性。

## 6.3 网络标记与结构操作（ADR-0018 修订 ADR-0010）

**结论**：**连接 = 网络**（统一模型：直连 = 匿名网络，标签 = 命名网络；**网络表现依附于口**；**分线器视觉件正式撤销**）；**网络 = 拓扑表达**（1:N 分发 / N:1 汇合由**网络成员关系**表达，绑定机制直接多播 / 汇合、**无运行时转发对象**；运行时"风暴 / 递归"防护 = **安全护栏（静默）+ 轻量提示（可见）**，**不做限流 / 环检测 / 阻断**）；**方向语义** = 口两态（发送 / 接收）⇒ 网络**严格单向**（双向 = 两个口 + 两条单向网络），**允许多对多**（逐 (源,宿) 对投递与判兼容）；**连线默认隐藏**（热键 / 按钮切换显示，显示时为**有向 / 流动样式**）；**命名** = 自动 `net-N` + 可重命名 + 冲突提示（默认弱化显示，悬停 / 展开看全名）；带逻辑的结构操作（缓冲 / 同步 / 聚合 / 条件路由）= **普通内容模块**（按功能命名）。**【ADR-0046 顶层冻结】**的细化（1 源 → N 宿 = 广播 · 多对多 N:M · 丢弃分类 · 数据角色只用于呈现 · 同一宿口永不混入两种长度）见 `docs/architecture/05-network-semantics.md` §3–§9 与 `docs/architecture/07-overlay-and-visual-baseline.md`——**正文见 `docs/architecture/05-network-semantics.md` §1–§4。**

# 7. Runtime 模型 【批次 4 已冻结】

## 7.1 已冻结前提（批次0冻结，源自用户裁决"全在线变更 / 即插即用"）

1. **无全局 Run/Stop**：系统常驻活动（无"加载工作区/启动工程"动作），模块加入即运行，即插即用。
2. **变更即运行时行为**：组合与配置修改在线即时生效；Core 负责**增量重建受影响子链路**（对"用户声明"与"运行时实现"做差异并 reconcile），而非整机重启。
3. **模块状态与异常隔离**：模块的状态变化（含离线/故障态）不影响任何无关模块；数据流因上游状态变化而中断，对下游是合法"无输入"状态而非错误（详见 §8 与判据 AC-2）。
4. 以上前提不依赖"电路"类比成立与否——类比仅服务用户心智（§2.3 边界），此处是独立论证的架构裁决。

## 7.2 运行时总流程（基线）

```text
用户拼接声明 → Composition Model → Validation → Runtime Construction
          → Runtime Binding → Module Execution
```

**数据通路语义（校准 · 落实 P2/E1）**：绑定（Runtime Binding）建立后，数据在**连接两端模块的接口之间直接流动**——Core 只负责创建/拆除绑定与管理生命周期，**不中转、不转发任何业务数据**（Core ≠ 交换机/总线，P2/E1；模块间为接口互联，P12 指实现不依赖另一具体模块）。

## 7.3 批次 4 冻结裁决（ADR-0012）

**结论**：组合声明在常驻框架中被解释为一组**模块间直接绑定（数据通路）**，数据报按序直通（§7.2）；**无全局 run/stop**；**变更 = ChangeSet 原子应用 → 增量重建受影响局部**（重建单位 = **绑定及其邻接数据面**，**模块实例、配置与业务状态保留**）；**慢消费者 = 有界缓冲 + 丢弃式默认**（默认丢最旧保最新，**绝不阻塞上游**；**v1 不做背压**）；**框架统一承载活动与调度**（实例加入即建，持有**专属线程 + 每 (实例, 口) 一条有界输入队列**；`Disabled` 只暂停数据流、**不释放线程与已分配资源**，`Removed` 才释放；模块**不自建、不直接管理线程**）；移除实例 = 原子移除 → 级联清连接 / 绑定 → 框架释放绑定与成员实例资源，**模块内部资源由模块在生命周期钩子中释放**——**正文见 `docs/architecture/04-runtime-mechanisms.md` §运行时总流程与重建判据 · §增量重建 · §线程、队列与停止协议 · §有界缓冲与丢弃；队列与投递另见 `docs/architecture/05-network-semantics.md` §7。**

# 8. Lifecycle 与 Error 【批次 5 已冻结】

## 8.1 生命周期阶段（批次 5 定稿 · ADR-0014）

**框架层状态机（权威）**：`Registered → Active ⇄ Disabled → Removed`（定义与转换条件见 §8.4）。

- 基线草案中的 `Created / Initialized` 属"加入"的转换过程，`Stopping / Stopped / Disposed` 属"移除"的转换过程——**均为过程而非稳态**；
- 基线草案中的 `Faulted / Recovering` **不作为框架状态**：软件级异常走"异常报告 → Issue"（§8.2 类 b、§8.5）；业务状态由模块自报（§8.4 四正交面）；
- 无全局 Run/Stop：**加入即运行**（即插即用）。

## 8.2 错误分类（**定稿 · ADR-0015**）

Configuration Error / Composition Error / Interface Error / Module Error / Communication Error / Runtime Error / Presentation Error。

原则：**Core 管理系统级故障，不理解具体业务语义。**

两类区分（**定稿**，ADR-0015）——"故障"并非单一概念：

- **(a) 领域/数据源状态变化**（如通信离线）：是模块**自身状态**的一部分（在线→离线），表现为状态切换与数据流消失。"下游无输入"是**合法的运行状态**，不是错误，不构成链路故障（类比：MCU 程序跑飞不意味着后级 I2C 器件损坏）。
- **(b) 软件级异常**（模块间契约违约、程序级异常）：是实打实的"异常"，属需修复的 BUG，或需按既定异常处理路径捕捉/处理的情况。

## 8.3 故障语义（**定稿 · ADR-0015**）

模块"故障"首先是**模块自身状态的一部分**，不是全局事件；不采用"停机/降级/阻断"等全局化表述。数据流因上游状态变化而中断时，下游处于**合法"无输入"状态继续运行**（§8.2 类 a）；软件级异常（§8.2 类 b）在模块边界被受控处理并转为 Issue（§8.5）。

## 8.4 批次 5 冻结裁决：生命周期模型（ADR-0014）

**结论 · 四个正交面** = 存在性（框架权威）· 活动面（框架权威）· 业务状态（模块自报，框架只登记 / 呈现、不解释）· 异常报告（模块产生，框架受控收集）。**框架层状态机 = `Registered → Active ⇄ Disabled → Removed`**（框架权威；基线 `Created`/`Initialized` 属"加入"的转换过程，`Stopped`/`Disposed` 属"移除"的过程；**基线 `Faulted`/`Recovering` 不设为框架状态**）。**Enable / Disable** = 保留实例与拓扑 / 配置、暂停数据流（绑定保留停流）、**通知模块**（内部处置自决，框架不替模块决定是否断硬件）。**移除不可逆** = ChangeSet 原子操作 → 级联清连接 / 绑定 → 框架释放成员资源 → 模块钩子释放内部资源。**Binding 独立于模块状态、随连接存在**（业务状态变化不触碰绑定）。**移除的例外 = 孤儿线程**（停止协议为"**有界等待 + 不强杀**"，超时记 Issue 并放弃等待——**有意接受的边界**）——**正文见 `docs/architecture/04-runtime-mechanisms.md` §生命周期状态机 · §停止协议（诚实的边界）。**

## 8.5 批次 5 冻结裁决：错误模型（ADR-0015）

**结论**：一切可呈现问题统一为 **Issue** = `归属对象`（实例 / 口 / **网络** / 配置项）+ `类别`（§8.2 七类）+ `来源`（框架判定 / 模块报告）+ 描述与时间，分**设计·变更问题**与**运行报告**两类语义；**模块业务状态不入 Issue**；呈现 = 对象标注 + 汇总列表；**不阻止其他部分运行**。**隔离与恢复 = 天然隔离 + 显式恢复**（框架**不自动重试 / 降级 / 阻断**；恢复 = 用户显式操作或模块内部恢复；可选标准动作"重建实例" = Remove+Add 复合 ChangeSet）。**通知与日志分层** = 框架层（Issue 列表 + 机制诊断日志）· 模块层（模块日志 / 诊断经框架汇集，可观测性 L3）；通知默认**轻量不打扰**，允许声明"需注意"级别——**正文见 `docs/architecture/04-runtime-mechanisms.md` §Issue 与可观测性。**

# 9. 抽象工作区与持久化（组合件载体） 【批次 6 冻结 · ADR-0016】

## 9.1 抽象工作区（无容器、无多开）

- **"工作区"是抽象概念**：由 Core 与全部已拼接模块自然形成的**运行整体（当前现场）**——**没有**独立容器对象、**没有**"新建/打开/关闭工作区"生命周期、**没有多工作区并行或切换**（此类裁决点撤销）。
- 不存在"工作区文档/工作区文件"；**持久化与复用的唯一载体是组合件**（§9.2）。
- 工作区内可并存任意多条互不相关的链路（如同时监控多个串口）——这是"拼接的多样"，不是"多个工作区"。
- 术语保留"Workspace/工作区"，但**仅指该抽象整体**；本文档中一切实体化用法（容器/文档/多开）均视为表述错误。

## 9.2 组合件：持久化与复用的唯一载体（ADR-0016）

- **保存** = 用户选择"一组模块实例 + 网络（成员与命名）+ 其配置 + 布局"物化为一个**组合件（Composite/蓝图）**；**1 文件 = 1 组合件**。
- **加载** = 将组合件**实例化进当前工作区**（生成实例群与网络）；可复用、可参与拼接（递归/嵌套细节 Gate）。
- **"保存全部内容"** = 一个覆盖当前全部实例与网络的**根组合件**（概念上仍是蓝图，不是"工程容器"）。
- **随件保存的内容边界**：Configuration ✅ / 网络 ✅ / Layout ✅（加载时可"忽略布局"）/ 实例活动面（启用·禁用）✅；**Runtime State 与绑定 ❌**（重建）。
- **Configuration 的登记语义【补充 · ADR-0035 D3】**：模块**首次读取**配置即登记该实例的**默认配置**（`ConfigurationAccess.Read<T>`），此后读取返回同一对象、`Write<T>` 覆盖；组合件加载时由恢复值覆盖。理由：模块通常"只读不改"配置，若不登记则保存组合件时该实例的配置会**整块丢失**，且框架无从生成配置表单（§10.4）。配置集合的访问点（读取/写入/快照/恢复）**统一加锁**——它同时被模块线程与管理线程访问。
- **会话快照（可选能力）**：退出/崩溃后自动恢复"上次现场"——独立于组合件的自动化行为（实现 Gate）。
- **保存机制**：显式保存为主 + 脏标记；**原子写**（临时文件替换）防半写损坏；自动保存/崩溃恢复属 UX/后续。

## 9.3 持久化细节冻结裁决（ADR-0017）

**结论**：**文本格式方向**（可读 / 可 diff / 易迁移；具体格式 Gate），文件**内嵌 Schema 版本**；**能迁移则自动迁移，不能则拒绝并保护原文件**；**序列化分工** = Configuration 按 Schema（**未知字段保留**，支撑 AC-4 无损往返）+ 网络（成员 + 网络名 + 匿名/命名标记）+ Layout；契约引用 = 具名契约 ID/版本或内联；**运行态 / 绑定不序列化**；**异常加载** = 缺失 Definition → 占位保留（配置与网络成员）+ Issue、其余照常运行 · 版本不兼容 → 缺失态 + Issue · 损坏 → 尽量部分恢复 + Issue，完全不可解析则**拒绝加载并保护原文件**；**成员重建与网络重锚定** = 加载 → 实例化（Definition + 版本）→ 恢复配置 → **重建成员（口）** → 按 `InstanceID.口名` **重锚**（**口消失 ⇒ 悬空态**：保留声明 + Issue；**部分源悬空不影响其余源投递，全部源悬空 = 停流**）；**网络记录 `schemaVersion` = 2**（`name` + `isAutoGenerated` + `sources[]` + `targets` + `unresolved` + 可选 `allowUnverifiedTypeMatch`；v1 单值 `source` 在解析期归一为单元素 `sources`，写回升版 v2 并移除旧字段）——**正文见 `docs/architecture/04-runtime-mechanisms.md` §组合件与持久化。**

## 9.5 应用级设置（Settings）【技术架构设计回写 · ADR-0030】

**定位与结论**：应用级 / 用户级**行为偏好**，独立于组合件、**不属"工作现场内容"**；由 **Core 管理**，持久化为**用户级独立文件**，**与组合件完全分离**（不随组合件保存/加载，组合件亦不携带设置快照）；与 Configuration（实例级、随组合件）**边界不重叠**；**范围仅应用级**（不提供"按模块类型的默认设置"）；**在线即时生效**；缺失或损坏 ⇒ 用内置默认值 + Issue、**不阻断启动**、写回走原子写。

**设置键的唯一来源 = 代码里的设置模型 + `docs/architecture/08-application-settings.md` §2（设置键清单）** —— 键名 / 默认值 / 适用范围 / 旧键兼容与迁移 / 校验与非法值处理均以彼处为准，本节不再复述任何键。**持久化内容全集 = 三类**：① 组合件（实例 + 网络 + 配置 + 布局，§9.2）② 应用级设置（本节）③ 会话快照（可选能力，Gate D，§9.2）。

# 10. Presentation 模型 【批次 7 已冻结】

## 10.1 已冻结约束（批次 7 更新）

1. 【用户侧体验目标】模块视图应可独立开关/重排而不影响运行（全在线变更的用户体验要求）；解耦结构见 §10.4（ADR-0019）。
2. **Module ≠ Window【修订 · ADR-0034】**：模块**不强制**等于窗口；**默认表现形态 = 每模块一个可拼接的无边框窗口**（同族窗口边缘吸附、整组拖动、可锁定）。Presentation 仍是模块面向用户的表现层，不同模块可有不同 UI 形态；框架按模块声明渲染（模块不提供 View 类型，§10.4）。
3. **模块视图直接挂载于 Application 模块区（自由排列）**，不存在工作区容器（ADR-0016）；**【修订 · ADR-0034】**多窗口形态下**连"模块区"背景也不存在**——背景即用户桌面，外壳主窗口为拼图"起始点"。**【修订 · ADR-0038 · 本节第 3 条的"外壳形态"部分作废】** 外壳**不再是"一条工具条"**：改为**主窗口 = A 区活动栏（图标化入口）+ B 区侧边界面（竖向排列的常驻页面，模块清单与交互在此）**+ 底部状态栏；顶部菜单撤销；设置/拓扑诊断/Issue/帮助仍为**弹窗**（非模态）；外壳**仍是拼图起始点**（模块窗口从属于它，层级规则见本节第 6 条）。**"外壳不存在主体区域"的旧口径作废**——主体区域即 B 区侧边界面。
4. **几何与连接解耦（ADR-0018）**：模块位置/拼接 = 排版对齐；**连接由网络承担**，网络标记依附于**口**（口上显示网络名弱化 + 方向标识 + 连接状态）；**分线器视觉件撤销**。**【修订 · ADR-0034】**连线表达与建网交互：多窗口下 v1 **不做跨窗口长连线**；建网 = **口上网络标签同名即连** + **"接触且对齐"即连**（ADR-0037）。**【现行 · ADR-0039/0045/0049/0052/0053/0054】连线表达 = 「叠加信息层」**（开关 `showInfoOverlay`）：**端口标记常显**（模块的标准件，也是唯一建网入口）；叠加层 = **「灰玻璃」上的角色投影**：**默认关闭**（`showInfoOverlay` 默认 `false`；它是**调试/观测层**，不是常驻层，快捷键 **L** 切换；**旧配置里显式写过的值保留**）；开启时 = **灰玻璃**（半透明深色遮罩，**故意压暗模块自身内容**以突出叠层信息）+ 其上绘**角色方块 / 角色间连线 / 模块内部关系线**（**每个模块窗口内自绘**；**拼接后线在公共边自然相连 ⇒ 不做跨窗口覆盖窗/长连线**；只读拓扑诊断保留）。**现行形态五条**（① 两个信息维度分离〔ADR-0053〕· ② 角色方块〔ADR-0052/0053〕· ③ 线〔ADR-0053〕· ④ 层级与交互〔ADR-0053〕· ⑤ 类型 → 颜色映射表〔ADR-0054〕）**与全部细节（几何常量、字号、快照自检、颜色表列宽等）的正文见 `docs/architecture/07-overlay-and-visual-baseline.md` §「叠加信息层：语义、开关、层级」· §「两个信息维度（角色维度 vs 通路维度）」· §「角色方块（角色维度）」· §「连线：端点、绘制、流向、相位」· §「类型 → 颜色：色板、覆盖、调色板窗口」**（端口标记见同册「端口标记（网络标签）= 数据接口的标准件」）；**外壳与窗口见 `docs/architecture/06-ui-shell-and-windows.md` §5（模块窗口）。**
5. **可拼接排版约定【修订 · ADR-0031】**：模块视图遵循**尺寸族**、接口靠边缘布局，保证"可直接拼接"的排版效果；**尺寸族为非强制开发约定**（用于内置模块），**不含网格吸附交互**（具体尺寸参数 → UX 原型 Gate）。原表述"网格对齐"指排版约定而非交互，网格吸附已由 Q5-1 排除。
6. **窗口层级统一【新增 · M1-17 / ADR-0036 D5】**：**应用内**——"弹窗 > 模块窗口 > 外壳"（模块窗口**从属于外壳**：外壳永在其下，最小化/恢复随外壳）；**应用整体（相对其他应用）只有两种统一状态**——**普通**（任一本应用窗口被激活时，其余本应用窗口一并抬升；其他应用激活时整体下沉）与**全体置顶**（应用级开关，外壳 + 模块窗口 + 弹窗**一起**置于最前，新开窗口与弹窗按当前状态继承）。**明确禁止**"一部分窗口被外部应用覆盖、另一部分置顶"的混合状态。快捷键作用域 = **应用内**（任一本应用窗口聚焦即生效），清单**以设置页为准**且可见、可改、可重置。

## 10.2 形态裁决（批次 7）

**定稿**：**模块视图自由排列（无容器） + 几何对齐 + 网络负责连接**——位置与连接解耦，网络标记依附于口（ADR-0018）。

- 不采用"画布容器"概念（无容器，ADR-0016/0018）；"面板/分组框/多页面"仅作为可选 UX 元素（Gate）。
- 形态议题的重心：**几何对齐 + 网络标记 + 可选连线**；具体视觉（窗口化/卡片化/尺寸族）→ UX 原型 Gate（§18.5 C）。
- 旧候选方案（画布式 / 面板停靠式 / 拼图式窗口）与取舍过程见 `docs/archive/superseded.md`（§4 交互与呈现类）。

**说明**：形态议题的核心已从"容器/画布之争"转移为"**几何对齐 + 网络标记 + 可选连线**"三件套；具体视觉（窗口化/卡片化/尺寸族）留 UX 原型细化（Gate，PQ-PR-01）。

## 10.4 批次 7 冻结裁决（ADR-0019）

**结论**：**不声明视图的模块允许存在，但仍有自己的窗口**（窗口内至少显示模块名与状态 + 框架补的**配置表单**；"没有窗口的模块"形态作废），锁定 / 隐藏 / 移除 / **还原** / 配置编辑都在**该模块自己的窗口**上完成；**无分组容器**（网络标记区分链路 + 聚焦/高亮；分组框 / 多页面为可选 UX，Gate）；**视图 = Instance 派生物**，**模块不提供 View 类型**、由框架按声明渲染；**网络严格单向 + 允许多对多**（§6.2/§6.3）；**模块窗口视觉规范** = 无标题栏 / 无身份行（整块窗口矩形即模块矩形）· 运行指示在左下 · 操作按钮簇在右上（纯图标）· 端口标记为标准件 **20×114 / 114×20**、与外边框重合、四段固定槽位 · 缩放手柄 **6×6** · 名称字号 **11 px**；**框架渲染子集** = A1/A3/A5/B1/B2/B5/A10/A11，输入类控件统一高度 **27 px**；**模块默认尺寸** = `ViewDeclaration.PreferredWidth/PreferredHeight`，未声明用 **320×220**，**SDK 只增不改看签名不看语义**（改 SDK 后必须重编全部模块包）；**还原 = 用同类型新默认实例替换**（不是清空）走两阶段变更模型并通知配置变更；**开关的唯一状态源**（一处状态、其余委托，禁各存字段再同步）——**正文见 `docs/architecture/06-ui-shell-and-windows.md` §5（模块窗口：形态与交互）· `docs/architecture/07-overlay-and-visual-baseline.md` §模块窗口视觉规范。**

# 12. 安全与隔离 【批次 9 冻结：轻量透明模型】

**评估结论（ADR-0021）**：沙箱/权限系统对本平台**过度**——核心风险是"用户主动加载不可信模块包"（信任决策在用户）。故采用"**避免风险 + 透明化 + 基础护栏**"：

| 风险点 | 对策 |
|---|---|
| 加载模块包=执行代码（核心风险） | ①默认不自动加载（ADR-0020）；②加载前显示来源/签名状态（签名可选，未签名提示不阻止）；③Manifest 声明所需能力（网络/串口/文件），**加载时提示**（透明不拦截） |
| 组合件被当作可执行载荷 | **天然免疫** → **组合件永不自动执行任何代码**（加载只重建声明结构） |
| 脚本模块逃逸 | **v1 不引入脚本宿主**（ADR-0028 §9），该风险面消除；未来引入须新 ADR 并重估执行权（顶层要求"不得引入更强执行权"） |
| 破坏数据（写入/路径穿越） | 文件操作限制在用户选择路径；原子写（ADR-0016）；不实现路径穿越 |
| 资源耗尽 | 框架轻量护栏（**安全 + 提示**，ADR-0029 C4-1）+ **加载上限：单文件 ≤ 16 MB、结构深度 ≤ 8 层**（v1 组合件不递归嵌套，深度上限用于防畸形文件；数值可在实现期按实测调整） |
| 组合件解析漏洞 | **受限解析器**：白名单字段 + 深度/大小上限（同上）；**拒绝而非猜测**；不可解析则拒绝加载并保护原文件（ADR-0029 R4-6） |
| 依赖链混淆 | 依赖显式声明（ADR-0020）；缺失依赖→Issue，不静默降级 |
| 数据泄露（模块联网） | 接受（用户自担）；能力声明透明化；不做网络拦截 |

**明确不做**（保留 Gate）：进程级沙箱 / 权限拦截系统 / 强制签名 —— 唯一正文见 §18.4（安全层）。

# 13. 非功能需求 【批次 9 冻结】

## 13.1 已冻结属性目标

- **首要原则：数据实时性 > UI 呈现**——**数据面绝不被 UI 阻塞**（依据：视图可独立开关不影响运行 §10.1、慢消费者丢帧不阻塞上游 ADR-0012、框架统一承载活动 ADR-0013）。
- **可扩展性**：新增 Module 不应要求修改 Core 业务逻辑（判据 AC-1）。
- **可维护性**：Core 职责清晰，避免 God Object。
- **稳定性**：单个 Module 故障不应无条件导致整个 Application 崩溃（判据 AC-2）。
- **可增长性**：模块数量**不设上限要求**；Core 不随模块数量线性膨胀。

## 13.2 性能与可观测性（ADR-0021）

- **数值指标（UI 刷新率 / 端到端延迟 / 内存 / 吞吐 / 连续运行时长）→ 实测回写**：由 `HYWDebugAssistant.Benchmarks`（BenchmarkDotNet，**不进常规门禁**）承载，时点 = M1 首轮 / M2 后第二轮；**用户裁决：仅记录、不设阈值**（ADR-0029/0032/0033）。
  - **M1 首轮实测已完成**（i9-13980HX · Windows 11 24H2 · .NET 10.0.12 · Release）：完整清单与逐项数值见 `docs/architecture/04-runtime-mechanisms.md` 的**实测基准**一节；运行方式 `.\build.ps1 -RunBenchmarks`。

- **承载参数现行值（来源 = 代码 `DataPlane/Carriers/CarrierOptions.cs`，非 ADR）**：**投递循环空闲等待粒度 `IdleWait` = 1 ms**（无数据时的等待上限，兼顾延迟与 CPU）；同文件其它默认值 = 输入队列容量 **1024**（按 (实例, 口) 计）· 满时**丢最旧**（`DropOldest`）· 停止超时 **5 s**。

| 层 | 内容 | 呈现 |
|---|---|---|
| L1 框架诊断 | 加载/注册/建网/绑定/增量重建/变更事件（结构化日志） | 诊断面板（可选开） |

# 16. 治理与验收 【冻结 · 含批次 1 治理裁决】

## 16.1 设计完成判据（基线九问 + 域判据）

一个架构阶段只有在以下问题能得到明确答案时才可进入下一阶段：

- 核心概念是否没有明显重叠？
- 每个对象是否具有明确职责？
- 对象之间的所有权是否明确？
- 生命周期是否明确？
- 持久化边界是否明确？
- Runtime / Design-time 边界是否明确？
- Core 是否仍然保持业务无关？
- Module 是否保持独立？
- Interface 是否保持稳定抽象？
- 新 Module 是否可以在不修改 Core 业务逻辑的情况下加入？
- 是否存在明显的架构循环依赖？
- 是否出现为了实现某个具体模块而修改顶层架构的情况？

（对每个核心对象的九问细化见 §4.9 九问对象卡：是什么/谁创建/谁拥有/谁管理/谁可修改/是否持久化/设计时还是运行时/生命周期/关系。**批次 10 逐条核对结果见 §18.3。**）

## 16.2 Agent 行为约束（基线 §20）

任何实现/设计 Agent：**不得自行修改已冻结的架构原则**。Agent 可以：实现已确定设计、补充局部实现细节、提出设计冲突、报告无法满足的约束。Agent 不应：自行改变 Core 职责、自行改变 Module 模型、自行改变 Interface 语义、自行引入新的核心概念、用具体技术限制反向改变顶层架构、自行裁决任何 PQ-* 项。

若发现设计缺口：

```text
发现问题 → 停止相关实现 → 提出 Architecture Issue → 人工/架构阶段决策
        → 更新本文档（含 ADR）→ 继续实现
```

## 16.3 批次冻结纪律（批次0）

- 每批裁决问题清单由用户确认后，才回写本文档并冻结（**本文档只承载基线结论**；日常回写落点见 `docs/DOC-WORKFLOW.md` §2）。

## 16.4 设计—实现推进阈值（用户裁决 · 批次1 前）

- **设计阶段消除 A 类不确定性（应该是什么），实现阶段处理 B 类不确定性（怎样实现）**；仅当剩余未知以 B 类为主时才进入实际开发。
- 进入技术选型/实现的唯一条件：**顶层所有域的结构决策冻结（"整版原理图"完成）**。域内细节为 Gate 项，不属设计阶段义务，但不得回避各域结构决策。
- 类比（用户）：顶层=原理图，选型=器件选型，实现=layout；**原理图未完成不 layout**，禁止以"用代码验证设计"提前进入实现。

## 16.5 层级推进协议（批次 1 经验沉淀 · roadmap §1.2）

主题域/裁决包一律按四步子阶段推进，前一步未冻结不进下一步：

1. **图景描述**：先写/叙该域"是什么"；用户类比须做"类比→抽象→边界"显式转换并经用户校验，不直接形式化（案例：电路/工厂/仿真框架类比的误读与过度形式化）。
2. **概念与支点裁决**：立该域"梁"（对象全集/边界/所有权/保存语义）。**支点信号**：多点悬空答不上 = 缺上层支点 → 停止点状裁决，先向上补支点。
3. **机制/结构**：支点之上再裁内部结构。
4. **细节 Gate**：格式/编号/分类枚举/调度等 B 类与确定性设计 → 登记 Gate，不裁决。

守护规则：**层级定位检查**（先问"这是哪层的问题、上层冻结没"，未冻结先补上层或转 Gate）；**转写校验门**（用户自由文本/类比 → Agent 转写命题清单 → 用户"确认即冻结"，不得扩写）；**逆例自检**（拟冻结措辞对照 P/E/AC，防"Core 中转数据"式违背不被拦截）。

## 18.4 边界裁剪：明确不做清单（汇总）

**产品层**：通用数据流编程/数据流编辑器、消息总线管理工具、路由表编辑器、通信拓扑编辑器、LabVIEW/Node-RED 类流程编程器（§1.3）；**国际化/多语言**；**自动更新通道**（便携包手动替换）；**无障碍支持**；**隐私/遥测声明**（产品自身不上报任何数据）；**安装包（MSI）与卸载程序**（v1 为便携包）；**诊断包导出**；**单实例限制**（允许多开，设置文件并发写采用"直接覆写、最后写入获胜"）。**结构层**：多工作区（无容器/无多开）、Project 概念、任何"工程文件容器"（由组合件承载）、分线器视觉件、**画布/面板容器形态**（含窗口停靠式布局——见 §10.2）。**机制层**：全局 Run/Stop、模块间自动类型转换、强制连接方向、自连/环的禁止、特殊"命令/控制/状态接口"类型、框架级业务分类、内置模块特权、Core 中转业务数据、框架自动重试/降级/阻断、模块业务状态入 Issue、业务类型枚举冻结、**背压**（v1 队列满只丢弃，绝不阻塞上游）。**安全层（本阶段）**：进程级沙箱、权限拦截系统、强制签名（保留 Gate）。

> 归属说明：**数据导出/打印**为模块自身能力（开发具体模块时讨论；若实现特殊需提前决定方式）；**首次运行引导**在计划中但 v1 不做。

# 附录 A 术语表（随批次冻结完善）

> 定义状态：`冻结` = 已随批次裁决冻结（附 ADR）；`Gate` = 待技术选型或后续阶段细化；`修订` = 术语语义已被新裁决取代/重定义。

| 术语 | 定义（一句话） | 状态 |
|---|---|---|
| Application | 平台整体：UI 构成（Shell）+ Core 构成（语义内核） | 冻结（ADR-0001） |
| UI 构成（术语 Shell） | Application 的表现构成：主窗口/全局 UI/模块视图宿主；非独立领域对象 | 冻结（ADR-0001） |
| Core（语义内核） | Application 的语义构成：模块宿主 + 运行时环境 + 系统管理 | 冻结（ADR-0001） |
| Module Registry | Core 内全局 Module Definition 登记服务 | 冻结（ADR-0002） |
| 抽象工作区（Workspace） | 模块拼接自然形成的运行整体；无容器/无多开/无生命周期 | 冻结（ADR-0016） |
| Module | 用户可感知的功能基本单元（"积木块"） | 基线 |
| Functional Block | 用户侧角色描述（功能块：数据处理与呈现），非框架分类 | 修订（ADR-0010）；**现行用词见下两行** |
| **功能角色**（层①） | **模块级**：这个模块"是什么/干什么" —— 用**一个名字**指代它（模块清单 / 模块自身 UI / 帮助）；**一个模块只有一个**；框架**不维护业务分类** | 冻结（ADR-0052 · §4.10 ③） |
| **数据角色**（层②，简称"角色"） | **模块内**：模块**声明的功能分块** = 一种数据类型 + 输入口/输出口集合；**框架不派生、不发明**，**只呈现** | 冻结（ADR-0052 · §4.10 ③） |
| 角色两侧同型 | 一个角色的**输入口与输出口承载同一种数据类型**；⇒ 类型转换 = **两个数据角色** + `DeclareFlow` | 冻结（2026-09 补充裁定 α · §4.10 ③） |
| Structural Block | 旧术语（Supersede：ADR-0010）→ 组合层"拓扑构造"元素（分线/汇线，不实例化运行时转发对象）；**现行**：无状态分/合由**网络成员关系（多源 N:M）**表达 | 修订（ADR-0010/0050） |
| Module Definition | 模块提供者的不可变能力发布物（唯一接口标准；内置与外部模块同形） | 冻结（ADR-0002/0005） |
| Module Instance | 工作现场中实际使用的模块实体（Definition≠Instance） | 冻结（ADR-0005） |
| Interface | 模块组合契约（≠语言 interface） | 冻结（ADR-0007/0008） |
| Interface Definition | 契约声明（含传递语义标注 + 形状原语组合/签名） | 冻结（ADR-0008） |
| Interface Instance（口/端口） | 模块实例上的端口级端点（方向两态：发送/接收；双向=两个口，ADR-0022） | 冻结（ADR-0005/0007/0022） |
| Composite（组合件/蓝图） | **持久化/复用唯一载体**：一组"实例+连接+配置+布局"物化而成的件；1 文件 1 件 | 冻结（ADR-0016） |
| Composition | 用户声明的模块+连接（网络）关系 | 冻结（ADR-0018） |
| **网络（Network）** | **连接统一模型**：直连=匿名网络，标签=命名网络；表现依附于口（名称+方向+状态）；**网络允许多对多（N:M；同名标签上的多个发送端即一条多对多网络）** | 冻结（ADR-0018/0050） |
| Connection | 组合中两端接口之间的一条连接（=网络成员关系的一种表述） | 冻结（ADR-0018） |
| 模块包（Module Package） | 模块供给单位：manifest（Definition 声明）+ 实现绑定 + 可选资源；内置=预装包 | 冻结（ADR-0020） |
| 成员（Member） | 模块组成单元（口/配置项/视图…），走统一"声明→实例化→存取·连接→表现"路径 | 冻结（ADR-0006） |
| Issue（问题标注） | 统一问题模型：归属对象 + 类别 + 来源（框架判定/模块报告） | 冻结（ADR-0015） |
| ChangeSet | 原子变更集合：整体校验 → 一次性应用与增量重建 → 失败整体回滚 | 冻结（ADR-0011） |
| 建网（命名网络 / 对齐网络） | 两条机制：口上**网络标签同名即连**（命名网络）；**未打标签**的口**接触且对齐即连**（匿名直连，拖开即自动断开） | 冻结（ADR-0037） |
| Runtime Binding | Core 依 Composition 建立的运行时绑定（数据在模块间直通，不经 Core 中转） | 冻结（ADR-0012） |
| Configuration | 用户可编辑、随组合件保存的参数（Schema 在 Definition） | 冻结（ADR-0005/0016） |
| Runtime State | 运行期产生、通常重建的状态（不持久化） | 冻结（ADR-0005/0016） |
| Presentation | 模块面向用户的表现层（Instance 派生物；可独立开关/重排） | 冻结（ADR-0019） |
| Layout | 视图/模块的布置信息（随组合件保存，可忽略加载） | 冻结（ADR-0016） |
| Plugin | 提供 Module 的实现机制（非产品概念）；模块供给的统称 | 冻结（ADR-0020） |
| 参考模块/桩模块 | 用于实证 AC 判据的专用模块与测试桩；**现行 = 四个正式模块 + 判据项目内测试桩**（§14.2）。原六个参考模块（如数据发生器）**已于 2026-09 删除** | 冻结（ADR-0021） |
| 参考组合 | 由正式模块与桩模块构成的架构判据验证组合（测试层 T1；**现行载体见 §14.2**） | 冻结（ADR-0021） |
| 内容模块 | 框架唯一维护的模块类型（业务能力载体；不设框架级业务分类） | 冻结（ADR-0010） |
| 框架机制 | 对模块与契约中立的通用服务（宿主/绑定/管理/生命周期承载）；见 §3.3.1 三分 | 冻结（ADR-0003） |
| 数据报（Datagram，旧称"数据单元/数据单元流"） | 模块间传递的统一载体：按序发布的**定长数据报**；流/消息/事件 = 契约层语义标注（术语按 ADR-0050 D2 规范为"数据报 / 发布"） | 冻结（ADR-0007/0050） |
| 契约 / 契约语言 | 口的形状与传递语义声明；三层能力（语义标注 / 受控原语目录 / 组合签名） | 冻结（ADR-0008） |
| 语义层 / 表现层 | 语义层=Core 与模块业务能力；表现层=UI 构成与模块视图（同进程契约分离） | 冻结（ADR-0001） |
| 缺失态 / 悬空态 | 缺失模块实例的占位态；网络成员因口消失而悬空（保留声明 + Issue） | 冻结（ADR-0017） |
| 会话快照 | 退出/崩溃后自动恢复"上次现场"的可选能力 | 冻结（ADR-0016） |
| 四正交面 | 存在性 / 活动面 / 业务状态 / 异常报告（模块状态图景） | 冻结（ADR-0014） |
| Module Assembly | 用户侧核心交互：拼接模块（几何对齐 + 建网） | 冻结（ADR-0018） |
| P-n / E-n | 跨层不变式（§17.1）/ 反模式（§17.2）编号体系 | 冻结（批次 0） |
