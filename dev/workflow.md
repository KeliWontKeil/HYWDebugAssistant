# 开发工作流

> 本仓库的构建、验证、打包与文档写作规则，不对外发布。约束与架构规则见 `dev/constraints.md`。

## 环境

| 项 | 要求 |
|---|---|
| 操作系统 | Windows（构建与发布脚本按 Windows 编写） |
| .NET SDK | 版本由仓库根 `global.json` 固定，安装对应 SDK 即可 |
| PowerShell | 7 及以上 |
| 文档站（可选） | Python 3.11 及以上，安装 `docs/requirements.txt` 中的依赖 |

文档站不是产品构建的必需项：只改代码时不需要安装 Python 依赖。

## 常用命令

| 命令 | 作用 |
|---|---|
| `.\build.ps1` | 完整门禁（步骤见下文） |
| `.\tools\dev.ps1 -Mode Build -Project <名称片段>` | 编译单个项目 |
| `.\tools\dev.ps1 -Mode Test -Filter <词>` | 运行匹配的测试（显式过滤词可以点到压力用例） |
| `.\tools\dev.ps1 -Mode Test` | 运行默认测试项目（不含压力 / 性能） |
| `.\tools\dev.ps1 -Mode Test -Pressure` | 只跑压力类别（数据面 / 外部接入 / 串口改动时） |
| `.\tools\dev.ps1 -Mode Test -IncludePressure` | 连性能测量一起跑 |
| `.\tools\dev.ps1 -Mode Snapshots` | 生成渲染截图（人眼验收用，不是判据） |
| `.\tools\dev.ps1 -Mode Gate` | 等价于 `build.ps1` |
| `.\tools\dev.ps1 -Mode Run` | 构建并启动应用 |
| `.\docs\build.ps1 -Mode Check` | 文档站结构检查（严格构建，不产出发布站） |
| `.\docs\build.ps1 -Mode Build -Languages all` | 构建中英文文档站到 `artifacts/docs-site` |
| `.\docs\build.ps1 -Mode Serve` | 本地预览文档站 |

## 构建产物

- 项目输出：`bin\<配置>\net10.0`，全仓只有一棵产物树。
- 模块包：`artifacts/modules/<配置>/`，构建时自动归拢。
- 应用输出中的 `modules/` 与 `resources/` 由构建镜像，不手工放入。
- 文档站：`artifacts/docs-site/`，不进版本库。
- 模块作者包：`artifacts/sdk-packages/`（五个包，按需清空重建）。

## 模块作者包

| 包 | 类别 | 谁用 |
|---|---|---|
| `Sdk` / `Sdk.Ui` / `Sdk.AccessKit` | 运行时（随宿主） | 模块的编译期引用；宿主输出必备 |
| `Sdk.Testing` | 作者包 | 模块作者的测试项目（契约自检） |
| `Module.Build` | 作者包 | 模块打包规则（props/targets） |

- 作者包**不随宿主发布、不得进模块包**；模块运行时引用 `Sdk.Testing` 会被加载器拒绝。
- 打包规则只有一份：`build/module-package.targets`，仓库内模块（`src/Modules/Directory.Build.targets` 导入）与外部作者（`Module.Build` 包）共用。
- 包内 XML 文档是模块作者拿不到源码时的 API 语义来源，四个运行时/作者程序集都必须带。

## 模块设计取舍

新增内置模块或改 `Sdk.Ui` 控件前，先按 [`docs/zh/project/module-design.md`](../docs/zh/project/module-design.md) 的检查表把需求映射到现有通道：

- 先看值 / 显示源 / 输入 / 命令 / 外观 / 文件定时器能否覆盖；固定值池可以承载动态行。
- 只有“现有控件组合不出布局”才新增控件；控件只消费真实值名和命令，不新增数据通道。
- 新增 `Declare*`、收件箱事件、持久化字段、视图状态 API 之前，必须指出哪条现有通道失败；没有证据不加。
- 最近案例：指令发送器最终是 256×6 声明值 + `order` / `selection` 值 + `ModuleValueList`，框架侧零数据通道改动。

## 已知环境问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 构建报平台配置无效 | 环境变量 `Platform` 被其它软件设置 | 使用 `build.ps1` 或 `dev.ps1`，它们会先清除该变量 |
| 输出文件被占用 | 应用正在运行，或 IDE 的预览器占用输出 | 关闭应用或预览器后重试；应急时用 `dev.ps1 -Mode Test -SkipAppRebuild` |
| 文档站提示 mkdocs 版本不一致 | 本机安装版本与 `docs/requirements.txt` 不同 | 按该文件重新安装 |

## 文档更新时机

- **开发期**：一个功能未完成时，只允许写/改**该功能自己的设计文档**（`dev/design/<功能>.md`）。不改站点页面、`mkdocs` 导航、README、约束、工作流与本文件的其他部分。
- **不得用文档描述未完成的功能**：不写"计划做 / 正在做 / 已实现待验证 / 待人工验收"；页面一旦存在，读者就会当成现状。
- **收尾**：功能代码、测试与人工验收都完成后，**由开发者显式要求**，在提交前一次性更新受影响的文档。没有显式要求就不改文档，只在回复里列出"这次需要更新的文档清单"。
- **设计文档只记决策**：边界、取舍、理由、被否决的方案。不记进度、轮次、门禁读数、验收条目、待办；"已实现"由提交与版本记录承载。

## 分层验证

按改动范围选择最小必要的验证层级：不为一行改动跑全量，也不让有风险的改动绕过门禁。

| 层级 | 适用时机 | 命令 |
|---|---|---|
| 文档改动 | 只改页面内容、导航或链接 | `docs\build.ps1 -Mode Check` |
| T0 单项目编译 | 每次小改，尽早暴露编译与静态分析问题 | `tools\dev.ps1 -Mode Build -Project <名称片段>` |
| T1 单类测试 | 改了某块逻辑或某个测试类 | `tools\dev.ps1 -Mode Test -Filter <词>` |
| T2 单测试项目 | 一个增量收尾 | `tools\dev.ps1 -Mode Test` |
| T3 完整门禁 | 见下文必须触发的三种情况 | `build.ps1`（或 `dev.ps1 -Mode Gate`） |

一次改动的固定顺序：

1. 一次改完，不在中途逐项验证。
2. 编译改动涉及的项目（T0）。
3. 跑一次 T2；有风险时直接跑 T3。
4. 在报告中写明实际跑了哪一层。

T3 必须触发的三种情况：

1. 把改动交给使用者手工验证之前。
2. 改动验收事实源：模块 SDK 公开面、核心契约、设置或组合件格式、架构规则与项目引用、依赖清单。
3. 一个功能完成、准备提交之前（含按开发者要求更新文档）。

例外：在最小验收指标就绪之前，界面、交互与模块改动只跑 T0 与受影响的 T1/T2，完整门禁与手工验收一并推迟。

验证优先级：

1. 人类可感知的问题优先。
2. 测试用于发现难以察觉的问题，不替代实际使用。
3. 测试面尽量小：一个判据能覆盖的，不拆成多个用例。

## 门禁

`build.ps1` 依次执行：

1. 文档站结构检查（`docs/build.ps1 -Mode Check`）。
2. 颜色口径审计。
3. 资源与文本审计。
4. 源码注释的布局数值审计。
5. 版本纪律审计。
6. 截图工程零断言审计。
7. 还原与构建，要求 0 警告、0 错误。
8. 内置模块包校验。
9. 模块作者包：`tools/pack-sdk.ps1` 生成五个包，`tools/verify-sdk-packages.ps1` 校验 dll/xml/依赖组（`-SkipPack` 可跳过，发布前不得跳过）。
10. 模块模板：`tools/verify-standalone-module.ps1` 用作者包构建模板，并由仓库内 `StandaloneModuleHost` 装入（门禁专用；该宿主不随产品/SDK 发布）。
11. 输出资源包校验（逐文件与仓库一致）。
12. 依赖许可审计。
13. 测试：按项目逐个串行执行；默认排除压力 / 性能类别与截图工具（`-IncludePressure` / `-IncludeSnapshots` 按需打开）。

任何一步失败都会终止门禁。跳过文档相关的检查只在明确不涉及 `docs/` 时使用；跳过作者包只在迭代期间使用。

## 测试分层与规则

| 项目 | 覆盖 |
|---|---|
| 架构测试 | 项目引用与模块边界规则（见 `dev/constraints.md`）；规则型检查，不设条数上限 |
| 模块测试 | 业务模块的契约自检与行为判据（组帧 / 编码 / 长度 / 错误回报）；不测 `Sdk` / `Sdk.Ui` 纯函数 |
| 主测试项目 | 数据面、运行时、持久化与格式、设置与路径、资源与文本降级、包加载、行为链路，以及几何 / 图表数学 / 换行与转义等共享纯函数 |
| 参考测试 | 参考组合的判据；最靠外的一层（真实装包 + 人机操作链路） |
| 截图工具 | **不是测试**：真实渲染出 PNG 供人眼；方法体内无断言；不进任何自动化门禁 |

规则：

- 常驻用例只收**共性 / 全局机制**：失败时能说出一句"用户会看到什么坏结果"，且这个后果不是控件样子、事故现象或某个读数。
- **一次性缺陷不保留为常驻用例**：判据是"能不能再复发"；与特定控件、特定事故现象、特定实测读数绑定的，修好即删。注释里的"回归网 / 被钉住的缺陷"不构成保留理由。根因是结构问题的，用设计消灭，不写用例、不立台账。
- **交付物式测试不写**：只验证"控件存在 / 字段被赋值 / 枚举映射 / 资源名清单 / 逐模块罗列声明"而说不出失败后果的，删；同类罗列合并为一条 `[Theory]`。
- 同一事实只保留**最靠外**的一处；下层用例在修 bug 时可临时加，定位完即删。
- 断言对象是来源 / 一致性 / 结构 / 边界，不是字面值；用户可改的文案、尺寸、颜色、资源名、字体实测读数不作判据。
- 不设覆盖率百分比；判据是机制改动必须有组合级验证。
- 压力测试（`Category=Pressure`）与性能测量（`Category=Perf`）是**开发期按需件**，不进常规门禁；功能收尾即删，不登记"可删"。
- 截图工具必须独立进程运行（无头渲染平台是进程级配置），只在 `-Mode Snapshots` 或 `-IncludeSnapshots` 时跑；不得依赖其中的断言判定对错。
- 架构测试自研，目标程序集缺失即失败，不允许"无对象则跳过"。
- **用例预算**：见 `dev/constraints.md`「测试面」（唯一登记处）。超预算新增一条 ⇒ 先删一条或写明它替掉了哪一条的覆盖。

## 手工验收

验收是功能收尾的一部分：每个功能完成后由使用者本人跑一遍（`-Mode Run` + `-Mode Snapshots`），通过后才进入下一个功能。不建验收清单文档、不记"待验收"条目；当次要看的现象直接写在回复里，验收完即失效。自动化只覆盖难以人工发现的问题。

## 功能收尾清理

功能通过自测与人工验收后、提交前，按顺序做一遍：

1. **删临时件**：本次为定位写的探针、临时用例、临时过滤词、一次性脚本全部删除；不留"以后可能用得上"。
2. **删事故用例**：本次修掉的缺陷若属特定、非共性、修好后不可能复发的，不加常驻用例；发现已存在的同类用例，删。
3. **过四问**：每条留下来的用例都要答得出——用户会看到什么坏结果？更外层是否已兜住？是否随无关重构变红？是否在钉某次事故的样子？任一答不上就删或合并。
4. **查重复**：同一事实是否在模块测试 / 主测试 / 参考测试各有一份；只留最靠外一处。
5. **清文档**：确认没有把未完成功能写进文档；需要更新的文档等开发者显式要求。
6. **一次验证**：删改一次做完后跑一次 T2（有风险跑 T3），报告删除条数、留下的判据各兜什么。

## 打包与发布

发布由 `tools/release.ps1 -OutputDirectory <仓库外空目录>` 统一驱动，产出两个**独立目录**（当前不压缩）：

- **产品**：`HYWDebugAssistant-<版本>-<rid>/`，`dotnet publish` 自包含目录；只含程序、内置模块、资源、设置种子、许可与 `release.json`，不含 SDK、样例、源码、用户数据。
- **SDK**：`HYWDebugAssistant.Sdk-<版本>/`，五个作者包、模板、本地 NuGet 源、README 与 `sdk.json`；不随产品发布。

规则：

- 发布默认要求工作树干净并先跑 `build.ps1 -Configuration Release`；`-SkipGate` 只用于本地迭代。
- 默认 `rid=win-x64`（承诺目标）；其他 RID 允许尝试，但不承诺编译/运行，元数据标记 `unverified`。
- 用户数据目录（`settings/`、`workspace/`、`logs/`、`composites/`、`framework/`）与外部模块目录（`modules/external/`）不进入产品。产品目录就地运行会生成它们的同名目录，因此**运行过的目录不再作为分发源**：`verify-release.ps1` 按 `release.json` 逐文件对账，多一个或少一个都失败。
- 产品只带目标平台需要的组件：Windows 目标去掉 Linux/macOS 后端（`Avalonia.X11` / `FreeDesktop` / `Native` / `Metal` / `Tmds.DBus.Protocol`）、设计器支持与运行时调试组件（`createdump` / `mscordac*` / `mscordbi` / `msquic` / `System.Net.Quic` / `DiaSymReader`）。`Avalonia.Vulkan.dll` **必须保留**：Win32 渲染后端初始化时无条件加载它，缺了直接抛异常、窗口不创建。
- 不引入 RID 之外的备用发布形态；自包含文件夹是当前唯一产品形态。安装器/压缩包/签名/自动更新暂不做。
- 模块项目构建时自动归拢到 `artifacts/modules/<配置>/<包名>/`，产品发布时镜像到发布目录的 `modules/`。
- 模块包只含模块自有文件：模块清单、模块程序集与自有资源；宿主提供的程序集不进入包。
- `tools/pack-sdk.ps1` 生成五个作者包；`tools/verify-sdk-packages.ps1` 校验包内容；`tools/verify-standalone-module.ps1` 用 SDK 包构建模板模块并由独立宿主装入，`build.ps1` 4d 每次执行。
- `tools/package-release.ps1` / `tools/package-sdk.ps1` 是分步入口；`tools/verify-release.ps1` 校验已产出的目录。
- 文档站构建产物在 `artifacts/docs-site/`，与产品发布包相互独立。

## 文档写作

### 归属

| 层 | 写什么 | 位置 |
|---|---|---|
| 开始使用 | 从零到第一条数据 | `docs/zh/start/` |
| 使用指南 | 每个可操作功能；每个模块一册 | `docs/zh/guides/` |
| 深入理解 | 机制、文件结构、可手工修改的范围 | `docs/zh/concepts/` |
| 模块开发 | 外部作者：流程、声明面、打包与排障 | `docs/zh/module-dev/` |
| 项目开发 | 仓库：结构、构建与门禁、版本、测试、文档规则 | `docs/zh/project/` |
| 关于 | 定位、许可、更新日志 | `docs/zh/about/` |
| 代码与仓库约束、开发工作流 | 不进站 | `dev/` |
| 功能设计文档（决策与边界，不记进度） | 不进站 | `dev/design/` |
| 历史材料 | 不进站，不作现行依据 | `dev/archive/` |

同一个主题只允许有一个家；其他位置提到它时只放路径，不复述步骤、数值或机制。

### 页面类型

| 类型 | 结构 | 用于 |
|---|---|---|
| 层首页 | 读者 / 回答 / 不写 + 页面表（回答什么、状态） | 六层的 `index.md` |
| 教程 | 完成什么、前置、步骤、结果、下一步 | 开始使用 |
| 任务指南 | 适用场景、步骤、验证、相关 | 使用指南 |
| 模块册 | 界面、典型用法、状态与提示 | 使用指南/模块 |
| 解释 | 解决什么问题、机制、边界、相关 | 深入理解 |
| 开发 | 目标、步骤、约束、验证 | 模块开发 |
| 仓库 | 事实、命令与位置、相关 | 项目开发 |
| 骨架 | 读者、回答、不写、事实来源 | 尚未写的页面 |

模板放在 `docs/templates/`，复制后按需删减。

### 写法

- 使用专业书面语：客观陈述，步骤用动词开头；避免口语、网络用语、拟人化与感叹号。
- 一页回答一个问题；内容能在一页说清就不拆分，规格表与兼容矩阵允许同页，用二级标题分段。行数不作为门禁。
- 先写做什么、怎么做，再写为什么；机制解释放在"深入理解"层。
- 面向用户的页面不出现类名、方法名、内部状态名与代码路径；开发层可以使用，但首次出现要给白话说明。
- 数值、版本号、模块清单不手写：版本由构建注入，模块清单与更新日志由构建生成。
- 不把界面文案写成规范：不写“某条提示应该是……”“某字段的格式必须是……”“状态行提示‘……’”，只写这条文本表示什么。具体措辞由文本表与开发者调整，文档不得把文案钉死。控件名称可以按当前界面引用；状态、错误、格式提示不抄原文。此条与“数值、版本号、模块清单不手写”同级。
- 术语首次出现给出一句定义，之后全文保持一致；定义集中在站点术语表。
- 不写"以前是 X，现在是 Y"；历史留在版本库与更新日志里。
- 界面截图在发布前统一补充，正文不描述无法复现的像素细节。

### 新增页面

1. 复制 `docs/templates/stub.md` 到对应层目录，填"读者 / 回答 / 不写 / 事实来源"；标题即页面标题。
2. 在 `docs/mkdocs.yml` 的 `nav` 中登记；未登记的页面、或 nav 顶层不是 7 项，都会让结构检查失败。
3. 按 `docs/templates/` 里对应的页面类型换掉骨架，再补正文。
4. 运行 `docs\build.ps1 -Mode Check`，通过后即可提交。
