# 模块清单的类型色与封面

模块清单页回答的问题是"这个模块是干什么的"。它有两个**只服务于识别的**视觉线索：
预览图块外圈的**类型色**，以及图块里的**封面**。两者都不参与任何判定。

## 类型色外圈

### 取色来源只有一个

颜色一律经 `PacketTypePalette`（`src/Ui/ViewModels/PacketTypePalette.cs`）取。
同一个类已经在给"端口标记的窄颜色条"与"叠加层角色方块的填充"取色 ⇒ 清单的环是**第三个消费者**，
不是第三套配色。用户改色后三处一起变。

由此派生两条硬约束：

- **不新造调色板**。清单里出现任何"自己的"颜色常量，都会立刻与端口标记脱钩；
- **取色看类型身份，不看呈现文本**。`{seq:u64, value:f32}` 这种形状文本会把"不同标识但形状相同"
  的两种类型涂成同一色，而角色合并规则明确二者不是同一种量。

### 类型集合从哪来

来自模块**声明端口**的 `TypeId`（视图 XAML 的 `<ui:ModulePort TypeId=…>`），即
`ModuleDefinition.PortSpecs`。清单条目（`ModuleCatalogEntryView.TypeKeys`）在
`RuntimeServices.GetModuleCatalog` 里一次性算好：去重、按序、空即 `null`。

**只取声明，不读运行期实例**，理由三条：

1. 清单回答的是"这个模块是干什么的"，与"当前现场装入了哪些实例"无关；
2. 读实例会让同一模块的行随现场变化而变色（同一个模块在两台机器上颜色不同，是错的）；
3. 清单按刷新节拍取，读实例要枚举全部端口。

代价：**用 C# `DeclarePort` 的旧模块没有类型色**（`PortSpecs` 为空 ⇒ 中性外圈）。
这是兼容路径的既有边界，不为它加"从已注册实例反推"的运行时回退——那会让上面的第 2 条重新成立。
作者的解法是迁到 XAML 声明（框架既定方向）。

### 一色一半

- 0 个类型 ⇒ **不画环**（保留图块自带的中性边框）。零口工具（`HexStringConverter`、`ImageFrame`）
  属于这一类：把"没有类型"画成某种颜色，等于凭空发明一种类型。
- 1 个类型 ⇒ 纯色环。
- N ≥ 2 ⇒ 沿**横向等分**，每段一色、**硬切换**。两个转换器（`RawToWaveform` / `WaveformToRaw`）
  各声明两种类型（入口 `RawBytes`、出口 `WaveformFrame`），因此正好一色一半。

"硬切换"用**同偏移的两个停靠点**实现（`0.5` 处先放前一色的终点、再放后一色的起点），
不是"两段颜色之间做渐变"——后者看起来像混出了第三色，而"它同时管两种东西"要的正是**分界可见**。

段序取类型标识的 `Ordinal` 序（不是端口声明顺序）：同一组类型在任何模块、任何次刷新里
都得到同一种排布，否则换个 XAML 顺序颜色就左右互换。

### 不占布局、不发散

环是图块上叠的一层 `Border`（`Classes="typeRing"`，`BorderThickness` 粗一档以盖过中性边框）。
它**不参与测量** ⇒ 图块仍是 72×40、行高不变（"区域尺寸不随内容变化"）。

环的身份按**签名**（类型标识按序 join）判等，且同一个签名**复用同一个实例**。
理由是清单列表用 `CollectionSync` 做增量同步：环若每次刷新都造新实例且不判等，
整个列表会被逐帧重建，表现为"鼠标悬停时所有项乱闪"。改色时由
`ModuleCatalogViewModel.RefreshTypeRings` 就地换画刷并发通知（不重建行）。

### 说明在哪

环本身不写文字（行宽已被"展示名 + 来源标注"占满，再加一列会把名字挤省略）。
类型标识正是那个不该出现在界面上的东西——它是框架的内部身份。因此：
**悬停时补一句**（`catalog.typeRing.tip` = `数据类型：{0}`），页面级帮助里补一段
（`catalog.help.body`）。这是"短语直接显示 / 一句解释挂悬停 / 多句进帮助"三层文本纪律的中间层。

## 封面

### 生效条件只有两条

1. 文件名是 `preview.png`，住在**包根**（与 `module.json` 同级）；
2. 构建时由 `build/module-package.targets` 从**模块工程根目录**归拢进包。

缺图不是错：清单显示占位字形 + 类型色环，其余一切照常。

### 为什么不在 `resources/` 下

`resources/<kind>/<拥有者>/` 是**框架按拥有者读取的资源类别**（`i18n`、`icons`）；
封面不由资源层解释——它是"这个包的一张图"，属于包元数据，与程序集同级。
放进 `resources/` 还会逼作者在 `module.json.resources` 里声明一个框架不认识的 kind。

### 为什么不靠 csproj 条目传递

文档过去只写：

```xml
<None Update="preview.png" CopyToOutputDirectory="PreserveNewest" />
```

这条路**不通**，两个原因：

- `None` / `Content` 的复制元数据**不经 `ProjectReference` 传递** ⇒ 下游程序集的输出目录里不会有它；
- 包归拢读的是**项目目录**（与 `module.json`、`resources` 同一模式），不是输出目录。

所以正确做法是让打包规则直接从工程目录取文件。作者侧因此**零配置**：图放到工程根就进包。
仓库内 18 个模块一件 csproj 都没改。

MSBuild 侧的名字是 `$(ModuleCoverFileName)`（缺省值在 `module-package.props`）；
读取侧的常量是 `ModulePackageLayout.CoverFileName`。MSBuild 引用不了 C# 常量，
两处必须同名，`tools/verify-module-packages.ps1` 会核对它们一致（改了名字忘记同步会当场判红）。

### 只换封面不要求重启

`ModuleInstaller` 把"包根最新修改时间晚于进程启动"当作"内容已变化，需重启"。
封面是展示资源、不承载代码 ⇒ 判定时**排除它**：换一张图不该要求重启应用
（重启之后唯一的差别还是那张图）。

反面同样要守住：**改程序集仍然算内容变化**。排除封面不能退化成"不看修改时间"，
那会让真正的代码更新静默失效。这条由 `只换封面_不算内容变化不要求重启` 用例的反面断言钉住。

### 封面从哪来

由截图工程按 9:5 画布生成（`modules/<模块>-cover.png`），再由
`tools/sync-module-covers.ps1` 复制成各模块工程根的 `preview.png`。

**"用截图作封面"不等于"封面就是窗口截图"**：生成时把模块按它**自己的尺寸**布局，
再整体等比缩放进 9:5 画布（`Viewbox Stretch=Uniform`），而不是把窗口拉成 9:5。
窄高模块（竖标尺 100×400、姿态球 400×400）被拉扁会严重失真；
等比缩放的代价只是四周多一点底，人眼看到的仍是"这个模块长什么样"。

比例 9:5 是清单图块（72×40）的比例：图块按 `UniformToFill` 居中裁切，
比例不对就会裁掉内容。`sync-module-covers.ps1` 因此校验 `360×200` 与 PNG magic bytes，
不合规直接失败退出（不静默跳过）。

封面内容后续可以被替换成任何图——机制不关心图从哪来。

## 被否决的方案

- **清单自己一套类型配色**：与端口标记、角色方块脱钩，同一类型三处三色。
- **自绘控件画分段环**：分段线性渐变已经能表达"每色一半"，自绘多一个控件、多一份坐标。
- **行里加类型文字标签**：违反三层文本纪律，且挤占行宽（名字被省略得比露出的多）。
- **封面放进 `resources/`**：逼作者声明框架不认识的 kind，且让"资源类别"概念发散。
- **每个模块 csproj 自己写 `<None Update>`**：不可传递、易漏、外部作者的零配置目标落空。
- **运行期文件监视封面**：代价远大于一次「重新扫描」。
- **把窗口拉成 9:5 当封面**：窄高模块失真，封面变成"这个模块被压扁的样子"。
