# 导入同名项：问一次，不静默改名

## 问题

导入外部组合件或模块包时，默认目录里已有同名项会被**无条件改名**为 `名字-2`：

- 组合包目录：`Directory.Exists` 就加序号；
- 旧扁平组合文件：内容不同就加序号；
- 模块包目录：`Directory.Exists` 就加序号。

于是三件事同时发生，用户一件都没被问过：既没有覆盖，也没有失败，界面还显示成"已导入"。
更糟的是状态行填的是**源名**，而列表里出现的是带 `-2` 的目标名 —— 显示与实际对不上。

保存组合时是问过的（`composite.overwrite.*` 那套文案），导入时却没有。这不是"统一设计如此"，
只是没补上。

## 做法：按 Windows 复制撞名的方式

逐条问「替换 / 跳过 / 取消」，可用「为所有同名项执行此操作」一次决定整批。

**覆盖不留副本**：用户手选替换即视为已知风险，不引入 `.bak`。安全只保证"不半写"。

## 两阶段：查询决定意图，命令执行事实

Core 的命令面是同步的，而弹窗必须 await，所以不能让 Core 在复制途中回调问用户。分成两步：

1. `IRuntimeQuery.GetImportConflicts(sourcePath)` —— 纯查询，返回**可处置的**冲突列表；
2. `ImportComposite` / `ImportFolder` / `ImportModuleDirectory` 各加一个决定表参数
   （键 = 来源全路径，值 = 替换或跳过）。

决定表只是**用户意图**；落点、是否撞名、内容是否相同，每次都由执行侧从文件系统重新推导。
两阶段之间的时间差不会造成误判 —— 用户改了文件，执行就按新事实来（找不到冲突就按普通导入走）。

### 为什么"没有决定"不等于"跳过"

决定表里**没有这个键**表示没人回答，该冲突按**失败**返回并说明原因。
如果缺省成跳过，用户会看到"导入成功"却发现什么都没进来 —— 与静默改名同类的欺骗。
所以 `ImportConflictChoice` 只有 `Skip` 与 `Replace` 两个值，缺省语义由"不在表里"表达。

## 哪些冲突能问，哪些只能失败

| 情形 | 处置 |
|---|---|
| 目标名已存在 | 问：替换 / 跳过（**只看名字，不比内容**） |
| 源就在默认目录里（同一个包） | 无操作早退，不问（这不是导入） |
| 模块包同名目录正被**已加载**的包占用 | **只能失败**，不给替换选项 |

最后一条是有意的：替换等于删掉正在运行的那个包的落地目录。模块本来就不支持热替换
（改代码必须重启），删掉它的目录只会让下次启动直接缺包。失败原因写明占用者的模块标识，
让用户知道该删谁。

## 为什么不再比较内容

**第一版按内容判等**：同名且逐字节相同就算"复用"，不问也不复制。这条捷径直接让机制失效 ——
现场复现是"把默认目录里已有的组合复制到桌面再导入"，内容一字不差，于是全程没有任何提示。
它有三个错：

1. **与参照物不一致**：资源管理器只比名字。名字被占用就是冲突，与两个文件内容是否相同无关。
2. **用户无法分辨**："已复用"与"打开时什么都没发生"在界面上几乎一样；而"没弹窗"在用户看来
   就是"这功能没做"。一个只在内容不同时才出现的对话框，等于一个不存在的对话框。
3. **把判断权从用户手里拿走了**：用户点"导入"是要求把这份内容放进现场，不是要求"确保默认目录
   里有一份内容相同的副本"。前者是意图，后者是我的推断。

因此判定收敛为：**目标名被占用 ⇒ 冲突**。内容比较器（文档 / 封面 / 资产逐字节比）整组删除。

## 源即目标必须早退

"源就在默认目录里"不是导入，直接无操作返回。**这条早退同时是数据安全前提**：包形态的替换
是「复制到临时项 → 删旧目标 → 改名」，如果来源目录就是目标目录，删除步骤会把来源本身删掉，
后续改名再失败 —— 用户的组合就没了。批量的路径也可能把默认目录本身当作外层文件夹扫进来，
所以早退必须发生在任何复制/删除之前。

## 覆盖的安全顺序

不保留副本，但绝不半写：

```
复制到同父目录的 <目标名>.importing-<时间戳>   →   删旧目标   →   临时项改名到目标名
```

复制失败（只读、占用、磁盘满）⇒ 清掉临时项、旧目标原样保留、记一条失败。
删除与改名之间窗口极小，且都在同一卷上。

组合包只复制**已知文件**（`composite.json`、`cover.png`、内容寻址的 `assets/`），
来源目录里的其它文件不属于组合件，不进默认目录；被替换时若新来源没有封面，旧封面一并删掉
（留着会与新组合对不上）。

## 批量导入怎么问

照 Windows 的做法：**逐条问**，勾上「为所有同名项执行此操作」后余下全部按同一选择。
取消 = 整批中止（已导入的保持原样，不回滚 —— 回滚要删用户刚写入的内容，风险比留着更大）。

拖入多个顶层项时，每项各问一轮；一项被取消余下的仍按各自情况处理。

**外层文件夹也算入口**：`ClassifyImportPath` 对"只装组合包、不含 `module.json`"的文件夹返回
`None`（它只认模块包的直接形态），批量导入走的是 `ImportFolder`。第一版 `GetImportConflicts`
在 `None` 分支上什么都没做，于是这类文件夹拿不到冲突列表、直接按"未决定"失败，同样没有提示。
现在 `None` 分支按 `FolderImportScanner` 的同一套规则（模块包在前、组合包在后）取冲突，
与真正执行时的顺序一致。

## 深度口径只有一处

**扫描深度 = 分类深度 = 冲突查询深度 = 执行深度**，唯一来源是 `FolderImportScanner`。

判据是一条不变式：*冲突列表里出现过的项，答复之后必须真的能导进来*。它同时排除两类错误：

- **问得到、做不到**：查询按扫描器递归找包，执行只认"路径自身就是包"。现场表现是
  组合页选一个装着三个组合包的文件夹，对话框把三个名字都列出来，用户答完却报「组合文件不存在」；
- **认得深、问得浅**：分类只往下看一层且只认模块包，于是混合文件夹被判成"单个模块包"，
  被送进只导模块的入口，里面的组合包被静默丢掉。

`ClassifyImportPath` 因此有四种答案：单个组合包、单个模块包、**外层文件夹**（自身不是包，
但扫描深度内有包）、不认识。UI 只按这四种分派，不再自己推断深度。

## 问的与做的必须同范围

三个入口导的包类别不同：组合页只导组合包、模块清单页只导模块包、拖入外层文件夹两类都导。
冲突查询因此带 `ImportScope`，调用方必须传它自己的范围 —— 否则用户会被问到本次根本不会导入的项
（例如组合页弹出模块包的撞名询问），那与"问得到做不到"是同一类错误，只是方向相反。

## 被否决的方案

- **async 命令 + 回调解算**：Core 命令面保持同步、无 UI 依赖；把弹窗塞进同步回调会锁死线程。
- **只改 UI 层**：落点判定在 Core（`CreateUniqueDirectory` 等），UI 拦不住批量与拖入路径。
- **所有冲突一律硬失败**：用户明明可以从 Windows 资源管理器直接覆盖过去，产品里只能失败会显得残缺。
- **按内容判等后静默复用**：见上"为什么不再比较内容"——第一版就是这么做的，现场直接失效。
- **保留副本（`.bak`）**：用户裁定不要；多一层"什么时候清、清了是不是丢了"的负担。
- **默认跳过**：等于没导入却报成功，见上。
