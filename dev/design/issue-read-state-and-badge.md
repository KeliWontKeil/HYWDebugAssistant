# Issue 已读归属与入口角标

## 问题

活动栏 Issue 图标上的红色角标读的是**错误级条数**，而"已读"是 Issue 面板自己的会话集合。
两者没有关系：用户把错误逐条读掉、甚至按「全部已读」，角标依旧挂着同一个数字，
只有删除 / 清空才会减少。于是角标既不能表达"有新东西"，也无法被用户消掉——
一个永远亮着的提醒等于没有提醒。

## 做法：已读是 Issue 条目自身的状态

已读（未读）是**条目的事实**，不是面板的私有集合。它由 `IssueCenter` 持有：

- 新上报 = 未读；
- 「选中即已读 / 标记已读 / 标记未读 / 全部已读」是命令面操作，写回中心；
- `IssueSummaryView` 带 `UnreadTotal / UnreadError / UnreadWarning / UnreadInfo`，
  计数与既有分档计数一样**增量维护**（`Report` / `Remove` / `Clear` / 淘汰最旧 都要同步扣减）。

面板不再有自己的 `HashSet<long>`：行状态直接取 `IssueView.IsUnread`，未读数取汇总。
这样"读了一条"在三处同拍生效：列表的未读标记、`只看未读` 筛选、活动栏角标。

## 角标 = 未读错误数

- 仍**只计错误级**：警告与信息不进角标（既有口径不变，否则角标会被无害信息点满）；
- 读掉即减、归零即灭；新错误进来重新出现；
- 面板**关着**时也准确：外壳每拍只取汇总，不拉列表（`RefreshSummary` 里一并抄未读数）。

状态栏摘要里的 `Issue N（错误 M）` 保持**全量**口径：那是信息，不是"待办"。
角标表达注意、摘要表达事实，两者不混。

## 边界

- **不落盘**：已读只在本次运行有效，与 Issue 本身一样是内存态；
- **全部已读覆盖全部条目**，含当前未加载（超出面板显示上限）的那些——
  "全部"就是全部，不能让用户按了还留着隐形未读；
- **删除与清空**天然带走已读状态：条目没了，未读计数一起减；
- 条目上限淘汰（4096）时，被淘汰条目的未读计数必须一并扣减，否则角标会越漂越高。

## 被否决的方案

- **角标继续报错误总数，另加"打开面板即清零"的水位线**：只改 UI 表面，
  逐条已读与角标仍会分叉（读了一条、角标纹丝不动），矛盾只是被藏起来；
- **已读留在面板，外壳读面板的未读数**：面板关闭时不拉列表，未读数只能靠已加载集合推算，
  与全量错误数对不上；改成"关着也每拍拉 500 行"是拿渲染成本换一个本可以不存在的问题；
- **角标计全部未读（含警告/信息）**：会把角标变成噪声源，与"只计错误级"的既有裁决冲突；
- **已读落盘**：Issue 本身不落盘，单为已读写文件没有可恢复的对象。
