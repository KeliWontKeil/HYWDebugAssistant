# 框架文本表的三层分片

## 要解决的问题

文本表原本是"每个拥有者一张扁平表"：`FrameworkUi` 514 条、`Core` 263 条。
对**维护者**这意味着两件事都不成立：

- 想让界面读起来更顺（改措辞、缩长度、统一口吻）时，得在几百条里逐条判断
  "这句是用户会看到的吗"——绝大多数不是，它们是配置校验、组合件解析、持久化的报错；
- 想保证专业报错"精准、不修辞"时，同样分不清哪几条属于这一类——
  改动时很容易把一条本该精确的诊断"顺手改顺口"。

两者要的编辑策略正好相反，混在一张表里就都没法执行。

## 三层

```
resources/i18n/<程序集简名>/
  zh-Hans.json              ① 用户可见的中短文本：短语、按钮、标签、状态句
  zh-Hans.diagnostics.json  ② 专业级/框架级报错与判定原因
  zh-Hans.help.json         ③ 长描述性文本：帮助正文、说明段落
```

- **① 是精调对象**：打开这个文件，看到的全是用户会看见的句子，改起来没有心理负担。
- **② 求精准不求好读**：这些句子要能被搜索到、能定位到文件行号，措辞以准确为先。
- **③ 是"多句内容"**：帮助正文不适合塞进按钮或悬停提示，单独一处便于通读。

三层**都是**可本地化文本，都受"零中文"审计约束；区分的是**编辑意图**，不是技术类别。

## 分类判据

判据只看**拥有者 + 键路径**，顺序判定、命中即止：

| # | 条件 | 落到 |
|---|---|---|
| ① | 末段 ∈ `{ body, note, tagline, tips }` | help |
| ② | 任一路径段 ∈ `{ diag, diagnostics, reason, failure }` | diagnostics |
| ③ | 末段含报错/约束类词（`failed`/`invalid`/`missing`/…/`empty`/`occupied` 等，见审计脚本的 `$shardDiagWords`）；**例外**：界面层拥有者的 `*.empty` 是空状态占位（「暂无模块」）⇒ base | diagnostics |
| ④ | 整个命名空间都是诊断（如 `core.settings`、`core.compat`、`core.composite.store`、`core.services.schema`） | diagnostics |
| ⑤ | 拥有者整体：`Hosting` / `DataPlane` / `Access`（这三个没有面向用户的中短文本） | diagnostics |
| ⑥ | 其余 | base |

判据的**唯一事实源**是 `tools/audit-resources.ps1` 的 ③e 段：新键落了错分片会判红，
并直接给出"该去的文件名"。上面这张表是它的说明，不是第二份实现。

### 为什么不用"值的长度"判 help

长度看起来是最省事的判据（超过 N 字就是长文本），但它**随译文漂移**：
同一条键在中文 60 字、在英文 140 字，于是一个语言判进 base、另一个判进 help。
跨语言分片错位后，"各语言键集合一致"的既有审计会开始报一些看不出原因的错。

键路径是**身份**，跨语言稳定。真正的长文本（帮助正文）本来就有 `body` / `note` 这类末段，
不需要靠字数猜。实测：全部 1041 条里超过 100 字的只有 4 条，其中 3 条正是 `*.body` / `*.tips`。

### 为什么 Core 需要"混合"判定

`Core` 是唯一一个两类文本都成规模的拥有者（48 条用户可见、215 条诊断）。
把它整体归到任何一边都会错：整体进 diagnostics 会让"扫描完成：新载入 N 个模块包"这类
用户每天看见的句子落到"不要动"的文件里；整体进 base 则让配置校验与组合件解析的报错
混进精调对象。

因此 ③④ 两条细判据主要就是为 `Core` 写的：`core.settings.*`（数值范围校验）、
`core.compat.*`（契约不匹配）、`core.composite.store.*`（文件解析）、
`core.services.schema.*`（配置表单结构）这些**整个命名空间**都是诊断；
而 `core.runtime.connected`、`core.services.rescan.*`、`core.services.composite.deleted`
这类**状态句**留在 base。

### 为什么模块表不拆

模块的文本表住在模块包里，作者侧本来就只有一张表、几十条。为它们引入三层：
作者要多记一条规则、拆分脚本要多覆盖一处、而收益（"分不清哪些值得精调"）
在几十条规模上并不成立。**框架表分层，模块表就近维护**。

审计对模块拥有者只做既有检查（键在不在、路径越不越界），不套分片规则。

## 运行时零改动

分片合并是既有能力：`TextCatalog.LoadTable` 按 `<culture>.json` 优先、
其余 `<culture>.*.json` 按文件名序合并、**先者胜**；跨分片重复键整份跳过并报诊断；
单文件上限 4 MiB。因此本次只改数据布局与审计，不动任何 C# 代码。

"先者胜"意味着分片顺序会影响结果，所以审计**禁止跨分片重复键**——
一条键只该出现在一个分片里，重复即是"第二份事实"。

## 落地

一次性脚本读原表、按判据分派、保持键的相对顺序不变（只抽走别层的键，留下的仍按原序），
输出三份文件。验收方式是**合并前后逐字相等**：拆分前把 8 张表读成"拥有者 → (键, 值)"的快照，
拆分后把每个拥有者的所有分片再合并一遍，比对键集合与每个值。

条数（拆分前 1041 条，拆分后合计仍 1041 条）：

| 拥有者 | base | diagnostics | help |
|---|---|---|---|
| Access | 0 | 2 | 0 |
| App | 1 | 0 | 0 |
| Core | 48 | 215 | 0 |
| DataPlane | 0 | 26 | 0 |
| FrameworkUi | 458 | 30 | 27 |
| Hosting | 0 | 69 | 0 |
| Sdk.Ui | 31 | 0 | 0 |
| Ui | 114 | 19 | 2 |

空层不建文件（Access / App / Hosting / Sdk.Ui 只有一个文件），避免"空壳分片"被误读成
"这一层正在使用"。

## 审计会在输出里打印分层形状

每次 `audit-resources.ps1` 都打印一行"拥有者 × 层 × 条数"。数字变化就意味着有人挪了键，
比逐条翻文件直观得多。它是**报告**，不是判据；判据仍是"键该在哪一层"。

## 被否决的方案

- **按值的长度判 help**：译文间会漂移，产生跨语言分片错位（见上）。
- **逐键白名单登记分片**：会变成第二份需要人工维护的事实，且新键必须同时改两处。
- **按"是否含报错关键词"判 diagnostics（只看值）**：同样是译文相关；
  中文"失败"在英文里是 "failed"、在别的语言里可能是一个不含拉丁词的单词。
- **给模块表也分层**：几十条规模下收益不成立（见上）。
- **新增一层目录（如 `i18n/<拥有者>/diagnostics/`）**：运行期不认，
  得改 `TextCatalog` 的目录遍历规则；而分片机制本来就是为此存在的。
