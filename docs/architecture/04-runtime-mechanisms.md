## 运行时总流程与重建判据 〔源: 主文档 §7.1–7.3 + ADR-0012 + ADR-0011〕

```text
用户拼接声明 → Composition Model → Validation → Runtime Construction
          → Runtime Binding → Module Execution
```

- **无全局 Run/Stop**：系统常驻活动，模块**加入即运行**（即插即用），不存在"加载工作区/启动工程"动作 〔主文档 §7.1〕。
- **数据直通**：绑定建立后，数据在**连接两端模块的接口之间直接流动**；Core 只创建/拆除绑定与管理生命周期，**不中转、不转发任何业务数据** 〔主文档 §7.2 / P2-E1〕。
- **变更即运行时行为**：任何组合或配置修改在线即时生效，Core 对"用户声明"与"运行时实现"做差异并 **reconcile 受影响子链路**，而非整机重启 〔主文档 §7.1〕。
- **变更的原子单位 = ChangeSet**：多步操作组装为一次复合变更，整体校验 → 一次性应用 → 增量重建；任一步失败整体拒绝（§ChangeSet 原子性）〔ADR-0011〕。
- **重建单位 = 绑定及其邻接数据面**（§增量重建）〔ADR-0012 R1〕。
- **模块状态与异常隔离**：模块的状态变化（含离线/故障态）不影响任何无关模块；数据流因上游状态变化而中断，对下游是**合法的"无输入"状态而非错误**（验收判据 AC-2）〔主文档 §7.1/§8.3 + ADR-0015〕。

## 生命周期状态机 〔源: ADR-0014 + 主文档 §8.1/§8.4 + architecture/04 §4.1〕

**框架层状态机（框架权威判定）**：`Registered → Active ⇄ Disabled → Removed` 〔ADR-0014 LC-01〕。

| 框架状态 | 线程 | 队列 | 说明 |
|---|---|---|---|
| `Registered` | 无 | 无 | 实例已建（成员实例化完成），**不占线程** |
| `Active` | 分配并启动 | 接收投递（**每口一条**） | 加入即运行；模块活动体开始执行 |
| `Disabled` | **保留** | **停流**（投递暂停，绑定保留） | 保留实例/拓扑/配置；`OnDisabled` 通知模块自决内部处置 |
| `Removed` | 请求退出 → 有界等待 → 回收 | 销毁（**全部口**的队列一起清空） | `OnRemoved` + 停止信号（见下节停止协议） |

> **结论：禁用（Disabled）不释放线程与资源；重新启用即继续**。依据 = **ADR-0029 第 1 条 + `04` §4.1 状态表 + 代码行为**〔源: ADR-0029 第 1 条 + architecture/04 §4.1 + 代码 `DataPlane/Carriers/CarrierHost.cs`〕。`04a` §6 与主文档 §7.3 的"按活跃实例计 / 为每个 `Active` 实例提供专属线程"描述的是**线程分配**，不作为本条的相反口径。

- `Created / Initialized` 属"加入"的**转换过程**，`Stopping / Stopped / Disposed` 属"移除"的**转换过程**——均为过程而非稳态；`Faulted / Recovering` **不作为框架状态**（软件异常走"异常报告 → Issue"）〔主文档 §8.1/§8.4〕。
- **四个正交面**：存在性（框架权威）· 活动面（框架权威）· 业务状态（模块自报，框架只登记/呈现、不解释）· 异常报告（模块产生、框架受控收集）〔ADR-0014〕。
- **Enable / Disable（LC-02）**：Disable = 保留实例与全部拓扑/配置、暂停数据流（绑定保留停流）、**通知模块**（内部处置自决：停采样/断连/保持）；Enable = 反向恢复。**框架不替模块决定"禁用时是否断硬件"**〔ADR-0014〕。
- **移除不可逆（LC-03）**：ChangeSet 原子操作 → 级联清连接/绑定 → 框架释放成员实例资源 → 模块钩子释放内部资源；**重新加入 = 新实例**（配置复制属 UI 便利；撤销由 UI 撤销栈承担，框架不做自动回滚补偿）〔ADR-0014 + ADR-0011〕。
- **绑定与生命周期解耦（LC-04）**：绑定**独立于模块状态、随连接存在**——`Disabled` → 绑定保留停流（UI 标注）；`Removed` → 级联销毁；业务状态变化（离线等）**不触碰绑定**（表现为无数据，§8.2 类 a）；绑定建立不要求特定业务状态〔ADR-0014〕。

## 线程、队列与停止协议 〔源: architecture/04 §4.1 + ADR-0029 Q4-1/Q4-5/Q4-2 + ADR-0050 Q2 〕

### 结构

```text
每个 Active 的 Module Instance
  ├── 1 个专属线程（由 L3 创建/管理/回收；模块不自建线程）
  ├── N 个有界输入队列（**每 (实例, 口) 一条**；容量与丢弃策略按口声明）
  ├── 1 个停止信号（框架设置 → 模块应尽快退出活动体）
  └── N 个订阅缓冲（供 UI 读取，见"UI 交接"节）
```

### 模块活动体（允许阻塞）

- 框架在自己的线程上调用模块的"活动入口"；**模块可以在其中自由阻塞、循环、做同步 IO**——线程是它的，阻塞只影响它自己（隔离语义）〔ADR-0029 Q4-5〕。
- 模块通过框架提供的**停止信号**感知停止请求；收到后应尽快返回活动体。
- 模块**不得**创建自己的线程/定时器 〔ADR-0013〕；需要周期活动时在自己的活动体内实现，或声明周期活动由框架承载。

### 停止协议（诚实的边界）

```text
框架：设置停止信号 → 有界等待（默认 5 s，可配置）
  ├─ 模块按时返回 → 正常回收（线程结束；队列/绑定/池化缓冲按序释放）
  └─ 超时 → 记 Issue（"模块未在期限内停止活动"，归属该实例）
             + 标记该线程为孤儿（框架放弃等待，不再管理）
             + 该实例的队列/绑定标记为「弃用」（停止投递，后续计入丢弃计数）
             + **不释放**队列/缓冲/池（放弃引用，交给 GC）；仅释放已确认安全的外部资源
```

- **.NET 不支持安全的线程中止**（`Thread.Abort` 已废弃且不安全）——因此框架**不假装能强杀模块**：超时后只放弃等待并报告。这是有意的设计选择（诚实优于不可靠的强制手段），并由 Issue 让用户可见。强制卸载程序集以终止超时模块亦被明确排除（可能导致进程崩溃）〔ADR-0029〕。
- 默认超时值 **5 s**，属**应用级设置**（修改后对**后续**停止操作生效，进行中的等待不追溯）〔04b §6 + 07 处置表实测回写〕。
- 移除后可能残留**孤儿线程**——此时"`Removed` = 资源已释放"对该线程不成立，属**有意接受的边界**，资源处置见下表 〔ADR-0014 例外登记 + ADR-0029 §4.1〕。

### 超时路径的资源处置规则（必须遵守 · 判据见 `09-test-and-gate.md` T5）

| 资源 | 处置 | 原因 |
|---|---|---|
| 输入队列 / 订阅缓冲 | **标记弃用、不释放**（停止投递；对象引用保留，交给 GC） | 孤儿线程可能仍在读写——释放会造成悬空访问 |
| 池化缓冲 | **不归还池**（放弃引用，由 GC 回收） | 归还后可能被重新分配，而孤儿线程仍在写 |
| 绑定 | 从绑定快照移除（不再被投递路径引用） | 断开数据流，避免污染其他模块 |
| 线程对象 | 保留（框架不再 Join、不中断） | 无安全中止手段 |
| 模块内部资源（句柄/文件等） | 由模块自己的 `OnRemoved` 释放；无法响应时由 OS 在进程退出时回收 | 框架无权替模块释放其内部资源 |

**安全承诺**：上述规则保证"孤儿线程的任何后续写操作**不会破坏框架或其他模块**"（最坏情况是它写自己那份已弃用的缓冲，随线程结束被 GC 回收）——这是"护栏 = 安全"在超时路径上的具体含义，也是 T5「停止超时路径」的通过标准。

### 异常边界

| 位置 | 处理 |
|---|---|
| 模块活动体入口 | 整体包裹：异常 → 捕获 → 转 Issue（归属实例）+ 该模块活动停止（线程进入"异常停机"） |
| 模块回调（生命周期钩子） | 逐个包裹：异常 → Issue；不中断框架流程 |
| 模块上报 API 内部 | 不抛：上报失败只记诊断计数（模块不应因上报失败而崩） |
| 框架自身代码 | 不捕获（属框架缺陷，应暴露给开发者） |

- **不引入 Faulted/Recovering 框架状态**：异常停机表现为"该实例不再产生/消费数据"，恢复由用户显式操作（"重建实例" = Remove+Add ChangeSet）〔ADR-0015 ER-02〕。
- **前端联调要点**：被动接收（框架投递循环驱动）与主动接收（模块在活动体内轮询）都是合法路径；**低频主动接收在 Windows 下会退化到定时器粒度**，实测数据见"实测基准"节。

### 落地缺口

- **`CarrierHost.cs` 的注释需修**：其类注释写"`Disabled` 的实例不占线程"，与现行行为（**禁用保留线程与资源**，见本节状态表结论）**不一致** ⇒ 以代码行为为准，**注释需改**。〔源: 代码 `src/DataPlane/Carriers/CarrierHost.cs`（"按活跃实例计……`Disabled` 的实例不占线程"）vs 本册生命周期状态表〕

## 数据单元、绑定与投递 〔源: architecture/04 §4.2 + ADR-0029 Q4-2/Q4-3 + ADR-0051〕

### 数据单元的物理形态

```text
契约类型（作者写的 C# struct，成员限定长原语）
   │ 加载期
   ├─► 形状元数据：字段偏移表 + 传递语义标注（供框架通用读写/兼容判定/序列化）
   └─► 强类型访问器（生成）：模块侧按类型直接读写，无反射、无装箱
存储与传递：池化定长缓冲（扁平），跨线程按值/所有权移交
```

- **框架不附加任何元信息**（时间戳/序号/来源）：缓冲里只有契约声明的字段；**需要时间戳/序号由模块在自己的契约形状中声明**〔主文档 §5.4.2〕。
- 例外：**多源网络的薄旁路头**随单元旁路携带、**不进 payload 字节流**（字节守恒不变），单源网络为 `null`（零附加）——细则见 `05-network-semantics.md`〔主文档 §5.4.2 · ADR-0050 Q6(c)〕。
- **兼容判定 = 形状完全一致**（原「接收 ⊇ 发送」子集口径已作废），用偏移表计算；判定实现在 L2/L4，不在 SDK〔ADR-0051〕。
- **分工**：**特化在访问层**（模块怎么读写字段）、**绑定对象在编排层**（谁投递给谁、诊断计数、动态增删）——两者正交〔ADR-0029 Q4-2/Q4-3〕。

### 绑定对象

| 字段 | 内容 |
|---|---|
| 标识 | 所属网络标识（匿名/命名） |
| 源 | 源实例 + 源口 |
| 目标 | 目标列表（目标实例 + 目标口 + **目标输入队列引用** + 每目标诊断计数） |
| 契约 | 形状元数据引用（偏移表 + 传递语义） |
| 诊断 | 投递单元数、丢弃数、最后数据时间（L4） |
| 状态 | 正常 / 停流（Disabled 或上游无输入）/ 悬空（口消失） |

### 投递流程

```text
发送模块（在自己的线程上）调用发送 API
   → 绑定对象：从池取定长缓冲（或复用调用方缓冲）→ 填充契约字段（访问器）
   → 对每个目标：写入目标模块的有界输入队列
   → 目标线程被唤醒/已就绪 → 调用目标模块的接收回调（访问器读字段）
   → 缓冲归还池
```

- **1:N 多播 = 绑定对象写多个队列**（无运行时转发对象、无转发模块）。
- **多源网络（N:M）**：同名标签的多个发送端 = 一条多源网络，逐 (源,宿) 对建绑定；部分源不可用 ⇒ 其余源照常投递 + 该源 Issue；全部源不可用 ⇒ 停流（保留声明、不建绑定）——完整语义（停流/悬空、悬空源、网络身份键）见 `05-network-semantics.md`。
- **不自动转换**：契约不兼容时该 (源,宿) 对不建立绑定并标注差异 + Issue〔ADR-0051〕。
- **绑定集合的增删与投递的并发**：绑定集合以**不可变快照 + 原子替换**（copy-on-write）方式发布；生产者线程读取当前快照完成投递，管理线程替换快照完成增删。绑定数量规模小、重建不频繁，此方案免锁且正确。
- **投递全程在 L3**：发送模块线程 → 绑定对象 → 目标队列 → 目标模块线程；L4 只做增删绑定（改快照），**从不接触单元数据**。

### 有界缓冲与丢弃

| 项 | 方案 |
|---|---|
| 缓冲归属 | **每 (实例, 口) 一条队列**：容量**按口计**、互不挤占 ⇒ 一个口满载/慢速**不会**堵住同实例其它口（消除跨口队头阻塞）；同口内仍严格 FIFO |
| 容量 | 按单元数计（**每口各自享有**）；默认 **1024 单元/口**，属**应用级设置**（修改后对**新建**队列生效；既有队列保持创建时容量，避免运行中改容量导致数据丢失） |
| 默认策略 | **丢最旧保最新**（实时场景默认）；可选**丢新**；**v1 不做背压**（与"绝不阻塞发送方"互斥）。各口独立取声明值，不需要"最严格合并" |
| 调度 | 投递循环在**非空口之间轮转**（每轮每口至多一个）⇒ 任一口都不会被饿死；主动接收（`TryReceive`）走同一轮转 |
| 计数 | 每绑定/每队列丢弃计数 + **队列水位**（L4 可见）；**丢弃与水位都按口归属** |
| 不阻塞上游 | 队列满时**绝不阻塞发送方**——只丢弃 |

〔源: architecture/04 §4.2 + ADR-0012 R2 + ADR-0029 C4-1/C4-3 + 04b §6 + 07 处置表实测回写；四档速率与丢弃三类的口径见 `05-network-semantics.md`〕

- **队列实现纪律**：**不自研无锁结构**，优先使用官方 `Channel<T>`；若确需自研，只做 **SPSC 环形缓冲**（并发正确性风险集中在框架，写错极难发现）。队列元素必须是**值类型或池化缓冲**（引用对象每单元 `new` 会把分配率推回 10⁶ 对象/秒，抵消零分配设计）〔源: 04a §2.3 代价 4/7〕。

## UI 交接：订阅缓冲 〔源: architecture/04 §4.3 + ADR-0029 Q4-4 + ADR-0035 D6-2〕

```text
模块线程                                  UI 线程
  │ 写入订阅缓冲（每订阅一个环形缓冲）        │
  └───────────────► 环形缓冲 ──────────────►│ 按刷新节拍读取
                     （有界，满则丢旧）       │ 抽样/降采样（曲线类）
                                            └─► 渲染
```

| 元素类型 | 交接形态 |
|---|---|
| A1 数值 / A2 状态灯 / A7 仪表 | **最新值槽**（容量 1 的订阅缓冲） |
| A3 曲线 / A4 表格 / A5 日志 / A6 字节视图 / A8 图像 | **环形订阅缓冲**（有界，满则丢旧） |
| B 交互控制 | 反向路径：UI 线程 → 命令/配置写回（经 L4 变更入口，**不直接触碰模块内部**） |

- **抽样与降采样在 UI 侧做**（刷新率是 UI 属性）：模块按自己的节奏写，UI 按自己的节拍抽。
- **UI 慢永不阻塞模块**：缓冲满即丢旧；丢弃计数计入 L4 诊断。
- **UI 不直接调用模块代码**：全部经 L4 变更入口 → 模块线程；UI 读取**一律经 `Core.Api` 统一查询**。

### 实现落定值

| 项 | 落定值 |
|---|---|
| 形态判定 | **按元素类型**（上表）：数据源被 A3/A4/A5/A6/A8 引用 → 环形；否则最新值槽。数据源**声明为非值类**（序列/行集/字节块/文本/帧）时同样用环形 |
| 环形容量 | **512 样本**（框架常量 `SubscriptionBuffer.DefaultRingCapacity`，**暂不可按实例配置**） |
| 单样本字节数 | **首次写入时确定**（= 首个样本长度，上限 1024）；此后更大的样本被丢弃并计数（同一数据源的样本长度必须一致） |
| 并发 | **单写者**（实例专属线程）+ **多读者**；写侧不取锁，读侧用**序号锁**乐观读（发现写入中即本次放弃，最多重试 8 次后返回"暂无数据"）——**读绝不阻塞写**；实测 2 万次并发读写零撕裂 |
| 分配 | 存储一次预分配（容量 × 槽尺寸），稳态**零分配**；尺寸不一致的丢弃**只提示一次**（不刷屏） |
| 未声明的数据源名 | 丢弃 + **只提示一次**（Issue：PresentationError） |
| 无 UI 模块 | 不建立任何订阅缓冲（合法） |
| 数据源声明 | 模块声明**名称 + 类型**（`ViewDataSourceKind`：值/序列/行集/字节块/文本/帧）+ 可选 `ValueType`（契约原语，供 UI 解码；**不猜类型**：未声明原语 → UI 不呈现数值） |
| UI 侧抽样 | 曲线窗口最多 256 点；样本数超过窗口时**等间隔抽样（不插值）** |

〔源: architecture/04 §4.3.1 + ADR-0035 D6-2〕

## ChangeSet 原子性 〔源: architecture/04 §4.4 + ADR-0011 + 主文档 §6.2〕

### 操作集

建立/加入/退出/断开网络 · Add Module · Remove Module · Enable / Disable · 配置更新 · 组合件加载（实例群 + 网络，作为一次复合）。

### 两阶段结构

```text
① Prepare（可失败，无副作用）
   解析操作集 → 校验（实例存在性 / 口存在性 / 方向 / 契约兼容 / 名称冲突 / 资源上限）
   → 计算 diff → 构建「应用计划」（新建绑定对象、待删绑定、实例创建/销毁清单、
     预分配：线程、队列、池化缓冲、订阅缓冲）
② Commit（无失败点）
   按序应用：创建实例 → 启线程 → 建绑定 → 拆绑定 → 停线程 → 销毁实例
```

- **失败整体拒绝**：Prepare 阶段任一校验失败 → 整个 ChangeSet 拒绝，**零副作用**（连线程都不创建）。
- **Commit 无失败点**：所有可能失败的事（分配、校验、生成）都在 Prepare 完成。
- **不引入全局事务/锁**：并发变更由 L4 的**变更入口串行化**（单管理路径），不与数据面争锁；无跨会话全局事务。
- **顺序保证**：Commit 采用"**先加后减**"——先建新实例/新绑定，再拆旧绑定/销毁旧实例；中途出现意外异常也不会留下悬空引用（最多留下多余资源，由 Issue + 诊断暴露）。
- 撤销：框架**不做自动回滚补偿**；用户侧撤销由 UI 撤销栈实现（= 反向 ChangeSet）；可选标准动作"**重建实例**" = Remove + Add 的复合 ChangeSet，由 UI/命令层组装，框架只执行 ChangeSet。

## 增量重建 〔源: architecture/04 §4.5 + ADR-0012 R1〕

```text
ChangeSet Commit
   → 声明侧（Composition 声明集）与运行侧（绑定集）做 diff
   → 重建单位 = 绑定及其邻接数据面
       · 新增连接 → 新建绑定对象 → 加入快照（原子替换）
       · 删除连接 → 绑定对象从快照移除 → 在途单元丢弃计数
       · 契约/方向变化 → 等价于删旧建新
   → 模块实例、配置、业务状态一律保留（插拔线不重置模块）
```

- **不触达模块的情形**：连接增删（模块无感知）。
- **触达模块的情形**：实例增删（`OnRegistered`/`OnRemoved`）、Enable/Disable（`OnActivated`/`OnDisabled`/`OnEnabled`）、配置更新（`OnConfigurationChanged`，**热生效或模块请求重建由模块自决**）〔钩子清单见 `02-module-sdk.md`〕。
- **悬空态**：口消失而网络仍在（加载重锚失败）→ 绑定进悬空态 + Issue，**不阻断其他部分**。
- **重建的并发安全**：diff 与快照替换在管理线程；数据面投递读快照——无锁、无停顿。

## 组合件与持久化 〔源: architecture/04 §4.6/§4.6.1 + ADR-0016 + ADR-0017 + ADR-0050 M11 + ADR-0035 D3〕

**组合件（Composite）= 持久化与复用的唯一载体**：**1 文件 = 1 组合件**；保存 = "一组实例 + 网络 + 配置 + 布局"物化为组合件；加载 = 实例化进当前工作区（生成实例群与网络），可复用、可参与拼接〔ADR-0016〕。不存在"工作区文档/文件"；"保存全部内容" = 一个覆盖当前全部实例与网络的**根组合件**（概念上仍是蓝图）。

### 随件内容边界

| 项 | 是否随件保存 |
|---|---|
| Configuration（实例配置） | ✅ |
| 网络（成员 + 名称 + 匿名/命名） | ✅ |
| Layout（视图位置与偏好） | ✅（加载时可"忽略布局"） |
| 实例活动面（启用·禁用） | ✅ |
| **Runtime State 与绑定** | ❌（加载后重建） |

**Configuration 的登记语义**：模块**首次读取**配置即登记该实例的**默认配置**，此后读取返回同一对象、`Write<T>` 覆盖；组合件加载时由恢复值覆盖（否则"只读不改"配置的实例保存时会整块丢失）。配置集合的访问点（读取/写入/快照/恢复）**统一加锁**——它同时被模块线程与管理线程访问〔ADR-0035 D3〕。

### 机制与流程

| 项 | 方案 |
|---|---|
| 格式 | **文本 JSON**（可读/可 diff/易迁移）；文件内嵌 `schemaVersion` |
| 内容 | 实例（ID 三元组 + 版本 + 配置）+ 网络（成员 `实例ID.口名` + 名称 + 匿名/命名）+ 布局 + 活动面；**运行态与绑定不序列化** |
| 未知字段保留 | 解析时按层保留原始片段；写回时**合并**：已知字段按当前 Schema 写，未知字段原样带回 → **AC-4 无损往返** |
| 原子写 | 临时文件 → 写入 → Flush → `File.Replace`（防半写损坏） |
| 版本迁移 | 能迁移则自动迁移；不能则**拒绝并保护原文件**（不破坏、不静默降级） |
| 加载流程 | 解析 → Schema 校验/迁移 → 实例化（Definition + 版本）→ 恢复配置 → **重建成员（口）** → 按 `实例ID.口名` **重锚网络成员** |
| 异常加载 | 缺失 Definition → 占位保留（配置与网络成员）+ Issue；版本不兼容 → 缺失态 + Issue（可手动指定替代版本）；损坏 → 尽量部分恢复 + Issue；完全不可解析 → **拒绝加载并保护原文件** |
| 会话快照 | 独立于组合件的可选能力（不在 v1） |

### 实现落定值

| 项 | 落定值 |
|---|---|
| 文件顶层 | 组合件**即根对象**（无包裹层）：`schemaVersion` / `name` / `savedAt` / `instances` / `networks` / `layout` |
| 实例记录 | `instanceId` + `moduleId`（含版本的三元组字面量）+ `enabled`（活动面）+ `configuration` + `ports` |
| 端口几何存放 | 作为实例记录内与配置并列的实例几何段 `ports`（键 = 口名，值 = `{ offset, locked }`）；**只记录被用户调整过的端口**——与"端口几何与模块参数同层"一致 |
| 配置段形态 | `configuration` = "**配置类型完整名 → 配置对象**"的统一映射（单类型时略啰嗦，但**无信息损失、无多义**，且天然支持同模块多配置类型）；不采用"特例展平 + 模式标记" |
| 布局段 | 顶层 `layout` = "实例 ID → `{ x, y, width, height, viewVisible }`"；**只存位置**，拼接组由几何派生 |
| 网络记录 | 【**schemaVersion 2**】`name`（空串 = 匿名）+ `isAutoGenerated` + **`sources`（声明的源数组，有序）** + `targets`（在场的宿）+ `unresolved`（悬空的**宿**成员）；**匿名/命名不另存布尔量**（与运行时模型同一事实源）。**v1 的单值 `source` 读入即归一为单元素 `sources`，写回升版 v2 并移除旧字段**（同一事实绝不留两个字段） |
| 序列化实现 | 组合件**信封**用手工 `JsonNode` 映射（**零反射**，且是"未知字段逐层保留"的实现手段）；**模块配置对象**因类型由模块定义、框架编译期不可知，走反射式 `JsonSerializer`（SDK 未要求模块提供源生成上下文）——信封实际比源生成更彻底，**模块配置为结构性例外** |
| 未知字段保留粒度 | **逐层**：根 / 实例 / 网络 / 布局 / 端口 / **配置对象内部**（已知属性合并写入、未识别属性原样带回） |
| 上限与拒绝 | 单文件 ≤ **16 MB**、结构深度 ≤ **8 层**；**超限/语法非法/版本过新 = 拒绝**，原因分类报告（不存在 / 过大 / 过深 / 不可解析 / 不可读），且**绝不改写原文件** |
| 加载期自动建网 | **不参与**：网络完全来自文件（否则加载会复制出一批自动连线） |
| 悬空与占位 | 悬空成员（口消失/契约不兼容）保留声明 + 不建绑定；**源/宿两侧都有悬空**（源侧 = `UnresolvedSources`）——**部分源悬空不影响其余源投递**，**全部源悬空 = 停流**；缺失定义/版本不兼容 → **占位实例**（保留配置与网络成员）；占位可经"指定替代版本"实例化并**自动重锚**其悬空成员 |
| 禁用实例 | 加载后其绑定置**停流**（网络在实例之后恢复，故停流在活动面收尾阶段统一置位） |

〔源: architecture/04 §4.6.1 + ADR-0050 M11/R3 + 主文档 §9.3〕

**持久化内容全集（三类）**：① **组合件**（本文件）② **应用级设置**（Core 管理 + 独立用户级文件，**与组合件完全分离**：不随组合件保存或加载、组合件不携带设置快照，见 `08-application-settings.md`）③ **会话快照**（可选能力，不在 v1）〔ADR-0016 + ADR-0030 + 主文档 §9.5〕。

## Issue 与可观测性 〔源: architecture/04 §4.7 + ADR-0015 + 主文档 §13.2 + ADR-0046〕

```text
来源：框架判定（L2/L3/L4）+ 模块报告（经 SDK 上报 API）
   → Issue 中心（L4）：归属对象（实例 / 口 / 网络 / 配置项）+ 类别 + 来源 + 描述 + 时间
   → 两条语义：设计/变更问题（Prepare 拒绝等）· 运行报告（异常/悬空/超时停止等）
   → 分发：UI 侧按归属对象取（对象标注）+ 汇总列表；不阻止其他部分运行
```

- **类别 = 七类**：Configuration / Composition / Interface / Module / Communication / Runtime / Presentation Error；原则：**Core 管理系统级故障，不理解具体业务语义**。
- **隔离与恢复**：**天然隔离 + 显式恢复**——框架**不自动重试、不自动降级、不阻断上下游**；隔离的实现保障 = **模块异常不逸出边界**（框架在边界捕获并转 Issue）；恢复 = 用户显式操作或模块自身内部恢复〔ADR-0015 ER-02〕。
- **通知与日志分层**：框架层 = Issue 列表（对象标注 + 汇总）+ 机制层诊断日志；模块层 = 模块自产日志/诊断经框架汇集呈现；通知强度 = **默认轻量呈现（标注/计数），不弹窗打扰**，允许模块声明"需要用户注意"级别〔ADR-0015 ER-03〕。
- **模块业务状态不入 Issue**（属状态面，走状态通道）。
- **线程安全**：模块线程报告 → 无锁并发队列 → UI 线程消费（不阻塞模块）。

### 可观测性分层与采集点

| 层 | 采集点 |
|---|---|
| L1 框架诊断 | 加载/注册/建网/绑定/增量重建/ChangeSet 应用（结构化日志） |
| L2 Issue 中心 | 归属对象标注 + 汇总列表 + 过滤 |
| L3 模块日志/状态 | 模块经 SDK 上报（分级 + 来源），框架汇集 |
| L4 数据流诊断 | 每绑定/每队列：投递单元数、**丢弃计数**、**最后数据时间**、队列深度（水位） |
| L5 性能监视 | CPU/内存/模块活动统计（不在 v1） |

- L4 的**速率与丢弃口径已细化**：四档速率（单元 / 搬运字节 / 有效载荷字节 / 样本-通道样本）与丢弃三类（停流未投递 / 传输丢弃 / 模块内部丢弃），UI **只显示有定义的口径**、**不做"实际 vs 框架"的单数字对比**——细则见 `05-network-semantics.md`〔主文档 §5.4.2/§13.2 + ADR-0046〕。
- 原则：默认轻量不打扰；L1/L4 为排障主力；录波/回放属未来能力。

## 护栏：安全（静默）+ 提示（轻量） 〔源: architecture/04 §4.11 + ADR-0029 C4-1〕

**明确不做**：每口发送速率上限、环/自连检测、任何阻断或拦截、给数据单元附加跳数/预算元信息（后者同时违反数据面边界）；**不改变"自连/环允许"的既有裁决**。

| 类 | 内容 | 可见性 | 时机 |
|---|---|---|---|
| **安全护栏** | 线程安全（快照/队列/池的并发正确性）、内存安全（池化缓冲的边界检查与归还保护）、缓冲满时的丢弃（丢旧）、栈/资源上限保护 | **不可见**（用户不需要看到） | 快速、静默、在热路径上无分支开销 |
| **轻量提示** | 事实陈述类指示，例如"该缓冲持续为满""该模块处理速度跟不上输入""该线程占用偏高""该模块未在期限内停止" | **可见但不打扰**（L2/L4 层） | 由框架按阈值生成提示，**不阻断、不预设问题场景、不替用户判断** |

**设计原则**：用户不关心通信速率限制，只关心"程序是否会崩溃、数据能否完整传到、是否会卡顿"——因此框架的责任是**保证安全 + 让事实可见**，而不是替用户管理流量。

### 发现一：空闲唤醒粒度与"等数据"原语

| 接收模式 | 单单元两跳延迟 | 说明 |
|---|---|---|
| **被动接收**（模块只 `SetReceiveHandler`，框架投递循环等待） | **893 ns** | 框架用 `SemaphoreSlim` + 入队即 signal，本就是事件唤醒 |
| **主动接收 + `StopSignal.Wait(1ms)`** | **15.70 ms** | `IStopSignal.Wait` 的语义是"等**停止**信号"，被当成"等数据"的轮询间隔用 → 每次空转等满 1 ms，而 Windows 定时器分辨率 15.6 ms |
| **主动接收 + 自旋轮询** | **781 ns** | 忙等；快但占一个核 |

- **根因**：不是 `Thread.Sleep` 的实现，而是**"等数据"缺少专用原语**——数据到达**不会**唤醒停止信号，因此把停止信号改成 `ManualResetEventSlim` 也解决不了（模块仍要等满超时才去看队列）。
- **影响面**：被动接收路径（框架驱动投递）无此问题；主动接收路径在**低频**下退化到定时器粒度，在**连续流**下无影响（1.82 µs / 3 跳）。
- **现行裁决**：参考桩模块**改用被动接收**（实测 893 ns；主动接收路径的组合级覆盖由 `ActiveReceiveTests` 保留）；`WaitForData` 列为**后续里程碑的 SDK 兼容扩展项**（让主动接收也能微秒级且不占核）——SDK 面落地归 `02-module-sdk.md`。
- 与延迟量级表的关系：稳态成本为**百纳秒级**（连续流下成立）；"空闲后唤醒"一侧的原估算（1–10 µs）**在按"停止信号当轮询"的写法下不成立**，实测为 15.6 ms 级——上表即该结论的实测修正。

### 发现二：投递路径每单元 40 B 分配

- 现象：`借+还` 与 `完整投递` 两个基准均为 **40 B/op**；订阅写入路径已是 **0 B**；两跳链基准另测得 **128 B / 2 跳**（与 40 B/单元 × 目标数一致）。
- 原因：`PooledPayloadBufferPool.Rent` 每次都 `new PooledPayloadBuffer(...)` 生成**包装对象**（`PayloadBuffer` 是 abstract class）；**1:N 组播时按目标数放大**。
- 实测影响：10⁶ 单元/秒 ≈ **40 MB/s** 分配；持续负载下 GC 回收 50/43/36 ~ 319/74/68 次、**总暂停 0.37–0.81%**、**最长暂停 0.06–0.90 ms**，即 **≈0.5% CPU 开销 + 亚毫秒尾延迟**，对"监视/分析"目标可接受。
- **现行口径**：与"每单元分配 0"的设计承诺不一致 ⇒ 已裁决 **① 池化包装对象**（L3 内部空闲链复用 wrapper：不动 SDK 面、不需 ADR，列入后续里程碑首项，约 40–60 行 + 补"复用后计数不增长"等测试）；**在此之前，文档承诺以实测为准 = "投递路径每单元 40 B、订阅路径 0 B"**，实现完成后回写为 0。
### 延迟量级（设计值与实测的对照口径）

| 路径 | 延迟量级 | 说明 |
|---|---|---|
| 同线程直接调用 | ~1–5 ns | 基线（实测 2.37 ns） |
| 无锁入队 + 出队（缓存命中） | ~20–80 ns | 含内存屏障（实测 34.7 ns） |
| 跨核缓存行传递（MESI 转移） | ~100–300 ns | 生产/消费不同核 |
| 自旋等待 | 百纳秒级 | = 队列传递成本；代价是占用一个核（实测 196.6 ns） |
| 事件/信号量唤醒（Windows 通用调度，有空闲核） | ~1–10 µs | 含系统调用与调度器；核忙时更差（实测 9.55 µs）；**不可与"用停止信号当轮询"的 15.6 ms 混为一谈** |
| RTOS 任务唤醒（对照，**不可直接类比**） | 百纳秒级 | RTOS 内核与应用同特权级、系统调用极轻；Windows 需进内核并走调度器 |

- **关键更正**：微秒级只出现在**空闲后唤醒**；**稳态流水线中消费者通常并未真正睡眠**，此时"唤醒"退化为"发现数据已就绪"，成本接近纯队列传递（百纳秒级）。
- **可用的收敛手段**（Windows 侧）：`SpinWait` / `ManualResetEventSlim` 的自旋+阻塞混合策略、线程优先级、CPU 亲和性与核隔离；必要时对少数高频模块采用忙等。

### 队列投递延迟相对数据到达间隔是否显著

| 场景 | 单元到达间隔 | 与 µs 级投递延迟比较 |
|---|---|---|
| 串口 115200 bps | ~87 µs/字节 | 延迟约为间隔的 1–10% |
| CAN 1 Mbps | ~8 µs/帧 | 延迟与间隔同量级（需注意） |
| 采集 1 kHz | 1000 µs/单元 | 延迟可忽略 |
| 采集 10 kHz | 100 µs/单元 | 延迟约 1% |
| 采集 1 MHz | 1 µs/单元 | **延迟超过间隔**（队列会成为瓶颈；需批量或单线程直调） |

**结论**：在 kHz 量级与常规总线速率下，队列投递延迟相对数据到达间隔通常很小；**只有在 10⁶ 单元/秒以上、或存在硬周期要求的模块上**，投递机制才会成为主导成本。

### 承载模型的演进路径（现行不采用，语义不变）

- 线程数**按活跃实例计**（`Disabled` 的实例不占线程；`Removed` 释放线程），设计前提假设 = **活跃模块数量级为数十**（用户口径：通常活跃模块不会超过 20–50）。
- 若未来出现数百活跃模块，演进方向 = **逻辑队列 + 池化消费**（线程数不再随模块数增长）+ **同线程快路径**（目标与当前执行线程相同则直接调用，零队列零拷贝）；**投递语义与绑定代码不变**，故保留成本低。当前 v1 **不采用**这两者〔ADR-0029 放弃方案〕。

> 注：本条描述的是**线程分配与演进路径**；"`Disabled` 的实例不占线程"应读作"不再**分配**新线程"，现行结论见本册"生命周期状态机"节：**禁用（Disabled）不释放线程与资源，重新启用即继续**。
