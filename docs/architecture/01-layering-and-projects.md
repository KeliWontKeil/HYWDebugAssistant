# 01 分层与项目结构

> 适用范围：七层的划分与唯一依赖链、层→程序集/项目的落地、`App` 组合根白名单、Application 构成与职责三分、以及"违反即失败"的架构规则。

## 1. 七层清单与运行时角色 〔源: architecture/01 §1.1 + ADR-0026〕

分层依据 = **按运行时角色切**（不是按变化率）。共六个框架/应用层 + 一类非框架实现 + 一类横切支撑：

| 层 | 名称 | 运行时角色 | 是否框架 |
|---|---|---|---|
| L1 | **契约层**（Contracts / SDK） | 模块作者与 UI 共同依赖的稳定抽象面；承载"模块世界"的声明与上报契约 | 框架 |
| L2 | **模块宿主层**（Hosting） | 模块包的发现/加载/校验/注册/实例化、实例世界（成员实例表）、框架侧生命周期状态机 | 框架 |
| L3 | **数据面层**（DataPlane） | 绑定执行、数据单元投递、有界缓冲与丢弃、模块活动的承载与调度、流量诊断计数 | 框架 |
| L4 | **核心管理面**（Core） | Composition 解释与校验、ChangeSet 原子应用、增量重建、持久化（组合件）、Issue 中心、公开查询 API | 框架 |
| L5 | **UI 构成层**（Shell） | 主窗口、全局命令、模块视图宿主（模块区）、视觉层、口上标记渲染、管理视图 | 应用 |
| L6 | **模块实现**（业务模块） | 用户功能单元的实现体（非框架组成部分） | 非框架 |
| L0 | **横切支撑**（基础设施） | 日志 sink、序列化、配置读写、时间/诊断等中性技术能力 | 框架附属 |

- **逻辑层 vs 程序集**：L1–L5 是**逻辑层**；一个逻辑层可以对应一个以上程序集（本方案：L1 = `Sdk` + `Sdk.Testing`，L4 = `Core` + `Core.Api`，L5 = `Ui` + `FrameworkUi`）。"层即程序集"（Q2-1/ADR-0027）指**层的划分以程序集为边界**，不是"每层恰好一个项目"。
- **`App` 不属于任何逻辑层**（**已裁定**）：`App` 是**入口与唯一白名单组合根**，位于 L1–L6 **之上**；**L5 = `Ui` + `FrameworkUi`**（不含 `App`）。依据：① 上表 L1–L6 本身**不含 `App`**（`App` 只在 §5 项目清单里作为 WinExe 入口出现）；② 依赖方向上 `App` **只引用、不被引用**——它引用 `Ui`/`FrameworkUi`/`Core`/`Core.Api`，而**没有任何层引用 `App`**〔源: 用户裁定 + 本分册 §1 层表 + §2 依赖链 + §5/§6〕。
- **AR-11 白名单**（操作侧的唯一约束，与层归属无关）：`App`（组合根）可引用 `Core`/`Core.Api`/`Ui`/`FrameworkUi`；该例外**显式白名单化、不得扩散到其它项目**〔源: architecture/06 §6.3 AR-11 + 本分册 §6/§8〕。"L5 = Shell / App"的旧写法**不再采用**（历史见归档）。

## 2. 唯一依赖链（允许的箭头穷举） 〔源: architecture/01 §1.3 + ADR-0026〕

```text
依赖链（唯一允许方向；"─►" = 依赖 = "可引用"）

  L6 模块实现   ─► L1 契约层
  L2 模块宿主   ─► L1 契约层、L0 横切支撑
  L3 数据面     ─► L1 契约层、L0 横切支撑
  L4 核心管理面 ─► L1 契约层、L2 模块宿主、L3 数据面、L0 横切支撑
  Core.Api      ─► L1 契约层                      （L4 的公开面程序集）
  L5 UI 构成    ─► L1 契约层、Core.Api            （L5 不引 L0）
```

| 从 | 可依赖（穷举，多一个都不行） |
|---|---|
| L1 契约层 | 无（**不得引 L0**，保持零框架依赖） |
| L2 模块宿主 | L1、L0 |
| L3 数据面 | L1、L0 |
| L4 核心管理面 | L1、L2、L3、L0（另：**实现自身公开面** `Core.Api`，见 §4） |
| `Core.Api`（L4 公开面） | L1 |
| L5 UI 构成 | L1、`Core.Api`（**不得引 L0**） |
| L6 模块实现 | **仅 L1** |

**核心禁令（违反即失败）** 〔源: architecture/01 §1.3〕

- **L1 不得依赖 L2/L3/L4/L5 与 `Core.Api`，也不得依赖 L0** —— 契约层必须零机制、零框架依赖。
- **L5（UI）不得引用 `Core`（L4 内部实现程序集）、不得引用 L2/L3 实现类型、不得引用 L0，也不得引用模块实现程序集** —— UI 与框架交互的唯一通道是 `Core.Api`。
- **L3 数据面不得依赖 L2/L4/L5** —— 数据面不查宿主、不问管理面；这是"管理面与 UI 无法进入数据投递路径"的结构保障。
- **L2 不得依赖 L3/L4/L5。**
- **L6 不得依赖 L1 以外的任何框架层**（含 `Core.Api`、L0），**不得依赖任何 UI 框架**（ADR-0026 C1-3：模块视图只能由框架按声明渲染，模块不得提供 View 类型），**不得引用另一个模块**（P12/A2）。
- **L4 不得让数据投递经过自身**（只调用 L3 原语，不承接数据）；**L4 内部实现类型不得出现在 `Core.Api` 的公开签名中**（只允许 L1 契约类型与 Api 自有 DTO）。
- **任何框架程序集不得引用模块程序集**（模块由包加载，不在编译期被依赖）。

## 3. 各层职责与内容边界 〔源: architecture/01 §1.2〕

| 层 | 可以放 | 禁止放 |
|---|---|---|
| **L1 契约层** | 抽象类型/接口；纯数据描述类型；枚举与常量；契约形状原语目录；兼容判定所需的**元数据描述**（不含判定实现）；框架公开查询 API 的抽象 | 任何机制实现（加载/绑定/缓冲/调度/持久化）；任何依赖具体传输或业务的知识；任何 UI 框架类型；对 L2–L5 的引用 |
| **L2 模块宿主** | 加载器；包校验；注册表（Registry）；实例工厂；成员实例表；生命周期驱动；模块清单数据；manifest 与实现的绑定对应 | 数据投递与缓冲（属 L3）；Composition 解释与原子变更（属 L4）；UI 类型；具体业务知识 |
| **L3 数据面** | 投递路径；绑定结构；**每 (实例, 口) 的有界输入队列**与丢弃策略；调度与承载（**框架为每个 Active 实例分配专属线程**，模块不自建线程）；护栏（安全 + 提示）；数据流诊断计数 | UI 类型与任何 UI 等待/同步原语进入投递路径；模块加载与注册；持久化；任何业务知识 |
| **L4 核心管理面** | 变更事务；差异计算；建网规则执行；持久化；Issue 管理；查询与命令面；**对 L2/L3 的编排调用** | 数据投递路径的实现（只调用 L3 原语）；UI 类型；具体业务知识 |
| **L5 UI 构成** | Avalonia 视图/ViewModel；UI 命令；视图宿主与视觉层；**对公开查询 API 的调用**；对契约面类型的展示适配 | 任何机制实现；直接引用模块实现程序集；修改 Core 内部状态（一切变更经变更入口） |
| **L6 模块实现** | 业务功能（**含带逻辑的结构操作模块**，如缓冲/聚合/条件路由） | 引用 L1 以外任何框架层、任何 UI 框架、另一个模块 |
| **L0 横切支撑** | 日志 sink、序列化、配置读写、诊断等中性技术能力（ADR-0024：日志极简自研） | 引用 L1–L5（保持纯净，避免形成事实上的"上层漏斗"） |

**L0 可见性（ADR-0026 C1-4）**：**仅 L2/L3/L4 可引用 L0**；L1 契约层、L5 UI、L6 模块实现均不得引用 —— 框架的日志/诊断能力对 UI 与模块只能**经 L1 契约面**暴露。

## 4. 层 → 程序集：项目清单 〔源: architecture/02 §2.1 + ADR-0027〕

| 层 | 项目名 | 类型 | 引用 |
|---|---|---|---|
| L1 契约 | `HYWDebugAssistant.Sdk` | 类库 | 无（**不得引 L0**） |
| L1 契约·测试套件 | `HYWDebugAssistant.Sdk.Testing` | 类库 | `Sdk` |
| L0 横切支撑 | `HYWDebugAssistant.Infrastructure` | 类库 | 无 |
| L2 模块宿主 | `HYWDebugAssistant.Hosting` | 类库 | `Sdk`、`Infrastructure` |
| L3 数据面 | `HYWDebugAssistant.DataPlane` | 类库 | `Sdk`、`Infrastructure` |
| L4 核心管理 | `HYWDebugAssistant.Core` | 类库 | `Sdk`、`Core.Api`、`Hosting`、`DataPlane`、`Infrastructure` |
| L4 公开面 | `HYWDebugAssistant.Core.Api` | 类库 | `Sdk` |
| L5 产品 UI 构成 | `HYWDebugAssistant.Ui` | 类库（含 XAML） | `Sdk`、`Core.Api` |
| L5 框架自身 UI | `HYWDebugAssistant.FrameworkUi` | 类库（含 XAML） | `Sdk`、`Core.Api`、`Ui` |
| 入口 | `HYWDebugAssistant.App` | **WinExe** | `Ui`、`FrameworkUi`、`Core`、`Core.Api` |
| L6 模块 | `HYWDebugAssistant.Modules.*` | 类库（模块包） | **仅 `Sdk`** |

- `Sdk.Testing` 是 **T6 契约测试套件**，供模块作者在自己的测试项目里自检声明与行为：**只引 `Sdk`、不引任何测试框架**（断言由作者用自己的测试框架做，套件只暴露问题清单）。
- **`Core` 需要引用 `Core.Api`**（M1-6 结构修订）：`Core.Api` 是 L4 的公开面程序集，其查询/命令接口必须由 L4 实现；`Core.Api` 自身仍**只引 `Sdk`**。这是"L4 实现 → L4 自身公开面"，**不构成跨层反向依赖**，也不属架构例外。
- `FrameworkUi` 可引 `Ui`（复用视觉层组件），**反向不可**（ADR-0027 C2-3）。

### 模块项目的形态 〔源: architecture/02 §2.3 + ADR-0027 Q2-3〕

- 开发期：模块 = 普通类库项目，**仅引用 `Sdk`**；目标框架与其他项目一致（`net10.0`，由 `Directory.Build.props` 统一）。
- 交付期：模块项目产出**模块包**（manifest + 实现绑定 + 可选资源）；包的物理形式与 manifest 载体属模块 SDK 分册与 Gate B。
- **参考模块与业务模块同构**：参考桩模块放在 `src/`，与第三方模块享受**完全相同的引用面与加载路径**（不享受测试程序集特权）—— 这是 AC-1~AC-6 实证保真度的前提。
- 参考桩模块现为 **5 个独立项目**（`DataGenerator` / `Recorder` / `Asserter` / `ManualSender` 手动数据发送器 / `Monitor` 信息显示模块），另有**多源融合器**（包名 `fuser`，双入一出，ADR-0050 R5 新增）。C2-4 冻结时的"三个"是当时的点数；**"一模块一包"为默认形态**的结论不变。
- 模块项目**不得**引用其它模块项目，**不得**引用 `Core.Api`/`Hosting`/`DataPlane`/`Core`/`Ui`/`FrameworkUi`/`Infrastructure`。

HYWDebugAssistant.slnx
├─ src/
│  ├─ Sdk/                     HYWDebugAssistant.Sdk            （L1 契约 · 模块作者唯一引用面）
│  ├─ Sdk.Testing/             HYWDebugAssistant.Sdk.Testing    （L1 契约·T6 自测套件）
│  ├─ Infrastructure/          HYWDebugAssistant.Infrastructure （L0 横切支撑）
│  ├─ Hosting/                 HYWDebugAssistant.Hosting        （L2 模块宿主）

│     └─ <业务模块>/        HYWDebugAssistant.Modules.<名称>
├─ tests/
│  ├─ HYWDebugAssistant.Tests               （T2–T5 机制与单元测试）
│  ├─ HYWDebugAssistant.Tests.Reference     （T1 判据测试：参考组合 + AC-1~6）

├─ docs/                        （文档组：不在产品项目内）

- **约定**：项目目录名 = 项目名（命名空间应与目录结构一致，AR-14）；模块一律置于 `src/Modules/` 之下，分 `Reference/`（参考桩模块）与业务模块两类。
- **工程根约定**：CPM 保留（`Directory.Packages.props`），**Avalonia 相关包引用只留在 `Ui`/`FrameworkUi`/`App`**（框架与数据面项目不得引用 UI 包）；`build.ps1`、`tools/audit-licenses.ps1` 保留，许可门禁覆盖全部依赖（含传递依赖）。
- **`VisualSnapshots` 必须独立进程**：`AvaloniaHeadlessPlatform` 配置是**进程级**的，同进程混用两种会话会让主测试项目的无头会话集体失败。

### 模块包的产出目录（构建期，不入库） 〔源: architecture/02 §2.2 M1-17 + ADR-0036 D2〕

| 目录 | 产出者 | 用途 |
|---|---|---|
| `artifacts\modules\<包名>\` | `src/Modules/Directory.Build.targets`（模块项目**构建即归拢**：`module.json` + 实现程序集 + 依赖） | 统一包库：应用扫描的"工程默认根"、发布打包源 |
| `<应用输出>\modules\<包名>\` | `App` 项目的构建后目标（把 `artifacts\modules\*` 镜像过去） | **内置模块包目录**：应用启动默认扫描，开箱可用 |

- 规则：**先清空该包目录再复制**（避免新旧 DLL 混放）；包名由项目属性推导（默认取项目名后缀），**新增模块项目无需改任何脚本/targets**。
- `artifacts/` 已在 `.gitignore`；`tools/stage-reference-modules.ps1` 降级为**发布打包用**（遍历 `artifacts\modules`，不再硬编码模块清单）；`build.ps1` 的"归拢"步骤改为**校验**（每个包目录是否齐全）。

## 6. `App`：唯一白名单组合根 〔源: architecture/02 §2.1/§2.5 + ADR-0027 + architecture/06 §6.3 AR-11〕

- **定位**：`App` 是**薄组合根** —— 只有 `Program`/`Main`、DI 组装、Core 与 UI 的装配序。**不含机制实现与 UI 布局**；`Ui` 承载产品 UI 构成（Shell），`FrameworkUi` 承载框架自身 UI（Module Registry 清单 / Issue 面板 / 诊断面板等，框架自身 UI 不作为普通 Module）。
- **唯一登记例外**：`App` 同时引用 `Core`（L4 内部）与 `Ui`/`FrameworkUi`（L5）。理由 = 装配序要求"先建 Core、再建 UI 并让 UI 引用 Core"，该动作必须发生在**两层的共同上层**。
- **硬约束**：**禁止 `App` 承载任何业务/机制逻辑**；此例外在架构规则集中**显式白名单化**（AR-11），不得扩散到其它项目。
- **DI 纪律**：容器注册**集中在 `App`**，各层不自行 `ServiceLocator`。

### 例外登记机制 〔源: architecture/06 §6.3 + ADR-0025 §8〕

确需违反某条依赖规则时：源码内写 `// ARCH-EXCEPTION: <原因> · <复查条件>` + **登记到 `docs/decisions.md`**；架构测试对**已登记的例外按显式白名单放行**；**禁止静默绕过**。M1 期间**无生效例外**（`Core → Core.Api` 与 `Sdk.Testing` 均为结构修订，非例外）。

## 7. Application 的构成与职责三分 〔源: 主文档 §3.2/§3.2.1/§3.3/§3.3.1 + ADR-0001/0003 + architecture/17 §1〕

- **Application = UI 构成（术语 Shell）+ Core 构成（语义内核）**，二者是 Application 的两个**逻辑构成面**，不是独立领域对象（同生命周期、双向引用）；早期基线"Application Shell / Core Runtime / Workspace 三个平级顶层对象"的表述**作废**，"Shell"仅作为 UI 构成面的实现术语保留。
- **装配链**：Application 初始化 → 创建 Core 构成（含 Module Registry）→ 创建 UI 构成（引用 Core）。
- **Core 职责三分（ADR-0003）**：Core 只持 **①框架机制**（对模块与契约中立：宿主、标准维护、模块生命周期、Workspace 文档管理、组合→运行时通用解释、Interface 兼容判定、点对点绑定执行、资源与错误管理）；**②业务功能**与 **③编排/拓扑决策**（Splitter/Router/Merger 等的分合、路由、聚合语义）**全部由内容模块承担**；宿主固有 UI 除外。技术实现阶段可对职责细分/分块，**不改变该顶层边界**。
- **表现层 / 语义层分离（§3.2.1）**：在"用户看到并操作的（表现）"与"规则/数据/状态/能力（语义）"之间放置稳定的契约边界，使两边可独立修改/测试/替换；**判据与"是否有数据库"无关**。本项目落点：**UI 构成与模块视图 = 表现层；Core 构成与模块业务能力 = 语义层**。术语**不用"前端/后端"**（后者暗示网络边界）。不分离的是模块内部实现与性能关键路径内聚。
- **Core 不应**：承担具体业务逻辑；成为所有业务数据的中央交换机；理解 FOC/UART/TCP/Plotter 等具体业务；为每种业务写特殊分支；成为 God Object。

### 边界四分：谁管什么 〔源: architecture/17 §1/§2〕

| 角色 | 管 | 不管 | 归属 |
|---|---|---|---|
| 传输 / 数据面 | 能不能传：尺寸完备性、投递、顺序、背压、丢弃计数、缓冲 | 数据"是什么"（单位/量程/精度/语义/解析方式） | 框架；只做**机械校验**（长度/尺寸合法、兼容关系成立），**不解析内容** |
| 应用 / 模块语义 | 数据是什么、怎么解析、单位、量程、精度、建议采样率、阈值、显示格式 | 传输细节（队列/背压/时序实现） | **模块**；语义与解码由模块自己负责，框架不解释 |
| 呈现 / 框架 UI | 通用信息：拓扑、连接、数据角色、传输级指标（投递/丢弃/速率/延迟/队列）、错误 | 应用语义（不解释单位含义、不做业务解析） | 框架（由传输面 + 拓扑派生）；只读**框架自己拥有的**数据（计数、绑定、几何） |
| 模块自身 UI（按声明渲染） | 该模块要让用户看的业务内容（数值/曲线/日志 + 单位） | —— | 模块声明视图、框架"照声明画"，值由**模块的解码器**产出 |

**两条纪律**（写进主文档）：① **框架永不内建业务解析器**，需要解析时一律"模块注册解码器、框架回调"；② **声明只在注册/实例化时读一次**（注册 = 登记、销毁 = 注销），运行期不重读（热重载除外，按既有"重扫/需重启"规则）。

## 8. 关键不变式的结构保障（逆例自检） 〔源: architecture/01 §1.4〕

| 基线约束 | 依赖图如何保障 |
|---|---|
| **P2 / E1 / E2**（Core 不是交换机/路由器，不中转业务数据） | 投递路径位于 L3，且 L3 不依赖 L4；L4 无数据面转发实现的位置。若把投递写成"经 Core 转发"，必然产生 L3→L4 依赖，被禁令直接拦截 |
| **§13.1 数据面绝不被 UI 阻塞** | L3 不依赖 L5；L5 只能经 `Core.Api` 与框架交互，UI 的任何等待都不能进入 L3 调用栈 |
| **ADR-0013 框架统一承载活动** | 模块活动的承载与调度**独占于 L3**；L6 只能引用 L1，物理上无法创建框架外活动载体（模块不得自建线程） |
| **P12 / A2**（模块不依赖具体模块） | L6 只依赖 L1；模块间连接只能是 L1 契约的组合 |
| **P1 / A1**（Core 是 Host/Runtime，不是 Module） | L2/L3/L4 均不得引用 UI 类型；框架自身 UI 位于 L5，与语义内核分离 |
| **P16 / §5.4.2**（具体数据类型不过早冻结、框架不加元信息） | 数据单元的类型语义只存在于 L1 的契约描述中；L3 只搬运不解释（是否需要元信息由契约自带，框架侧无字段） |
| **AC-1 / AC-5**（新增模块 Core 零改动） | 新增 L6 只引 L1，不触碰 L2/L3/L4 ⇒ "Core 零改动"在依赖图上可判定 |
| **§3.2.1 表现/语义分离** | L5（表现）→ L4 公开面（语义）为唯一跨面通道；L6 不感知 L5 |

**反模式对照**：E3（Core = God Object）由 L2/L3/L4 职责三分 + L1 抽象面限制；E4（Module = Window）由 L6 不依赖 L5 且不得依赖任何 UI 框架保障；E5（Plugin = DLL）不影响层图（模块包物理形式属 Gate）；E6（Workspace = 数据流图）由 L4 的 Composition 表示限制；E7（Interface = 每业务一类型）由 L1 的受控原语目录限制；E8（Composition = 任意连接）由 L4 的校验与建网规则限制。
