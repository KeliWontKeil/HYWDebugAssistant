## 1. 架构能力判据总纲（验收三分法）〔源: 主文档 §14.1–§14.4 + ADR-0021 §四 + ADR-0032〕

| 部分 | 内容 | 用途 |
|---|---|---|
| ① **架构能力判据** | AC-1~AC-6（下表），**与业务无关** | 顶层（架构）验收 |
| ② **架构验证参考组合** | 一组专用模块/桩模块构成的"参考组合"（**现行 = 四个正式模块 + 判据项目内测试桩**，见 §2） | AC-1~6 的**实证载体**；**不进入核心领域模型，也不作为架构验收标准** |
| ③ **产品验收场景** | 具体业务闭环（真实串口/FOC 链路等） | **只做业务正确性验收，不做架构验收**（防架构对具体业务过拟合）；在顶层冻结后的 Concrete Module 阶段由用户定义 |

| 判据 | 内容 | 验证方法 |
|---|---|---|
| **AC-1** | 新增一个 Core 从未见过的业务模块，仅凭声明 Interface 即可接入运行，**Core 零改动** | T1：桩模块接入 + **框架程序集引用集不变（依赖图断言）+ 全量回归** |
| **AC-2** | 模块状态变化（含离线/故障态）不影响无关模块；上游无数据对下游是合法"无输入"；软件级异常在边界受控捕获与报告 | T1 + T5：故障注入（异常/断流/慢消费） |
| **AC-3** | 组合/配置变更在常驻运行中在线生效，无需重启（五类变更） | T1 + T3：五类 ChangeSet 在线应用与增量重建 |
| **AC-4** | 保存 → 加载 → 运行 → 再保存的无损往返 | T1 + T4：组合件 round-trip（含未知字段保真） |
| **AC-5** | 同一批新增模块的接入不要求修改其他既有模块（无隐藏耦合） | T1：多模块批量接入回归 |
| **AC-6** | 平台对未知未来数据类型保持开放（不改 Core/既有模块即可承载） | T1 + T2：新契约/新形状的模块接入（Core 零改动） |

**AC-1 的判定口径（用户裁决 Q6-1）**：**依赖图断言 + 回归**。
- 依赖图断言：`Core`/`Hosting`/`DataPlane`/`Core.Api`/`Sdk` 的**引用集**与基线一致（新增模块不得引入新引用，更不得被反向引用）；
- 回归：既有测试全绿 + 新模块功能测试通过；
- **不采用** IL/二进制级基线比对（成本高、误报多），也**不依赖人工改动面检查**。

**纪律归属**：AC-1~6 的纸面路径在设计阶段完成，**实证在 M1 的 T1 中完成**；产品阶段只做业务正确性验收。〔源: architecture/07 §7.4 + ADR-0033〕

## 2. 判据落地（AC → 测试方式与通过标准）〔源: architecture/06 §6.4 + ADR-0027 Q2-3〕

**参考组合（判据载体 · 现行）** = **四个正式模块**（`hyw/text-sender` · `hyw/hex-sender` · `hyw/data-monitor` · `hyw/hex-string-converter`，包目录 `artifacts/modules/<包名>`）+ **判据项目内测试桩**（`tests/HYWDebugAssistant.Tests.Reference/Stubs/`：`FusionStubModule` = 两入一出融合 · `RateSourceStubModule` = 定时定值数据源 · `JudgementSinkStubModule` = 记录统计 + 三类判据 + 按类别限流上报）；二者与第三方模块**同构同路径**，保证实证保真度。**测试桩不进产品模块目录、不打包、不是产品模块**（见 §7）。

> 原参考组合（判据桩三件）`Modules.Reference.DataGenerator` + `.Recorder` + `.Asserter`，以及参考模块的**其余三个**（`ManualSender` / `Monitor` / `Fuser`），**已于 2026-09 按用户裁定删除**（现行判据载体如上）。

| 判据 | 测试方式（T1） | 通过标准 |
|---|---|---|
| **AC-1** 新增模块 Core 零改动 | 新增一个模块（现行范例 = 判据项目内测试桩）→ 跑架构规则集 + 功能回归 | AR-12 通过 + **框架程序集的引用集与构建产物未变**（依赖图断言）+ 模块可加载、可建网、可运行 |
| **AC-2** 隔离与异常不逸出 | 故障注入：模块抛异常 / 慢消费 / 上游断流 | 异常不逸出边界且转 Issue；无关模块继续运行；下游"无输入"为合法状态 |
| **AC-3** 在线变更 | 五类变更（建网/断网/加模块/删模块/配置改）在常驻运行中应用 | 无需重启；受影响局部重建；**模块实例与业务状态保留** |
| **AC-4** 保存/加载无损往返 | 组合件 round-trip（保存 → 加载 → 运行 → 再保存） | 内容逐字段等价，**含未知字段保真**（片段保留） |
| **AC-5** 无隐藏耦合 | 多模块批量接入回归 | 新增模块不要求修改既有模块；既有模块测试全绿 |
| **AC-6** 对未知类型开放 | 接入**新契约形状**（新的定长原语组合）模块 | 框架零改动即可承载；兼容判定正确 |

## 4. 架构规则集 AR-0~AR-16 〔源: architecture/06 §6.3 + architecture/02 §2.1 修订 + ADR-0032 + 代码 tests/HYWDebugAssistant.ArchitectureTests〕

**两类规则、两套判定手段**（保留两类是用户授权设计方推荐项 **C6-1**：全部改成程序集检查会直接丢掉两条有价值规则）：

| 类 | 判定手段 | 原因 |
|---|---|---|
| **依赖类**（AR-1~AR-12） | **程序集引用检查**：用 `MetadataLoadContext` / `System.Reflection.Metadata` 读取已编译程序集的 `AssemblyRef` 表 | 能覆盖**间接依赖**（源码扫描只能看直接 `using`/`ProjectReference`），是依赖禁令的可靠判据 |
| **源码类**（AR-13~AR-16） | **源码扫描** | 命名空间一致性、业务词汇、第三方命名空间这类规则属源码层，程序集元数据无法表达 |

**前提**：依赖类规则要求产品程序集**已构建**（架构测试在构建之后运行；`build.ps1` 的顺序已满足）。

**"跳过 vs 失败"语义（硬规则）**：**目标程序集不存在时报失败而非跳过**——避免规则在重构中静默失效；工程基线阶段的"无对象则跳过"逻辑**必须移除**（已移除）。

| 编号 | 规则（一句话） |
|---|---|
| AR-1 | 模块程序集（`Modules.*`）**只允许**引用 `Sdk` |
| AR-2 | 模块程序集之间**不得互相引用**（P12） |
| AR-3 | `DataPlane` 不得引用 `Hosting`/`Core`/`Core.Api`/`Ui`/`FrameworkUi`（数据面不反向依赖） |
| AR-4 | `Hosting` 不得引用 `DataPlane`/`Core`/`Core.Api`/`Ui`/`FrameworkUi` |
| AR-5 | `Core` 不得引用 `Ui`/`FrameworkUi`；**允许引用 `Core.Api`**（实现 L4 公开面） |
| AR-6 | `Core.Api` **只允许**引用 `Sdk` |
| AR-7 | `Ui` **只允许**引用 `Sdk` + `Core.Api` |
| AR-8 | `FrameworkUi` **只允许**引用 `Sdk` + `Core.Api` + `Ui` |
| AR-9 | `Sdk` **不得引用任何框架程序集**，也不得引用任何 UI 框架（零依赖） |
| AR-10 | `Infrastructure` 不得引用任何框架程序集；**只允许**被 `Hosting`/`DataPlane`/`Core` 引用（**测试项目豁免**：AR 规则只约束 `src/` 下的产品程序集，`tests/` 可跨层引用） |
| AR-11 | **唯一白名单**：`App`（组合根）可引用 `Core`/`Core.Api`/`Ui`/`FrameworkUi` |
| AR-12 | 任何框架程序集**不得引用模块程序集**（模块由包加载，不在编译期依赖） |
| AR-13 | `Core`/`Hosting`/`DataPlane` 内不得出现具体业务词汇（UART/FOC/Plotter/串口/Modbus/CAN 等） |
| AR-14 | 命名空间应与目录结构一致 |
| AR-15 | 不得引用 ADR-0024 排除清单中的第三方组件（MediatR/AutoMapper/FluentAssertions 8+/Moq/商业控件等） |
| AR-16 | `Core.Api` 的公开成员签名中不得出现 `Core`/`Hosting`/`DataPlane` 的内部类型（只允许 `Sdk` 契约类型与 Api 自有 DTO） |

- 规则集**取代**工程基线阶段的 A1–A6（A1/A3/A5 语义并入 AR-1~AR-13；A2 并入 AR-2；A4 并入 AR-14；A6 并入 AR-15）。
- **例外机制**：确需违反时用 `// ARCH-EXCEPTION: <原因> · <复查条件>` + **登记到 `docs/decisions.md` §3**（`ARCH-EXCEPTION` 的唯一登记处）；架构测试对**已登记的例外按显式白名单放行**；禁止静默绕过；例外清单每批次收尾复查。
- **架构测试项目不引用产品项目**：它以"被分析对象"身份读取产品程序集（元数据 + 源码），若引用则被编译期依赖绑住，且无法表达"禁止引用"这类规则。

## 5. 验证层级 T0–T3 与完整门禁 〔源: 代码 tools/dev.ps1 + build.ps1 + DEVELOPMENT.md §1–§5〕

### 5.1 四个层级（`.\tools\dev.ps1`）

| 层级 | 何时用 | 命令 | 典型耗时 |
|---|---|---|---|
| **T0 单项目编译** | **每次小改**（改完即编，最早发现编译/分析器错误） | `.\tools\dev.ps1 -Mode Build -Project Core`（项目名片段或 csproj 路径；不传则编译整个解决方案） | 1–3 s |
| **T1 单类测试** | 改了某块逻辑/某个测试类 | `.\tools\dev.ps1 -Mode Test -Filter 端口标签` | 3–6 s |
| **T2 单测试项目** | **一个增量收尾**（如"修好闪烁"） | `.\tools\dev.ps1 -Mode Test`（默认跑主测试项目 `HYWDebugAssistant.Tests`） | 4–8 s |
| **T3 完整门禁** | **仅 §5.3 的三种情况** | `.\tools\dev.ps1 -Mode Gate`（= `build.ps1`，含许可审计） | 25–40 s |
| UI：只编 + 跑起来看 | 纯 XAML/样式/文案/间距改动 | `-Mode Build -Project FrameworkUi`（或 `Ui`）→ `-Mode Run` | 3–8 s |

其他开关与模式：`-TestProject <名>`（换测试项目）· `-AllTests`（跑全部测试项目，**不含**许可审计）· `-SkipAppRebuild`（应用正在跑时的应急：只重编测试项目，前提是改动过的项目已 T0 编译过）· `-StopApp`（直接停掉正在运行的应用，**会丢失运行现场**）· `-KeepDesignerHost` · `-Mode Tree|Stop|Run`。

`-Mode Test` 的语义细节：过滤词**没匹配到任何测试不算失败**（脚本明确区分并提示换过滤词）；测试失败抛"测试失败"。

### 5.2 T3 完整门禁实际做什么（`build.ps1`）

| 步骤 | 内容 |
|---|---|

### 5.4 手工验证（T7）与门禁的关系

- **UI 应用层面由用户手工验证**：实现阶段须交付**可执行的手工验收清单**（步骤 + 预期结果 + 判据映射），覆盖模块加载、拼接、建网/连线、配置修改、保存/加载、持续运行观察。

## 6. 测试与验证纪律 〔源: architecture/06 §6.6 + ADR-0025 + ADR-0021 §四 + DEVELOPMENT.md §1〕

**测试纪律（现行约束）**

- 验证以**模块级 + 组合级**为准；**不做**框架级"MCU 式"单元测试——框架机制以**组合级**（参考组合）验证为准（纪律 C1）。
- **不设覆盖率百分比**；以"**机制改动必须有组合级验证**"为判据。
- **警告即错误**（`TreatWarningsAsErrors=true`）在测试项目同样生效；测试专用豁免（如 `CA1707`）以 `NoWarn` + **理由登记**。
- **不做一次性原型**（纪律 C3）：测试代码属常备基础设施（参考组合/桩模块），不是原型。
- **许可门禁**（`tools/audit-licenses.ps1`）覆盖测试依赖（含 xUnit/Shouldly/NSubstitute/BenchmarkDotNet）。
- 架构级测试优先（不依赖具体业务模块）；参考组合/桩模块为**常备基础设施**；判据可回归。

**"简单快捷"原则（用户要求的具体落实）**

| 原则 | 落实方式 |
|---|---|
| 快 | 常规门禁只跑 `Tests` + `Tests.Reference` + `ArchitectureTests`；**基准测试不进常规门禁**（`build.ps1 -RunBenchmarks` 按需运行，设计方推荐 C6-2）。**当前实际**：T3 的测试步骤对**解决方案内全部测试项目**执行（`dotnet test` 整个 `.slnx`）——该行的现行含义 = "**基准不进常规门禁**"；`VisualSnapshots` 是此后新增的项目，也在解决方案内、随 T3 一起跑 |
| 简 | 优先**表驱动**测试（契约矩阵、建网两机制），不为每个组合写一个测试方法 |
| 只验主要问题 | 自动化聚焦六项判据（AC-1~6）与四类机制（ChangeSet / 增量重建 / 持久化 / 丢弃与停止）；**不追求边界穷举** |
| 做不到就跳过 | UI 自动化（T8）v1 不做；视觉形态（Gate C）由原型与手工验证 |
| **用户侧验收** | UI 应用层面由用户手工验证（§5.4） |

**分层验证纪律（开发内环）**

1. **批量改完再编译**（不要"改一行编一次"）；
2. **T3 不是"收尾仪式"**：只有 §5.3 的情况才跑；
3. **纯 UI 改动不做"测试一轮"**：XAML/样式/文案/间距 → **T0 编译 + `-Mode Run` 眼睛看**即可，**不跑** T2/T3、不跑整套测试；只有**连带改了逻辑**（视图模型、命令、数据结构）时，才按 T1 跑**受影响的那个测试类**；
4. **报告结论时必须区分"我跑了哪一层"**，不得把 T0/T1 的通过说成"全量通过"。

**"简单快捷"相关的其余推荐项**：资源释放验证以**计数断言为主**（活动线程/队列/池计数归零）+ **少量关键点弱引用断言**（弱引用受 GC 时机影响易 flaky，只在关键路径用，C6-3）；判据载体（现行 = 四个正式模块 + 判据桩）**只声明少量视图**（数值为主，C6-4）—— 已核实：三只桩分别声明 3 / 2 / 4 个数值元素，均无曲线与容器（`tests/HYWDebugAssistant.Tests.Reference/Stubs/`）。

|---|---|
| 时点 | **M1（框架最小闭环）完成之后、M2（UI 完整化）之前**做一次 UX 原型 |
| 理由 | ① 数据面机制是最大技术与性能风险，应先闭环验证；② Gate C 的形态细节不改变数据面设计；③ M1 之后已有可运行系统，原型可直接站在真实数据上做，避免"原型与实现两张皮" |
| 原型范围 | 模块视图视觉形态与尺寸族具体参数 · 吸附容差与拖动手感 · 拼接/整体拖动/快捷键交互 · 网络标签块形态 · 信息类层（连线/标记/诊断）呈现 · 窗口与整体布局 · 配置界面形态（按 Schema 生成的具体样式）· 分组框/多页面等可选 UX 元素 |
| **不属** Gate C | 层分类与职责、模块视图与信息层的归属、拼接语义、快捷键可配置性（均已冻结） |

**Gate D（后续阶段）**

| 项 | 处置 | 理由 |
|---|---|---|
| **会话快照**（崩溃/退出恢复现场） | **预留**（低成本接口位：与组合件并列的独立机制） | 用户价值明确（调试现场易丢），预留成本极低 |
| **模块版本迁移路径**（旧版本实例 → 新 Definition） | **预留**（ID 三元组已含版本；加载期保留"迁移钩子"位置） | 多版本共存已冻结，迁移是自然延伸 |
| 组合件递归嵌套（组合含组合） | **明确不预留**（v1 不做；未来若做属增量特性） | 会显著复杂化组合件格式与加载流程，且 v1 无需求 |
| 录波 / 回放 | **明确不预留**（可由普通内容模块实现） | 属模块能力，框架无需预留 |
| 沙箱（进程级隔离） | **明确不预留**（保留 Gate） | 与轻量透明安全模型一致；未来若需要属架构级变更 |
| 跨平台是否为硬性要求 | **明确不预留**（Windows 优先；Avalonia 天然跨平台但不为它牺牲性能） | ADR-0023 §8 |
| L5 性能监视 | **明确不预留**（未来按需加信息层/面板） | 已有 L1–L4 覆盖排障主力 |

**预留原则**：只预留**成本极低且会改变接口形态**的项；其余明确不做，避免"为想象的未来付费"。

**Gate E（顶层之后）**

| 项 | 处置 |
|---|---|
| 具体模块清单与设计 | **开发启动后的第一件事**（M1 后进入 M2 前）由用户给出首批真实模块需求 |
| v1 产品验收场景（业务闭环） | 由用户定义（真实串口/FOC 等）；**只做业务正确性验收，不做架构验收**（§1 三分法③） |
| 架构验收 | 纸面路径已完成（AC-1~6）；实证在 M1 的 T1 中完成 |
| 建议的首批模块方向（**供参考，非裁决**） | 串口收发模块 · 协议解析模块 · 波形/曲线显示模块 · 数据记录模块 · 参数配置类模块（**具体清单由用户定**） |

### 10.2 推进方式与 M1 目标

- **推进方式（用户审核）：垂直切片** —— 先打通**一条最小完整链路**（"模块包 → 实例 → 网络 → 数据投递 → 界面显示"），而不是按层横向做完。理由：最早暴露端到端风险；符合纪律 C2「只有最小可验证形态才算可验证」；每完成一片都有可运行系统，便于用户随时手工验证。
- **M1 规模**：**不拆分、中间不停，全量完成后一次性验收**（用户裁决）。〔源: architecture/08 §5 C8-1〕
- **`08` 对 `07` §7.5 的修正（现行，执行以 `08` 为准）**：① **数据面基础设施先于建网**（并以"队列 + 投递原语 + 独立夹具"验收，解除原依赖倒置）；② **`App` 装配独立成步**（否则没有运行入口）；③ **`Tests`(T2–T5) 与 T6 明确纳入**；④ **应用级设置独立成步**（是"可配置"参数的归属）；⑤ **架构规则集先于业务代码**（避免"先写代码后补护栏"返工）。

| **M1-17 模块自动发现 · 窗口层级统一 · 设置分类与快捷键** | ① **构建即归拢**（`src/Modules/Directory.Build.targets` + `App` 镜像；脚本降级为发布打包、`build.ps1` 步骤 2.5 改校验）② **声明根发现**：`moduleSourceDirectories` 有序列表 + 多根扫描（先到者胜、去重、逐包结果）+ `GetModuleSources()`/`RescanModuleSources()` + 「模块清单」诊断区 + **"本次启动后重建过 → 需重启"提示** ③ **窗口层级统一**：模块窗口 `Owner=外壳`；任一本应用窗口被激活 → 其余窗口一并抬升（Win32 `SetWindowPos`，仅表现层）；**应用级「全体置顶」开关**；模块窗口不进任务栏（**固定行为、不加设置项**）④ **设置分类化**（七类：常规/模块与来源/窗口与交互/外观与显示/快捷键/日志与诊断/关于）⑤ **快捷键可编辑**（应用内作用域 + 动作枚举 + 捕获/冲突提示/重置，存 `settings.json`）⑥ 更新手工验收清单 | 新增模块项目 → `dotnet build` → 「立即重扫」出现可用模块（**无需重启**）；改代码重建后给出**需重启**提示；点外壳不覆盖模块；切换其他应用再切回时**整个应用一起回来**；置顶开关打开后**所有**窗口一起最前（无混合状态）；模块窗口聚焦时快捷键生效；设置里能看/改/重置每个快捷键；`build.ps1` 全绿。依据 ADR-0036 |
