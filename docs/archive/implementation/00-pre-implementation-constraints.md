## 1. 用户确立的开发约束（硬纪律）

| # | 约束 | 说明 |
|---|---|---|
| C1 | **验证方式 = 模块验证 + 组合验证** | 不用"MCU 式单元测试经验"套用框架本身；框架的正确性通过**模块级验证**与**组合级验证**（= 顶层 §14.1 参考组合 / T1）来证明，最终面向半成品/成品验收 |
| C2 | **最小可验证形态**才可开始验证 | 需要"**框架完全就绪 + 最小可验证模块完成搭建**"才算具备验证条件；不做"半成品早期验证" |
| C3 | **禁止把简易原型并入工程** | 避免技术债；如确需原型，必须**独立搭建**（独立目录/独立方案，不参与主构建、不被工程引用） |
| C4 | **代码风格约束 + 开发约束** | 环境就绪后专项讨论并冻结（议题见 §3） |

> C1+C2 与顶层已冻结的测试架构一致：T1（判据测试，参考组合＝桩模块的组合验证）+ T6（模块契约测试套件）。**参考组合即"组合验证"的落地形式**。

## 2. 环境就绪后的议程（按序执行）

1. **环境与工具链核对**：SDK 版本 / TFM 统一 / Avalonia 模板 / 中央包管理 + lock / **许可审计门禁**跑通 / 免费 IDE 就位。
2. **讨论并冻结「代码风格与开发约束」**（§3 议题清单）→ 产出 ADR。
3. **技术架构设计**（产出 ADR + 架构文档）：
   - 分层与依赖方向（Core 语义内核 / 模块 SDK / UI / App；**依赖单向**、无循环）；
   - 项目结构与命名空间边界（可被 Architecture Test 检查）；
   - **模块 SDK 形态**（原语层契约 + 行为层接口 + Manifest 的 C# 表达，落 ADR-0006/0020）；
   - 关键机制技术方案：Registry/生命周期（ADR-0014 状态机）、**ChangeSet 与增量重建**（ADR-0011/0012）、**网络与绑定**（ADR-0018/0022）、有界缓冲与丢帧（ADR-0012 R2）、持久化与重锚定（ADR-0016/0017）、Issue 模型（ADR-0015）；
   - **UI 架构**：模块视图宿主（自由排列）+ 叠加层方案（多视觉层，ADR-0023 §7）+ 口上标记渲染；
   - 测试架构落地：T1–T8 的项目映射（含 `Avalonia.Headless` 的 UI 测试）。
4. **最小可验证形态搭建**：框架骨架 + 最小模块（如"数据发生器"桩模块 + 一个显示模块）→ 达到 C2 条件。
5. **AC-1~6 实证**（参考组合，T1）→ 结果回写文档；再进入具体业务模块开发。

## 3. 「代码风格与开发约束」议题清单（环境就绪后讨论）

1. **编码规范**：`.editorconfig` 规则集、命名约定、`TreatWarningsAsErrors` 范围、分析器级别（**仅内置分析器**——开关 S1；不引入 StyleCop/Roslynator 等第三方分析器）。
2. **架构约束的自动化**：Architecture Test（依赖方向、命名空间边界、禁止 UI 引用数据面内部实现、禁止模块相互引用——对应 P12）。
3. **性能纪律（数据面）**：热路径禁用 LINQ/装箱/隐式分配；`ArrayPool`/`Span` 使用约定；基准测试**不进常规门禁**（`build.ps1 -RunBenchmarks` 按需运行，ADR-0032 C6-2）。
4. **提交与审查**：commit 约定、分支策略、变更粒度、PR 自查清单（含"是否违反 v1.0 冻结结论"检查）。
5. **文档要求**：XML 文档注释范围、模块 Manifest 必填项、ADR 触发条件（何时必须写 ADR）。
6. **测试要求**：哪些层必须测（模块契约、组合、持久化 round-trip、故障注入）；覆盖率目标（若有）；UI 测试边界。
7. **依赖引入纪律**：新依赖必须 ① 过许可审计（MIT/Apache/BSD）② 说明不可替代性 ③ 记录到 ADR 或决策日志。
8. **例外与豁免**：违反约束时的申报与记录流程（不得静默绕过）。
