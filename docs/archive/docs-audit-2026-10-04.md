评估方式：**未读任何 C# / AXML 代码**，只做文档层面的结构测量、重复统计与一致性检查。所有数字为本次实测。

## 0. 结论（一句话）

**问题不是"文档写得不好"，而是"文档里装着两种东西"——「生效事实」和「开发过程」——却被塞进了同一批文件、同一张表、同一节标题下。**
因此任何"精简/分类"若不先把这两者物理分开，都只是在搬家：删掉的段落还会以别的形式长回来。

你说的四条症状（开发事项混进事实结构 / 框架线与模块线交错 / 大量无用描述与过期案例 / 重复术语），我逐条测到了量化证据，见 §1。它们**有共同的一个根因**，见 §2。

## 3. 建议：（不改写内容，先重建骨架）

### 3.1 核心原则：从"按层分"改成"按「事实 / 过程」分"

现在的问题是**同一份文件里同时承担两种职责**。先做一次纯粹的分类切分：

| 类别 | 性质 | 唯一落点 | 现在住哪（要搬离） |
|---|---|---|---|
| **A. 生效规则** | 是什么 / 必须怎样 | 主文档 + 分册 | 与过程混住 |
| **B. 决策记录** | 为什么这么定 + 被谁取代 | `decisions.md`（**须删掉被取代行**） | 混入 62 条开发流水 |
| **C. 事实与数据** | 实测数值、取证 | **唯一**数值表（或在 B 内一个 R 区） | 分册散布、重复 |
| **D. 进度与缺口** | 到哪了 | `roadmap.md`（**须移除已完成项**） | 5 份副本 |
| **E. 过程日志** | 改了什么 / 修了什么缺陷 / 哪轮反馈 | **新建独立区（建议 `docs/journal/` 或干脆 `.dsh/drafts/`）** | 挤满 decisions 85% + 主文档 34% + UI-ADJUST §3 + 模块页 §9/§10 |
| **F. 方法/技能** | 怎么做这件事 | `.dsh/skills/` | 与 A/D 混住（DEVELOPMENT.md、LESSONS.md） |
| **G. 历史** | 不作为依据 | `docs/archive/` | 现状可用 |

**关键动作只有一个：给 E 类一个明确的家，然后把 E 从 A/B/D 里搬出去。** 一旦 E 有了家，你列的四个症状会同时消失。
