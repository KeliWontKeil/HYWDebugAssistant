# 技术选型：UI 层对比 —— Avalonia vs Web/TS（03）

> **状态：历史论证材料**（选型过程的判据与评估；结论已由 ADR-0023/0024 收敛，生效结论见主文档 §15 与 ADR-0023/0024）。
> 阶段：技术选型。前提：数据面采用 C#（见 02 文档）；本项目 UI 需求已由 v1.0 冻结。
> 目的：回答"**Avalonia 还是 Web**"，重点是**开发难度**与**与本项目形态的契合度**。

---

## 1. 本项目的 UI 需求（v1.0 冻结，来自 §10/ADR-0018/0019）

| 需求 | 含义 |
|---|---|
| U1 模块视图**自由排列**（无容器） | "拼图式"：模块视图可自由摆放、可扩展；无画布容器 |
| U2 **几何对齐/吸附** | 拖动时对齐辅助（纯排版，不带连接语义） |
| U3 **口上的网络标记** | 小体积标签（网络名弱化 + 方向标识 + 连接状态），随口移动、可堆叠 |
| U4 **可选连线**（默认隐藏） | 热键/按钮切换；有向/流动样式动画 |
| U5 **实时波形/曲线自绘** | 大数据量（10⁵–10⁶ 点）、增量刷新、GPU 友好 |
| U6 配置面板 / Issue 面板 / 诊断面板（L1–L4） | 表格、树、属性编辑、日志视图 |
| U7 无 UI 模块的兜底入口（模块清单/管理视图） | 列表视图 |
| U8 **窗口化模块视图**（可能的多窗口/浮动块） | 与 U1 同源：桌面原生窗口行为更自然 |

## 2. 对比矩阵

| 维度 | Avalonia（C# / Skia） | Web/TS（配 Rust 或 C# 宿主） |
|---|---|---|
| **技术栈** | **单栈单进程**（UI 与数据面同为 C#；一套调试器/构建） | **双栈**（前端 TS + 宿主）；跨进程桥接 |
| **开发难度（UI 自绘）** | 中：XAML 布局 + 自定义 `Control` + SkiaSharp 绘制；绘图 API 成熟，需熟悉渲染循环 | 中：HTML/CSS + Canvas2D/WebGL；绘图资料极多，但需自行处理帧同步与脏矩形 |
| **开发难度（常规界面）** | 中：XAML + MVVM（绑定/命令）；资料量中等，但模式清晰 | 低：前端生态与示例最多，组件化成熟 |
| **U1/U8 自由排列与多窗口** | **高契合**：原生窗口/无边框窗口/自定义布局自由，桌面"拼图"体验自然 | 中：浏览器窗口受宿主控制，浮动/多窗口需 Tauri 多窗口 API 或自绘伪窗口（体验打折） |
| **U3 口上小标记** | 高：自绘粒度精确（Skia），可做高 DPI 精细小标签 | 高：DOM/CSS 灵活；但在自绘画布内需自绘 |
| **U4 连线动画** | 高：Skia 绘制 + 合成器动画 | 高：WebGL/Canvas 动画生态成熟 |
| **U5 大数据量波形** | 高：Skia GPU 后端 + 自绘降采样；内存可控（与数据面同进程，**可零拷贝共享缓冲**） | 高（Canvas/WebGL 性能上限高）但需**跨进程传输**（序列化/共享内存）→ 额外拷贝与延迟 |
| **U6 复杂控件（表格/树/属性编辑器）** | 中：基础控件齐全，高级控件（数据网格/停靠）生态较弱，需自研或采购 | **高**：现成组件极多（含开源与商用） |
| **性能（UI 侧）** | 原生渲染、无 WebView 层；内存占用低 | 依赖 WebView（Windows 用 WebView2 已内置）；JS GC 与 IPC 开销；内存占用较高 |
| **打包/分发** | 单可执行 + .NET 运行时（自包含 ~60–100 MB，或依赖已安装运行时）；启动快 | 需 WebView2 运行时（Win10+ 多已内置）；Tauri 体积小但与 Rust 宿主绑定 |
| **调试体验** | **单进程直调**（断点贯穿 UI↔数据面） | 跨进程/跨语言（浏览器 DevTools + 宿主调试器）→ 边界问题排查成本高 |
| **跨平台（未来可能）** | 好（Win/macOS/Linux） | 好（WebView 各平台差异需处理） |
| **许可** | MIT（Avalonia）+ MIT（.NET） | MIT/Apache（前端库多为 MIT）+ 宿主许可 |
| **长期维护风险** | 中：Avalonia 社区活跃、商业支持存在；高级控件需自研 | 低（前端生态）+ 中（跨栈复杂度、WebView 演进） |
| **与"数据面优先"的契合** | **高**：同进程可直接共享缓冲（零拷贝），UI 慢不影响数据面（可线程/通道隔离） | 中：跨进程桥接需要专门的零拷贝通道（共享内存/环形缓冲）设计 |

## 3. 开发难度小结（按人×时间的主观量级）

| 任务 | Avalonia | Web/TS |
|---|---|---|
| 首个可运行壳（主窗口 + 模块视图 + 拖动排列） | 中（XAML 布局 + 自定义面板；~几周） | 中（HTML/CSS + 拖拽；~几周） |
| 实时波形自绘（10⁵ 点、30–60 FPS） | 中高（Skia 自绘 + 降采样；需自研） | 中高（WebGL/Canvas 自绘；资料多） |
| 口上标记 + 连线动画 | 中（自绘 + 命中测试） | 中低（DOM/Canvas 灵活） |
| 复杂控件（表格/属性编辑器/停靠） | **高**（生态弱，多需自研） | **低**（现成组件多） |
| 跨层调试与问题定位 | **低**（单进程） | **高**（跨栈） |

---

## 4. 结论与推荐

- 若数据面采用 **C#**：推荐 **Avalonia**——**单栈单进程**（构建/调试/内存共享/零拷贝潜力）、**原生窗口与自由排列最契合 U1/U8**、MIT 许可、Skia 自绘能力强；主要短板是**高级控件生态较弱**（U6 表格/属性编辑器需自研或采购）。
- **Web/TS 的优势**集中在 U6（复杂控件生态）与 UI 迭代速度；若未来有"UI 复用/网页端"需求，或团队更擅长前端，可改选 Web（但需接受双栈与跨进程桥接成本）。
- **决策建议**：以"本项目 UI 高度定制（自绘波形 + 自由排列窗口 + 口标记 + 连线）"为事实依据——**现成控件生态的价值有限，单栈与原生窗口契合度的价值更高** → **Avalonia 为首选**；Web 作为备选（记录在案，若 U6 需求在未来权重上升可重评）。
