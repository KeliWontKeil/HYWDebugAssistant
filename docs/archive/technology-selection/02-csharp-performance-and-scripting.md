# 技术选型：C#（.NET）性能量化与模块行为载体（02）

> **状态：历史论证材料**（选型过程的判据与评估；结论已由 ADR-0023/0024 收敛，生效结论见主文档 §15 与 ADR-0023/0024）。
> 阶段：技术选型。用途：回答"**C# 能达到什么量级**""**GC 长暂停究竟影响什么**""**模块行为（脚本）语言怎么选**"。
> 说明：下表中带 ~ 的数值为**工程量级区间**（行业经验 + 架构推断），**精确数字需在选定环境后用基准实测**（验证项，非承诺值）。

---

## 1. C# / .NET 能达到什么量级

前提：**数据面按"零分配"设计**（`struct` 值类型、`Span<T>`/`Memory<T>`、`ArrayPool<T>` 缓冲池、批量传递、避免装箱与委托分配）。这是可控的工程设计，不是语言运气。

| 场景 | 量级（单核，量级区间） | 说明 |
|---|---|---|
| 内存队列传递结构体消息（无分配、批量） | **~10⁶–10⁷ 单元/秒** | Channel/RingBuffer + 值类型；每单元约 10–100 ns |
| 字节流解析（Span 切片 → 结构） | **~10⁸–10⁹ 字节/秒（0.1–1 GB/s+）** | 接近内存带宽；协议解析（帧同步/校验）通常远低于此限 |
| SIMD 数值处理（`Vector128/256`，.NET 9 支持 AVX-512） | **~10⁹ 元素/秒级**（float 数组简单运算） | 滤波/FFT 类可用 SIMD 或原生库 |
| 全托管 UI 线程（Avalonia/Skia 自绘） | 取决于绘制复杂度 | 与数据面线程解耦（§10.1） |

**结论**：对"工程人员上位机"的典型乃至较激进场景（多路串口/TCP、10⁵–10⁷ 单元/秒、GB 级/分钟流），**C# 在零分配设计下有余量**；只有跨入 10⁸+ 单元/秒或微秒级确定性要求，才必须无 GC 语言。

## 2. GC 暂停究竟影响什么（关键澄清）

- 它**不影响吞吐**（GC 是并发/后台为主），影响的是**延迟的长尾（jitter）**：极端情况下某次交付出现 ~几毫秒–几十毫秒的停顿。
- **影响链**：数据面抖动 → 数据单元延迟到达 →（若下游缓冲小）丢帧 → 波形出现微小缺口。
- **关键**：本项目顶层已冻结 **有界缓冲 + 丢帧策略 + 数据面直通 + UI 与数据面隔离**（ADR-0012/§10.1）。这些机制**天然吸收**抖动：数据监视/分析类工作台不是硬实时控制器，**抖动以"丢失若干采样点"的形式被吸收，而非破坏系统**。
- 缓解手段（全部可用）：Server GC + `<ServerGarbageCollection>` 与 **SustainedLowLatency/低延迟模式**；**池化缓冲**把分配率压到近零；大缓冲预分配避免 LOH；.NET 8+ **DATAS** 自适应堆大小；必要时按进程/线程隔离热路径。
- **结论**：在已冻结架构下，C# 的 GC 风险等级**由"高"降为"中低"**；剩余风险是"极端负载下的长尾"，可用"池化 + 低延迟 GC + 缓冲深度"工程解决，且被架构吸收。

**一个重要技术细节（须记录）**：**Native AOT** 可减小体积/启动时间与内存，但**会限制运行期动态加载（AssemblyLoadContext）与反射/脚本**；本项目要求模块动态加载（ADR-0020）与可选脚本行为载体 → **倾向保留 JIT 运行时**（AOT 作为部分组件可选）。

## 3. 升级路径（保留性能上限）

若未来出现极端热点（如超高速采集的协议解析/滤波），可**把该热点下沉为原生库**（Rust/C++ 编译为动态库，经 P/Invoke/`LibraryImport` 调用），**其余仍为 C#**。这使技术栈具备"性能上限可扩展"而不必整体换栈——与"混合架构允许"的裁决一致。

---

## 4. 模块"行为载体"（脚本/描述）选型

背景（ADR-0006 三分模型）：模块 = **原语层**（底层能力库）+ **行为层**（如何组织原语）= 行为载体。行为载体的选择直接影响数据面性能与扩展性。

| 候选 | 性能（相对 C#） | 集成难度 | 生态 | 沙箱/隔离 | 评价 |
|---|---|---|---|---|---|
| **C#（预编译程序集 / Roslyn 动态编译）** | **1×（基准，JIT 原生）** | 低（同栈、同调试器） | 最强（.NET 生态） | 中（程序集级信任；可用 ALC 卸载） | **热路径首选**：类型安全、性能最优、与框架同构 |
| **Lua（NLua / KeraLua / MoonSharp）** | ~1/10–1/50 | 中 | 中 | 好（易沙箱、轻量） | **非热路径**的行为/胶水；第三方扩展友好 |
| **JS（ClearScript(V8) / Jint）** | ~1/3–1/10（V8）；Jint 更慢 | 中（V8 体积大） | 强 | 中 | 适合编排/UI 逻辑，不适合每单元执行 |
| Python（Python.NET / IronPython） | ~1/50–1/500 | 高（运行时重） | 强（科学计算） | 差 | 不推荐（除非要复用科学库，走批量接口） |
| 自创 DSL / 模块描述标准 | 取决于实现 | 高（长期维护成本） | 无 | 好 | **用户已否决**，且违背"不要发明语言"原则 |

**推荐策略（分层）**：
1. **主路径：C# 作为模块实现语言**（编译型）——承载热路径与高性能模块；
2. **可选路径：脚本宿主用于非热路径**（配置逻辑、条件编排、一次性处理、第三方轻量扩展），首选 **Lua**（轻量、易沙箱、成熟）或 JS（若作者生态更偏 Web）；
3. **行为载体不锁定**：保持 ADR-0006 的"原语层/行为层"分离，脚本只是行为载体的一种实现；具体脚本语言作为**后续 ADR**（可在实现阶段按需引入，不阻塞选型）。

## 5. 与"性能优先"裁决的关系（诚实结论）

- 用户裁决"越高越好"，C# 的**性能上限低于 Rust/C++**，这是事实；但对本项目**实际场景与已冻结架构**而言，C# 的余量与抖动可由架构吸收，且带来：单栈开发效率、成熟生态、与**开发者既有技术栈契合**（额外优势，但**不作为主依据**）。
- 因此建议：**数据面采用 C#**，同时**冻结"热点可下沉原生库"的升级路径**（§3），使"性能上限"保持可扩展——这样"性能优先"与"技术栈契合"不再对立。
