# 分层验证与最小工作量的测试策略

> 本技能是**可复用方法论**：不依赖具体语言、框架或项目。括号里的"例：…"只提示该条通常来自哪一类经历。

## 0. 先把"层"定义清楚，并给出代价

分层的目的不是"少跑测试"，而是**让每次验证的代价与这次改动真实的风险相称**。

| 层 | 做什么 | 首次能发现什么 | 量级 |
|---|---|---|---|
| **T0 单项目编译** | 只编译本次改动的项目（含其下游） | 语法、类型、分析器/风格规则、可见性 | 秒级 |
| **T1 单类测试** | 只跑匹配的测试（按名称/类名过滤） | 该逻辑分支的行为回归 | 数秒 |
| **T2 单测试项目** | 一个增量收尾时跑整个测试项目 | 跨类耦合、共享状态冲突 | 十秒级 |
| **T3 完整门禁** | 还原 + 构建（0 错误 0 警告）+ 依赖/许可/架构规则检查 + 全部测试 | 契约/格式/依赖/架构违规 | 几十秒 |
| **表现层通道** | 只编译 + 把应用跑起来用眼睛看 | 布局、间距、颜色、文案、观感 | 秒级 |

**必要的基础设施**：把这一切做成**一个入口脚本**，并把已知的"环境摩擦"内置进去（清理会污染构建的环境变量、停掉会锁定输出产物的进程、检测"目标程序在跑"并**快速失败**而不是让构建重试十次）。**纪律写进工具，比写在文档里可靠**。

## 1. 按改动范围选层（判据表）

| 改动性质 | 跑哪层 | 判据 |
|---|---|---|
| **纯表现层**（样式/文案/间距/颜色/布局字面值） | T0 + 跑起来看 | **不跑测试、不跑门禁**。这类改动没有可自动判定的"对错"，跑测试是空转 |
| **连带逻辑**（视图模型 / 命令 / 数据结构 / 校验） | T1 只跑**受影响的那个测试类** | 只跑被改动的逻辑面 |
| **契约 / 公开面 / 文件格式 / 依赖清单 / 架构规则** | **必须 T3** | 影响面不可枚举 |
| **机制类改动**（并发、缓冲、生命周期、持久化） | T3 + **组合级验证** | 只有端到端组合能证明 |
| **交给人类手工验证之前** | **必须 T3** | 不能让人在未自证的构建上做验收 |
| **宣布某个步骤/里程碑完成时** | **必须 T3**（并与文档回写同时发生） | 状态回写必须有事实支撑 |

**执行纪律**：
1. **批量改完再编译**——不要"改一行编一次"（编译是最便宜的层，但它的价值在于"尽早发现"，而不是"高频触发"）。
2. **完整门禁不是收尾仪式**：只在上面表里那三种时点跑。频繁跑全量会让人开始"为了快而跳过"，反而降低纪律。
3. **例外要有裁决**：若有人明确要求"某阶段一律不跑全量门禁"（例：表现层还在大规模调整期），把这条**写成带触发条件的例外**（"直到 X 就绪后恢复"），而不是变成默契。
4. **跳过重编 = 使用旧产物**：只重编测试项目而不重编被改动的库项目，测试跑的是旧产物，会让人误判"改了没生效"。**这条必须写在工具注释或验证表第一行**，因为它太容易被踩。

## 2. 报告纪律：让"通过"有确定的含义

- **必须区分"我跑了哪一层"**，例如"T0 + 受影响的 T1"，**不得把局部通过说成全量通过**。
- **过滤词没匹配到任何测试 ≠ 失败**：工具应单独识别并提示"换个过滤词或去掉过滤跑整项目"。把这种情况当失败会浪费人的时间，当成功则会掩盖漏测。
- **报告"通过"时给出**：跑的命令、范围、耗时量级、以及**没覆盖的部分由谁验**。
- **不要为了跑验证而杀掉别人正在使用的实例**（会丢失现场）：先问；需要时用"应急模式"（只重编测试项目、不碰被引用应用的输出），或在提示里明确"会丢现场"。

## 3. 让缺陷可复现：探针与回归

- **主观/时序类缺陷先做探针，不先改代码**：
  - 记录关键量（输入、输出、差值、状态前后、几何前后）；
  - 只在异常条件成立时**落盘最近 N 帧**，并在界面上把落盘路径告诉人；
  - **定位完成即删除探针**，并把其中稳定的判据**转正为回归断言**。
- **断言要断言"来源/一致性"，不要断言"某个具体值"**：断言具体值在"功能恒回落到占位值"时也会通过，等于没测。
- **对"恒定噪声"的断言要写成与次数无关的形式**：例如分配/调用类断言，写成"**次数翻倍不新增**"，而不是"等于 0"——后者会被首次调用的一次性开销污染成偶发失败。
- **几类高价值的固定断言模式**（可直接照搬）：
  - **反向断言**：数据未变时，对象引用必须相同（抓"刷新即重建"）。
  - **幂等断言**：同一次刷新里读两次，必须得到同一个数（抓不可重复读的指标）。
  - **来源断言**：颜色的来源必须等于某个键，而不是"是某种颜色"。
  - **唯一性断言**：键必须唯一且一一对应（抓"显示名当键"）。
  - **边界拒绝断言**：越界/版本过新/形状不符必须被拒绝且原文件不被改写。
  - **数值钉住断言**：端到端跑真实链路，断言"这个数必须 > 0"（抓静默归零）。
- **先假设自己可能改错**：用户说"还是老样子"时，先确认**我的改动真的被加载了**（产物是否重编、是否被缓存、是否被另一条实现路径覆盖），再去改代码。

## 4. 验证真正跑不动时：排查顺序

### 4.1 "单独跑绿、一起跑红"

**先怀疑共享可变状态，再怀疑测试本身**，顺序：
1. **静态 / 单例 / 进全局资源字典的可变对象**（尤其有线程亲和性、有缓存、有懒初始化的）；
2. **进程级配置**（渲染模式、环境变量、全局开关）——不同配置的测试会话**必须拆进程**，同进程混用会把两边的会话一起弄坏；
3. **需要专属线程/专属资源的测试**：放进"禁止并行"的集合，或串行执行；
4. 最后才怀疑测试自身的写法。

### 4.2 构建/测试被环境挡住

| 症状 | 常见根因 | 规避 |
|---|---|---|
| 构建配置解析失败 | 外部环境变量污染 | 工具启动即清理/固定；并建议在系统层删除 |
| 输出文件被占用 | 运行中的实例 / 设计器宿主 | 工具先检测并**快速失败**给可操作提示；必要时提供"停掉它"开关（并提示会丢现场） |
| 重试十次才失败 | 同上（没做前置检测） | 前置检测必须在构建之前 |
| 测试"改了没生效" | 跳过了被改动项目的重编 | 应急模式的前提写清楚：**先编改动的项目** |
| 输出刷屏无法定位 | 未降级日志级别 | 平时用静默模式；失败时再加过滤定位单个测试 |

## 5. 验证的边界：明确"不做什么"

- **不设覆盖率硬性百分比**：以"机制改动必须有组合级验证"替代。
- **自动化只覆盖主要问题，不追求全覆盖**；**不可自动化的应用层行为交给人类手工验收清单**（并保持"清单只写人能观察到的现象"）。
- **基准/性能测试不进常规门禁**（按需运行）；但**热路径改动要给出分配或吞吐数据**。
- **架构/规则类检查必须"目标缺失即失败"**，不允许"没有对象就跳过"——**规则的静默失效比误报危险得多**。
- **规则报错时先确认真违规还是误报**；确属误报走**例外登记**（代码注释 + 唯一登记处 + 复查条件），**不擅自改规则或关规则**。
- **关键约束必须能映射到可执行检查**（检索/构建/测试/规则），只写在文档里的约束等于不存在。
- **不静默降级**：未做到的事必须登记为待办或例外，不能"暂不实现"就算完成。
