# UI / 自绘与第三方控件的排障与回归纪律

> 本技能是**可复用方法论**：不依赖具体框架。括号里的"例：…"只提示该条通常来自哪一类经历。

## 0. 三条排查主线（先判断属于哪一类，再动手）

| 症状 | 主线 | 查序 |
|---|---|---|
| **看不见** | 有没有画出来 | **有没有模板 → 有没有尺寸 → 有没有被裁 / 被盖 / 被压** |
| **点不到** | 命中 | 层级顺序 → 命中可见性 → "唯一入口"控件是否在最上层 |
| **改了没生效** | 接线 | 有没有消费者 → 有没有绑定 → 有没有重绘声明 → 产物是否真的重编 |

- **最坏的缺陷不是崩溃，而是"可改可存但没人读"**（俗称死开关）：用户会认为功能坏了，而且不会有任何报错。**规则：每个可交互控件都必须能指出"谁读它"。**
- **"看得见"是功能的一部分**：对比度极低、字号过小、被相邻控件压掉几个像素，都会让用户得出"功能不存在"的结论。
- **先分清"没画"和"画了看不见"**：报"看不到"时，先确认可见性判据是否直接把它排除了（很多"看不见"的根因在**判断**，不在**绘制**）。
- **先量几何，再调颜色与粗细**：用户说"看起来像 bug / 不清晰"时，优先量线长、层级、间距——装饰件的尺寸常常小到与它要表达的东西不成比例。

## 1. 自绘的坐标系与"唯一事实源"

自绘缺陷的大多数根因是**口径不唯一**。逐条对照：

- **物理像素 vs 逻辑单位**：几何用物理像素、绘制用逻辑单位时必须**显式换算**（含缩放），原点取"客户区原点"，并给根容器设置裁剪（否则会画到窗口外）。
- **两个矩形不是一回事**：窗口/元素的"外框矩形"与"客户区矩形"尺寸与原点都可能差一点点（例：装饰边框内缩）。要哪一个就用**同源取值**，不要把两者的字段拼起来。
- **参照基准取"用户看到的那条边"**：内部可计算的边（客户区）与用户眼睛看到的边（可见外框）可能差 1 个像素的边框——**1px 的缝会被用户一眼抓到**。
- **世界坐标 vs 画布坐标**：几何函数**要么全用世界坐标、要么全用局部坐标**，并在签名/注释里写死；跨窗/跨层一律经**显式换算函数**。**几何用例失败时，先怀疑输入坐标的口径，再怀疑算法**。
- **尺寸只能有一个来源**：凡"两端各算一半、拼起来要对得上"的几何，两端必须取**同一个变量**；"布局结果尺寸"与"意图尺寸"不是一回事，混用会造成系统性错位。
- **一个量化点**：模型与目标（例如窗口只能取整）之间**只允许一处取整**；并且**只由驱动者写模型**——交互中被指针带着走的成员，不能被刷新用旧值回写。
- **判定用"事件发生前"的几何**：拿移动后的坐标去判"谁贴着谁"，会把条件悄悄改成"位移足够小才成立"。**修法：把"移动前的值"做成显式参数传进判定函数**——这样第二处也不会再犯。
- **别拿"被自己移动的对象"当输入基准**：拖动时用"窗口位置 + 窗口内坐标"算屏幕指针，两个来源不是同一次采样 ⇒ 指针误差 = 位移量 ⇒ **正回授振荡**。**"只在一个方向出现"的抖动往往就是线索**：那个方向正是我们自己动过的方向。
- **贴边元素会被自己的裁剪吃掉**：贴边的线/边框有一半落在裁剪区外。**两条一起改**：① 可见性判据要容忍"贴边超出"，但仍排除离得远的；② 绘制时按"线宽/2"内缩。只改一条 → 用户复验"还是没有"。
- **留白是几何参数**：凡"从 X 画到 Y"的线，**先算最坏情况下的实际长度**再定 X 的留白，并把它写进几何用例；极窄尺寸要有**明确的退化策略**（例：单列居中、只画得下的、如实标出省略数量），别指望"把参数调小一点就行"。

## 2. 几何要"两点一线"，不要"业务推断补几何"

- **画线就是"两点之间，被容器裁一刀"**：起点 = 语义上的中心，终点 = 对端的中心，交点由裁剪自然得出 ⇒ 长度、角度、箭头朝向全部自然成立。
- **需要"方位分类 + 特判"通常说明几何选错了**：两点定线天然与方位无关。**一条几何规则若要用两套推断才能讲清，它就不是简单规则。**
- **端点要落在语义锚点上**：对象中心 ↔ 边界是锚点；中间的装饰件（标记、手柄、边带）**不是几何锚点**——把端点画在装饰件上会产生"两个小残段"，用户判定为"像出了 bug"。
- **相对尺寸是错位之源**：±2 像素的内缩在单窗里看不出来，两端各算一半时就会变成系统性错位。**先用一条跨窗口/跨容器的用例把它钉住**（"本端算出来的对端位置 = 对端实际画出来的位置"）。

## 3. 渲染引擎的语义靠实测，不靠注释

- **凡依赖渲染引擎语义的东西**（虚线相位与它的单位、渐变端点、字体度量、像素对齐），**先写一条能测量的探针**，再改业务代码。
- **量"单调可测的量"**：例：量虚线的"第二段"起点，而不是"第一段"（第一段可能被相位吃掉或推到线外，不单调）。
- **探针留在测试里**：它同时是文档——下次谁再改方向或单位，用例会告诉他。
- **单位不要靠推演**：同一份"偏移"在不同引擎里可能是长度、可能是"线宽倍数"；**推演错了会导致实现与预期正好相反**，而且只在真机上看出来。

## 4. 接入第三方控件 / 换控件版本

- **第一件事：查"它的模板/样式从哪来"**。**"自带"不等于"自动生效"**——模板常常在自己的程序集里，主题里并不包含它，必须**显式挂载**。
- **"没有模板的控件不报错，只是什么都不画"**：于是它表现为"窗口只有标题和几个按钮"之类的怪样子，还可能因为自适应高度被压成一条。**没有异常、没有警告。**
- **"字错位 / 被裁"常是同一场景的次生现象**：内容没渲染出来后，其余元素挤在一行并超出固定宽度。**排查时按主线走，不要被次生现象带偏。**
- **版本对齐**：引包前核对它依赖的目标框架大版本；**落后一个大版本 = 运行时不兼容风险**。框架大版本移除某个 API 时，靠编译错误清单逐项清理。
- **每个自绘/第三方控件都要有一条"出像素"的判据**（见 §6）。
- **同类交互出现第二遍就抽公共件**：抽的时候**顺手删掉旧路径**（否则留下两套行为，用户会在不同页面看到不同本事）；**"精简"是公共件的准入条件**（明确不要什么：不要那些模式、不要透明度、不要自定义格）；**当人建议"做精简"时，他是在批准删，不是批准加。**

## 5. 刷新纪律（交互异常的高发区）

- **区分"刷新数据"与"重建视图"**：前者改属性，后者动集合。**有悬停/展开/弹窗等跨帧状态的列表，一律不许在刷新里重建**——否则目标控件被换成新对象，表现为"鼠标一指上去就不停闪烁"（看着像样式/动画问题，实为**对象身份**问题）。
- **排这类 bug 的第一问**："**这个控件还是刚才那个对象吗？**"
- **行模型用值语义**（否则无法判断"有没有变"，只能退化为每帧重建）；**列表用增量同步**，并断言"数据未变时行实例引用必须相同"。
- **查询路径不做 IO**：会被每帧调用（例：每帧枚举目录）；这类判定**在扫描/变更时算一次并缓存**。
- **"内存领先于落盘"的成员，刷新一律让路**：交互中先改内存、稍后再提交的路径，必须在刷新里显式跳过——否则会被旧值一帧帧拉回。
- **会画东西的控件必须显式声明"哪些属性变化要重绘"**；每个公开属性都要有消费者（没有消费者的属性、没人调用的绘制路径都是死代码，**编译器和分析器都看不见**）。
- **降权要分清"加法"与"减法"**：给元素加覆盖层/加降权样式是**加法**，把元素沉到下层是**减法**——先确认用户要的是哪一种（这两者观感与实现完全不同，做反了会被明确否决）。

## 6. 观测、指标与"静默归零"

- **区分"事件"与"观测"**：事件消费一次就没了（用队列）；观测可被任意多个消费者读，**必须幂等**。凡"读的时候才算"的指标，都要回答"**同一次刷新里读两次会怎样**"。
- **两套"看起来都像键"的标识是静默归零的高发现场**：先用一条**端到端断言把数值钉住**（"真实链路里这个数必须 > 0"）；**"查不到"与"查到 0"必须分开表达**。
- **身份必须由框架/模型给出**：显示名（可空、可重复）**永远不能当键**；高频刷新路径**一律不抛**（宁可少显示也不让界面崩）。
- **一个"成功/失败"背后有性质不同的原因时，用枚举**；"看起来成功但其实丢了点什么"的操作，**返回值必须带出那份损失**。
- **派生量不要另存**（否则标志与成员各说一套）；用相等判断"状态有没有变化"前，先确认**被比较的对象真的携带了那个差异**。
- **指标来源唯一要落到"只有一个写入点"**；删掉第二来源时，**顺手检查它是不是还承担了"刷新时机 / 口径统一"**——否则删完会出现"状态不更新"或"两个地方看到不同数字"。
- **信息归属于它所描述的对象**：决定"这行字写在哪"之前先问"**它在说谁**"；两个维度的数字挤进同一个控件，用户必然读成同一个意思。**维度分开之后，视觉权重也要跟着分开**（否则等于没分）。
- **信息要按"一眼看到什么 → 再看什么"分层**：主指标用大一号字，事实/细节用小一号字；**不要把并列关系硬塞进一行**；面积紧张时先问"这块信息该不该出现在这里"（最常见的后果是**叠字**）。

## 7. 回归网（让界面缺陷变成"提交前能拦住"的）

四层，缺一层就会有整类缺陷永远只能靠用户截图发现：

1. **真实资源 + 真实窗口的无头测试**：它是**视图层性价比最高的兜底**。能拦住：资源类型错误（只在运行时炸）、模板命名域冲突（只在首次布局时炸）、命中层级错误、可见性/尺寸/贴边断言。**规则：目标缺失即失败，不许"无对象则跳过"。**
2. **自绘的"真出像素"自检**：无头测试**默认是空绘制**——忘了调用绘制、画到窗外、两块字叠在一起，**断言一律看不见**。必须另有一条把窗口**渲染成图片**的路径，并人工看一眼。**这类会话与空绘制会话不可同进程混用**（后者的配置往往是进程级的，混用会让另一批会话集体失败）。
3. **几何/纯函数断言**：把"线长必须显著大于装饰带"、"贴边必须判定为可绘制"、"两端算出的位置必须一致"、"同坐标只留最高级别"这类**薄判据**钉死；它们便宜、稳定、且能防后人调参数时悄悄改回去。
4. **渲染冒烟断言**：把"图里有多少种颜色/高度是否合理"这类可计数的特征写成断言（空白图与正常图的特征数差异巨大）。

**另外两条与界面强相关的纪律**：
- **文字信息的三种写法**：短语（≤ 十几个字）直接显示；一句解释用悬停提示；多句/教程用**独立弹窗**（**绝不就地展开**——就地展开会改变布局，用户会明确反对）。帮助入口放在分区右侧/右下角并保持 X 对齐。
- **区域尺寸不随内容变化**：选择区/列表放在固定行高或弹性行里并**内部滚动**；标签/按钮用固定宽度 ⇒ 切换分类、搜索、数量变化都**不推动其它控件**。
