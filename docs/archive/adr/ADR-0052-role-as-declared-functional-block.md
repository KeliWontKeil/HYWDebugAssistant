## 1. 用户原话（本轮裁定的依据）

> "使用文字 `m/n`，可以放在角色方块内部，说明**输入连接了几个角色 / 输出连接了几个角色**，没有输入或输出使用 `--`。
> 我认为可能需要**细化"角色"的定义和属性**：**角色是模块的子功能分块表达**，通常**一个角色只能有一种数据类型**，
> **最多只会有两个口，一个输入，一个输出**。这一点为**模块自身声明**，角色是模块本身**内部数据处理功能的抽象**，
> **网络标签（数据接口的抽象）我认为可能不需要在叠加视图中高亮**，它们**不是一个层级和意义领域内的东西**。
> 我的表达可能有误，需要慎重。包括所有其他问题需要在这一层意义上仔细考虑。"

**我的读法**（先复述，错了请纠正）：他说的"角色"与我 P3 落的"角色"**不是同一个东西**：

| | **现行（ADR-0048 · 我设计的）** | **用户本轮的意思（拟采纳）** |
|---|---|---|
| 是什么 | **（方向 × 类型身份）** 的**派生量**（同方向同类型的口自动归成一个角色） | **模块的子功能分块**（模块自己声明："我有哪几块处理功能"） |
| 谁定义 | **框架派生**（不声明，v1 纯派生） | **模块自身声明** |
| 方向 | 角色**带方向**（发送角色 / 接收角色各一个方块） | 一个分块**同时**可能有输入与输出（**一个方块**，左入右出） |
| 口数 | 一个角色**可有多个**同类型口（8 通道记录器 = 1 角色 8 口） | **通常 ≤2 个口**（1 入 + 1 出）；"多通道"应由**类型的 `ChannelCount`** 表达，而不是多个口 |
| 与"网络标签"的关系 | 叠加层里"角色对线"带**网络名 + ×N**（把接口层信息也画了） | **网络标签（接口层）不进叠加层** —— 与角色**不是一个层级/意义领域** |
| 方块里的数字 | `N 口 · M 连`（口数与口级连接数） | **`m/n` = 输入侧连接的**角色**数 / 输出侧连接的**角色**数**（无该侧 ⇒ `--`） |

**一句话**：**角色 = 处理功能的抽象（模块的功能分块）；网络标签 = 数据接口的抽象（端口/建网机制）**。
两者**不同层级**，叠加层只表达前者；后者继续由**端口标记**（模块窗口标准件、唯一建网入口）承担。

## 3. 新模型精确定义（**已生效**）

**R1′. 角色（Role）= 模块声明的功能分块**，由模块在 `OnRegistered` 中声明，字段：

| 字段 | 含义 | 约束（拟） |
|---|---|---|
| `Id` | 角色标识（模块内唯一，稳定） | 非空；重复即报 Issue 并忽略后者 |
| `DisplayName` | 功能名（给人看，如"融合"） | 可空 ⇒ 回退为类型短名 |
| `Type` | **该分块处理的数据类型引用**（标识 + 版本） | 必须能在本模块解析；**一个角色只有一种类型** |
| `Inputs` | **输入口名集合** | 可为空（纯源）；通常 1 个 |
| `Outputs` | **输出口名集合** | 可为空（纯汇）；通常 1 个 |
| `Icon`（可选） | 功能图标（v1 建议不做，见 Q6） | —— |

**R2′. 口与角色的归属**：一个口**最多属于一个角色**（不得一鱼两吃）⇒ 校验时冲突即报 Issue。
**未归属任何角色的口**：合法（旧模块、纯 IO 口）⇒ 在叠加层里**不表达**（它们仍以**端口标记**呈现，属于接口层）。

**R3′. 仍然只呈现**：角色、`m/n`、角色间连线一律**不参与**建网、兼容判定、停流、投递与计量，**不进组合件**
（与 ADR-0048 R9 同一红线；这一条**不放宽**）。

> **R3′-补（第三十三轮落地时定稿）**：**不对角色的口数设上限**；**"口数 &gt; 2"只给建议、且建议与"问题"分通道**。
> 定位过程（记录在案）：最初把该建议写进 `ModuleContract` 的 `Problems`（其语义是"**空 = 合法**"）⇒ 它在
> **自家参考融合器**（2 入 1 出，用户已裁定的合法范例）上必然触发，门禁用例"三个参考模块的声明面应无契约问题"**当场失败**；
> 运行期若也报 Issue，用户会在**正确模块**的 Issue 中心看到警告。定稿口径：
> ① **SDK 自检**通过 `ContractProbeResult.Advisories`（**独立通道**，不影响 `IsValid`/`CheckAll`/门禁）给出建议，
> 文本里**明说"若是一件事（例如多路合成一路）则不必拆"**；② **运行期不产生这条提示**（Issue 中心不得在自家正确模块上报警）。
> 角色形态由作者定，框架**只校验结构**（Id 唯一 / 类型可解析 / 口存在且方向相符 / 一口最多一角色 / 至少一个口），**外加这条可忽略的建议**。

**R4′. `m/n` 的定义（要钉死的口径）**：

- `m` = **本角色输入侧连接的对端角色数**（去重键 =（对端实例, 对端角色））——"输入连接了几个角色"；
- `n` = **本角色输出侧连接的对端角色数**（同样的去重键）——"输出连接了几个角色"；
- **没有该方向的口 ⇒ `--`**（与该方向是否连上无关）；**有口但没连 ⇒ `0`**（两者含义不同，必须区分）；
- 计数是**角色数**（不是口数、不是网络数）：同一对端角色的多个口连到本角色 ⇒ 仍算 **1**。

**R5′. 类型与"多通道"**：多通道/批量**由类型的计量块**表达（`ChannelCount` / `SamplesPerUnit`，ADR-0046 D2/D8 已落地），
**不再用多个口**表达（这正是"**一入一出是常态**"能成立的前提；8 通道记录器 = **1 个角色 1 个口**，通道数在类型里）。

**R6′. 零口/零角色**：没有声明任何角色 ⇒ 叠加层**不画方块**；模块若有数据口但**没有声明角色** ⇒ 见兼容策略（§6）。

## 4. 叠加层的相应重述（方块 = 左入右出的功能块）

| 项 | 新画法 |
|---|---|
| **方块形状** | 一个矩形（宽度够放"类型名 / `m/n`"两行；高度单行到两行） |
| **两侧接口** | **左侧 = 输入边**（有输入口才画；口数 **&gt; 1** 时在该边上画短刻痕）· **右侧 = 输出边**（同理；1 个口不画刻痕——常态不加噪） |
| **颜色** | **填充 = 类型色**（按 `TypeKey`，跨模块一致）· **输入边 = 接收方向色**、**输出边 = 发送方向色**（与端口标记同构；一个方块可同时有两种颜色的边） |
| **文字** | 第一行 = **功能名**（无则类型短名）· 第二行 = **`m/n`**（`2/1`；无输入 ⇒ `--/1`） |
| **去掉** | 类型长文本（`{seq:u64, value:f32}`）、`N 口 · M 连`、线上的网络名与 `×N` |
| **悬停**（端口标记保持现状；方块 v1 不参与命中） | 详情（类型标识/版本/尺寸/语义/口列表/速率）仍在端口标记悬停与拓扑诊断里 |

**摆放（Q4 已裁定 = (a)，已落地）**：**单列竖直堆叠、居中**；**宽度随文本自适应**〔ADR-0053 修订：[64,176]，块高 34〕；放不下 ⇒ 只画得下的 + 底部 **`+K`**（如实报出未画数量）〔ADR-0053：删除"缩方块"中间档〕。
(b) "发送靠右、接收靠左"在新模型下**不再适用**（一个方块同时有两侧）；(c) 按声明顺序成链需要"顺序"这一新声明概念，留作将来的增强。

## 5. 线的定义（与 ADR-0049 D14 合并）〔**端点已由 ADR-0053 修订为「两个角色方块中心」**〕

> **⚠️ ADR-0053 修订（第三十四轮）**：用户："**我希望连线从角色方块中心出发**" ⇒ 端点 = **两个角色方块的中心**
> （不再是"输出侧/输入侧中点"）；绘制时裁掉**本端方块内部**那一段（视觉上从方块中心出发，又不横穿方块）；
> **虚线沿数据流方向流动**（两侧共用 `-相位 ÷ 线宽`）。以下"每个窗口只画交集""未拼接画断口 + 对端名"**继续有效**。

- 一条线 = **一次"角色 → 角色"的数据流**：由**发送角色的输出侧锚点** 与 **接收角色的输入侧锚点** 定义；
  **锚点 = 该侧边的中点**（在各自窗口局部坐标里算好，再换算到同一坐标系）。
- 每个窗口只画**这条线段与自己窗口矩形的交集** ⇒ 两段**严格共线**：
  相邻/拼接时**无缝接上**；未拼接时各自被自己的边界裁断（缺的那段**恰好是两窗之间的空隙**）；重叠时仍共线。
- **未拼接末端**：**竖杠断口 + 对端名**（用户第三十三轮已裁定）。
- **线上不再写网络名/`×N`**；线上保留**信息卡**（速率 / 投递 / 丢弃，见 §7）。
- 对端角色不可用（未装入/该模块未声明角色/占位）⇒ 回退：① 对端**窗口中心** → ② 沿本端接口边方向出窗。

## 6. 兼容与迁移（**裁定：不做兼容，只做声明**）

> **用户第三十三轮裁定**：**"1.6 兼容与迁移：不考虑，当前是开发早期……无需过度考虑兼容，减少工作量。"**

| 情形 | 处理（**已落地**） |
|---|---|
| 模块**声明了角色**（新面） | 按声明画；`m/n` 按 R4′ 算 |
| 模块**没声明**角色但有数据口 | **不画方块、不画线**（叠加层**不发明角色**）；信息区给一句事实：`未声明角色（N 个数据口）`——接口本身仍由**端口标记**表达 |
| 模块**既无角色也无口**（纯 UI） | 不画任何方块；信息区给一句事实：`无数据口` |
| 旧组合件 | **无影响**（角色是声明派生的呈现，不进组合件 —— R3′） |

**为什么不做回退（"每口一个匿名角色"）**：那是**第二套角色模型**——它会把融合器重新画成"一收一发两块"（正是 B2 要修的病），
且需要永久维护两条路径 ⇒ **真正的技术债**（§12.6 的原话："真正该避免的不是'声明'，而是'两套模型并存'"）。
开发早期没有需要兼容的存量模块，**回退路径的成本换不到任何东西**。
**作者负担的补偿**：`ModuleContract` 自检 + 运行期 Issue 会给"有口但未声明角色"的模块一句提示（**提示，不是错误**）。

## 7. 信息卡（沿用 ADR-0049 D17，按本轮口径微调）〔**已被 ADR-0053 取代：改为角色方块上方的纯文字**〕

> **⚠️ ADR-0053 修订（第三十四轮）**：用户指出"这些信息表达的**不是「数据通路信息」，而是「角色本身速率信息」**" ⇒
> **卡片整体删除**（连同 `OverlayCard` 令牌与 `ConnectionOverlay.DrawCard`），改为画在**角色方块上方/周围**的**纯文字**，
> 口径从"某条流"改为"**该角色自身**"（产出侧优先）。下表的内容（速率 / 投递·丢弃 / 类型语义·标称）**保留**，
> 但落点与口径见 **ADR-0053 D4**；**线上不再写任何文字**。

| 行 | 内容 | 依据 |
|---|---|---|
| ① | **速率**（`123 B/s`；无流量 `---`） | `BindingDiagnosticView.BusByteRate`（按宿合计的搬运字节速率） |
| ② | **投递 / 丢弃**（用户已裁定口径 = **三类丢弃**里的"传输丢弃"与"投递"） | `Delivered` / `DropTransport`（**停流未投递**另计，不混算） |
| ③ | 类型语义 · 标称速率（如 `normal · 100 Hz`；无声明则省略） | `SemanticTags` / `MeteringBlock.NominalRateHz` |

- **只由发送端窗口画一次**（一问一对只一张卡）；**v1 不展开**（用户已裁定）；**删掉模块级汇总行**（用户已裁定）。

## 12. **我的评估（供你决策；你问的是"这会不会更好，还是带来无意义的技术债"）**

### 12.1 结论（一句话）

**建议做**，但**按"增量 + 两步走 + 六条红线"做**——理由是：**你要的收益（图上能表达"一块功能把两路合一"、`m/n` = 连了几个角色）在派生模型里拿不到，且没有更便宜的路**；
反过来，保持派生式则要**永久放弃**这两项能力。**这不是"技术债 vs 干净"，而是"多花一次增量成本，换一项结构性能力"**。

### 12.2 收益（逐条说清"**派生模型做不到什么**"，而不是泛泛说"更好"）

| # | 收益 | 派生模型下的**具体失败**（不是理论） |
|---|---|---|
| B1 | **功能分解成为一等概念**，指导模块开发 | 派生模型只能回答"这个模块有哪几种类型、几个口"，**回答不了"它内部有哪几块功能"**。作者写模块时没有任何地方需要交代自己的分解 ⇒ 分解只存在于作者脑子里，评审与文档都抓不到 |
| B2 | **图不再误导** | 现参考模块里**融合器** = `in1`+`in2`（同类型）+ `out` ⇒ 派生模型画成 **"一个接收方块（2 口）+ 一个发送方块"**，看起来像"两进两出的转发器"，而真实语义是**一块"两路合一"的功能**；再如"采集 → 计算 → 输出"的模块会被画成**两个互不相干的方块**，丢掉"链" |
| B3 | **`m/n` 才有信息量** | 派生模型的计数只能按**口**算（"几个口 / 几条连接"）——这正是你第一轮说"有几个口/几个角色不需要用文字表达"的原因：**这个数字没有诊断价值**。换成"**输入连了几个角色 / 输出连了几个角色**"才有价值：一眼看出"我下游有几个听众""谁在喂我" |
| B4 | **为后续观察手段打地基** | 侧边栏的"数据包类型表"、拓扑诊断的分组、将来的模块级指标都要一个**语义单位**；派生模型给的"方向×类型"是个机械组合，挂不住业务含义 |

### 12.3 成本（诚实清单 + 关键判断）

| 面 | 内容 | 量 |
|---|---|---|
| SDK | `RoleDeclaration` + `DeclareRole`（**只增**，不改既有签名 ⇒ **已编译的第三方模块仍能加载**） | 2 文件 |
| Hosting | 收集 + 校验（口归属唯一、类型可解析、Id 唯一、>2 口给建议） | 3 文件 |
| Core / Core.Api | **一个** `RoleView`（含 `Inputs`/`Outputs`/`InboundRoles`/`OutboundRoles`），两个生产者：**声明**（新）与**匿名回退**（旧派生代码**保留**为回退） | 4 文件 |
| Ui | 方块画法（左入右出 + `m/n`）· 线的端点（输出侧锚点 ↔ 输入侧锚点）· 删网络名/`×N` · 卡片保留 | 4 文件 |
| 参考模块 | 6 个模块各加 1 条角色声明 | 6 文件 |
| 测试 | P3 的 9 项按新定义重写 + 新判据 + 快照场景 | 4 类 |
| 文档/验收 | 本 ADR · ADR-0048/0049 标注 · 主文档修订 · `18` · **L 组整组重写** · roadmap/LESSONS | 8 处 |

**三个关键判断**（决定了这笔成本值不值）：

1. **是"增量"不是"重写"**：旧派生逻辑**保留为回退路径**（已测试、已在跑），新路径是**加在上面**的。⇒ 风险不是"推翻重建"，而是"多一条分支 + 一次观感调整"。
2. **现在是切换成本最低的时刻**：叠加层**还没通过验收**（L 组 #85–99 一次都没跑过），而这一轮本来就要改方块画法、信息区、线端点 ⇒ **切换成本几乎被"本轮返工"吸收**；等验收后再改就是**纯返工**。
3. **回退保证现场不炸**：无角色声明的模块（含第三方旧模块）走匿名回退 ⇒ **不存在"必须升级才能用"**。

### 12.4 反方论据（我认可的风险，必须登记为已知局限）

| # | 风险 | 缓解 |
|---|---|---|
| R1 | **声明 ≠ 证明**：作者可以声明"融合"块，而代码里两个口走的不是同一条路径。框架**只校验"口存在且归一"，校验不了语义** | 登记为已知局限；在 `ModuleContract` 自检里给**建议性**提示（不是错误）；文档写明"角色是**声明**，不是**证明**" |
| R2 | **作者负担**：每个模块都要想清楚分解 | 声明**可选**（不声明不报错）；自检 + 运行期 Issue 给"有口但未声明角色"一句提示（**提示，不是错误**） |
| R3 | **升级即改观感**：同一现场，模块升级到声明面后图会变 | 已按"不做兼容"一次性切换（§6）；组合件不受影响（角色不进组合件）；无存量第三方模块需要迁移 |
| R4 | **滑向"业务分类"**：如果哪天框架开始内置 `Source/Sink/Processor` 这类枚举，就违反主文档 §6.2 | 见 §12.5 红线 ①（写成硬条件，架构测试可查） |

### 12.5 与既有纪律的一致性检查（这是我认为"可以做"的关键）

- **同构于已有先例**：`ViewDeclaration`（模块声明 UI 结构，框架渲染）、`DeclareFlow`（模块声明内部关系，框架只投影）、`DataTypeDeclaration`（模块声明类型，框架只持机械镜像）——**都是"模块声明、框架只投影"**。`RoleDeclaration` 与它们**同一范式**，不是新范式。
- **不违反 §6.2**：框架**不定义**角色分类，只**登记**模块给的名字与分组；`DisplayName` 与 `ViewDeclaration.Title` 同级（纯呈现文本）。
- **不放宽 ADR-0048 R9**：角色/`m/n`/角色间连线**不参与**建网、兼容、停流、投递、计量，也不进组合件。

**六条红线（我建议作为将来验收的硬条件）**：

| # | 红线 | 可查方式 |
|---|---|---|
| ① | **框架不内置任何角色类型枚举/图标/业务词**（只有"标识 + 名字 + 类型 + 口集合"） | 代码评审 + 架构测试（`Sdk` 中不得出现业务角色常量） |
| ② | 角色**不参与任何判定**（兼容/建网/投递/计量/停流） | 反向断言用例（加/删/改角色声明 ⇒ 网络与投递结果逐字段不变） |
| ③ | **不发明角色**：没声明 ⇒ 叠加层**不画方块**（**不得**由框架派生/回退凑出角色）；有数据口而未声明 ⇒ 一律提示作者补声明 | 反向断言：未声明角色的模块 `GetRoles` 为空、叠加层零方块 |
| ④ | **不与口/网络重复表达**：口仍是唯一接口与建网单位；角色只是**分组与命名** | 评审 + 端口标记相关用例不变 |
| ⑤ | `m/n` 必须是**框架派生量**（连了几个对端角色），**不得**由模块自报 | 派生用例 + 无对应 SDK 字段 |
| ⑥ | 一个角色**只有一种类型**；一个口**最多属于一个角色** | 自检用例 |

### 12.6 我排除的替代方案（免得你以为"还有更便宜的"）

| 方案 | 成本 | 为什么不够 |
|---|---|---|
| **D. 只加"模块功能名"**（其实 `ViewDeclaration.Title` 已有） | ≈0 | 只说明"这个模块干什么"，**完全拿不到 B2/B3**（内部有几块、`m/n`） |
| **C. 保留派生角色 + 额外加"分组框"**（框套框把 in1+in2+out 圈起来） | 中 | 视觉上"框套框"比"角色=功能块"**更难懂**；且"角色"与"分组"两套并存 ⇒ 两套模型都要维护（**真正的技术债**） |
| **B. 只把 `m/n` 定义为"连了几个模块"** | 小 | 拿不到 B1/B2；且"连了几个模块"与"连了几个角色"在诊断价值上差一个量级（多角色模块分不清） |

⇒ **如果 B2/B3 对你有价值，就必须走声明式**；如果它们对你不重要，那**保持现状**（派生式）也完全可用 —— **真正该避免的不是"声明"，而是"两套模型并存"**。

### 12.7 建议的裁定顺序（你只需先回答第一问）

1. **先答 Q1**：做（声明式）还是不做（保持派生式）。
2. 若"做"：**Q3/Q4/Q5/Q7/Q10 我按推荐落地**（常见形态允许 >2 口 · 单列居中 · 网络标签完全不进叠加层 · `DeclareFlow` 改为角色→角色 · 两步走），你只需在验收时看效果；有任何一条你想改，随时叫停。

## 13. 落地记录（2026-09 · 第三十三轮裁定后一次性落地）

### 13.1 一处需要你知道的落地口径（**>2 口的"建议"落在哪**）

**Q3 的"自检给出建议（&gt;2 口时警告）"我按"建议、不报警"落**（R3′-补）：
- **SDK 自检**保留该建议，走**独立通道** `ContractProbeResult.Advisories`（**不计入 `Problems`** ⇒ 不影响 `IsValid`、`CheckAll`、参考模块门禁用例），文本里明说"若是一件事（例如多路合成一路）则**不必拆**"；
- **运行期不产生**这条提示（`ModuleInstanceFactory` 不再报这条 Issue）——否则**你自己的参考融合器**会在 Issue 中心里带一条警告，看着像模块写错了。

**为什么不是"写进 Problems"**：`Problems` 的语义是"**空 = 合法**"（`IsValid`/`CheckAll`/门禁用例都按它写）；
把建议塞进去，会让"三个参考模块的声明面应无契约问题"这条门禁用例**直接失败**（实测发生过），
也会把"能跑但有话说"变成"不合法"。
**若你想要"运行期也警告"**：说一声即可恢复（改动约 5 行）——但我建议不要（正确模块不该有告警）。

### 13.2 关键实现口径（钉死，便于以后查证）

| 事实 | **唯一来源** |
|---|---|
| 一个模块有哪几个角色、各叫什么、什么类型、哪些口 | **模块声明**（`DeclareRole`），框架只校验结构 |
| `m/n`（连了几个对端角色） | `RoleModel.PeersOf`——从**网络成员关系**派生，去重键 =（对端实例, 对端角色）；**模块无法自报** |
| 角色间的线（哪两个角色之间有数据） | `RoleModel.FlowsOf` + `ModuleRuntime.DescribePortLinks()`（与**绑定构建同一入口** ⇒ 与真实投递不漂移） |
| 线的两端锚点 | 发送角色方块的**输出侧中点** ↔ 接收角色方块的**输入侧中点**；两端用**同一个** `LayoutRoles` 算 ⇒ 严格共线 |
| 卡上的速率 / 投递 / 丢弃 | 绑定诊断（`BusByteRate` / `Delivered` / `DropTransport`），**UI 不自算** |
| 连接 / 停流状态 | 网络成员关系（`FindPortNetwork`），**不看绑定** |

**"看哪条线动了"的事仍然做不到**（同网络内 A→B 与 A→C 都亮）：这是 ADR-0050 已登记的已知局限（来源不进数据面），
`PortPairCount` 只是**如实报出**"这一对角色之间有几条口对投递"，不假装它是流量。

### 13.3 改动的文件（按层）
