# ADR-0051：兼容判定简化为「形状完全一致」——作废"接收 ⊇ 发送"子集判定与"尾部追加 = 兼容"

> 状态：**Accepted**（用户第三十轮裁定："**使用 B 宽范围。其他同意。**"）
>
> 修订对象：**ADR-0008 PQ-IF-04**（兼容判定 = 语义可匹配 + **接收契约 ⊇ 发送契约**）·
> **ADR-0046 D6 第二层**（同标识不同版本 → **尾部追加 = 兼容**）。
> 保留：D6 第三层（不同标识 = 框架无资格判定 ⇒ 默认不兼容 + 显式确认可强连）与 PQ-IF-05（不自动转换）。
>
> 回写：主文档 §5.4.1（兼容判定 + 三层判据 → **两层**）· §5.4.2（链路语义对照表第三行）· 修订表 **1.0.23**；
> 分册 `03` / `04` / `04a` / `16` / `17` / `18` 同步；ADR-0028 / 0037 / 0046 / 0050 局部标注修订。

---

## 1. 背景：一次实测暴露的缺口

用户问："不使用多源融合器、直接用网络标签连线也能运行——**这种情况下的链路融合规则是什么？是巧合还是确实正确？**"
取证（临时探针，用完即删）后，**除了语义澄清，还测到一个真实缺口**：

| 情形 | 实测结果 |
|---|---|
| 单源 **v1（12B）→ v2 接收口（16B，尾部追加）**，接收方**按自己的契约整块读** | `ArgumentException: 数据单元过小：布局需要 16 字节，实际 12 字节`；异常从**投递回调**逸出 ⇒ **该实例的投递循环整体退出**（再发一次毫无反应、计数不再增长），只留一条写着"**活动体**异常"的 Issue（文案不符）⇒ 现场表现为"**模块莫名不再收数**" |
| 同名标签把 **v1 与 v2 两个发布者**连到**同一个宿口** | 同上（同一口上混入两种长度） |

根因不是实现 bug，而是**规则本身**：旧判据"**接收契约 ⊇ 发送契约**"（形状子集）**允许接收方字段更多**，
于是**到达的数据报可能短于本口契约**——"能连上"与"能安全读"被规则分开了。

## 2. 用户裁定

> "你的版本兼容可能考虑的有些过了，对于这种'同一口混入**不同尺寸**的源'的问题，**直接拒绝建网即可**，
> 通常这种问题是有**大型非兼容版本调整**导致的，**无需考虑兼容**。"
>
> 追问范围后裁定：**"使用 B 宽范围。其他同意。"**

即：**不做"尺寸不同的直连兼容"**——连"接收方多带一个字段"也一并拒绝，让"能连"与"能读"重新成为同一件事。

## 3. 决定

### D1. 直连的唯一结构条件是「**形状完全一致**」

**传递语义一致 + 形状结构完全一致**：
字段**名称** / **原语种类** / **数组与字节块长度** / **字段顺序** / **字段数量** 全同（⇒ 尺寸必然相同）。

- **作废**"接收契约 ⊇ 发送契约"（子集判定）——**不再允许接收方字段更多**；
- **作废**"同标识不同版本 → 尾部追加 = 兼容"；
- 结构形状的相等判定必须**逐字段结构比较**（新增 `ContractShape.AreSame`）：
  这些形状是 record，但结构形状的字段集合在 record 默认相等里做的是**引用比较** ⇒
  直接写 `left == right` 会把"两个模块各自构造的同一形状"判成不同（隐形陷阱：只有引用同一静态实例才连得上）。

### D2. 类型身份与版本（保留 D2/D6 的其余部分）

| 情形 | 判定 |
|---|---|
| **双方都声明类型**：同标识 + 同版本 + 形状一致 | ✅ 兼容 |
| **同标识 + 不同版本** | ❌ **不兼容**（版本升级按**破坏性变更**处理）——请两侧升到同版本，或插入转换模块 |
| **不同标识** | ❌ **默认不兼容**（框架**无资格**判定二者是否同一种量）；用户**显式确认**后可强连，**此时仍要求形状完全一致** |
| **任一方未声明类型**（旧模块） | 只按**形状完全一致**判定（不再有子集判定） |

- 类型注册表本身**不变**：标识 / 版本 / 尺寸 / 传输语义 / 计量块 / 解码器（ADR-0046 D2）照旧声明与镜像；
- **版本号仍然要声明**——它现在表达"**换了版本就不再是同一种数据报**"，而不是"可自动兼容的演进"。

### D3. 明确保留

- **传递语义必须一致**（跨语义不判兼容；模块内部组帧）；
- **PQ-IF-05 不自动转换**：转换 = 用户显式插入转换模块；
- **方向**判定（两个发送口相接 = 连接存在但无数据流）不动；
- **多源**仍是合法一等组合（ADR-0050 不动）；逐 (源,宿) 对判定 ⇒ 形状不一致的那一路**只排除该对** + Issue，其余源照常；
- **读取纪律仍保留为防御**：`PayloadReader.TryCreate`（长度不足返回 false 不抛）与参考模块的防御式读取**不删**——
  新规则下"到达长度 = 本口契约尺寸"成了**不变量**，但防御式读取让"万一"不至于演变成"模块停摆"。

## 4. 这一改动买到了什么 / 付出了什么

**买到**：

1. **"能连" ⇒ "能安全读"**：不再存在"合法连接但接收方读不了"的状态——整类异常（含"模块莫名不再收数"）从源头消失；
2. **规则从三层降到一句话**：不需要向使用者解释"兼容 ≠ 能按自己契约读"；
3. **同一宿口上永不出现两种长度**：多发布者共用一个口时，形状不一致者被逐对排除。

**付出（明确记录）**：

1. "接收方多带字段"不再兼容 ⇒ 想把接收方做成"超集"的设计必须**两侧同版本**或**加转换模块**（转换模块是既有机制）；
2. 升级一个类型必须**同时改发布方与接收方**（或加转换模块）——按用户判断"大版本往往是破坏性调整"，这与现实相符；
3. 若干历史文档表述需同步（已在本 ADR 中列出并已回写）。

## 6. 验证计划（判据 → 测试）

| # | 判据 | 层 |
|---|---|---|
| 1 | 形状完全一致（含"各自独立构造的同一形状"）⇒ 兼容 | T1 |
| 2 | 形状不一致（尾部追加 / 缺字段 / 改类型 / **改顺序** / **同尺寸不同字段名**）⇒ **拒绝**且原因可读 | T2 |
| 3 | 同标识**不同版本**（形状相同）⇒ 拒绝，原因点明"版本不同" | T1 |
| 4 | 不同标识 ⇒ 默认拒绝；显式确认后放行（仍要求形状一致） | T1 |
| 5 | 未声明类型的旧模块 ⇒ 仅按形状一致判定 | T1 |
| 6 | 同名标签混入不同形状的源 ⇒ **只排除该 (源,宿) 对** + Issue；**同一宿口只出现一种长度** | T1 |
