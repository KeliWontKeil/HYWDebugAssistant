# ADR-0027 项目与解决方案结构（技术架构设计 第 2 章冻结）

> 状态：**Accepted**（用户逐条裁决，议程 ③ 第 2 章）
> 关联阶段：技术架构设计（选型后 · 实现前）
> 关联主文档章节：§3.4（装配链）、§11.2（模块供给）、§14.2（参考组合）
> 关联文档：`docs/architecture/02-project-structure.md`（全文）
> 关联 ADR：**ADR-0026**（分层与依赖方向 —— 本章是其物理落地）
> 取代：无 · 被取代：无
> 依据：顶层基线 v1.0 · ADR-0020（模块供给）· ADR-0023/0024（栈与库）· ADR-0025（工程约束）

## 问题

第 1 章（ADR-0026）冻结了七类逻辑层与依赖禁令，但层是逻辑概念：**一个层对应几个程序集、项目如何命名与组织、模块项目以什么形态存在、测试与参考组合放在哪里、既有工程骨架如何重组**均未确定。若不先定，第 3 章之后的 SDK 边界与机制归属将缺少物理坐标系，且工程无法按层禁令被机器检查。

## 背景

- 用户裁决：Q2-1 **层即程序集**；Q2-2 **单一 SDK 程序集**；Q2-3 参考模块放 **`src/`**；Q2-4 框架 UI **独立项目**；Q2-5 **建示例业务模块并随产品发布**（内容属 Gate E）。
- 约束：ADR-0026 的七层与依赖禁令必须可被架构测试执行；ADR-0025 要求中文注释、警告即错误、自研架构测试；现有工程基线（`Directory.Build.props`/CPM/`build.ps1`/许可门禁）须继续有效。
- 现状：`src/HYWDebugAssistant`（WinExe + Avalonia）同时承担 UI 与入口，尚无分层项目。

## 候选方案

### 程序集粒度
- **A1 层即程序集**：每层一个项目（+ 模块各自项目）。
- A2 关键层再拆：L4 拆为建网/持久化/Issue 等多个程序集。
- A3 细拆到机制：每个机制一个程序集。

### 契约面形态
- **B1 单一 SDK 程序集**：模块作者只引一个项目。
- B2 按关注点拆（契约/数据/上报）。
- B3 单程序集 + 内部命名空间（不物理拆）。

### 参考桩模块位置
- C1 `tests/` 下测试专用；**C2 `src/` 下参考模块**；C3 独立 `reference/` 目录。

### 框架 UI 归属
- **D1 独立项目**；D2 与产品 UI 同项目；D3 作为内置预装模块。

### 示例业务模块
- **E1 建且随产品发布**；E2 建但不发布；E3 不建。

## 最终选择

- **A1 + B1 + C2 + D1 + E1**，落地为九个框架/应用项目 + 模块项目 + 三个测试项目：

```text
src/  Sdk · Infrastructure · Hosting · DataPlane · Core · Core.Api · Ui · FrameworkUi · App
src/Modules/Reference/{DataGenerator,Recorder,Asserter} · src/Modules/<业务模块>
tests/ Tests · Tests.Reference · ArchitectureTests
```

- 唯一登记的依赖例外：**`App` 组合根**同时引用 `Core`（L4 内部）与 `Ui`/`FrameworkUi`（L5）——装配序（§3.4）要求先建 Core、再建 UI 并让 UI 引用 Core，该动作必须发生在两层共同的上层。
- 现有 `src/HYWDebugAssistant` 按"拆分并移除旧项目"重组（§2.4 顺序）。

## 选择理由

1. **A1**：层与程序集一一对应，使 ADR-0026 的禁令可直接按"项目引用"检查（而非跨命名空间推断），规则简单且不会漏检；编译时间与 `InternalsVisibleTo` 面最小。
2. **B1**：模块作者引用面最小且稳定（Q1-2「仅契约面」在包管理层面即可体现），避免作者为用一个契约而引多个包。
3. **C2**：参考桩模块与第三方模块**同构同路径**（同引用面、同加载方式），AC-1~AC-6 的实证才具备保真度；放 `tests/` 会使其享受测试程序集特权，削弱结论。
4. **D1**：§3.2 明确"框架自身 UI 不作为普通 Module"，独立项目使框架 UI 与产品 UI 的演化速率解耦，也避免把框架管理界面混入产品 Shell。
5. **E1**：v1 需真实业务闭环反馈（Gate E 定义具体模块），否则框架缺乏真场景检验；项目位置与发布方式先行固定，具体模块内容仍留 Gate E。

## 放弃方案

- **A2/A3（再拆）**：当前无证据表明需要更细程序集边界，反而增加项目间接口与友元扩散；若未来某机制确实需要独立边界，按 ADR-0026 增补层内项目即可（不违反本章）。
- **B2（拆 SDK）**：与"模块作者只引一个包"的体验目标冲突；命名空间已足以组织内部结构。
- **B3**：等价于 A1+B2 组合，未采用。
- **C1（tests/ 下桩模块）**：保真度不足（见选择理由 3）。
- **C3（独立 reference/）**：多一套归属约定而无额外收益。
- **D2（框架 UI 与产品 UI 同项目）**：边界模糊，违背 §3.2 的分离意图。
- **D3（框架 UI 作为内置预装模块）**：与 §11.2「内置=预装包，无结构特权」一致，但当前模块 SDK 与视图机制尚未定型（第 3/5 章），作为模块实现会引入未决依赖 → 记为未来可选演进方向，不在 v1 采用。
- **E2/E3**：无法提供真实业务反馈，v1 产品形态不完整。

## 影响

- **工程落地顺序**（本章不立即执行，待第 3–7 章设计完成后统一落地）：建 `Sdk`/`Infrastructure` → 建 `Hosting`/`DataPlane`/`Core`/`Core.Api` 空壳 → 拆分 `Ui`/`App` 并移除旧项目 → 更新架构测试规则集 → 加 `Modules/Reference/*` 与 `Tests.Reference`。
- **连带约束**：
  - **第 3 章**须确认"一个模块包是否可含多个模块"（C2-4 选择三独立项目，隐含"一模块一包"为默认形态）；
  - **第 6 章**须把 `App` 组合根白名单化，并加规则禁止 `App` 承载业务/机制逻辑；须按新命名扩展角色推断（`Sdk`/`Infrastructure`/`Hosting`/`DataPlane`/`Core.Api`/`FrameworkUi`）；
  - 命名（`Sdk` 等）此后变更须走 ADR。
- **对主文档**：不修改任何冻结结论；本章属实现层结构设计（Q0-2 边界内）。
