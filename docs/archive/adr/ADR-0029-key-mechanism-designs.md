# ADR-0029 关键机制技术方案（技术架构设计 第 4 章冻结）

> 状态：**Accepted**（用户逐条裁决，议程 ③ 第 4 章）
> 关联阶段：技术架构设计（选型后 · 实现前）
> 关联主文档章节：§6.2（ChangeSet 原子性）、§7.2/7.3（数据直通、增量重建、慢消费丢旧）、§8.4/8.5（生命周期与错误）、§9.2/9.3（持久化）、§13.1/13.2（数据实时性、可观测性）
> 关联文档：`docs/architecture/04-key-mechanisms.md`（全文）、`04a-execution-and-data-unit-analysis.md`（Q4-1/Q4-2 评估与延迟数据更正）
> 关联 ADR：ADR-0026（L3 不反向依赖、承载归 L3）· ADR-0028（C3-2/C3-3/C3-5/C3-6）· ADR-0012（护栏与重建单位）· ADR-0013（框架统一承载）· ADR-0022（口两态/严格单向）
> 取代：无 · 被取代：无

## 问题

基线冻结了七个机制的语义（ChangeSet 原子、增量重建单位、有界缓冲丢旧、数据直通不经 Core、直接绑定、Issue 模型、持久化重锚），但未确定其**技术结构**：线程与队列如何布置、数据单元在内存中如何表示、绑定如何执行、缓冲与丢弃如何实现、ChangeSet 如何做到"整体拒绝"、重建差异如何计算、Issue 与诊断如何采集与分发。

## 背景

- 用户裁决（本章）：Q4-1 **每模块绑定一个框架分配的线程 + 有界输入队列**（核心理由："让模块开发者专注界面与功能实现，而不是自己设计框架级数据调度与线程调度"；活跃模块数量级 = 数十）；Q4-2 **扁平存储 + 加载期特化访问**；Q4-3 **绑定对象**；Q4-4 **模块写订阅缓冲、UI 节拍读**；Q4-5 **允许阻塞（线程归模块使用）**。
- 第 3 章硬约束：C3-2 承载模块自发活动、C3-3 配置未知字段片段保留、C3-5 定长契约、C3-6 需抽样/环形缓冲/刷新节流。
- 对延迟估算的复核结论（`04a` §7）：稳态投递成本为**百纳秒级**；微秒级仅出现在空闲后唤醒的低频路径，且 Windows 可用自旋+事件混合策略收敛。数值由 Gate B 实测（用户已接受"结构先定、数值实测回写"）。

## 最终选择（七机制要点）

1. **执行与承载**：每 `Active` 实例 = 1 个 L3 分配的专属线程 + **每 (实例, 口) 一条**有界输入队列 + 停止信号 + N 个订阅缓冲；`Registered` 不占线程，`Disabled` 保留线程并停流，`Removed` 请求退出→有界等待→回收。模块活动体**允许阻塞**、不得自建线程。〔**局部修订 · ADR-0050 Q2（2026-09 落地）**：队列粒度由"1 个"改为"每口一条"——消除跨口队头阻塞；**线程模型与投递语义不变**〕
2. **停止协议**：停止信号 + 有界等待（默认值可配置）；超时**不强杀**（.NET 无安全中止），记 Issue + 标记孤儿线程（诚实边界）。
3. **异常边界**：活动体入口整体包裹 → Issue + 该模块活动停止；钩子逐个包裹；上报 API 内部不抛；框架自身代码不捕获。
4. **数据单元**：池化定长扁平缓冲（契约字段，无框架元信息）+ 加载期生成的形状元数据（字段偏移表）与强类型访问器；兼容判定用偏移表计算。
5. **绑定与投递**：绑定对象（源/目标列表/契约引用/诊断计数/状态）；1:N = 写多个目标队列；投递全程在 L3，L4 只增删绑定（不可变快照 + 原子替换）。
6. **有界缓冲与丢弃**：**每 (实例, 口) 一条**输入队列（〔**局部修订 · ADR-0050 Q2**〕 原为"每实例一个"），容量按口计、固定默认值 + 可配置；默认**丢最旧保最新**（或按口声明丢新/背压）；**绝不阻塞发送方**。
7. **UI 交接**：单值/状态 = 最新值槽；流数据 = 环形订阅缓冲（满则丢旧）；抽样在 UI 侧；UI 一律经 `Core.Api` 读取，从不调用模块代码。
8. **ChangeSet**：两阶段 **Prepare（可失败、零副作用）→ Commit（无失败点、先加后减）**；变更入口串行化；无全局锁、无自动回滚补偿。
9. **增量重建**：声明集 vs 绑定集 diff；单位为绑定及其邻接数据面；模块实例/配置/业务状态保留；悬空态 + Issue。
10. **持久化**：文本 JSON + 源生成 + `schemaVersion`；未知字段**片段保留 + 合并写回**（AC-4）；临时文件 + `File.Replace` 原子写；加载 = 实例化 → 恢复配置 → 重建成员 → 按 `实例ID.口名` 重锚；不可解析则拒绝并保护原文件。
11. **Issue 与可观测性**：Issue 中心（归属对象 + 类别 + 来源，两条语义）；无锁并发队列汇集；L1–L4 采集点（含每绑定/每队列的投递数、丢弃数、最后数据时间、队列深度）。
12. **护栏（对 ADR-0012 R3 的具体化）**：**不做速率上限、不做环/自连检测、不做阻断、不给数据单元加跳数元信息**；护栏 = ①**安全护栏**（线程/内存安全、缓冲满丢旧、池化缓冲边界与归还保护；静默、快速、无热路径分支开销）+ ②**轻量提示**（"缓冲持续为满""处理速度跟不上输入""线程占用偏高""未在期限内停止"等事实陈述；可见但不打扰、不预设问题场景、由用户自行判断）。

## 选择理由

1. **Q4-1 方案**同时满足"模块作者零调度负担""隔离性最强""与 ADR-0013 相容（线程由框架分配而非模块自建）"；在活跃模块为数十的量级下，线程数增长不构成约束；若未来出现数百活跃模块，可演进为"逻辑队列 + 池化消费"而**投递语义不变**。
2. **Q4-5 允许阻塞**：线程本就是模块自己的，阻塞只影响自己——这使模块可以写"读硬件→处理→投递"的同步循环，**不需要异步化改造**，直接服务"快速开发"的目标。
3. **Q4-2/Q4-3 组合**：存储层类型擦除（框架通用性）+ 访问层加载期特化（零反射、强类型体验）+ 绑定对象（编排与诊断）——三者正交，分别解决通用性、性能、可管理性。
4. **C4-1 护栏简化**：限流与环检测**无用户可见收益**，只会限制使用、增加实现与调试负担；用户真正需要的是"不崩、数据在传、不卡顿"以及**可见的事实**。因此护栏收敛为"安全 + 提示"，且提示不替用户下判断。
5. **两阶段 ChangeSet**：把"可能失败的一切"前置到无副作用的 Prepare，使 Commit 真正无失败点，从而"整体拒绝"可严格实现（而非依赖回滚）。

## 放弃方案

- **池化消费（D）／拓扑分区（C）／统一投递 + 同线程快路径**：用户裁决采用每模块线程方案；C/D 作为**未来演进路径**保留（投递语义不变，故保留成本低）。
- **单线程串行（A）**：单模块阻塞即影响全局，隔离性不足。
- **引用类型数据单元／纯字节解释（不生成访问器）**：前者分配压力抵消零分配设计；后者牺牲模块作者的强类型体验。
- **绑定数组/函数指针式投递**：动态增删与诊断计数需要编排层，纯函数指针式会把这些散落到别处。
- **UI 推送模型（②以外的选项）／UI 直读模块**：与"UI 慢不阻塞数据面"（§13.1）及 Q1-4/C1-3 冲突。
- **速率上限 / 环检测 / 阻断式护栏 / 数据单元跳数元信息**：无可见收益、限制使用、且跳数元信息违反 §5.4.2（已由 C4-1 明确排除）。
- **强制卸载程序集以终止超时模块**：.NET 无安全中止，可能导致进程崩溃（C4-2 排除）。
- **自动回滚补偿**：与 §8.5"框架不自动重试/降级/阻断、天然隔离 + 显式恢复"冲突。

## 影响

- **对第 5 章**：UI 侧渲染数据来自"最新值槽 / 环形订阅缓冲"；UI 一律经 `Core.Api`；抽样在 UI 侧；18 元素 + 4 容器的渲染方式据此设计。
- **对第 6 章**：T1 参考组合需覆盖——多模块线程下的投递正确性、丢弃计数、停止协议超时路径、ChangeSet 整体拒绝零副作用、AC-4 片段保留、异常不逸出边界。
- **对 Gate B**：`04a` §5 的实测清单（投递延迟、唤醒延迟、端到端、分配字节数、吞吐、10⁶/s 下丢弃率与 GC、多线程内存、池归还断言开销）在框架骨架可运行后执行并回写。
- **新暴露的设计缺口**：**应用级设置（Settings）模型缺失**（基线只定义 Configuration 与 Layout，未定义"不随组合件、属应用/用户级"的偏好）；由此第 4 章中"停止超时""队列容量"等可配置参数的**归属暂挂**，需作为补遗议题裁决（`04-key-mechanisms.md` §4.12 的 S-1~S-4）。
- **对主文档**：已将 §7.3 护栏口径（收窄为"安全 + 提示"）、§7.3 线程模型（改述为"不自建、不直接管理线程"）、§7.3 慢消费者（v1 不做背压）回写主文档，修订记录登记为 1.0.3；其中护栏具体化属对 ADR-0012 R3 的实现层细化。
