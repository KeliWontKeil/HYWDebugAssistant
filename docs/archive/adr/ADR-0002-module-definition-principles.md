# ADR-0002 Module Definition 原则（发布物 / 同形 / Gate）

> 状态：Accepted（用户裁决，批次 1）
> 关联批次：批次 1（原则部分）；清单/机制部分关联批次 8
> 关联主文档章节：§4.4、§11（Plugin/扩展）、术语表
> 取代：无 · 被取代：无

## 问题

Module Definition 的定位与供给方式（PQ-DM-06 及相关）：Definition 是什么性质的物？内置模块与外部模块是什么关系？（早期候选把"内置模块预注册、与插件同形"当作实现细节，用户要求将其提升为原则并慎重处理内置清单。）

## 背景

- 已冻结：P3（Module 是基本功能单元）、P15（Plugin 是 Module 的供给机制而非产品概念）、AC-1（新模块 Core 零改动接入）、E5（Plugin ≠ DLL）。
- 用户评审意见：
  1. 抽象的接口/协议必须作为**发布物**；用户不应修改、不应感知底层，只面对**唯一、不可变的接口标准**。
  2. 内置模块需慎重、保留决策；除系统默认内置模块外，模块可能以"后期可外部加载"方式接入，或由脚本/编码定义（类比：游戏 mod 对游戏内容的拓展）。
  3. **无论何种接入方式，系统内置模块与外部可加载模块必须在设计上同形**（同一 Definition/接入模型，仅来源不同）。

## 候选方案

### 方案 A（采纳）：Definition = 不可变发布物 + 全模块同形 + 内置清单 Gate

1. Module Definition 是模块提供者发布的**不可变能力发布物**，携带唯一、不可变的接口标准（Interface 契约声明）；注册于 Core 内 Module Registry 后可供实例化。
2. **用户不可修改 Definition**：只可在 Instance 上做配置；用户不感知底层实现（语言/进程/脚本与否）。
3. **同形原则**：系统内置模块与外部可加载模块（mod）共用同一 Definition 模型与接入契约，仅来源不同（内置随主程序 / 外部经加载机制）。
4. 内置模块**具体清单**与加载/接入机制（进程内加载、脚本定义等）**保留决策，Gate：批次 8**；本轮只冻结 Registry/Definition 结构原则。

### 方案 B：Definition 可随工程文件保存（文档内定义）

与"唯一不可变发布物"冲突（能力随工程漂移、无全局唯一标准），否决。

### 方案 C：内置模块由 Core 硬编码、不走 Registry

违反 AC-1/P1/P15 与同形原则，否决。

## 最终选择

方案 A。

## 选择理由

1. "唯一不可变接口标准发布物"保证契约稳定性：用户与第三方模块都面对同一标准，Core 不必理解实现。
2. 同形原则使"新增外部模块"与"内置"成本一致，直接支撑 AC-1；mod 类比给出清晰的扩展心智。
3. 内置清单与加载机制推迟（Gate 批次 8）符合推进阈值 §16.4：结构决策（Registry/Definition/同形）先冻结，机制细节后置。

## 放弃方案

- B、C 如上（漂移 / 违反不变式与 AC-1）。

## 影响

- PQ-DM-06（Registry 定位）关闭；PQ-DM-01（Definition 最小组成清单）仍需在批次 1 内逐项裁决（以 A 为前提）。
- §4.4、§4.2 对象图、术语表（Module Definition/Module Registry）更新；§11（Plugin）以同形原则为前提，Gate 项不变。
