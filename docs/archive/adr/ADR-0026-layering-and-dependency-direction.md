# ADR-0026 分层与依赖方向（技术架构设计 第 1 章冻结）

> 状态：**Accepted**（用户逐条裁决，议程 ③ 第 1 章）
> 关联阶段：技术架构设计（选型后 · 实现前）
> 关联主文档章节：§3.1/§3.2.1/§3.3.1（系统级结构与职责三分）、§7.2（数据直通）、§13.1（数据实时性 > UI）
> 关联文档：`docs/architecture/01-layering-and-dependencies.md`（全文）、`docs/architecture/00-architecture-outline.md`（提纲）
> 取代：无 · 被取代：无
> 依据：顶层基线 v1.0 · ADR-0001（域重构）· ADR-0003（职责三分）· ADR-0013（并发与资源）· ADR-0023/0024（栈与库）· ADR-0025（工程约束）

## 问题

顶层基线冻结了"表现层 / 语义层分离"（§3.2.1）、"Core 职责三分"（§3.3.1）、"Core 不中转业务数据"（§7.2/P2）、"数据面绝不被 UI 阻塞"（§13.1）、"框架统一承载活动"（ADR-0013）等结论，但**未确定这些结论在技术结构上的载体**：程序集如何分层、依赖箭头指向何方、每层能放什么与禁止放什么、这些不变式靠什么机制在实现中不被破坏。若不先定分层与依赖方向，项目结构、SDK 形态、数据面实现与 UI 架构均无依据。

## 背景

- 议程 ③ 的议事顺序把本章置于首位：分层是**支点**，其余六章由其推导（提纲 §0.4）。
- 用户裁决的前置问题（议程 ③ P0）：Q0-2 架构设计仅允许引入**实现层结构概念**（领域概念走 ADR）；Q1-1 分层**按运行时角色**切；Q1-2 模块实现**仅可见契约面**；Q1-3 数据面**独立成层（独立程序集）**；Q1-4 UI **仅可见契约面 + 公开查询 API**。
- 约束来源：P1/P2/P12/P16/P17、E1–E8 反模式、AC-1/AC-2/AC-5、ADR-0025（自研架构测试为唯一的机器执行手段）。

## 候选方案

### 方案 A：按变化率/稳定性分层（表现 / 语义 / 契约 / 基础设施）
- 优点：与 §3.2.1 的分离思想同构，稳定性导向，长期演化友好。
- 缺点：与基线 §3 的运行时结构图不是同构映射，需要额外建立"角色→层"的对应关系；数据面/宿主这类运行时角色无自然归属。

### 方案 B：按运行时角色分层（UI / Core / 模块宿主 / 数据面 / 契约）
- 优点：与基线 §3.1/§3.3 结构直接对应；每个层的**职责与运行时角色一致**，禁令可按角色表述（如"数据面不依赖管理面"）；便于把 AC/不变式转成机器可查的依赖规则。
- 缺点：跨角色的中性技术能力（日志/序列化/诊断）需单列一类。

### 方案 C：两者组合（变化率为主、角色为辅）
- 优点：表达力最强，能同时表达"稳定性"和"运行时角色"。
- 缺点：跨维度归属需逐类型判定，规则集复杂、争议面大。

## 最终选择

**方案 B：按运行时角色分层**，并落地为七类层与一组依赖禁令：

| 层 | 名称 | 角色 |
|---|---|---|
| L1 | 契约层（Contracts / SDK） | 模块作者与 UI 共同依赖的稳定抽象面（零框架依赖） |
| L2 | 模块宿主层（Hosting） | 包发现/加载/校验/注册、实例世界、框架侧生命周期状态机 |
| L3 | 数据面层（DataPlane） | 绑定执行、投递、有界缓冲与丢弃、**模块活动的承载与调度**、流量诊断计数 |
| L4 | 核心管理面（Core） | Composition 解释与校验、ChangeSet 原子应用、增量重建、持久化、Issue 中心 |
| L5 | UI 构成层（Shell / App） | 主窗口、模块区宿主、视觉层、口上标记渲染、管理视图 |
| L6 | 模块实现 | 业务功能单元（非框架组成部分） |
| L0 | 横切支撑 | 日志 sink、序列化、配置读写、诊断等中性技术能力 |

依赖链（唯一允许方向）：`L6→L1` · `L2→{L1,L0}` · `L3→{L1,L0}` · `L4→{L1,L2,L3,L0}` · `Core.Api→L1` · `L5→{L1,Core.Api}`。**L3 数据面没有任何指向 L2/L4/L5 的依赖。**

## 选择理由

1. **不变式变成结构事实**：L3 不依赖 L4/L5 ⇒"Core 中转数据""UI 参与投递"在结构上无法成立；L6 只依赖 L1 ⇒ 模块无法自建活动载体、无法引用另一模块、无法引用 UI 框架。
2. **与基线同构**：§3.1 的结构图、§3.3 的 Core 三段职责、§7.2 的直通通路在层图上直接可读，减少转译损失（P17：技术实现不反向决定架构）。
3. **可机器执行**：禁令可按"项目角色 + 引用关系"表述，由 ADR-0025 的自研架构测试直接检查（第 6 章重写规则集）。
4. **AC-1/AC-5 可判定**：新增模块只引 L1 ⇒"新增模块不修改 Core"在依赖图层面可判定。

## 放弃方案

- **方案 A（变化率）**：与基线结构非同一坐标系，需额外映射，且数据面/宿主无自然归属 → 未采纳为分层主依据（其"稳定性"思想仍体现在 L1 的零依赖要求上）。
- **方案 C（组合）**：规则复杂度与逐类型归属争议成本高于收益 → 未采纳。
- **合并 L2 入 L4**：宿主与管理面职责不同（实例存在 vs 拓扑与变更），合并会使"数据面只与宿主交互"的边界模糊 → 未采纳。
- **拆分 L3（投递与调度分两层）**：调度与投递共享同一活动承载语义，拆开需额外跨层接口 → 未采纳。
- **契约层分面（允许模块依赖 UI 框架）**：会打破 L1 的零框架依赖，并削弱 E4（Module=Window）防线 → 未采纳；模块视图改为**由框架按声明渲染**（连带收窄第 3/5 章选项）。
- **L0 允许 L1/L5 引用**：会使契约层携带框架依赖、UI 与框架能力耦合 → 未采纳。
- **公开面用 L4 程序集 `public` 面**：L4 内部类型对 UI 仍可见，解耦强度不足 → 未采纳独立 `Core.Api` 方案。

## 影响

- **层清单与依赖禁令成为后续五章的上位约束**（第 2 章项目划分、第 3 章 SDK 边界、第 4 章机制归属、第 5 章 UI 边界、第 6 章规则集）。
- **连带收窄**（必须遵守）：
  - Q3-7（模块视图提供方式）→ 模块**不得提供 View 类型**，只能由框架按声明渲染；
  - Q5-3（视图与状态绑定方式）→ 不得要求模块引用 Avalonia；
  - 第 2 章须为 `Core.Api` 单列项目；
  - 第 6 章须按七层重写 A1–A6 规则集（补齐 L3/L0/Core.Api 角色与"跳过 vs 失败"语义）。
- **对主文档**：已将 §10.4「模块视图自备」收窄为**"框架按模块声明渲染"**（模块不得提供 View 类型、不依赖 UI 框架；本章 C1-3 的连带收窄，SDK 侧形态见 ADR-0028）；§3.1/§3.2.1/§3.3.1（系统结构与职责三分）、§7.2（数据直通）、§13.1（数据实时性 > UI）的既有表述未改写（本章属实现层结构设计，符合 Q0-2 的边界），修订记录登记为 1.0.3。
- 现有项目 `src/HYWDebugAssistant` 与 `tests/*.ArchitectureTests` 将按本章调整（第 2 章给出项目清单）。
