## 3. 角色模型（**R1–R10**）

### R1. 定义：**数据角色 = (方向 × 数据类型身份)**，在**模块内聚合** 〔**已由 ADR-0052 修订（见下方 R1-修）**〕

- **发送角色**：本模块**所有同类型**的发送口构成的"生产这种数据"的角色；
- **接收角色**：本模块**所有同类型**的接收口构成的"消费这种数据"的角色；
- 一个角色**可以有多个口**（例如 8 通道记录器 = 8 个同类型接收口 = **1 个接收角色**，其下挂 8 个口标记）。

⇒ 角色是**模块自身**的属性（"我生产/消费什么"），**与对端是谁无关**；对端只在"角色对"里出现（R6）。

> **R1-修（ADR-0052 · 用户第三十三轮裁定，已落地）**：角色**不再由框架派生**，改为**模块声明的「功能分块」**：
> **角色 = 1 种数据类型 + 输入口/输出口集合**（通常 1 入 1 出；融合块 = 2 入 1 出，**口数不设上限**），
> **一个方块同时可有两侧**（左入右出），不再因方向拆成"发送角色/接收角色"两个方块。
> 理由：**功能分解是设计信息，框架推不出来**——派生模型只能给出"方向 × 类型"的机械组合，
> 会把多源融合器画成"一收一发两块"（看起来像两进两出的转发器）。
> **仍然保留的**：R2（类型身份不得用呈现文本）· R4（零数据口 ⇒ 不画方块）· R6/R7（角色对级聚合、条数）· **R9（只呈现，不进组合件）** · R10（Core 算、UI 只画）。
> **被取代的**：R3 的"纯派生"（改为**声明式**，且**不做回退**——未声明角色 ⇒ 不画方块 + 提示补声明，框架**不发明角色**）；
> 呈现口径 `N 口 · M 连` → **`m/n` = 输入/输出侧连接的**对端角色数**（无该侧 ⇒ `--`；有口未连 ⇒ `0`）。

### R2. 类型身份用**类型身份**，不用呈现文本

角色键的类型部分 = **已声明类型**：`(TypeId, Version)`；**未声明类型**（旧模块）：契约形状的**结构描述**（`ContractShape.Describe()`，即现有 `ContractText`）。

- **为什么不能用 `ContractText` 一律代替**：`f32` 这个文本对"声明了 `hyw/f32@1`"与"声明了 `acme/gain@2` 但形状同为 f32"是**同一个文本**，
  而 ADR-0051 明确二者**不是同一种量**（不同标识默认不兼容）⇒ 用文本会把两种角色**错误合并**。
- 反向也安全：**同标识同版本 ⇒ 形状必然一致**（ADR-0051 要求两侧镜像一致），故角色键稳定。

### R3. **纯派生**（v1 不引入任何"角色声明"） 〔**已由 ADR-0052 取代：改为模块声明；不做回退**〕

角色**完全由端口 + 类型派生**，框架与模块都**不额外声明角色**。

- 依据：`architecture/17` §4 已定"数据角色 = 端口 + 类型**派生**"；主文档 §6.2"**不引入业务分类**"。
- 登记为**未来可选扩展**（不实现、不预留字段）：模块可**声明"把若干同类型口归为一组"**用于呈现分组——
  即使将来做，也**只能影响呈现**，**不得参与任何框架判定**（"可声明 ≠ 可判定"）。
- 〔**ADR-0049 D13 局部扩展（用户第三十一轮）**〕**角色身份仍然纯派生不变**；另增一个**不同的东西**：
  模块可**声明"内部处理关系（接收口 → 发送口）"**（`DeclareFlow`），用于叠加层画**模块内部的角色→角色线**
  （用户："该关联与底层通信网络拓扑无关，属于模块自身配置/属性的一部分"）。
  它**不是角色声明**（不改变角色的合并规则），且同样**只呈现、不参与任何判定**；**零声明 ⇒ 不画**（不猜）。

### R4. **零口回退**：没有数据口 ⇒ **没有角色**，不画任何角色方块

模块无口（纯 UI/控制模块、占位实例）时，角色集合为**空**：叠加层**不画方块**，信息区照常显示并写明"**无数据口**"。

- **不算错误状态**（无 UI 模块合法、占位实例合法）。
- 不画"空角色"占位方块——避免给出"它好像在传数据"的错觉。

### R5. 角色的**状态**不单独着色

角色方块**不带状态色**（不区分停流/悬空/未连）。状态由**端口标记**（已有：灯/悬空）与**线**（停流）表达。

- 理由：同一事实**只在一处表达**（LESSONS：同一事实两处显示必然漂移）；角色方块只表达**身份**（方向 + 类型）。

### R6. **角色对**与**角色对级聚合**

- **角色对** = （本端角色，**对端角色**）——方向由"本端发送 ↔ 对端接收"隐含，不需额外字段；
- **一条角色对 = 一条线**：把**所有**落在同一角色对上的连接（可能来自**多条网络**、**多个口**）**聚合**为一条；
- 聚合后**必须标出条数**（如 `×2`）：条数 = 该角色对下的**连接数**（按 (本端口, 对端口) 计）；条数 = 1 时不显示；
- **多源网络**（ADR-0050）：对端有多个**不同模块**的源 ⇒ 是不同的**对端角色** ⇒ **各自一条线**（这正好满足"叠加层多生产者"）；
  若对端的多个源**同属一个角色**（同一模块的多个同类型发送口）⇒ 聚合为一条线 + `×N`。

### R7. 线的**几何规则不变**（沿用 ADR-0045，仅起点与聚合粒度变化）

- 起点：**本端角色方块**中心（不再是"该类型方块"，因为方块现在含方向）；
- 终点：**窗口边界**上该口所在边带（**不做跨窗口覆盖窗**，ADR-0034）；两窗拼接时因**两侧同一规则** ⇒ 线在公共边**自然相接**；
- 对端**不在现场/未拼接** ⇒ 朝方位 + 末端淡出 + 标对端 `实例.口名`（ADR-0045 现状保留）；
- 未连接的口：仍画**短虚线残段 + `未连`**（它**有角色**，只是没连）。

### R8. **功能角色**边界（不进叠加层）

| | 功能角色 | 数据角色 |
|---|---|---|
| 是什么 | 这个模块**是什么、干什么、怎么用** | 这个模块**怎么处理数据**（几种、进出关系） |
| 来源 | 模块（`DisplayName`/`Description`/`Tags` 已足够） | **派生**（R1–R3） |
| 显示在 | **模块清单页 · 模块自己的窗口/帮助** | **叠加层 · 拓扑诊断** |
| 框架是否分类 | **否**（自由文本；§6.2 不引入业务分类） | 不适用（派生量，无业务语义） |

**v1 不新增"功能角色类型"字段**（如 `ModuleRole.Source/Sink/Processor` 枚举）——那等于框架定义业务分类，与 §6.2 冲突。

### R9. 角色**不参与任何判定**（红线，重申 ADR-0046 §4/D3）

不参与：建网（标签/几何）· 契约兼容（ADR-0051）· 停流/悬空 · 投递与队列 · 计量归属 · 持久化（**角色不入组合件**）。

### R10. 角色在**哪里算**：Core 算，`Core.Api` 暴露，UI 只画

- **为什么**：R2 的"类型身份"判定必须与**兼容判定同源**（`ContractShape.AreSame` + 类型注册表）；若让 UI 自行派生，UI 就得复制一套"什么算同一种类型"的逻辑 ⇒ **必然漂移**；
- 形态：`IRuntimeQuery` 新增（**只增不改**）
  - `IReadOnlyList<DataRoleView> GetDataRoles(string instanceId)` —— 该实例的**角色**列表：`Key`（稳定身份键）· `IsSend` · `TypeKey`（标识@版本 / 结构描述）· `TypeText`（呈现文本）· `Ports`（该角色下的口名）· `ConnectionCount`；
  - `IReadOnlyList<DataRolePairView> GetRolePairs(string instanceId)` —— 该实例参与的角色对：`LocalRoleKey` · `PeerInstanceId` · `PeerRoleKey` · `Count` · `NetworkKeys`；
- `PortView` 增 **`TypeKey`**（只增可选字段；`ContractText` 保留为呈现文本）；
- UI 侧：`ModuleWindowsViewModel` 把角色对喂给 `ConnectionOverlay`（替代当前"按类型方块 + 按口线"）。

## 8. 落地结果（实测取证）

**用例**：`tests/HYWDebugAssistant.Tests/DataRoleModelTests.cs` —— 判据 1–9 **一条一例**（9/9 通过）；
派生实现 `Core/Services/DataRoleModel.cs`（纯函数）+ `RuntimeServices.GetDataRoles/GetRolePairs`（经 `ModuleRuntime.DescribePortTypeKey`/`DescribePortLinks` 复用**同一**兼容判定，故与绑定不会漂移）。

**实现要点（与设计一致的落点）**：

| 项 | 落点 |
|---|---|
| 类型身份 | `ModuleRuntime.DescribePortTypeKey`：已声明 ⇒ `标识@v版本`；未声明/引用不可解析 ⇒ `ContractShape.Describe()`（**不得**用呈现文本代替，否则"不同标识同形状"会被合并） |
| 角色聚合与稳定序 | `DataRoleModel.Collect`：按 `send:{TypeKey}`/`recv:{TypeKey}` 归并，**发送在前 + 类型键字典序** |
| 口级连接 | `ModuleRuntime.DescribePortLinks`：**网络声明 + 逐对兼容**（停流网络的成员关系照样呈现），与 `RebuildBindingsCore` 同一 `CheckCompatibility` |
| 角色对聚合 | 键 =（本端角色, 对端实例, 对端角色）⇒ 跨网络/跨口聚合出一条 + `Count` + `NetworkKeys`（去重有序） |

**落地期实测到的两个问题（都已处置）**：

1. **`GetRolePairs` 条数恒为 0**（已修）：字典存的是**值元组**，`entry.Count++` 改的是**取出的副本**；
   同一条目里的 `Networks` 是 `List`（引用）所以"看起来生效"，掩盖了计数丢失。修法 = 累加后**写回** `pairs[key]`。
   ⇒ 教训入 `LESSONS.md`（第 56 条）；用例 6/7/8 正是靠"条数"判据把它抓出来的。
2. **`PortInstance.IsConnected` 是"悬空的第二事实源"**（**已按用户裁定整体删除**）：
   该字段**既无写入方、也无读取方**（恒为 `false`）——运行时从不置位；UI 读的是**另一个**字段
   `PortView.IsConnected`（`RuntimeServices.IsPortConnected`：按**绑定/网络成员关系**派生，**正确且在用**），
   UI 另在 `ModuleWindowsViewModel` 里直接按 `GetNetworks()` 成员关系判定连通。它**不是** P3 引入的问题，
   P3 也没用它（判据 8 改用"两口各自真实投递 + 网络数 + 连接数"取证）。
   **处置（用户第三十一轮裁定"整体删除该字段"）**：删除 `PortInstance.IsConnected`（Hosting）与该字段
   **唯一**一条断言（`HostingLifecycleTests`）；连接状态的**唯一来源** = **网络成员关系**。
   **由此暴露的同类问题（列为待裁定项，未擅自改语义）**：① `PortInstance.IsStalled` 同样**无写入方**（恒 `false`），
   却被**读进** `PortView.IsStalled` → UI 标记 ⇒ 与 `IsConnected` 是同一类缺陷；② `PortView.IsConnected`
   走**绑定**、UI 走**网络**，对**停流网络**（停流不建绑定）两者会给出不同答案。
   处置建议见 `docs/roadmap.md` v1.59 的待裁定项。
