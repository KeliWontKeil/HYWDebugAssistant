# 15. 吸附与锚定整改方案（用户第十二轮反馈 · **待裁决**）

> 状态：**方案待用户裁决（未实现）**　依据：用户实测报告 + 代码证据 + 一次数值实验（详见 §2.1）
> 范围：**吸附（SnapEngine）· 外壳锚定与跟随（FollowShellMove）· 几何坐标系与像素量化（ModuleWindowManager / ModuleWindowsViewModel）**
> 不在范围内：建网判定（`DockRule`，ADR-0037，判定口径不变）· 端口标记视觉（ADR-0039）· 组合件布局格式（不变）

## 2. 根因（逐条给证据，不猜）

### 2.1 U-1 吸附振荡：**同一轴上多个候选同时落在容差内，且没有粘滞（hysteresis）**

**代码证据**
- `SnapEngine.Snap` → `FindBest`：每个轴一次性生成 5 类候选（左右贴合 ×2、左/右/中心对齐 ×3，`SnapEngine.cs:302-324`），
  选出唯一的赢家，规则只有两条：**贴合优先于对齐**、**同级取 |Δ| 最小**（`SnapEngine.cs:258-267`）；**没有进入/释放两个阈值，也不记住上一次命中谁**。
- 容差 `DefaultTolerance = 8`（`SnapEngine.cs:38`），而指针在屏幕上是**整数像素**——1px 的抖动即可改变"谁 |Δ| 更小"。

**数值实验（临时测试，已跑过并删除；几何：邻居 320×200 @ (1000,400)，被拖模块 330×220，X 已贴合）**

| 指针 rawY | 386 | 387 | … | 394 | **395** | 396 | … | 408 | 409 |
|---|---|---|---|---|---|---|---|---|---|
| 模块 snappedY | 390 | 390 | … | 390 | **400** | 400 | … | 400 | 409 |
| Δ（模块 − 指针） | +4 | +3 | … | −4 | **+5** | +4 | … | −8 | 0 |

- 在 `rawY 394 → 395`（指针**只动 1px**）时，模块从 390 **跳到 400（+10px）**；反向移动时同样 10px 回跳。
- 在 `[386,408]` 这 23px 区间内，模块**始终处于吸附态**（Δ≠0），只在 380/390/400 三个位置之间台阶式跳——**它不跟随指针**。
- **10px 这个数**= 两个模块尺寸差的一半（220−200=20 → 中心对齐与边缘对齐相差 10px）。**这正对应"标签接近中心线时"**：两模块中心线接近时，"中心对齐"与"边缘对齐"两个候选只差几个像素，同时落入 8px 容差，赢家随 1px 抖动来回切换 ⇒ **振荡**。

**次生缺陷（同一根因，须一并修）**
- `SnapEngine.Snap` 的贴合候选**不要求交叉轴重叠**：`XCandidates` 无条件产出"右边缘贴左边缘"候选（`SnapEngine.cs:304`），
  而"是否拼成一组"用的 `AreJoined` **要求重叠**（`SnapEngine.cs:146-153`）——两处口径不一致。
  实测：两模块竖直相距 **1400px**（完全无重叠）仍被 X 吸附走 3px，并生成一条 **1844px 长的参考线**（388..2232）。这既"莫名其妙被吸走"，又"线画得离谱"。

### 2.2 U-2 "拉脱"：锚定判定**用的是移动之后的外壳矩形**——只要单次位移 > 2px 就永久脱开

**代码证据（三步推导，可复核）**
1. `ModuleWindowManager.OnShellMoved()`（`ModuleWindowManager.cs:267-279`）：先记 `previous = ShellRect` → **`PublishShellRect()` 把 `ShellRect` 更新为新位置** → 再调 `FollowShellMove(dx, dy)`。
2. `ModuleWindowsViewModel.FollowShellMove`（`ModuleWindowsViewModel.cs:421-428`）的锚定条件是
   `Math.Abs(m.Rect.Left - shell.Right) <= 2` —— 此处 `shell` 已是**新的** ShellRect，而模块 `m` **还在旧位置**（还没被移动）。
3. 设模块原本严丝合缝贴着外壳：`m.Left == 旧 shell.Right`，于是
   **gap = |m.Left − 新 shell.Right| = |dx|** ⇒ 判定退化为 **"本次外壳位移 ≤ 2px 才跟随"**。

**推论（与用户描述完全吻合）**
- 慢速拖动：每个 `PositionChanged` 的位移 1–2px ⇒ 跟随正常；
- **快速拖动**：单个事件位移 10–40px ⇒ gap > 2 ⇒ **不跟随**；下一次事件里模块与外壳的差距更大 ⇒ **永远不会重新锚定** ⇒ 表现为"**被拉脱**"（且是永久性的，直到用户手动拖回去）。

**放大器**：`FollowShellMove` 末尾**每个事件都提交一次 `UpdateModuleLayouts`**（`ModuleWindowsViewModel.cs:457`）→ 拖动中每秒几十次变更提交 → 外壳拖动本身卡顿 → OS 合并鼠标消息 → **单次位移更大** ⇒ 更容易触发脱开。即"加速度越大越容易拉脱"存在**自增强**链路。

### 2.3 U-3/U-4 缝与像素级错位：**模型存小数物理像素，窗口只能落在整数物理像素，两处各自取整**

**代码证据**
- 模型几何是**物理像素的小数**：`Width = PreferredWidth * _scale`（`ModuleViewViewModel.cs:99`）、拖动目标 `targetX = pointerX - _dragPointerOffsetX`（`ModuleWindowsViewModel.cs:471`）都是 double。
- 窗口落位/落尺寸时才取整：`position = new PixelPoint((int)Math.Round(geometry.X), …)`、`window.Width = geometry.Width / scaling`（`ModuleWindowManager.cs:224-247`）。**位置与尺寸各自独立取整**，没有任何"回写对齐"。
- 本机实测 DPI：`HKCU\Control Panel\Desktop\LogPixels = 120` ⇒ **缩放 125%**。于是
  - 参考模块"手动数据发送器"声明 330×330 DIP ⇒ **模型 412.5 × 412.5 px（小数）**；外壳 858 DIP 高 ⇒ 1072.5 px（小数）；
  - 320×220 → 400×275 px（整数，恰好没问题）——**所以只有部分模块/部分方向会"有时"错位**。
- 相邻两模块的贴合关系是在**模型坐标**里成立的（`A.Right == B.Left`，小数），但**屏幕上**两个窗口各自取整 ⇒ 视觉上可能是 0px、1px 缝或 1px 叠 —— 这正是"经常有缝或是错位""有时像素级错位"。
- **U-4 的"再拖动时"额外一击**：拖动中只有**被拖模块**被标记 `IsInteracting`（`ModuleWindowsViewModel.cs:383`），**同组其他成员没有**；而 `OnWindowMoved`（`ModuleWindowManager.cs:192-208`）对 `IsInteracting == false` 的模块会把**窗口取整后的位置写回模型**（`module.X = window.Position.X`）⇒ 组内成员在拖动过程中被逐个取整、被拖模块保持小数 ⇒ **组内相对位置被破坏**；`EndDrag` 再把这份"半整数"布局落盘（`ModuleWindowsViewModel.cs:570-600`）⇒ 下次拖动的起点就带着 ≤0.5px 的错位。
- **待确认的一面（不猜）**：U-3 里"外壳与模块的缝"还可能来自**参照基准取的是外壳客户区右边缘**（`PublishShellRect` 用 `PointToScreen(0,0)` + `ClientSize`，`ModuleWindowManager.cs:290-300`），而用户视觉上的"窗口边缘"是**可见外框**（Win 的窗口矩形还含不可见缩放边与 1px 可见边框）。这一步需要**一次性测量**才能定论（见 §3.4）。

## 3. 改进方案

### 3.1 统一坐标系与**单一量化点**（修 U-3 / U-4，且让 U-1 的"整数候选"成为可能）

| 措施 | 说明 |
|---|---|
| **模型几何一律整数物理像素** | 新增一个量化入口（`ScreenPixels.Round(double) → int`，统一 `MidpointRounding.AwayFromZero`）；`ModuleViewViewModel` 的 X/Y/W/H 在**构造（含 `PreferredWidth*scale`）/拖动 / 缩放 / 跟随 / 从布局恢复**时全部取整 |
| **窗口只做"整数 ÷ 缩放"** | `ApplyGeometry` 不再自己取整，直接吃整数模型值；`window.Width = W / scaling`（W 整数 ⇒ 物理像素精确，125% 下不再出现 412.5） |
| **参照值也整数化** | 外壳矩形、参照线、其他模块边缘全部来自整数模型 ⇒ **候选位置恒为整数** ⇒ 吸附结果天然落在整数像素上 |
| **组内成员在拖动期间一并标记"由指针驱动"** | 修掉"组内成员被窗口回写逐个取整"⇒ 组内相对位置在拖动中保持不变（U-4 的直接原因） |
| **交互结束时一次性回收** | `EndDrag`/`EndResize` 结束时统一取整并落盘（**只在结束**，拖动中不引入新的写入） |

> 效果：屏幕上"相邻模块的边"与"模型里的边"是同一个整数，**缝与错位从"有时发生"变成"不可能发生"**；参考线与模块窗口也不再差半个像素。

### 3.2 吸附决策：**分段优先级 + 双向阈值（粘滞）+ 明确切换**（修 U-1）

`SnapEngine` 改为**有状态**（状态由调用方在 `BeginDrag` 建立、`EndDrag` 清空，纯结构体，仍可单测）：

1. **候选分级**（跨级不比较，高级别永远赢）：
   - ① **贴合（相邻边）**——**必须**交叉轴投影重叠 ≥ 最小重叠（与 `AreJoined` 同口径，建议 8px）；同时修掉"隔着老远也贴"与超长参考线；
   - ② **端口/网络标签中心对齐**（有标签时最相关，正是用户抱怨的那条"中心线"）；
   - ③ **模块中心线对齐**；④ 边缘对齐（左/右/上/下）。
2. **进入阈值 8px / 释放阈值 16px**：命中后**保持**（不再每帧重新比大小），直到原始位置离开该候选 > 16px 才释放 ⇒ 台阶式跳变消失，模块在两次吸附之间**跟手**。
3. **切换余量 4px**：粘滞期间只允许"**同级且更近至少 4px**"的候选顶替 ⇒ 边界处不再来回切换。
4. **一个轴最多一条粘滞候选**，并记住它的身份（参照对象 + 轴 + 类型），避免被别的对象的候选"抢走"。
5. 端口对齐候选**恒参与**（不再与"是否显示叠加信息层"绑定——当初的取舍是"有标签时标签承担对齐"，但实测表明标签本身就在中心线附近，反而更需要这条对齐）。

> 可验证判据（回归网，纯几何）：**1px 步进扫过容差边界，模块位置跳变必须 ≤ 1px**（即 §2.1 那张表不得再出现 +10px），且"离开 > 释放阈值后不再被吸住"。

### 3.3 外壳锚定与跟随：**用移动前的几何判定 + 锚定集 + 合并落盘**（修 U-2）

| 措施 | 说明 |
|---|---|
| **传入移动前的矩形** | `PublishShellRect` 之前先算出 `dx/dy`，`FollowShellMove(dx, dy)` 内部用 **`shell.Right - dx`** 做锚定判定（等价于"用旧几何判定"）⇒ 快速拖动不再脱开 |
| **锚定集（粘性）** | 拖动结束时把"贴在外壳上的模块集合"记为锚定集（内存态，可由几何重算兜底）；跟随按锚定集 + 组传播，**不再逐帧重新判定**（避免"某一帧没判定上就永久脱开"） |
| **释放条件明确** | 用户把模块拖离外壳（间隙 > 释放阈值）或改动外壳位置使重叠消失 ⇒ 退出锚定集并给一次轻提示（状态栏） |
| **合并落盘** | 跟随过程中只更新内存与窗口；**停止移动约 200ms 后（或外壳拖动结束）合并提交一次** `UpdateModuleLayouts`，避免每秒几十次变更 |
| **组传播** | 跟随仍按"接触连通分量"整组平移（ADR-0037 组关系不变），锁定成员依旧不跟随（第十一轮口径不变） |

### 3.4 外壳参照基准：**改用可见外框边缘**（U-3 的那一半，需一次测量确认）

- 现状参照 = 外壳**客户区**右边缘；用户看到的是**可见外框**右边缘。两者相差"不可见缩放边 + 可见边框"。
- 方案：用**已有的 P/Invoke 通道**（`AppWindowGroup` 已用 `SetWindowPos`）加 `GetWindowRect` + `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`，得到**可见外框矩形**作为唯一参照；取不到时回退客户区（并记录一次 Issue/日志，不静默）。
- **先测量再定论**：实施第一步先加一个**临时诊断**（状态栏显示：客户区矩形 / 可见外框矩形 / 当前吸附参照线），请你复现一次并截图/口述——**如果两者相差 0，则本项不做**（避免我凭猜测改基准）。

### 3.5 回归网（纯几何 + 视图模型，仍按"只跑对应测试"的纪律）

| 用例 | 断言 |
|---|---|
| 吸附单调性 | 指针 1px 步进扫过容差边界：模块位移 ≤ 1px、方向不反转 |
| 粘滞与释放 | 进入 8px 内吸附；离开 16px 前保持；离开后释放 |
| 无重叠不贴合 | 交叉轴无重叠 ⇒ `SnappedX/Y == false`，且不产生参考线 |
| 整数化 | 任意输入（含 125% 缩放下的小数尺寸/参照）⇒ 吸附结果与模型几何均为整数物理像素 |
| 组内稳定 | 组拖动过程中组内相对偏移恒定；`EndDrag` 后组内边严丝合缝 |
| 外壳跟随 | `dx = 1 / 8 / 40px` 三种位移，贴壳模块**都必须跟着走**（现有实现只有 ≤2px 通过） |

### 6.2 B1 + B2 已实现（代码事实）

| 项 | 落点与取值 |
|---|---|
| **候选分级** | 新增 `Ui.Geometry.SnapKind`（`Edge=0 · ModuleCenter=1 · PortCenter=2 · Flush=3`）；**跨级不比较**，同级才比 \|Δ\| |
| **改进的一处设计**（相对 §3.2 初稿） | 初稿写的是"贴合**必须**交叉轴重叠，否则丢弃该候选"——实作为：接触型候选在**有重叠时升级为 `Flush`**、**无重叠时退化为 `Edge`**。理由：把"一条边对到另一条边"整类丢掉会连带砍掉正当的边缘对齐（对齐参考线本来就允许跨很远），而它一旦降级为最低优先级，就**抢不过中心线**，也就不会再有"隔着老远却被当成贴合"的观感问题 |
| **双向阈值（粘滞）** | `SnapSticky`（X/Y 各记住"轴 + 类别 + 参照坐标"）；进入 8px 吸住、**离开 16px 才松开**；同级顶替需"更近至少 4px"；更高级别候选可直接顶替 |
| **端口/标签中心对齐恒开** | 新增 `PortCenterPair`（端口中心 + 对方矩形）；对齐轴由"哪个轴更近"决定（左右相邻比 Y、上下相邻比 X）；**接近范围 24px**（`PortAlignReach`）——超出则完全不参与 |

### 7.2 定位到**指针坐标的取法**（`ModuleWindow.ScreenPoint`）—— 回授振荡

原实现：`屏幕点 = Position（窗口位置） + GetPosition(this)（窗口内局部坐标） × 缩放`。

**两个来源不是同一次采样**：窗口位置是我们**自己刚设进去的**（拖动中每帧都改，吸附命中时还会整块跳几像素），
而局部坐标来自**系统在消息生成时刻**算出的"光标 − 当时的窗口矩形"。两者一旦差一帧：

> 指针读数误差 = 窗口位移量 → 原始位置抖 → 模块位置抖 → 窗口再动 …（**正回授**）

**与现象逐条吻合**：
- **只有左右抖、上下不抖** —— 拖动通常是水平的，窗口只在 X 方向被我们移动；Y 方向不移动 ⇒ 无回授；
- **与网络标签无关** —— 这不是吸附决策的问题，标签只是最容易注意到的场合；
- **吸附命中时更明显** —— 吸附会让窗口整块跳（几到十几像素），回授误差与之同量级。

**修复**：拖动/缩放取指针位置时**优先用系统光标**（`GetCursorPos`，屏幕物理像素，与本窗口自身位置无关）
→ 新增 `Ui/Views/NativeCursor.cs`；非 Windows / 非鼠标（触摸、笔）/ 调用失败时回退到原换算。
窗口换算值仍会照算并留存，供诊断比对（见 §7.3）。

### 7.3 关于"尺寸不匹配"（你的怀疑）：**登记为待确认，并已布好测量**

§6.2 已把参照矩形与窗口落位量化到整数物理像素，但"**模型尺寸 vs 窗口实际客户区尺寸**"在 125% 缩放下是否恒等

**每次拖动都把每一帧完整追加**到 `%TEMP%\hyw-drag-diag.log`（不再只记异常帧），拖动结束时状态栏给出路径。每帧记录：

## 9. 本方案明确**不做**

- 不改**建网判定**（`DockRule` 的接触/标记对齐容差与契约判定，ADR-0037 口径不动）；
- 不改组合件布局**格式**（仍是绝对屏幕像素整数化后的值；旧文件照常读入并量化）；
- 不做"网格吸附"（ADR-0031 早已裁决不做）；
- 不引入第三方布局/吸附库；
- 不改端口标记与叠加信息层的**视觉规范**（ADR-0039）。
