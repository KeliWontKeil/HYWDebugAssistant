## 0. 本议程的定位、边界与议事方式

### 0.1 定位

顶层基线是"**整版原理图**"（§16.4），技术选型是"器件选型"（ADR-0023/0024）。本议程完成的是**从原理图到可施工结构**的最后一层设计：把基线的域结论落到**程序集边界、类型职责、执行模型、数据物理形态**上去——仍属设计，不属编码（§16.4：原理图未完不 layout）。

### 0.2 输入（全部已冻结，本议程不得违反）

| 来源 | 约束内容 |

### 0.3 边界（本议程**不做**）

1. 不修改 v1.0 基线任何冻结结论（§16.2：任何变更走 ADR + 人工决策）；
2. 不解决 **Gate C**（UX 原型细节：尺寸族/网格/视觉形态）与 **Gate D**（组合件递归嵌套、会话快照、录波回放、沙箱、跨平台硬性要求、模块版本迁移路径）；
3. 不写产品代码、不建业务模块（§16.4 纪律）；
4. 不做具体业务模块设计（Gate E）。

### 0.4 议事顺序（依赖关系）

```text
第0章 议程形态（怎么裁、产出成什么、怎么算完）
   ↓
第1章 分层与依赖方向      ← 支点：后续一切程序集/类型归属由它推导
   ↓
第2章 项目与解决方案结构   ← 分层的物理落地
   ↓
第3章 模块 SDK 形态       ← 框架对外的唯一契约面（依赖第1/2章边界）
   ↓
第4章 关键机制技术方案     ← 运行时内核（依赖第3章的数据形态选择）
   ↓
第5章 UI 架构             ← 表现面（依赖第1章隔离点、第4章交接模型）
```

## 1. 分层与依赖方向

> 状态：**已冻结**（全文 `01-layering-and-dependencies.md`；Q1-1~Q1-4 与 C1-1~C1-5 已裁决，见 ADR-0026）。

### 1.1 本章要确立的结论点（非裁决，来自基线）

- 把 §3.2.1「表现层 / 语义层分离」与 §3.3.1「Core 职责三分」翻译为**程序集级分层图 + 单向依赖箭头**；
- 明确**数据面**（绑定执行、缓冲、投递）在层图中的位置，以及它与 UI 之间的隔离点（承载 §13.1「数据面绝不被 UI 阻塞」）；
- 明确**契约面 / 框架内部面**的边界（P16：具体数据类型不过早进入框架；§5.4.2 框架不附加元信息）；
- 给出**依赖方向禁令清单**（将成为架构测试 A1–A6 的规则来源）；
- 逆例自检：任何一条依赖箭头都不得使 Core 变成数据中转（P2/E1/E2）或使模块依赖另一具体模块（P12）。

### 1.2 必须由你裁决的问题

| 编号 | 问题 | 取值轴（仅界定问题边界，不排序、不推荐） | 影响面 |
|---|---|---|---|
| **Q1-1** | 分层的**切分依据**选哪一种？ | ①按**变化率/稳定性**切（表现 / 语义 / 契约 / 基础设施）；②按**运行时角色**切（UI / Core / 模块宿主 / 数据面 / 契约）；③两者的组合 | 决定后续所有项目划分与类型归属，返工代价最高 |
| **Q1-2** | 模块实现对外部世界（框架）的**可见面**有多宽？ | ①仅契约面（契约类型 + 模块基元 + 上报 API）；②契约面 + 宿主服务面（日志/配置/资源访问等框架服务）；③契约面 + 框架只读查询面（可查其他模块是否存在等） | 决定模块能力上限、Core 暴露面、AC-1/AC-5 的可达成强度 |
| **Q1-3** | **数据面**是否独立成层（独立程序集），与 Core 的管理面分离？ | ①同一程序集内的独立模块/命名空间；②独立程序集，单向依赖；③完全同层不分 | 决定「数据面不被管理操作/UI 阻塞」的可验证强度与架构测试强度 |
| **Q1-4** | **UI 构成**可以引用框架的哪一层？ | ①只能引用契约面 + 公开查询 API（UI 与 Core 内部解耦）；②可直接引用 Core 内部类型（开发效率优先）；③UI 通过独立「UI 服务面」间接访问 | 决定 UI 与 Core 的可替换性与 §3.2.1 分离的实际强度 |

## 2. 项目与解决方案结构

> 状态：**已冻结**（全文 `02-project-structure.md`；Q2-1~Q2-5 与 C2-1~C2-5 已裁决，见 ADR-0027）。

### 2.1 本章要确立的结论点

- 项目（`.csproj`）清单、命名、目标框架、以及**项目与第 1 章分层的对应关系**（一个层 = 一个还是多个项目）；
- 模块作者使用时需要引用哪些项目（与 Q3 相关）；
- 测试项目划分（单元 / 架构 / 参考组合 / UI 自动化）与产品项目的引用关系；
- 现有骨架（`src/HYWDebugAssistant`、`tests/*`）如何被重组。

### 2.2 必须由你裁决的问题

| 编号 | 问题 | 取值轴 | 影响面 |
|---|---|---|---|
| **Q2-1** | 程序集**粒度** | ①少程序集（Core 一个，内部用命名空间组织）；②多程序集（按机制拆分，如宿主/建网/持久化/数据面/UI 各一）；③按"是否需要被模块作者引用"二分 | 编译速度、架构测试可表达强度、`InternalsVisibleTo` 扩散程度、模块加载边界 |
| **Q2-2** | 是否设立**独立契约/SDK 程序集**作为模块作者唯一引用面 | ①设（作者只引用它，框架其余不可见）；②不设（通过 `internal` + 友元限定）；③设但不强制（作者也可引框架） | 直接决定 Q1-2 的可执行性；影响 AC-1「Core 零改动」的机器可判定性 |
| **Q2-3** | **参考组合桩模块**（数据发生器/记录器/断言器，§14.2）常驻位置 | ①`tests/` 下的测试专用项目；②`src/` 下的"参考模块"程序集并随产品分发；③独立目录，两者共用 | 影响 AC-1~6 实证的保真度（桩模块是否与第三方模块同等待遇） |
| **Q2-4** | **框架自身 UI（Core UI）** 的项目归属（§3.2：不作为普通 Module） | ①与主程序同一项目；②独立框架 UI 项目；③作为内置预装模块实现 | 影响 §11.2「内置=预装包，无结构特权」的一致性 |
| **Q2-5** | v1 开发期是否建立**示例业务模块**项目，及其是否随产品发布 | ①建且发布；②建但不发布（仅开发期验证）；③不建（用桩模块代替） | 影响 Gate E 的开展时点与产品初版形态 |

## 3. 模块 SDK 形态

> 状态：**已冻结**（全文 `03-module-sdk.md`；Q3-1~Q3-7 与 C3-1~C3-6 已裁决，见 ADR-0028；C3-6 专项分析见 `03a-view-rendering-options.md`）。

### 3.1 本章要确立的结论点

- Definition「6 项声明」（§11.2）与成员声明集（口/配置/视图，§4.10.1）在技术上的**表达载体**；
- 生命周期钩子集合与签名（对应 §8.4 状态机与 Enable/Disable「通知模块」）；
- 成员统一路径四阶段（声明→实例化→存取·连接→表现）在 SDK 上的对应 API 面；
- 模块包 manifest 的技术形态（§11.2：声明 + 实现入口 + 依赖 + 框架兼容范围 + 资源）；
- 模块状态上报与异常上报 API（§8.4 业务状态自报、§8.5 Issue）；
- 模块如何取得框架服务（与 Q1-2 呼应）。

### 3.2 必须由你裁决的问题

| 编号 | 问题 | 取值轴 | 影响面 |
|---|---|---|---|
| **Q3-1** | 模块**声明载体** | ①C# 类型 + 特性（Attribute）+ 反射读取；②源生成器（编译期产出声明）；③外部 manifest 数据文件 + 实现绑定；④前两者的组合 | 启动/加载性能、可校验性、作者体验、manifest 与代码的一致性风险 |

| **Q3-6** | v1 是否引入**脚本宿主**作为模块行为载体 | ①不引入（仅 C#）；②引入（语言另立 ADR）；③预留接口不实现 | 影响 §12 安全模型强度与依赖面（ADR-0023 §5 已留位） |

## 4. 关键机制技术方案

> 状态：**已冻结**（全文 `04-key-mechanisms.md`；Q4-1~Q4-5 与 C4-1~C4-4 已裁决，见 ADR-0029；评估材料 `04a`）。**补遗已裁决**：应用级设置模型（`04b` + **ADR-0030**，主文档 §9.5 已回写）。

### 4.1 本章覆盖的机制（基线已定"是什么"，本章定"怎么构成"）

| 机制 | 基线已冻结的结论 | 本章要定 |
|---|---|---|
| 4.1 ChangeSet | 单操作原子、复合整体校验+一次性应用、无全局锁（§6.2） | 事务实现结构、校验与提交的分离方式、失败整体拒绝的落地 |
| 4.2 增量重建 | 重建单位 = 绑定及邻接数据面；模块实例/配置/业务状态保留（§7.3） | 声明与实现之间的差异计算结构、重建触发与边界 |
| 4.3 网络绑定 | 数据在两端模块间**直接流动**，Core 不中转（§7.2/P2）；网络严格单向、1:N 原生多播（§6.3） | 绑定的技术形态、投递路径、可观测挂钩点 |
| 4.4 有界缓冲 | 有界 + 丢旧默认 + 不阻塞上游；策略由模块口声明（§7.3） | 缓冲归属、容量与策略参数化、丢弃计数（L4） |
| 4.5 调度与承载 | 框架统一承载活动与调度，模块不自建线程（ADR-0013） | 执行模型、模块活动的承载方式、隔离与并行度 |
| 4.6 持久化 | 文本格式 + 内嵌 Schema 版本 + 原子写 + 重锚规则（§9.2/9.3） | 序列化结构、原子写落地、加载与重锚流程、部分恢复 |
| 4.7 Issue 与可观测性 | Issue 统一模型、天然隔离+显式恢复、L1–L5（§8.5/§13.2） | 收集通道、分发与呈现通道、与数据面的挂钩方式 |

### 4.2 必须由你裁决的问题

| 编号 | 问题 | 取值轴 | 影响面 |
|---|---|---|---|
| **Q4-1** | **数据面执行模型**（ADR-0013 遗留的"实现 Gate"，全章最关键） | ①单调度线程串行执行全部绑定；②绑定/模块映射到工作线程并行；③按拓扑分区（互不相关的链路并行、链路内串行）；④模块自选声明（框架给默认） | 性能上限、AC-2 隔离强度、模块作者编程模型（是否需要考虑并发）、实现复杂度；与 §13.1 首要原则直接相关 |
| **Q4-2** | **数据单元的物理表示** | ①引用类型对象（语义直观、分配压力）；②扁平字节缓冲（`Span`/池化）+ 元数据解释；③两者按契约声明分层（热路径扁平、慢路径对象） | 零分配目标（ADR-0023 §2）能否达成的**方式**；与 Q3-2 契约表达强耦合；决定丢弃与缓冲的实现成本 |
| **Q4-3** | **绑定执行形态** | ①直接调用（委托/函数指针式，无运行时常驻对象）；②绑定对象 + 虚调用（便于观测与动态替换）；③编译期生成的紧致投递路径 | P2/E1 边界（Core 是否"经手"数据）、每次投递开销、L4 诊断（流量/丢弃/最后数据时间）的挂钩难度 |
| **Q4-4** | **UI 与数据面的交接模型**（§13.1 的落地方式） | ①UI 定时拉取快照（节流）；②数据面推送 + 限流；③共享双缓冲/环形缓冲无锁交换；④混合（数值流拉取、事件推送） | "数据面绝不被 UI 阻塞"的实现强度、UI 刷新率上限、实现复杂度 |
| **Q4-5** | **模块活动的承载方式**（"框架统一承载"落成什么编程模型给模块作者） | ①协作式：框架调度 + 模块实现回调（模块不得阻塞）；②抢占式：每模块一个框架管理的任务；③按模块声明选择 | AC-2 隔离强度、作者门槛与易错点、调度器复杂度；与 Q4-1 互为约束 |

### 4.3 我出方案、你审核的落细项（R 类，本文不展开）
