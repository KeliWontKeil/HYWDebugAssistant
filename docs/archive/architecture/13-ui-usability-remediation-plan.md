| 4 | 尺寸吸附（Visio 式）、参考线（含中心对齐）、标签对齐吸附 | ① `SnapEngine` 已算 `Guides`，但 **M1-15 后没有任何地方渲染它**（旧画布版有绘制，多窗口版丢了）→ 参考线"缺少"；② `SnapEngine` 的对齐候选只有"左边/右边/上边/下边 + 贴合"，**没有中心对齐**；③ 尺寸吸附（把宽高吸到邻近模块的边长）**从未实现**；④ 标签对齐吸附与自动建网（问题 1）是同一件事的两面 | ① 是**缺失**；②③ 是新能力（几何，成本低）；④ 与裁决项绑定 |

## 1. 实施顺序（我的建议：**四批**，严格按依赖排）

### 批次 1 · 基础可用性（**先做**：2 + 3(2) + 3(3)）

| 内容 | 说明 |
|---|---|
| 窗口**首屏按内容定尺寸** | 新增"内容驱动尺寸"：首次摆放时按声明元素估算/测量高度（恢复并改进 M1-15 丢掉的逻辑），并钳制在屏幕工作区内；用户手动调整过则以布局为准（不覆盖用户选择） |
| 内容**内边距与预留带** | 模块窗口四周预留**标记带**（左/右/上/下各约 18 px）；内容区再加内边距，**不再贴边** |
| **控件尺寸策略** | 输入类控件（TextBox/ComboBox/CheckBox）用**固定/首选尺寸**，不随窗口拉伸；只有"曲线/日志/表格"这类展示元素随窗口伸缩；表单标签列固定宽，行高统一 |
| **消除"重影"** | 配置表单每个字段的控件**独占一行/一列**（不再叠在同一单元格）；去掉模块窗口上那处可疑的 `TransparencyLevelHint` Style；确保窗口背景不透明 |
| **端口标记移入预留带 + 边感知排布** | 左/右边缘：标记块**窄而高、文字竖排**；上/下边缘：标记块**宽而扁、文字横排**（当前端口只在左右，规则先泛化到位） |
| **就地编辑修复** | 焦点改为**在 TextBox 挂到可视树后**再获取（`AttachedToVisualTree` / `Dispatcher.Post`）；Enter 提交、Esc 取消、失焦提交 |
| **建网反馈闭环** | 提交结果**送到状态栏 + Issue（Info/Warning）+ 标记即时更新 + 拓扑诊断即时反映**；失败给明确原因（契约不兼容/多发送端/端口不存在等，这些运行时已经返回了，只是被我扔掉了） |
| **标签信息增强 3(1)** | 标记显示：**网络名 · 方向（发送→/←接收） · 连接状态点 · 累计投递数 · 估算字节数**（字节 = 投递数 × 契约尺寸；**按网络粒度**，非单宿口，界面注明）|

> **为什么先做这批**：布局（预留带 + 尺寸）是**后续一切几何交互的基础**（对齐判定、吸附、标签位置都依赖它）；反馈闭环是"能不能用"的前提。全部是修我自己的缺陷，**不需要新设计批准**。

### 批次 2 · 交互增强（**几何部分**：4 的②③ + 对齐反馈的窗内方案）

| 内容 | 说明 |
|---|---|
| **中心对齐候选** | `SnapEngine` 增加"水平中心/垂直中心对齐"候选（与现有左右/上下边对齐并列） |
| **尺寸吸附（Visio 式）** | 缩放时，被拖的边接近**其他模块的宽/高**（容差内）→ 吸附到该尺寸；同时保留"边对齐"吸附 |
| **对齐反馈（窗内方案）** | 命中吸附时：被拖窗口的对应边**高亮 1 px 主色**、对方窗口对应边**同步高亮**、状态栏显示对齐类型（"左对齐/中心对齐/贴合…"）——**不跨窗口画线** |
| **跨窗口虚线参考线**（**裁决项 B**） | Visio 式虚线必须画在**两个窗口之间** → 需要**全屏透明点击穿透覆盖窗**（Win32 layered + click-through + z-order + 多 DPI）；ADR-0034 当时已推迟。**要么接受窗内方案，要么单独立项做覆盖窗** |

### 批次 3 · 自动建网语义变更（**1**，设计变更）

| 内容 | 说明 |
|---|---|
| 新语义：**对齐即连** | 拖动/缩放**结束**时，对"边缘贴合且端口对齐（或网络标签对齐）"的配对：发送口 ↔ 接收口，**契约兼容**且**双方都未入网**（或该网络允许加入）→ 自动建立网络；拖动**过程中**给出"将对齐"的视觉提示（可先做状态栏提示，再做标记块加粗） |
| 原"加入即连" | **建议移除**（或改为默认关）：它会在用户毫无意图时把模块接起来。需你裁决（**裁决项 A**） |
| 反馈 | 建网成功/失败都给出状态栏 + Issue 提示；失败原因用运行时的既有判定（契约不兼容、多发送端） |
| 文档 | 主文档 §6.3 的 R0–R6 需回写"触发时机 = 对齐（几何）而非加入"→ **ADR-0037** + `05`/`11` 回写 |

### 批次 4 ·（可选）跨窗口虚线参考线

仅当你在裁决项 B 里选"要 Visio 式虚线"时立项：全屏透明覆盖窗（点击穿透、z-order 在模块窗口之上弹窗之下、应用失活随之下沉、多 DPI 坐标换算）——**本次不做，除非你要求**。

## 3. 我建议**不做**的（避免过度设计）

| 项 | 理由 |
|---|---|
| 现在就把端口拖到上下边 | 需要 C5-7 的端口任意边能力，与本轮"可用性修复"不是一个主题；布局规则先留口 |
| 标签内显示"每个宿口的独立投递量" | 框架诊断是**按网络**统计的；按宿口会牵动数据面计数结构，收益低 |
| 拖动过程中实时建网（而非释放时） | 拖动中反复建/拆网络会让"取消拖动"语义变复杂（可能留下半成品连接）；**释放时提交**更符合"原子变更" |
| 跨窗口参考线（若选替代方案） | 覆盖窗的四件事（穿透/z-order/DPI/失活）任一没做都会变成新的坑 |

### 4.1 用户第五轮追加裁决（2026-09）

| 编号 | 裁决 | 落地要求 |
|---|---|---|
| **D** | **吸附对齐（UI 行为）与对齐建网（网络行为）必须分开**，不得混为一谈 | 吸附只负责"让用户容易对上"；建网只按**几何事实**判定（接触 ≤2 px + 标记中心对齐 ≤12 px + 契约兼容 + 双方未打标签）。两者**共用同一条判定规则**（唯一实现 = `Core/Composition/DockRule`），但**触发时机不同**：吸附在拖动中，建网在**布局提交（松开鼠标）**后 |
| **E** | 新增**"即将自动建网"预览高亮** | 拖动窗口且刚好满足建网条件（通常已吸附对齐、**尚未松开鼠标**）时，**高亮将被连接的双方标记**；松手后由网络行为真正建网。UI 通过 `Core.Api` 的预览查询向 L4 询问"现在松手会连上什么"，**不复制判定规则** |
| **F** | 对齐网络的生命周期 | **拖开即自动断开**（几何派生） |
