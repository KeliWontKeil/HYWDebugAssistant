## 0. 依赖图：为什么这一层最先

```
① 数据语义与包结构（本文）：数据类型 == 什么 · 单位/量纲/范围 · 时序与序号 · 包/帧信封 · 批量
      ↓ 契约才不只是"字节布局"
② 端口契约的兼容与映射（P2）：谁能连谁 · 语义不一致怎么办 · 转换归谁 · 不兼容如何提示

③ 模块角色与处理关系（P3）：源/汇/处理器 · 进→出关系 · 声明 vs 派生 · 零端口兜底
      ↓ "模块是什么"才可表达
④ UI 投影（P4）：角色方块 · 信息区 · 角色→角色数据流线 · 类型色板 · 小窗降级
```

**一句话**：① 定不下来，②③④ 只能靠猜；UI 就只能反复调字号/颜色/粗细（这正是前十五轮返工的成因）。

## 1. 现状盘点（代码事实，2026-09）

| 层 | 已有什么 | **缺什么** | 证据 |
|---|---|---|---|
| **契约形状** | `ContractShape` = 原语 / 数组 / 结构（成员名 + 类型 + 顺序），**定长**，`SizeInBytes`；`Describe()` 生成 `f32`、`{seq:u64, value:f32}` 这类文本 | **命名数据类型**（类型库/语义身份）、**嵌套以外的语义**（见下） | `src/Sdk/Contracts/ContractShape.cs` |
| **传递语义** | `TransferSemantics` = `Stream` / `Message` / `Event`（**已有**，参与兼容判定：**跨语义不判兼容**） | 只有"交付形态"三态；**没有**单位、量纲、有效范围、精度、采样率、枚举域 | `src/Sdk/Contracts/TransferSemantics.cs` · `PortDeclaration.Semantics` |
| **兼容判定** | `ContractCompatibility.Check(...)`：**语义相同 + 形状完全一致**〔**ADR-0051 修订**：原「形状子集（接收 ⊇ 发送）」已作废〕；**不自动转换**（8 字节的 u64 与 f64 明确算不兼容，避免按错类型解读） | **语义级兼容**（同结构不同单位？）、**映射/转换规则** | `src/Core/Composition/ContractCompatibility.cs` · `DockRule.cs:154` |
| **数据单元** | 投递 = **裸载荷**（`PayloadBuffer`，定长，按契约布局切片）；队列 `InboundBuffer` 有界、满即丢弃并计数 | **时间戳 · 序号 · 来源 · 质量位**（框架级无任何包头）；**批量投递** | `src/DataPlane/Queues/InboundBuffer.cs` · `Carriers/ModuleCarrier.cs` |
| **时序信息** | UI 的"速率"是**用两次采样差分**算的（投递字节数 ÷ 间隔）；模块若需要序号/时间，**自己在契约里带**（如参考模块的 `{seq:u64, value:f32}`） | **框架统一的时间戳/序号**（延迟、抖动、时序对齐、丢包定位都依赖它） | `ModuleWindowsViewModel.RefreshMarkerStatus`（速率采样）· 参考模块契约 |
| **配置/视图的"单位"** | 配置字段有 `Unit`（`ConfigurationFieldAttribute`）、视图元素有 `Unit`（`ViewDeclaration`） | **端口契约没有** `Unit` ⇒ 同一条数据"显示时有单位、契约里没单位" | `Sdk/Configuration/ConfigurationFieldAttribute.cs` · `Sdk/Views/ViewDeclaration.cs` |

**结论**：底层机制（不可变网络模型、严格单向、1 源 → N 宿、定长契约、队列背压/丢弃计数、声明式视图）**都在，且是好的**；缺的是**语义层**。所以 P1 是"**在既有骨架上加一层语义**"，不是重写。

## 2. 问题清单（每题：现状 → 选项 → **我的推荐** → 影响面 → 不定的风险）

### 2.1 必答内核（不定就无法继续）

#### Q1. 数据类型：继续"匿名结构"，还是引入**命名数据类型**？
- **现状**：端口契约 = 结构形状（`{seq:u64, value:f32}`），没有类型身份/名称。
- **选项**：
  - (a) **只保留结构**（现状）——UI 永远只能显示 `f32` 这种结构描述，色板无依据；
  - (b) **命名类型 = 结构 + 语义元数据**（如 `hyw.temperature.celsius`：结构 `f32` + 单位 °C + 量程 + 精度 + 建议采样率）；
  - (c) **命名类型 + 结构分离**（类型可被多个模块共享/加载类型库，结构只是其一种实现）。
- **我的推荐**：**(b)**。理由：① 只增不改（既有模块继续用纯结构，兼容）；② UI 立刻有东西可显示（类型名/单位/色板键）；③ (c) 的类型库分发属于"包与依赖"范畴，可在 (b) 稳定后再演进。
- **影响面**：端口声明、兼容判定、UI 类型色板与语义名、模块清单展示、Issue 文案；**解锁 P4 的"类型色板 + 语义名"**。
- **不定的风险**：P4 的中心方块只能写 `f32`（你已指出"含义没有表达"），色板继续占位。

#### Q2. 语义元数据的**字段集**与必填性
- **候选字段**：单位（`°C`/`rpm`/`V`）· 量纲 · 有效范围（min/max）· 精度/分辨率 · 建议采样率 · 枚举值域（状态字）· 数组语义（见 Q5）· 显示格式提示。
- **选项**：(a) 全部可选（模块作者写多少算多少）· (b) 单位必填 + 其余可选 · (c) 全部必填（严格）。
- **我的推荐**：**(a) 全部可选**，但**框架保证"有就显示、无就留白"**。理由：调试工具的价值在于"渐进填满"，强制必填会逼模块作者写假数据。
- **影响面**：`Sdk` 声明面（`init` 属性增量）、UI 信息区字段、曲线纵轴标签、告警阈值（将来）。
- **不定的风险**：信息区不知道显示什么字段（P4 无法定稿）。

#### Q3. **数据包信封**：框架统一，还是保持裸载荷？
- **现状**：投递 = 裸载荷；序号/时间由模块自理；框架只统计"投递/丢弃"。
- **选项**：
  - (a) **保持裸载荷**（现状）：零开销、模块自由；但延迟/抖动/时序对齐/丢包定位**无框架数据**；
  - (b) **框架统一信封**（每个单元带：单调时间戳 + UTC 时间戳 + 全局/按绑定序号 + 来源 + flags），**作为与载荷分离的旁路元数据**（不塞进 payload 字节流 ⇒ 不破坏既有契约、不额外深拷贝）；
  - (c) **可选信封**（模块声明"需要信封"才带）。
- **我的推荐**：**(b)**，且**旁路元数据**（元数据与载荷分开存放，UI/诊断可读，模块默认不可见、按需可读）。理由：工程调试助手的核心价值之一是**看见时序**；而"旁路"避免了两大代价（拷贝 + 破坏现有契约语义）。若你担心开销，可退到 (c)。
- **影响面**：`DataPlane`（`InboundUnit`/`ModuleCarrier`/队列）、`Core.Api`（诊断与订阅面新增只读字段）、监控类模块（可获得精确时间）、UI（延迟/抖动/时序）。
- **不定的风险**：叠加层的"最后数据时间/速率"只能继续用差分估算（现在就是这样），**延迟类指标根本无法提供**。

#### Q4. 时间戳与序号的**归属与来源**
- **子问题**：① 时间戳 = **框架接收时刻**（自动、可信、统一）还是**模块采集时刻**（真实、但需要模块提供）？② 时基 = 单调时钟 / UTC / 两者兼有？③ 序号 = 全局单调 / 按绑定 / 按口？④ 模块内部丢弃（如显示器"覆盖旧值"）如何并入"丢弃"统计？
- **我的推荐**：① 框架记**接收时刻**为默认，**模块可选覆盖**为采集时刻（两个字段并存）；② **单调 + UTC 双写**（单调用于间隔/抖动，UTC 用于显示）；③ **按绑定**（每条网络一条序号）× 全局序号（用于跨网络排序）；④ 框架统计"队列丢弃"，模块可选**上报自身丢弃**（`Issue`/诊断合并显示）。
- **影响面**：信封结构、诊断视图、UI 信息区（"最后数据 0.3s 前"可升级为"延迟 12ms"）、测试（时序断言）。
- **不定的风险**：Q3 定了但 Q4 不定 ⇒ 信封字段无定义，等于没定。

#### Q5. **数组语义**：`f32[8]` 是"8 通道"还是"批量 8 个采样"？
- **现状**：`ArrayShape` 只有长度，无语义 ⇒ **UI 无法决定"画 8 条曲线"还是"画 1 条曲线（8 点）"**。
- **选项**：(a) 语义标注（`Channels` / `Batch`）；(b) 由模块在视图声明里自行解释（框架不管）；(c) 新增独立类型（`Channels8F32` 之类）。
- **我的推荐**：**(a)** —— 在类型语义里加一个"数组语义"标注；这是"曲线/多通道显示"能否正确工作的前提。
- **影响面**：曲线元素、信息区、将来的多通道显示、`ContractShape` 的语义标注。
- **不定的风险**：P4 的曲线与信息区会**画错**（把 8 通道当 8 个点）。

#### Q6. **语义不一致**时的行为：阻止还是警告？
- **现状**：跨 `TransferSemantics` **直接不判兼容**（连通被拒绝/成员被排除 + Issue）；**不自动转换**。
- **选项**：(a) 保持"阻止"（安全）；(b) **放宽为警告 + 允许强连**（同结构、不同单位 ⇒ 允许但明确提示"按 X 解读为 Y"）；(c) 引入"显式确认"（用户勾选"我知道单位不同"才连）。
- **我的推荐**：**(b) + (c) 的组合**：结构兼容但语义不同 ⇒ **默认阻止**，但提供**显式确认**后允许（调试现场经常需要"我就是要这么接"）；**转换仍不由框架做**（P2 再定归属）。
- **影响面**：`ContractCompatibility`、`DockRule`、网络成员排除逻辑、UI 提示与确认弹窗、Issue 分级。
- **不定的风险**：P2 的"谁能连谁"无法定稿；用户会遇到"明明结构一样却连不上，且无法强连"。

### 2.2 次级（影响面中等，可与内核同批定）

#### Q7. 类型的**注册与命名空间**
- 选项：(a) 框架保留前缀（如 `hyw.`）+ 包内声明类型（前缀 = 包 ID）；(b) 全局扁平命名（易冲突）；(c) 用户可在工作区自定义类型（v1 不做）。
- **推荐**：**(a)**，重名 = 加载期拒绝并报 Issue（沿用"不静默改名"纪律）。
- **影响**：模块包清单格式、类型库检索、UI 显示名（短名 + tooltip 全名）。

#### Q8. **类型演进规则**（只增不改的具体化）
- 选项：(a) 类型带版本号，**尾部新增字段 = 兼容**，改类型/删字段 = 不兼容；(b) 无版本（结构相等即兼容）；(c) 显式转换器（P2）。
- **推荐**：**(a)**，并写进 `Sdk` 的"只增不改"纪律（与 ADR-0041/P30 一致）。
- **影响**：兼容判定、组合件持久化（保存的类型引用）、Issue 文案。

#### Q9. **映射/转换的归属**（与 P2 强耦合，这里只定"原则"）
- 选项：(a) 框架**永不自动转换**（现状，推荐保留）；
- **推荐**：**(a)**，并把"转换"表达为**独立的转换模块**（用户显式插入），框架只**提示差异**。
- **影响**：P2 的全部内容、UI 的"不兼容"提示设计。

#### Q10. **1 源 → N 宿的语义**明确化 + 多源处理
- 现状（**冻结当轮**）：1 源 → N 宿（**广播**，每个宿都收到）；**多源（同名标签多个发送端）⇒ 整条网络不创建 + Issue**（"网络严格单向、只能有一个源"）—— 这是**模型限制下的临时规则**（`Network.Source` 单值），**不是"停流"**。
- **> ⚠️ 该"整条拒绝"规则已作废**【ADR-0050 · 主文档 1.0.16】：多源是**合法的一等组合**，同名标签多发送端 = **一条多源网络**（`Network.Sources` 列表）；**部分源不可用 ⇒ 其余源照常投递 + 该源 Issue**；**全部源未锚定 ⇒ 停流**。落地细节见 `18-network-semantics.md` §8。
- **推荐**：**显式确认 1→N 广播**（已写进主文档 §6.3）；**多源问题另立清单**（用户第二十一轮指出"多源可能是真实需求"）⇒ **`architecture/18-network-semantics.md` N1–N9**（裁决落 ADR-0050）。
- **影响**：网络语义文案、UI 状态说明、Issue 文案。

#### Q11. **批量投递**（性能相关）
- 现状：一次投递 = 一个类型实例。高频数据（如 10 kHz 采样）会产生巨量单元。
- 选项：(a) 不做（现状）；(b) 类型可声明"批量容器"（一次投递 N 个实例）；(c) 框架自动合并。
- **推荐**：**(b)**（类型语义里声明），不做 (c)（自动合并会改变时序语义、且难以调试）。
- **影响**：Q5 的数组语义、数据面队列、曲线采样、诊断计数含义（"单元数" vs "样本数"）。
