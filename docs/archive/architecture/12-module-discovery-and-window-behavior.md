## 0. 先回答你的一句判断

> "这个功能似乎和构建完成后的文件集有关，我首先需要详细的分析和方案设计……这似乎需要修改构建产物目录或是文件结构"

**你的判断是对的。** 三件事的真实关系是：

| 层次 | 事实 |
|---|---|
| **包物理形式（已冻结）** | 1 个模块包 = **1 个目录**（`module.json` + 实现程序集 + 依赖），主文档 §11.2 / ADR-0020，**这层不需要改** |
| **包的产出位置（未冻结）** | 现在由 `build.ps1` 第 2.5 步"归拢"到两处：`<应用目录>\modules\`（内置）与 `artifacts\modules\`（分发副本）。**"谁来产出、产到哪里"从未在设计里定过** —— 这是缺口 |
| **包的发现方式（未冻结）** | 现在只扫**一个**目录（`ApplicationSettings.ModuleSourceDirectory`，默认 = 应用目录 `modules\`）。**"扫哪些目录、按什么顺序、旧包怎么办"也从未定过** —— 这也是缺口 |
| **开发期热更新（未冻结）** | `Assembly.LoadFrom` 走默认 `AssemblyLoadContext` → **程序集一旦载入不可卸载**：改了模块代码后**必须重启应用**才生效（详见 §1.5）。这是你调试不便的第二个来源 |

所以确实要动"构建产物目录/文件结构"——但**不需要动包的形式**，只需要**把产出与发现规则定死**。

## 1. 议题一：模块自动发现（你的第 1 条）

### 1.1 现状（已核实的实现事实）

| 项 | 现状 | 位置 |
|---|---|---|
| 来源目录 | **单个**字符串 `ModuleSourceDirectory`；为空时用 `<应用目录>\modules\` | `ApplicationSettings` · `CompositionRoot` |
| 扫描规则 | 只扫**直接子目录**中**含 `module.json`** 者；每个包独立处理，失败记 Issue | `RuntimeServices.TryScanSourceDirectory` |
| 包有效性 | 目录内必须**同时**有 `module.json` 与 `entryAssembly` 指定的程序集 | `ModulePackageLoader` |
| 重复包 | 注册表**同 ID 同版本重复即拒绝**（不覆盖），并记 Issue | `ModuleRegistry` |
| 运行期重扫 | **没有**：只有启动扫描 + 手工「选择…加载」 | `Core.Api` 无对应命令 |
| 打包入库 | `build.ps1` 步骤 2.5 → `stage-reference-modules.ps1` → 应用输出 `modules\` + `artifacts\modules\` | 工程脚本 |

**结论**：现在的"自动发现"只覆盖**内置 5 个包**；工程里新写的模块、重新构建的模块，都要你手工找目录。这正是你的痛点。

### 1.2 方案选项（核心分歧：**扫哪里**）

**选项 A｜"声明根列表 + 启动自动扫描"（建议）**

- 设置里的来源目录从**单值升级为列表**（`moduleSourceDirectories: []`），按**顺序**扫描；
- 默认列表（开箱即用）：
  1. `<应用目录>\modules\`（内置包，随构建产出）
  2. `<仓库根>\artifacts\modules\`（**仅当设置里点了「填入工程默认值」才加入**，不做隐式探测）
- 启动时逐根扫描；同名同版本重复 → **先到者胜**，后续重复只记 **Info**（不刷 Warning）；
- 提供**「立即重扫」**按钮（新增 `Core.Api` 命令）→ 新加的包无需重启；**改过代码的包仍需重启**（§1.5）。
- 兼容主文档 §11.2 的"**不自动扫任意位置**"：只扫**用户可见的声明根**，不猜、不递归遍历磁盘。

**选项 B｜A + "开发期自动识别仓库产物"**

- 在 A 之上，启动时若检测到上层目录存在 `HYWDebugAssistant.slnx`，**自动**把 `<仓库根>\artifacts\modules` 加进根列表。
- 优点：开发期**零配置**；
- 缺点：**隐式行为**（同一个 exe 在不同目录启动会扫到不同东西）——与"显式加载"的设计传统冲突（§11.2 的原文就是反自动）。

**选项 C｜递归/全盘搜索**

- 递归扫描磁盘或仓库，找所有 `module.json`。
- 我**不建议**：① 与 §11.2 直接冲突；② 会扫到 `obj/`、旧版本、他人构建产物；③ 性能与可预测性差（用户无法回答"我的模块从哪来的"）。若坚持，必须做深度/白名单/超时护栏。

**选项 D｜把所有包做成"单一文件"（zip/`.hympkg`）**

- 包形式变化 → 破坏 ADR-0020 结论、模块包脚本、既有加载路径。**建议不做**（收益仅是"拷贝方便"，与自动发现无关）。

### 1.3 配套：谁产出包、产到哪里（**这是你说的"文件结构"部分**）

现状是**脚本归拢**（`build.ps1` → `stage-reference-modules.ps1`）。建议改为**构建即产出**，理由是"不依赖人记得跑脚本"：

| 方案 | 做法 | 评价 |
|---|---|---|
| **建议：MSBuild 归拢** | 新增 `src/Modules/Directory.Build.targets`：模块项目构建后，把 `module.json` + 输出程序集 + 依赖复制到 `artifacts\modules\<包名>\`；`App` 项目构建后把 `artifacts\modules\*` 复制到 `$(OutDir)modules\` | `dotnet build` 一步到位；`artifacts/` 已在 `.gitignore`（构建产物不污染仓库）；脚本保留用于**发布打包** |
| 备选：保持脚本 | 现状 | 每写一个新模块都要改脚本里的模块清单（现在就是硬编码 5 项）——**这正是"每次都要找目录"的根因之一** |
| 备选：模块项目直接输出到统一目录 | 用 `OutDir` 重定向 | 会打乱 `bin/<cfg>/net10.0` 既有布局与测试引用路径，风险高 |

> 说明：`module.json` **不写死**在脚本或 targets 里；targets 通过项目属性（`<ModulePackageName>`，默认取项目名后缀）推导，新增模块项目**零改动**。

### 1.4 包的唯一性与版本（必须定规则，否则会踩坑）

| 情形 | 建议规则 |
|---|---|
| 两个根含**同 ID 同版本** | 先到者胜；后者记 Info（"已由更早的来源装入"） |
| 两个根含**同 ID 不同版本** | **都装入**（注册表本就支持多版本共存）；「加入现场」时以**最新版本**为默认（现在没有"选版本"的入口 → 属可选增强） |
| 应用目录里的**旧版本残留** | 归拢时**清理目标包名目录再复制**（避免新旧 DLL 混在同一目录） |
| 包目录里有**多余文件** | 允许（不校验白名单），但加载失败时提示要给出**具体缺什么** |

### 1.5 开发期热更新的边界（**你调试不便的第二个来源，必须讲清**）

- 事实：`Assembly.LoadFrom` → 默认 ALC → **程序集不可卸载**；同一路径的 DLL 被替换后，**进程内仍是旧代码**。
- 因此："重扫"只能发现**新增**的包；**改过代码的包必须重启应用**。
- 三条路：
  1. **【建议 v1】重启 + 明确提示**：重扫时若某包目录的写入时间**晚于本进程启动时间**，提示"该包在本次启动后被重新构建，重启应用才会生效"（Issue + 模块清单红字）；
  2. 【建议 M2】**可卸载的 `AssemblyLoadContext`**：为每个包建 collectible ALC 实现真热重载。要点与风险：`Sdk` 程序集必须由**默认上下文**解析（否则类型标识不同一，`IModule` 判定失败）；模块静态状态、后台线程、池化缓冲的生命周期都要能被回收；需要新的设计（ADR）+ 不小的工作量；
  3. 【不建议】改包目录名/版本号假装新包 → 语义混乱（同一份代码两个身份）。

### 1.6 诊断能力（顺带解决"我不确定它到底扫了什么"）

在「模块清单」弹窗显示：**每个根的路径 · 扫到的包数 · 失败的包与原因 · 跳过（无 module.json）的目录数**；并提供「打开目录」「立即重扫」。这条对调试的价值不低于自动发现本身。

### 1.7 议题一的影响面

| 层 | 变更 | 需要什么 |
|---|---|---|
| `Sdk` | **无** | — |
| `Core.Api` | 新增：`GetModuleSources()`（根 + 每根结果）· `RescanModuleSources()` 命令 | ADR + 主文档 §11.2 回写 |
| `Core` | 扫描逻辑支持**多根 + 顺序 + 去重**；`ModuleSourceDirectory` → 列表 | 同上 |
| `Core.Api`/`Settings` | `ApplicationSettings` 增 `moduleSourceDirectories`（列表）；**兼容扩展**（已知字段增加，旧文件照常读） | 主文档 §9.5 回写 |
| 构建 | `src/Modules/Directory.Build.targets` + `App` 的输出复制 target | `02` §2.2/§2.4 回写（产物目录约定） |
| 脚本 | `stage-reference-modules.ps1` 改为"发布打包用"，模块清单不再硬编码 | `02` |
| 文档 | §11.2"不自动扫任意位置"的**措辞细化**（明确 = 只扫声明根） | ADR-0036 |

## 2. 议题二：模块窗口的层级（你的第 2 条）

### 2.1 现状（已核实的实现事实）

- 模块窗口：`ShowInTaskbar=false`、`WindowDecorations=None`、**没有设置 `Owner`**（`ModuleWindowManager` 里是 `window.Show()` 无参调用）；
- 外壳工具条：普通窗口；
- 弹窗（模块清单/Issue/设置/拓扑诊断）：`dialog.Show(this)` → **有 Owner**，因此弹窗始终在外壳之上。

**结论**：模块窗口与外壳**没有从属关系** → 点一下外壳就把它盖住；被其他应用盖住后（不在任务栏/Alt+Tab 里）就"找不着了"。**这是我漏掉的语义，不是有意的取舍。**

### 2.2 方案选项

| 选项 | 做法 | 效果 / 评价 |
|---|---|---|
| **A（用户已裁决采用）** | ① 模块窗口 **`Owner = 外壳窗口`**；② 每个窗口按钮簇加~~「置顶」开关~~（**已撤销，见下**）；③ 菜单/工具栏加**「全部置前」**；④ **应用整体层级统一**：任一本应用窗口被激活 → 其余窗口一并抬升；应用级「全部置顶」开关控制整个应用相对其他应用的位置 | **符合用户口径**：应用内 弹窗 > 模块窗口 > 外壳；应用整体相对外部应用**只有两种统一状态**（普通 / 全体置顶），不存在"一部分被覆盖、一部分置顶" |
| ~~B~~ | ~~模块窗口一律全局 `Topmost`~~ | 用户排除：会造成整体层级不一致 |
| ~~C~~ | ~~模块窗口 `ShowInTaskbar=true`~~ | 改为**设置项**（默认关），不作为默认行为 |
| D（**用户否决**） | ~~不做层级，只加「全部置前」~~ | 治标：点外壳仍会盖住模块 |

> **用户补充裁决（原话要点）**："我提到的不只是应用内的层级，而是在其他应用下的应用内层级统一性，整个应用的各个模块应为一个整体的层级，不应被外部其他应用的窗口覆盖一部分，一部分又置顶，所有模块和主窗口应具有层级上的统一性。"
> → **因此撤销"每窗口各自置顶"的设计**，改为**应用级**两种统一状态（普通 / 全体置顶）+ **激活时组抬升**。完整规格见 **ADR-0036 D5**。

> 可组合：**A +（可选）C**。C 是否要，我倾向**默认关**、作为设置项（"模块窗口显示在任务栏"），由你定。

### 2.3 议题二的影响面

`ModuleWindowManager`（设 Owner、`全部置前`）· `ModuleWindow`（置顶按钮）· `ShellViewModel`（命令）· `05` §5.14 窗口行为表 · 验收清单增 1~2 条。**不涉及契约与构建**，是实现层修复 + 一处行为约定（"模块窗口从属于外壳"）需回写。

## 3. 议题三：设置分类 + 快捷键显式化（你的第 3 条）

### 3.1 现状

- 设置弹窗是**一列平铺**（框架行为 / UI 偏好 / 模块来源与日志），无分类导航；
- 快捷键**硬编码**在 `MainWindow.axaml.cs` 的 `KeyDown` 里（`M/I/S/T/L/G/Ctrl+L`），**只在"外壳窗口聚焦"时生效**；
- 设置里**看不到**快捷键清单，更不能改；
- `10-delivery-and-ops.md` §"快捷键清单位置"本已把"快捷键清单"归到设置界面 —— **我漏做了**。

### 3.2 设置分类方案（建议）

```text
设置（左侧分类 · 右侧页面，即时生效）
├─ 常规              启动行为（上次组合件恢复，后续）· 便携目录说明
├─ 模块与来源   ★    来源根列表（增/删/排序/「填入工程默认值」/「立即重扫」）+ 每根结果 + 包清单（内置/第三方）
├─ 窗口与交互   ★    吸附开关与容差 · 整组拖动修饰键（Ctrl）· 临时停用吸附修饰键（Alt）· 锁定语义说明 · 模块窗口是否进任务栏
├─ 外观与显示        刷新率 · 口上标记 · （主题 = 后续）
├─ 快捷键       ★    动作清单 + 当前绑定 + 修改/重置/冲突检测（见 3.3）
├─ 日志与诊断        日志级别 · 诊断提示阈值 · Issue 上限 · Issue 保留策略
└─ 关于              版本 · 构建配置 · 依赖许可摘要 · 帮助（快捷键/用法）
```

（★ = 本次要新增/改动的内容）

### 3.3 快捷键设计（建议）

| 项 | 方案 |
|---|---|
| **作用域** | **应用内**：本应用**任一无边框模块窗口或外壳窗口聚焦**时都生效（现在只有外壳聚焦时才生效 → 这是你现在"似乎有但按不出来"的原因之一） |
| **模型** | `hotkeys: { "<动作>": "<键+修饰键>" }`；动作 = 固定枚举（打开模块清单/Issue/设置/拓扑诊断 · 切换口上标记 · 切换吸附 · 全部锁定 · 全部置前 · 显示全部窗口） |
| **编辑** | 点一行 → 按新键捕获（含修饰键）；**冲突即时提示**；「重置该项」「全部重置」；空值 = 不绑定 |
| **持久化** | 进 `settings.json`（**已知字段增加 = 兼容扩展**；无需迁移，旧文件缺该项即用默认） |
| **不做（v1）** | **系统级全局热键**（应用未聚焦也响应）需要 Win32 `RegisterHotKey` 互操作（占用全局热键、可能与其他软件冲突）→ 列为后续选项，需单独裁决 |
| **文档** | 快捷键清单以设置页为准（`10` 已如此规定），验收清单同步 |

### 3.4 议题三的影响面

`ApplicationSettings`（+`hotkeys`、+`moduleSourceDirectories`、可选 +`snapTolerance`/`showModuleWindowsInTaskbar`）· `SettingsPanelViewModel` 拆分为**分类化结构**（每类一个子视图模型）· 新增 `HotkeyService`（挂在所有本应用窗口上）· `SettingsView` 改为左右分栏布局 · `05` §5.7/`10` 回写 · 验收清单同步。
