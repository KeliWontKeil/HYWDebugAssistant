# 第 4 章支撑分析（一）：数据面执行模型与数据单元物理表示评估

> 状态：**已裁决（参考材料）**——Q4-1/Q4-2 已由 ADR-0029 裁决，Q4-3/Q4-4/Q4-5 与 C4-1~C4-4 见 `04-key-mechanisms.md` §4.10；本文保留为决策依据。
> 关联：`04-*`（第 4 章）· `03-module-sdk.md` C3-2/C3-5/C3-6（硬约束）· ADR-0013（框架统一承载活动）· ADR-0023 §2（零分配数据面）· `technology-selection/02` §1/§2（既有量级图景）
> 用途：评估用户提出的"**每模块绑定一个工作线程 + 线程间通信**"方案，并评估数据单元物理表示。本文只做评估，不含倾向性推荐（末尾列出需裁决项）。

---

## 1. 背景

Q4-1（执行模型）与 Q4-2（数据单元物理表示）是第 4 章的两块基石：前者决定**投递路径的成本与隔离性**，后者决定**每个单元在内存里的样子**。二者强耦合——投递机制决定了数据是否必须搬运、以什么形式搬运。

用户提出的方向：**每个模块绑定一个工作线程，数据传输经线程间通信机制；调度与运行时全部交给框架，模块自身不做调度设计。**

---

## 2. Q4-1 执行模型评估

### 2.1 先澄清一件事：这不是 IPC

同进程内的"线程间通信"**不是**进程间通信：不需要序列化、不需要系统调用、不需要协议。它的本质是**共享内存 + 内存可见性/同步管理**。因此"可行性"不构成障碍——这是 .NET 生态中最成熟的模式之一。真正需要评估的是**代价**。

.NET 现成设施（无需自研）：

| 设施 | 形态 | 元素类型 | 备注 |
|---|---|---|---|
| `System.Threading.Channels` | 有界/无界队列，异步消费 | 支持 `struct`（泛型特化，无装箱） | 官方维护；有界模式提供等待/丢弃策略 |
| `BlockingCollection<T>` | 同步阻塞集合 | 值/引用 | 有锁，同步阻塞，适合专用线程 |
| 自研 SPSC 环形缓冲 | 无锁、单生产单消费 | 值类型/字节 | 最简单的无锁结构；需自行保证正确性 |
| `System.IO.Pipelines` | 面向字节流的分段缓冲 | 字节 | 适合"解析流"类场景 |
| 专用 `Thread` / 线程池 `Task` | 承载者 | — | 决定线程数模型（见 §2.5） |

### 2.2 该方案的优点（客观）

1. **隔离性最强**：一个模块阻塞、卡顿或长耗时，不影响其他模块——AC-2 直接受益；这也是与"上游无数据是合法状态"（§8.2 类 a）配合最自然的结构。
2. **模块作者模型最简单**：每模块单线程执行（Actor/消息驱动语义）→ **模块内部无需加锁**，不存在"回调被并发进入"的心智负担。
3. **与 ADR-0013 相容**：线程由**框架**创建与管理，模块只是"跑在框架给的线程上"——模块仍不自建线程，"框架统一承载活动"成立。
4. **调度集中**：线程生命周期、队列、公平性、丢弃策略、异常边界全部属于框架 L3 的职责，符合 C1-2（承载与调度归 L3）。
5. **实现难度确实较低**：不需要拓扑分区分析、不需要协作式让步协议；丢弃语义按模块（或按口）天然清晰。
6. **天然支持模块自发活动**（C3-2）：线程在无输入时可执行周期活动，不需要额外的"活动调度器"概念。

### 2.3 该方案的代价（量化）

| # | 代价 | 量级 / 说明 | 缓解手段 |
|---|---|---|---|
| 1 | **线程数随模块数线性增长** | §13.1 要求模块数量不设上限。每模块一线程时，1000 模块 = 1000 线程（Windows 默认 1 MB **保留**栈/线程，实际提交通常 4–64 KB；可指定 256 KB） | ①限定栈尺寸；②改用"逻辑队列 + 池化消费"（§2.5 形态 B），线程数不再随模块数增长 |
| 2 | **投递延迟上升** | 直接函数调用 ~1–5 ns；无锁队列入队+出队 ~20–50 ns（含内存屏障）；若需**唤醒**等待线程 → OS 调度 ~1–10 µs；忙轮询可压到 ~100 ns 但占满 CPU 核 | 批量投递（一次搬多个单元）；就绪队列 + 短自旋；按场景调队列深度 |
| 3 | **每单元数据搬运** | 跨线程必须把数据搬进消费者可见的缓冲，或移交所有权。**定长契约（C3-5）使拷贝成本可预测**：64 字节 ≈ 几 ns | 池化缓冲 + 所有权移交（零拷贝）；或用值类型 struct 直接入队（一次拷贝） |
| 4 | **分配风险** | 若队列元素是引用对象（每单元 `new`）→ 10⁶/s 即 10⁶ 对象/s，GC 长尾回升（`technology-selection/02` §2 的缓解被抵消） | 队列元素必须是**值类型或池化缓冲**；由框架提供，不落在模块作者身上 |
| 5 | **链式延迟累积** | A→B→C 三模块三线程 = 两次队列交接 + 两次唤醒。端到端可能从纳秒级升到**微秒级** | 同线程快路径（§2.7）；拓扑分区；批量 |
| 6 | **调试与可观测性变难** | 多线程 + 队列使问题定位困难（谁丢了数据？队列积压多少？） | 框架必须提供 L1/L4 诊断：队列深度、丢弃计数、最后数据时间（§13.2 已有此项） |
| 7 | **并发正确性风险集中在框架** | 队列、可见性、池归还协议一旦写错极难发现 | **不自研无锁结构**，优先 `Channel<T>`；若需自研，只做 SPSC 环形缓冲 |

### 2.4 一个关键量化判断：队列延迟相对数据到达间隔是否显著？

这决定该方案在**目标场景**下是否"够用"（技术选型 02 已定位本项目为**数据监视/分析类工作台，非硬实时控制器**）：

| 场景 | 单元到达间隔 | 与 µs 级投递延迟比较 |
|---|---|---|
| 串口 115200 bps | ~87 µs/字节 | 延迟约为间隔的 1–10% |
| CAN 1 Mbps | ~8 µs/帧 | 延迟与间隔同量级（需注意） |
| 采集 1 kHz | 1000 µs/单元 | 延迟可忽略 |
| 采集 10 kHz | 100 µs/单元 | 延迟约 1% |
| 采集 1 MHz | 1 µs/单元 | **延迟超过间隔**（队列会成为瓶颈；需批量或单线程直调） |

**结论**：在 kHz 量级与常规总线速率下，队列投递延迟相对数据到达间隔通常很小；**只有在 10⁶ 单元/秒以上、或存在硬周期要求的模块上**，投递机制才会成为主导成本。这属于 Gate B 的实测范围（§5）。

### 2.5 该方案的两种具体实现形态

| 形态 | 承载 | 线程数 | 优点 | 代价 |
|---|---|---|---|---|
| **A. 每模块一个专用线程**（用户原始设想） | `Thread` + 阻塞/自旋等待队列 | = 模块数（线性） | 语义最简单；隔离最强；延迟可预测（可自旋） | 线程数随模块数增长；线程空闲也占资源 |
| **B. 每模块一个逻辑队列 + 池化消费** | `Channel<T>` + 线程池任务（异步消费），或框架自建"就绪队列 + 固定工作线程" | 与应用并行度相关（可固定，如 = 核数） | 保留"模块单线程语义"，线程数**不随模块数增长** | 需异步/就绪队列调度；唤醒延迟受线程池影响；模块回调不得阻塞（否则饿死池线程） |

形态 B 保留了用户方案的全部语义优点（每模块一个队列、模块单线程、调度归框架），同时消掉了"线程数线性增长"这一最主要代价。

### 2.6 五个候选架构对比

| 候选 | 隔离性 | 投递延迟 | 吞吐上限 | 线程/资源 | 实现难度 | 模块作者模型 |
|---|---|---|---|---|---|---|
| **A 单线程串行** | 低（一个模块卡住全局） | 最低（直调 ns 级） | 单核 | 1 个数据面线程 | 最低 | 单线程，无锁 |
| **B 每模块一线程 + 队列**（用户方案） | 最高 | 队列 + 唤醒（ns–µs） | 多核 | 随模块数线性 | 中 | 单线程，无锁 |
| **C 拓扑分区**（每链路一线程，链路内直调） | 中高（跨链路隔离，链路内不隔离） | 链路内直调、跨链路队列 | 多核 | 随链路数增长 | 中高（需拓扑分析） | 链路内串行 |
| **D 池化消费**（每模块逻辑队列 + 固定工作线程） | 高 | 队列 + 唤醒 | 多核，可控 | 固定（≈核数） | 中高 | 单线程语义，但不得阻塞 |
| **E 混合**（分区内直调 + 分区边界队列） | 中高 | 边界处队列，内部直调 | 多核 | 随分区数增长 | 最高 | 混合语义 |

### 2.7 一个贯穿性的设计洞察：统一投递模型 + 同线程快路径

无论最终选哪个候选，下列结构可以把"性能"与"隔离"解耦：

```text
投递语义务必统一为：写入「目标模块的输入队列」
若目标模块与当前执行线程相同 → 直接调用模块回调（零队列、零拷贝）
否则 → 入队（有界、可丢弃）+ 由承载者调用
```

- 受益：**执行模型成为可配置策略**（单线程串行 / 每模块线程 / 池化消费 / 拓扑分区），而**模块与绑定代码不变**；
- 性能：单线程模式下自动退化为直调（无队列开销，延迟最低）；多线程模式下才有队列成本；
- 演进：可以先用最简单模型落地（先直调），在 Gate B 实测后**按数据开启并行**，而不是设计期一次性押注。

> 这是本文最重要的工程结论：**"执行模型"不该被实现代码硬编码，它应是 L3 承载设施的一个策略。**

## 3. Q4-2 数据单元物理表示评估

### 3.1 既有图景回顾（已冻结/已评估）

- **ADR-0023 §2**：数据面 = C# **严格零分配设计**（`struct`/`Span<T>`/`Memory<T>`/`ArrayPool<T>`、批量传递、避免装箱与委托分配）；GC = Server GC + 低延迟模式。
- **`technology-selection/02` §1**：内存队列传递结构体消息 **~10⁶–10⁷ 单元/秒**（每单元约 10–100 ns）；字节流解析 0.1–1 GB/s+。**均为待实测的量级区间，非承诺值。**
- **`technology-selection/02` §2**：GC 不影响吞吐而影响**延迟长尾**；本项目"有界缓冲 + 丢帧 + 数据面直通 + UI 隔离"天然吸收抖动；池化缓冲可把分配率压到近零。
- **C3-5（本次已裁）**：契约 = **定长原语 + 结构组合**，无变长 → **每个数据单元的大小在加载期已知且恒定**。这是本问题最重要的前提：它使"扁平化"与"预分配"成为可能。

### 3.2 四个候选方案

| 方案 | 数据在内存中的样子 | 模块作者看到的 | 关键依赖 |
|---|---|---|---|
| **① 引用类型对象** | 每单元一个托管对象（class/record） | 强类型对象 | 无 |
| **② 扁平字节 + 元数据解释** | 池化定长缓冲 + 契约元数据（字段偏移/类型） | 通过读写 API 访问字段（`reader.Get<float>(offset)`） | 池化与归还协议 |
| **③ 加载期特化** | 同上（存储仍是扁平/池化） | **强类型 struct 视图**（按契约类型生成的访问器） | 加载期为每个已注册契约生成投递/访问代码（动态方法或源生成） |
| **④ 泛型 struct 直传** | `Channel<T>`/队列里的值类型实例（泛型特化，无装箱） | 强类型 struct | **框架侧需要已知 T** → 对"未知契约类型"不通用 |

### 3.3 关键约束：框架必须面对"未知契约类型"

框架在设计期不知道任何具体契约类型（P16/E7），因此：

- 方案 ④（泛型 `Channel<T>`）只能用在**框架与契约类型在同一泛型上下文**的地方；跨"未知类型"的通用投递路径无法直接使用它——除非加载期为每个契约生成专用通道（即退化为方案 ③）。
- 方案 ①（引用对象）对框架最通用（`object`），但正是零分配目标的对照面。
- **框架通用性的自然结果是"类型擦除"**：统一以"定长缓冲 + 契约元数据"表示（方案 ②）。方案 ③ 则是在类型擦除的存储层之上，为每个契约**生成强类型访问层**。

### 3.4 对比

| 维度 | ① 引用对象 | ② 扁平字节 + 解释 | ③ 加载期特化 | ④ 泛型 struct 直传 |
|---|---|---|---|---|
| 每单元分配 | **有**（每单元一对象） | 零（池化） | 零（池化） | 零（值类型） |
| 10⁶ 单元/秒下的 GC 压力 | 高 | 无 | 无 | 无 |
| 缓存局部性 | 差 | 好（连续缓冲） | 好 | 中（按值拷贝） |
| 类型安全 | 强（编译期） | 弱（运行期检查/偏移） | 强（生成的访问器） | 强（编译期） |
| 模块作者体验 | 最直观 | 需学读写 API | **直观**（强类型视图） | 最直观 |
| 跨线程/队列友好度 | 中（引用需注意所有权） | 好（值语义） | 好 | 好 |
| 未知契约类型的通用性 | 好 | **好** | 好（加载期生成） | **差** |
| 实现难度 | 低 | 中 | **中高**（需代码生成设施） | 低（但仅限已知 T） |
| 与 C3-5 定长契约契合 | 一般 | 完全 | 完全 | 完全 |
| 调试友好度 | 好 | 差（需工具解码缓冲） | 中 | 好 |

### 3.5 可能的组合（"更优做法"的候选）

**存储层统一为扁平定长缓冲（方案 ② 的物理形态），访问层按契约类型生成强类型视图（方案 ③）**：

```text
契约类型（作者写的 C# struct，成员限定长原语）
        │  加载期：读取形状元数据
        ├─► 生成「字段偏移表」        → 供框架侧通用读写（兼容判定、诊断、序列化）
        └─► 生成「强类型访问器/视图」  → 供模块侧直接按类型读写（无反射、无装箱）
存储：池化定长缓冲（跨线程、排队、丢弃、可零拷贝移交）
```

- 收益：零分配 + 强类型作者体验 + 框架通用性三者同时成立；兼容判定可直接用偏移表计算（**形状结构比较**〔**ADR-0051**〕）。
- 代价：需要一套"加载期生成"设施（表达式树/`DynamicMethod`/源生成），以及池化缓冲的**所有权与归还协议**。
- 风险点：生成代码的调试与错误提示；池归还错误（双重归还/泄漏）需框架侧断言与诊断计数。

### 3.6 与执行模型（Q4-1）的耦合

| 执行模型 | 与数据表示的相互作用 |
|---|---|
| 单线程串行（直调） | 可以零拷贝传引用/`ref`/`Span`；对象方案也可接受（但仍建议扁平，避免 GC 长尾） |
| 每模块线程/池化消费（队列） | 必须解决"数据如何跨线程" —— 值拷贝或所有权移交；**引用对象需明确所有权（谁释放）** |
| 拓扑分区 | 分区内可零拷贝，分区边界需要队列 → 边界处用扁平缓冲最自然 |

**结论**：若执行模型保留"队列"这一路径（用户方案的核心），则**扁平池化缓冲是代价最小的共同分母**；方案 ②与③的区别只是"访问层是否生成强类型视图"。

## 5. Gate B：需要原型实测的数值

无论选哪一个，下列数值都必须在框架骨架可运行后用 BenchmarkDotNet 实测（对应 §18.5-B 的"数值指标"与 ADR-0023 §2 的"待实测"）：

1. 单次投递（直调 vs 入队+出队）耗时（ns）；
2. 跨线程唤醒延迟（µs），自旋 vs 事件两种策略；
3. A→B→C 三跳端到端延迟（µs）；
4. 每单元分配字节数（目标 0）；
5. 单线程与多线程吞吐上限（单元/秒）；
6. 10⁶ 单元/秒持续负载下的丢弃率、GC 次数与最长暂停；
7. 每模块一线程时，100 / 300 / 1000 模块的线程内存占用与上下文切换开销；
8. 池化缓冲的归还正确性断言开销。

### 5.1 首轮实测结果（M1-13 · **只记录、不设阈值**）

> 环境：13th Gen Intel i9-13980HX（24 逻辑核）· Windows 11 24H2 · .NET 10.0.12 · Release · 简版 job（预热 1 / 迭代 3）

### 5.2 首轮实测暴露的两个**待裁决**项（M1-13 只记录，不改机制）

**发现一：空闲唤醒粒度 = 15.6 ms——但**根因是"用错了等待原语"，不是 `Thread.Sleep` 的实现****

- 现象（**三种接收模式对照实测**，同一两跳链 A→B、同一契约、单单元往返）：

  | 接收模式 | 单单元两跳延迟 | 说明 |
  |---|---|---|
  | **被动接收**（模块只 `SetReceiveHandler`，**框架投递循环**等待） | **893 ns** | 框架用 `SemaphoreSlim` + **入队即 signal**（`ModuleCarrier._dataAvailable`），本就是事件唤醒 |
  | **主动接收 + `StopSignal.Wait(1ms)`**（参考桩模块当前写法） | **15.70 ms** | `IStopSignal.Wait` 的语义是"等**停止**信号"，被当成"等数据"的轮询间隔用 → 每次空转等满 1 ms，而 Windows 定时器分辨率 15.6 ms |
  | **主动接收 + 自旋轮询** | **781 ns** | 忙等；快但占一个核 |

- **根因更正**：问题不在 `Thread.Sleep`，而在**"等数据"缺少专用原语**——`IStopSignal.Wait` 只等停止，数据到达**不会**唤醒它（`ModuleCarrier.TryEnqueue` 只 signal 数据信号，不 signal 停止信号）。因此"把停止信号改成 `ManualResetEventSlim`"**解决不了**这个延迟（模块仍要等满超时才会去看队列）。
- **影响面**：被动接收路径（框架驱动投递）**完全没有该问题**（893 ns）；主动接收路径在**低频**下退化到定时器粒度，在**连续流**下无影响（1.82 µs / 3 跳）。
- **用户裁决（M1-13 收尾）**：**① + ②** —— ① **参考桩模块改用被动接收**（**已实施**：`Recorder`/`Asserter` 不再实现 `IActivitySource`，改由框架投递循环驱动，实测 893 ns；主动接收路径的组合级覆盖由新增的 `ActiveReceiveTests` 保留）；② **`WaitForData` 列为本里程碑之后的 SDK 兼容扩展项**（让主动接收也能微秒级且不占核；新增成员 + 回写 `03`/`04`）。
- 与本文件 §7 结论的关系：§7"稳态成本为百纳秒级"**在连续流下成立**（实测 1.82 µs / 3 跳）；**"空闲后唤醒"一侧原估算（1–10 µs）偏乐观**——Windows 默认调度下按"停止信号当轮询"的写法实际是 15.6 ms 级。本节即该结论的实测修正。

**发现二：投递路径每单元 40 B 分配（未达"每单元分配 0"目标）**

- 现象：`借+还` 与 `完整投递` 两个基准均为 **40 B/op**；订阅写入路径已是 0 B（M1-9 实测）。两跳链基准另测得 **128 B/2 跳**（与 40 B/单元 × 目标数一致）。
- 原因：`PooledPayloadBufferPool.Rent` 每次都 `new PooledPayloadBuffer(...)` 生成**包装对象**（`PayloadBuffer` 是 abstract class）；**1:N 组播时按目标数放大**。
- 实测影响：10⁶ 单元/秒 ≈ **40 MB/s** 分配；持续负载下 gen0/1/2 回收 50/43/36 ~ 319/74/68 次、**总暂停 0.37–0.81%**、**最长暂停 0.06–0.90 ms**（进程为 Concurrent Workstation GC）。即 **≈0.5% CPU 开销 + 亚毫秒尾延迟**，对"监视/分析"目标可接受。
- 但**它与设计承诺不一致**：`04a §5` 第 4 项目标写的是"每单元分配 0"（ADR-0029 Q4-2 的"零分配热路径"）。因此必须**二选一**：改实现，或改承诺。
- **用户裁决（M1-13 收尾）**：**① 池化包装对象** —— 列入**后续里程碑首项**（L3 内部空闲链复用 wrapper：不动 SDK 面、不需 ADR；改动约 40–60 行 + 补充"复用后计数不增长"等测试）；**在此之前文档承诺以本节实测为准**（即"投递路径每单元 40 B、订阅路径 0 B"），实现完成后回写为 0。
- 相关残余问题（**另记、不属本项**）：`ReceiveHandler` 只收到 `ReadOnlySpan<byte>`，**不带布局**；当接收契约是发送契约的**超集**（形状子集兼容允许）时，接收方无法知道发送方的字段偏移，按自身布局读取会读错位置。这是"不自动转换"语义下的**契约/布局缺口**（不属性能问题），列为后续里程碑的待议项。
  - **〔已关闭 · ADR-0051〕**：该缺口的**前提已被移除** —— 兼容判据由"接收 ⊇ 发送"（子集）改为 **形状完全一致**，不存在"接收方是超集"的合法连接；且框架保证**到达的数据报长度 = 本口契约尺寸**（接收方按自身布局读取因此总是正确）。防御式读取（`PayloadReader.TryCreate`）保留为兜底。

## 7. 延迟数据的修正说明（对 §2.3 代价 2 的更正）

用户在裁决中指出本文对"线程唤醒延迟"的估算可能偏高，要求慎重。经复核，**原估算偏保守，更正如下**：

| 路径 | 延迟量级 | 说明 |
|---|---|---|
| 同线程直接调用 | ~1–5 ns | 基线 |
| 无锁 SPSC 入队 + 出队（缓存命中） | ~20–80 ns | 含内存屏障 |
| 跨核缓存行传递（MESI 转移） | ~100–300 ns | 生产/消费不同核 |
| **自旋等待** | **百纳秒级** | = 队列传递成本；代价是占用一个核 |
| 事件/信号量唤醒（Windows 通用调度，有空闲核） | ~1–10 µs | 含系统调用与调度器；核忙时更差 |
| RTOS 任务唤醒（对照，**不可直接类比**） | ~百纳秒级 | RTOS 内核与应用同特权级、系统调用极轻；Windows 需进内核并走调度器 |

**关键更正**：1–10 µs 只出现在**空闲后唤醒**；**稳态流水线中消费者通常并未真正睡眠**（刚处理完上一单元即继续等待），此时"唤醒"退化为"发现数据已就绪"，成本接近纯队列传递（百纳秒级）。而需要微秒级唤醒的低频场景中，该延迟相对数据到达间隔本身不敏感。

**可用的收敛手段**（Windows 侧）：`SpinWait` / `ManualResetEventSlim` 的自旋+阻塞混合策略、线程优先级、CPU 亲和性与核隔离；必要时对少数高频模块采用忙等。

**结论**：原 §2.3 代价 2 的量级对"活跃模块数十、以监视/分析为主"的目标场景而言，稳态成本为**百纳秒级**；微秒级仅出现在低频唤醒路径，可接受。具体数值仍由 Gate B 实测（§5）。
