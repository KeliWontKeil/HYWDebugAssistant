## 2. 设计决定（**多源必须实现**前提下的推荐；M1–M14）

### M1. 多源的定性：**合法的一等组合**（不再拒绝）

- **框架不隐式仲裁**（不猜优先级、不做语义合并）；**框架提供中立的"多源 → 多宿"投递**；语义级合并/仲裁由**模块**或未来"策略声明"承担。
- **被拒的旧行为作废**；改用**显式表达**：同名标签的多发送端 = **一条多源网络**（用户意图最自然的表达方式）；几何对齐**不自动合并**（见 M8）。
- **Issue 语义更新**：仅当"部分源契约不兼容 / 源悬空"时标注**该源**，**不再整条拒绝**（M6）。

### M2. 模型：**多源 + 多宿**（N:M）

```
Network {
  Name                 // 命名网络名（匿名对齐网络为空）
  Sources : [NetworkMember]    // ≥1（本轮解禁：可多源）
  Targets : [NetworkMember]    // ≥1（已是多宿）
  MergePolicy : ArrivalOrder   // v1 唯一策略（见 M3）
  IsAutoGenerated · IsStalled · UnresolvedMembers
}
```
- **绑定**：仍按**网络**建立；**投递**：每个源独立投递到每个宿（1:N×M 由"每 (源,宿) 对"一条投递关系表达），**保持零拷贝与字节守恒**（ADR-0046 D4）。
- 术语：`Network.Source` → **`Sources`**（列表）；相关 API/视图同步（`NetworkView.Sources`）。

### M3. 接收策略：**框架中立投递（按到达顺序）**，不做排序/优先级/去重

| 策略 | 是否由框架做 | 说明 |
|---|---|---|
| **按到达顺序投递（ArrivalOrder）** | ✅ **v1 唯一** | 最中立：不猜语义、零开销；冲突由用户用模块解决 |
| 交叉接收（interleave） | ✅ 即 ArrivalOrder 的自然结果 | 宿队列里多源数据按到达顺序混装；**来源可辨**（M4） |
| 按优先级 | ❌ 框架不做 | 需要"谁更重要"= 应用语义；由**模块**（或未来策略声明）承担 |
| 按时间戳排序 | ❌ 框架不做 | 框架不附加时刻（ADR-0046 D5）⇒ 只有模块自带时刻才可能 |
| 去重/节流 | ❌ 框架不做 | 属应用语义 |

### M4. ~~来源识别（sideband）~~ → **撤回；改为"来源属应用层 + 观测面从模型取"**

**用户第二十三轮提议（更符合分层，采纳）**："或许**不用显式来源识别**，而是通过某种**压栈/出栈**的模式，只要定好**压栈规则**，数据包**出栈顺序自然明确**，**接收端本身并不需要关心数据从哪来的**，底层接收端只需要知道'这是数据'然后压栈，能不能解析成功、怎么用是**应用层**的事情，**输入输出是任意的**……就好像**交换机看起来不会提供任何仲裁**一样。"

**采纳后的形态**：

| 面 | 是否携带/暴露来源 | 依据 |
|---|---|---|
| **数据面**（投递到宿） | **不暴露**（框架零附加；不写 payload、也不给 sideband 参数） | 用户口径 + ADR-0046 D4（既有裁决，**保持一致**） |
| **应用层** | **需要来源就自己带**（在模块契约里加来源/序号字段，如 `{seq,t,value}`） | ADR-0046 D4 / §5.4.2 第一条（**原裁决不变**） |
| **观测面**（拓扑 / 叠加层 / 诊断） | **可以显示来源** —— 框架**从绑定模型（网络成员关系）就能知道**，**无需读数据** | 本 ADR 新增：来源是**声明/拓扑事实**，不是数据事实 |

⇒ **M4 原方案（`SetReceiveHandler` 加重载传来源）撤回**；§5.4.2"下游不应知道数据源身份"**不再需要修订**（回到原裁决）。

### M4b. **顺序保证等级**（"压栈规则"必须写死的内容）

用户"只要定好压栈规则，出栈顺序自然明确"**成立**，但须明确**保证等级**（**FIFO 队列，不是 LIFO 栈**——见 §5.1 术语澄清）：

| 范围 | 保证 |
|---|---|
| **同一 (源, 宿) 对** | **FIFO 强保证**：不得乱序、不得重复、不得丢（除非明确丢弃并计数） |
| **不同源之间** | **无顺序保证**（只保证每源各自 FIFO）；多源到同一宿口时 = **按到达顺序交织** |
| **跨源时间序** | **框架不提供**（不附加时刻，ADR-0046 D5）⇒ 需要时间序的应用**自带时刻字段** |

### M5. 停流 / 悬空 / 合法性（多源版）

| 情形 | 处理 |
|---|---|
| 源集合为空（只有宿） | **未建网**（保留标签 + 提示"等发送端"）——现状语义保留 |
| 宿集合为空 | **未建网**（保留标签 + 提示"等接收端"）——现状语义保留 |
| **全部源**未锚定（口/实例缺失） | **停流**（`IsStalled`，保留声明、不投递、每源标注 Issue） |
| **部分源**不可用/不兼容 | **其余源照常投递**；不可用者**保留声明 + 该源 Issue**（M6） |
| 多源同名标签 | **合法**（M1），不再拒绝 |

### M6. 契约兼容：**逐 (源, 宿) 对判定**，不兼容者**只排除该对**

- 现状已是"逐接收者判定"⇒ 扩展为**逐对**：某源与某宿不兼容 ⇒ 仅该 (源,宿) 不建立投递 + Issue（**不牵连其他对**）。
- 兼容判据沿用 ADR-0046 D6（标识 + 版本 + 结构三层 + 显式确认可强连）。

### M7. 计量与丢弃（多源版，落地 ADR-0046 D8 / N6）

- 丢弃**按源归属**（F7 已具备）；**再细分**：`队列满` / `无承载` / `载荷非法` / `停流未投递`；**暴露队列水位**；
- 四档速率**按源、按网络、按宿**三种聚合都可查（UI 择一显示，P4 定）。

### M8. 建网方式（多源版）

| 途径 | 是否产生多源网络 | 说明 |
|---|---|---|
| **同名标签**（多个发送口同名） | ✅ **是**（M1） | 用户显式表达"这几路是同一网络" |
| **接触且对齐**（几何） | ❌ **不自动合并** | 仍**按源口一条网络**；若两条几何网络指向同一宿口 ⇒ **宿口多路输入合法**（M9） |
| 未来的显式连接操作 | 可选 | Gate 后 |

### M9. **宿口多路输入 = 合法**（原 N4 的结论反转）

- 不再加"宿口唯一"不变量；`宿口被多条网络指向` **是正常形态**（多路输入），靠 **M4 来源识别 + M7 按源计量**支撑。
- 需补：**拓扑/诊断**能表达"某宿口当前有几路输入"。

### M10. 速率极限与背压：**不做背压**，但**让上限可见**

- 保持"有界队列 + 满即丢弃 + 计数"（护栏既有裁决：**安全 + 提示，不做限流/阻断**，ADR-0029 C4-1）；
- **新增可见性**：队列**水位**（当前/容量）、**丢弃原因细分**（M7）、**按源归属**；
- 若将来要背压 ⇒ 需改模块线程模型（ADR-0029）⇒ **单独 ADR**。

### M11. 持久化与格式迁移

- 组合件网络记录：`source`（单值）→ **`sources: [...]`**（有序）；
- **`schemaVersion` 升级** + **旧文件读入迁移**（单源 → 单元素列表）+ **写回新格式**；
- 旧文件必须**可加载、可运行**（兼容性判据：`docs/implementation/04` 加一条"旧组合件加载"验收）。

### M12. 呈现（多源版，P4 落地）

- 网络标签（端口块）**不变**（ADR-0043 规格）；
- 拓扑页：网络行显示**源列表 + 宿列表 + 每源状态**；
- 叠加层（ADR-0049）：**多个生产者角色方块 → 一个消费者角色方块**；角色对级线聚合（按 (源角色, 宿角色) 对）。

### M13. 与 ADR-0046 的关系（**不推翻，补一条**）

- **D4（包不自描述）保持**：来源走 sideband（M4），不写入 payload；
- **D5（时序只统计不附加）保持**：框架仍**不附加时刻** ⇒ 需要"按时刻排序"的多源合并**只能由模块自带时刻字段**；
- **唯一修订**：§5.4.2 第一条中"**下游不应知道数据源身份**"在下游**主动索取**时放开（M4）。

### M14. 不做（明确边界）

- 框架**不**做优先级/时间排序/去重/限流/背压（M3/M10）；
- **不**引入变长载荷（ADR-0046 D3）；
- **不**改"模块不提供 View"（ADR-0026/0028）；
- **不**自动把几何相邻的多个源合并成多源网络（M8）——避免误连。

## 5. 数据面具体结构（"哑交换"模型 · **用户第二十三轮提议的设计 + 我的补全**）

> 用户判断："**需要设计整个具体的结构后，才能回答部分待裁决项**" —— 同意。本节是 R1/R2 的设计输入；**先裁决 §5.2 的 Q1–Q6，再回头确认 M1–M14 的剩余项**。

### 5.1 术语澄清（避免一个会误导的词）

- 用户说的"**压栈/出栈**"：语义上要的是 **FIFO（先进先出）**，**不是 LIFO（栈）** —— LIFO 会**反转**数据顺序，与数据流语义冲突。
  在本工程里对应两个既有动作：**发送侧入队**（`Deliver → InboundBuffer.TryEnqueue`，= "压"）与**接收侧取用**（`TryReceive` / `ReceiveHandler`，= "出"）。
- 建议术语：**"入队 / 出队（FIFO）"**；"压栈"仅在口语里用。

### 5.2 结构草案（哑交换 = 声明驱动的转发表 + 每宿 FIFO 队列）

```
        ┌──────────── 数据面（哑交换：不解析 · 不仲裁 · 不排序）────────────┐
源口 S1 ─┐
```

## 6. 与既有成熟模型的对照：**我们是不是在重新发明 UDP？**【用户第二十四轮提问，新增】

> 用户："我是否在**重新以一种复杂的方式实现某种本已完善存在的协议，比如 UDP**？如果确实是，这是否意味着**整个底层可以重构为一个'UDP 网络'**？这似乎更加成熟。"

### 6.1 结论（三句）

1. **我们在"重新发明"的不是 UDP 协议本身，而是一套消息传递语义** —— 而且这套语义**确实与 UDP 高度重合**（无连接 · best-effort · 不保证跨源顺序 · 数据报边界 · 端口=端点 · 1:N 多播 · 无背压）。
2. **因此"照抄 UDP 语义"是对的，但"进程内改用真 UDP socket"是错的**：我们是**零拷贝内存投递**（本项目实测：完整投递 **54 ns**、三跳端到端 **1.8 µs**、单实例 ≈**3.2 M 单元/秒**），走环回内核栈会变成 **µs 级（量级估算 1–10 µs/次，约 20–100× 慢）**并引入抖动、MTU/分片、系统缓冲与防火墙因素。
3. **比 UDP 更贴切的成熟参照是"发布/订阅 QoS"**（DDS / ROS 2 / ZeroMQ 的 inproc 传输）：**topic = 网络 · publisher = 源 · subscriber = 宿 · QoS = 我们正在争的那些策略**。建议**用这套标准术语重述 M1–M14 与 Q1–Q6**，能省掉大量自造词的争辩。

### 6.2 逐项对照：我们的数据面 vs UDP

| 维度 | UDP | 本工程数据面 | 判定 |
|---|---|---|---|
| 连接 | 无连接 | 按**声明**建立"绑定"后投递（无握手） | **一致**（无连接语义） |
| 可靠性 | best-effort（可丢） | **有界队列满即丢** + 计数 | **一致** |
| 顺序 | 不保证 | **同 (源,宿) 对 FIFO 强保证**（M4b）· 跨源不保证 | **比 UDP 略强**（同对保序是合理的工程加强） |
| 边界 | 数据报（自带长度） | **定长单元**（契约尺寸） | 一致（且更严格：定长） |
| 1:N | 多播 | **网络 1 源 → N 宿**（框架复制） | 一致 |
| 端点 | port | **口（端口）** | 一致 |
| 校验 | 校验和 | **长度校验**（`payload.Length >= SizeInBytes`） | 一致（无内容校验和——见 Q6） |
| 拥塞/背压 | **不背压**（丢包） | **不背压**（丢弃 + 水位可见） | 一致 |
| **转发表** | 你自己给**目的地址** | **声明驱动**（标签同名 / 接触对齐派生） | **不同**：我们更像**静态 VLAN / 订阅关系**，不是"每包带地址" |
| **地址** | IP + port | **网络名 / 绑定**（无每包地址） | 不同（我们不需要地址，因为拓扑是声明的） |
| **类型/契约** | 无（纯字节） | **强类型定长契约 + 兼容判定**（ADR-0046 D6） | **不同：我们独有、且是核心价值** |
| 变长/分片 | 支持（MTU 分片） | **不支持**（v1 只定长，ADR-0046 D3） | 不同（我们更简单） |
| 实现 | 内核栈 + 复制 | **零拷贝内存 + 池化缓冲** | 不同（我们更快，且无内核依赖） |
| 可观测 | 极少（统计/ICMP） | **四档速率 + 三类丢弃 + 水位**（ADR-0046 D8） | **不同：我们更可观测** |

**⇒ 结论**：我们的数据面 = **"UDP 式数据报语义" + "声明驱动的转发表" + "强类型契约" + "可观测计量"**。**前一半该照抄成熟语义，后三者是我们自己的必要增量**（UDP 不提供，也不该提供）。

### 6.3 "整个底层重构为 UDP 网络"：四种读法

| 读法 | 含义 | 我的评估 |
|---|---|---|
| **(i) 语义照抄 UDP（推荐）** | 把数据面**正式定义**为"UDP 式数据报语义"，采用标准术语（datagram / best-effort / no cross-source ordering / multicast / port / 长度校验 / 不背压），**停止自造词** | ✅ **强烈推荐**：直接收敛 M3/M4b/M9/M10 的争论（它们本来就是 UDP 的已知行为） |
| **(ii) 进程内改用真 UDP socket** | 模块间通信走 `127.0.0.1` UDP | ❌ **不推荐**：慢 20–100×（实测内存投递 54 ns）· 抖动 · MTU/分片 · 端口与防火墙 · 失去零拷贝与对象模型 |
| **(iii) 混合（推荐）** | **进程内 = 内存数据面（UDP 语义）**；**跨进程/跨机 = 真 UDP/TCP/共享内存**（未来能力，**同一语义契约**） | ✅ **推荐**：成熟度来自**语义**而非把内核栈塞进进程里；为"模块远程化"留门但不现在做 |
| **(iv) 把模块改成独立进程/跨机** | 模块作为网络端点 | ⏳ **产品级决策**（序列化 · 版本 · 安全 · 延迟 · 调试），**不属于本轮**；但 (iii) 让它将来可行 |

**关于 (iii) 的一个现实提醒**：**与真实设备通信本来就该用真 UDP/TCP/串口，而那是"模块"的职责**（`ModuleCapability.Network/SerialPort` 已存在）——框架数据面是**模块之间的织物**，两者不要混为一谈（混了就会出现"为了内部传递把内核栈塞进热路径"的错误）。

### 6.4 术语映射（建议采纳，替换我们自造的说法）

| 我们现在的说法 | 标准术语（建议） | 出处 |
|---|---|---|
| 数据单元 / 投递 | **数据报（datagram）** / **发布（publish）** | UDP / DDS |
| 网络（1 源 N 宿） | **topic（主题）**；成员 = **publisher / subscriber** | DDS / ROS 2 |
| 多源 | **多发布者（multiple publishers）** | DDS / ZeroMQ pub-sub |
| 停流 / 悬空 | **liveliness（活性）** / **deadline（截止）** | DDS QoS |
| 有界队列 + 丢弃 | **best-effort reliability + history depth** | DDS QoS |
| 队列水位 | **history depth / queue depth** | DDS / 通用 |
| 契约兼容（标识+版本+结构） | **type matching**（DDS 的 topic type 匹配） | DDS |
| 序列 / 时刻（我们不提供） | **sequence number / source timestamp**（DDS 头里有） | DDS |

### 6.5 因此对 Q6（"薄框架头"）的**重新评估**（把事实摆全，供你重新裁决）

| 事实 | 说明 |
|---|---|
| **行业惯例是"有头"**：UDP 头 8 B · ZeroMQ 有帧头 · **DDS 头含 writer GUID + 序号 + 源时间戳** | 我们若要"跨源排序 / 去重 / 精确计量 / 按源诊断"，**薄头是常规做法**，不是异想 |
| **但我们已明确两条**：ADR-0046 **D4（包不自描述）**、**D5（时序只统计不附加）** | 二者是"零附加 · 字节守恒 · 零开销"的选择；与"薄头"互斥 |
| **分层的正解** | 头属于**传输层**（下层读、不解释）；载荷属于**应用层**。用户"接收端不需要关心来源"在**应用层**成立；但**传输层要不要带头**是独立问题 |
| **成本** | 每单元 +8–16 B 与一次写入（可旁路存储，不必进 payload 字节流） |
| **收益** | 跨源顺序、去重、按源精确计量、延迟/抖动测量、按源诊断（**观测面已经从模型拿到来源**，所以收益主要在**应用处理**与**跨源时序**） |

⇒ **我修正先前的倾向**：把 Q6 从"推荐不做"改为 **"三选一，取决于你是否需要跨源时序/去重"**：
- **Q6(a) 不做**（保持 D4/D5）：最简、零开销；跨源时序由应用自带字段；
- **Q6(b) 薄头（旁路）**：传输层带头（源/序/接收时刻，**可选旁路、不强制进 payload**），应用可选用；**与 UDP/DDS 惯例一致**；
- **Q6(c) 折中**：**只在"多源网络"上带头**（单源网络零附加）——把成本放在真正需要的地方。
**我的新推荐**：**(c)**（单源零开销、多源才付代价；且它把"多源"这一新能力与"可观测/可排序"一起交付）。

> 属"把语义落到可实现模型上"），代码与主文档 §5.4.2/§9.3 同步（主文档 **1.0.17**）、ADR-0050 §3 同步回写。

### 8.1 源集合分**两态**（"在场" vs "声明"）

| 集合 | 含义 | 谁填 |
|---|---|---|
| `Network.Sources` | **在场（已锚定）的源** | 建网（派生/显式）与加载期成功锚定的源 |
| `Network.UnresolvedSources` | **悬空的源声明**（方向 = 发送，保留待重锚） | 加载期重锚失败的源 |
| `Network.Targets` / `Network.UnresolvedMembers` | 宿侧同构（在场 / 悬空） | 同上 |
| `Network.DeclaredSources` | 两者之并（**持久化与展示的事实源**） | 派生只读 |

- **根因**：加载期"源字面量"与"锚定后的成员"**取值完全相同**（`g2.out` 就是 `g2.out`）⇒ 只用一个集合时
  **无法区分"这个源在场"与"这个源只是声明"**，重锚因此无法判断"刚刚锚定成功"（历史缺陷：重锚会悄悄
  不建绑定）。分两态后该信息**可判**。宿侧一对（`Targets`/`UnresolvedMembers`）本来就是两态，此处只是补齐对称。

### 8.2 `IsStalled` 是**派生量**（`⇔ Sources.Count == 0`）

- **不再单独存布尔量** ⇒ 不可能出现"标志说停流、成员却在场"这类**两套说法**；
- **部分源未锚定 ⇒ 不是停流**（该源不参与投递 + 该源 Issue，其余源照常，M5）；
- 读取方**必须先看 `IsStalled`**：`Sources` 为空是**合法状态**，不是错误。

### 8.3 **算 / 报分离** + 加载与重锚**共用同一套锚定规则**

- `AnchorNetwork`（`ModuleRuntime.Persistence`）= **唯一**的"字面量 → 网络"实现，**加载与重锚都走它**
  ⇒ 重锚**不可能**再把多源网络打回单源（旧实现按 `network.Source` 单源重算，是真实缺陷）；
- `NetworkAnchoring` = 锚定结果（网络 + 逐源在场明细 + 悬空成员及原因）⇒ **算而不报**；
- `ReportNetworkAnchoring` 决定报什么：**加载全报**（源侧 + 宿侧）；**重锚只在"源在场状态变化"时报源侧**、
  宿侧**只在加载时报**（问题只减不增，重报 = 噪声）；
- 停流 Issue **不再由 `RebuildBindingsCore` 报**（同一事实只有一个 owner）。

### 8.4 网络身份键用**声明的源**

- `NetworkView.Key = 声明源集合 → 宿集合`（旧实现用"在场的源"）⇒ 两条都停流的网络不会因"在场源为空"
  而撞成同一个键（P40 的身份键**必须唯一**）。

### 8.10 澄清：不用融合器时，"直接标签连线"到底成立吗？（2026-09 · 用户提问 → 实测取证）

> 用户问："不使用多源融合器、直接用网络标签**一对多**也能运行 —— 这种情况下的链路**融合规则**是什么？
> 是巧合能运行，还是确实正确？"

**先分清两种连线**（"一对多"与"多对一"是两件不同的事）：

| 形态 | 框架实际行为 | 判定 |
|---|---|---|
| **1 源 → N 宿** | **广播（多播）**：每条数据报**每个宿各一份独立拷贝**（`RentCopy` 到各宿队列），宿之间**互不影响**；每个宿看到的都是该源**完整、有序**的流（同 (源,宿) 对 FIFO） | ✅ **正确，非巧合**。这里**没有"融合"**可言 —— 没有东西需要合并。**注意**：同一模块的**两个口**打了同一标签 = **两次订阅** = 收到**两份**（合法语义，但常出乎意料） |
| **N 源 → 同一宿口** | 框架**只做**：把每个被接受的数据报按**到达顺序**写进该口的**同一条 FIFO 队列** = **匿名多路复用**。**不排序 · 不去重 · 不仲裁 · 不告知来源**；**每个源自身的顺序仍保证** | ✅ **语义正确**（= M3"框架中立按到达"/Q3"多源到同一宿口合法"/Q4"合并由模块承担"），但它**不是合并**：需要"每源一个值 / 取最新 / 取平均 / 按源区分"时必须由**模块**做 —— **推荐一源一口**（多源融合器即范例），或应用**自带来源字段**（M4） |

**实测发现的缺口（探针取证后即删）→ 已由 ADR-0051 从规则上根治**：在 **接收方按自己的契约整块读** 时，

1. 被 D6 判为"兼容"的**尾部追加升级**（v1 源 12B → v2 接收口 16B）**必然抛** `ArgumentException: 数据单元过小：布局需要 16 字节，实际 12 字节`；
2. **同口混入不同尺寸的源**（v1 与 v2 同标签投一个口）同样抛；
3. 抛出的后果是**该模块的投递循环整体退出**（再发一次毫无反应、计数不再增长），只留一条
   `[Error] 模块活动体异常退出：…（该实例已停止活动）` 的 Issue —— **文案与真实原因不符**，
   现场表现是"模块莫名不再收数"，定位成本极高。

**落地内容（见主文档 1.0.22 / 1.0.23 与 §5.4.1）**：

| 项 | 内容 |
|---|---|
| **规则（ADR-0051 根治）** | 直连要求**形状完全一致** ⇒ 到达长度 **恒等于**本口契约尺寸，"合法连接却读不了"这一状态**不复存在**；**同一宿口永不混入两种长度**（形状不一致的源被逐对排除 + Issue） |
| **规则（防御，保留）** | 接收方**按到达长度读**（`PayloadReader.TryCreate`：长度不足返回 `false` 不抛），只读"一定存在"的字段；**到达长度 = 发送方的契约尺寸**（框架不投影、不补零、不截断） |
| **SDK** | `PayloadReader.TryCreate(payload, layout, out reader)`（只增不改）；构造注释写清适用边界 |
| **参考模块** | Monitor / Recorder / Asserter / Fuser 全部改为防御式读取：长度不足 ⇒ **丢弃 + 计数 + 首次报一条 Issue**（不静默、不崩） |
| **回归判据**（T1） | `ContractReadDisciplineTests`（3 项）：读原语行为（硬构造抛 / `TryCreate` 安全失败 / 够长可读）· **形状不一致 ⇒ 拒绝直连且不产生投递** · **混形状多源 ⇒ 只保留形状一致的那一路，同一口只出现一种长度** |

**仍待用户裁决的一项（异常隔离政策）** —— **已由用户第三十轮裁定收口**：
用户选择"**直接拒绝建网**"（并且追问范围后选 **B 宽范围**：形状必须完全一致，连"接收方多带一个字段"也不算兼容）
⇒ **框架制造的数据问题（短数据报）从源头消失**，剩下的回调异常**全是模块自身的代码错**（确定性），
而"**报 Issue + 停止该实例活动**"对确定性代码错**是正确的**（一个坏掉的模块继续跑只会持续产出错误数据）
⇒ **ADR-0029 的异常边界政策保持不变**，不做投递期异常隔离。
详见 **ADR-0051**；`PayloadReader.TryCreate` 与参考模块的防御式读取**保留为防御**（新规则下"到达长度 = 本口契约尺寸"是不变量）。

### 8.11 P3：模块**数据角色**模型（ADR-0048 落地 —— R6 的前置）

> 结论：**角色 =（方向 × 类型身份）**，在模块内聚合、**纯派生**、**只用于呈现**；**Core 算、`Core.Api` 暴露、UI 只画**。
> 为什么它排在 R6 前面：R6 要画"**角色方块 + 角色对线**"，而"什么算同一种类型""谁连谁"必须与**兼容判定同源**，
> 否则 UI 会复制一套规则并慢慢漂移。P3 先把这层派生关系钉在 Core 里，R6 只是**投影**。

| 项 | 内容 |
|---|---|
| **定义与聚合** | **角色 =（方向 × 类型身份）**，**模块内聚合**（同方向 + 同类型身份的口 = 一个角色；一个角色可有**多个口**，如 8 通道记录器 = 1 个接收角色 + 8 个口） |
| **类型身份（关键）** | 已声明类型 ⇒ **`标识@版本`**；未声明（旧模块）⇒ **`ContractShape.Describe()`**。**不得**用呈现文本（`{seq:u64, value:f32}`）一律代替——那会把"**不同标识但同形状**"合并成一个角色，而 ADR-0051 明确二者**不是同一种量**。类型身份由 `ModuleRuntime.DescribePortTypeKey` 给出（与兼容判定的解析**同一来源**） |
| **派生（v1）** | **纯派生，无角色声明**（不引入业务分类；主文档 §6.2 的裁决不变）；**零口 ⇒ 角色集合为空**（不画方块，信息区写"无数据口"，**不是错误状态**）；角色**不带状态色**（停流/悬空只在端口标记与线上表达） |
| **口级连接** | `ModuleRuntime.DescribePortLinks()`：**网络声明 + 逐对兼容**（`IsPairCompatible`）⇒ **停流网络的成员关系照样呈现**（停流是合法状态，用户仍需要看到"本来连给谁"）；判定与 `RebuildBindingsCore` **同一 `CheckCompatibility`** ⇒ 两者不会漂移 |
| **角色对聚合** | 键 =（本端角色, **对端实例**, 对端角色）⇒ **一条线 + 条数 `Count`** + 承载它的 `NetworkKeys`（去重有序）；**跨网络也聚合**；**多源网络**下不同模块的源 = 不同对端 ⇒ **各自一条线**，同一模块的多个同类型口 ⇒ 一条 + `×N` |
| **接口（只增）** | `Core.Api`：`DataRoleView` / `DataRolePairView` / `IRuntimeQuery.GetDataRoles(instanceId)` / `GetRolePairs(instanceId)` / `PortView.TypeKey`。UI 只读这些，不自行派生 |
| **红线** | 角色**不参与**建网 / 兼容判定 / 停流 / 投递 / 计量，且**不进组合件**（持久化里不得出现任何角色字段）；`GetDataRoles` 为**只读**（调用前后组合件快照逐字段一致，已断言） |
| **回归判据**（T1，判据 1–9 各一条） | 多口同向同类型 ⇒ 一个角色多个口 · 同类型异向 ⇒ 两个角色 · **不同标识同形状 ⇒ 不得合并** · 未声明类型 ⇒ 角色键 = 结构描述 · 零口/不存在 ⇒ 空 · 同一角色对跨两条网络 ⇒ 一条 + ×2（正反向对称）· **多源网络**：不同模块的源 ⇒ 两条线、同模块两个同类型口 ⇒ 一条 + ×2 · **反向断言**：角色聚合**不折叠口级连接**（两个口各自真实投递）+ 角色**不进组合件** · **只读**（快照一致）。用例 = `tests/HYWDebugAssistant.Tests/DataRoleModelTests.cs`（**9/9 通过**） |
| **落地期实测（两条）** | ① **`GetRolePairs` 条数恒为 0**：字典存的是**值元组** ⇒ `entry.Count++` 改的是**取出的副本**；同条目的 `Networks` 是 `List`（引用）故"看起来生效"，**掩盖了计数丢失**。修法 = 累加后**写回** `pairs[key]`（教训见 `LESSONS` 56 / `implementation/02` P49）。② **`PortInstance.IsConnected` 是"悬空的第二事实源"**（既无写入方也无读取方，恒 `false`；UI 读的是按**网络成员关系**派生的 `PortView.IsConnected`）⇒ **用户裁定整体删除该字段**（Hosting + 其唯一一条断言），连接状态的**唯一来源** = **网络成员关系**；**并由此暴露两条同类问题（待裁定）**：`PortInstance.IsStalled` 同样无写入方却被读进 `PortView.IsStalled`（推荐同样删除、改由网络派生）· `PortView.IsConnected`（按**绑定**）与 UI（按**网络**）对**停流网络**口径不一致（推荐统一到网络口径） |
| **验证层级** | T0 全解决方案 0 警告 · **T1 `Tests` 288 → 297** · T2 参考 **35** + 架构 **10**（合计 **342** 全绿）；**T3 未重跑**（R6/UI 切换时一并跑） |

### 8.13 R6 第二版：**角色 = 模块声明的「功能分块」**（ADR-0052 落地）

> 用户第三十三轮："**角色是模块的子功能分块表达**……**这一点为模块自身声明**……**网络标签（数据接口的抽象）我认为可能不需要在叠加视图中高亮**，
> 它们**不是一个层级和意义领域内的东西**" ⇒ 裁定"**兼容不考虑 · 其他按推荐 · 一次做完**"。
> **一句话**：上一版 §8.12 把角色当成**框架派生**的"（方向 × 类型身份）组合"，于是**融合器被画成"一收一发两块"**（看起来像两进两出的转发器）；
> 现在角色改为**模块自己声明的功能分块**（一种数据类型 + 输入口/输出口），**框架不派生、不发明**。

| 项 | 落点 |
|---|---|
| **角色声明面（SDK 只增）** | `RoleDeclaration(Id, Type, Inputs, Outputs, DisplayName)` + 静态 `Input/Output/Both`；`IModuleDeclaration.DeclareRole`。**一种类型一个角色**；一个口**最多属于一个角色**；**口数不设上限** |
| **校验两处同规则** | `ModuleInstanceFactory.BuildRoles`（运行期：非法 ⇒ **报 Issue 并忽略该条**）与 `ModuleContract.CheckRoles`（SDK 自检）；规则 = Id 唯一 · 类型可在本模块解析 · 口存在且方向相符 · 一口最多一角色 · 至少一个口。**>2 口只在 SDK 自检给建议**（独立通道 `Advisories`，不进 `Problems`、运行期不报） |
| **`m/n` 的唯一来源** | `RoleModel.PeersOf`：从**网络成员关系**算"该侧连了几个**对端角色**"，去重键 =（对端实例, 对端角色）⇒ 同一对端角色的多个口仍算 **1**；**无该侧口 ⇒ `null`（界面 `--`）**；**有口未连 ⇒ `0`**。**模块无法自报这个数** |

| **线的几何** | 一条全局线段 = **发送角色方块「输出侧中点」 ↔ 接收角色方块「输入侧中点」**；各窗只画自己窗内的那一段（`ClipSegment`，Liang–Barsky）⇒ **严格共线**：相邻无缝 · 未拼接恰好缺两窗之间那段 · 重叠也不错位。**对端锚点用与对端同一套 `LayoutRoles` 算**（`ModuleWindowsViewModel.ResolvePeerAnchor`） |

| **信息区** | 左上第一行 `实例 · 模块名`（12px）；第二行**只在需要说明时**非空（`无数据口` / `未声明角色（N 个数据口）`，10px）。**删除**：网络名 · `×N` · 模块级汇总 · 「未连」文字（用户："没连上时指示灯会灭，文字多余"） |

| **内部处理顺序**（原 D13） | `FlowDeclaration` 改为 **`(FromRoleId, ToRoleId, Label)`**：角色已含 in/out ⇒ 块内部不必声明，只表达**块与块之间**的顺序。参考模块都是单块 ⇒ **零声明零线** |
| **兼容回退** | **不做**（用户："当前是开发早期……无需过度考虑兼容"）：未声明角色 ⇒ **不画方块**（叠加层不发明角色）+ 信息区一句可执行的事实。⇒ 不存在"两套角色模型并存"（ADR-0052 §12.6 认定的**真正技术债**） |
| **旧路径** | `DataRoleView`/`DataRolePairView`/`DataFlowView` · `DataRoleModel` · `Ui/ViewModels/DataRoleViewModels.cs` · `PortAnchorCalculator` · `RoleLineOf`/`UnconnectedStubOf`/`UnconnectedLabelOrigin` **全部删除**；旧断言**改写带走**（不留双轨） |

1. **测试用"世界矩形"去裁"局部坐标"**：`ClipSegment(window, from, to)` 的 `window` 必须是**本窗的局部矩形**（每窗画布原点恒为 0,0），
   世界原点只用于把对端锚点**换算进本窗**。第一版几何用例把 B 窗的世界矩形（`x=320`）直接传进去 ⇒ 裁剪判定"整段在窗外"⇒

2. **"建议"混进"问题清单"会在自家正确模块上报警**（已在实现中分开，见 ADR-0052 R3′-补）：把"角色口数 &gt; 2 ⇒ 建议拆成两个角色"

### 8.6 R2-b：队列粒度改**每 (实例, 口)**（§5.3 Q2 落地）

| 项 | 内容 |
