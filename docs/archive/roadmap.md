## 1. 推进原则（与主文档 §0.1 / §16.4 / §16.5 一致）

### 1.1 设计—实现推进阈值（工作流约束 · 用户裁决，批次 1 前）

**目的**：设计阶段只为消除 A 类不确定性（"什么东西应该是什么"——语义/结构决策）；实现阶段处理 B 类不确定性（"已确定应该是什么的东西怎样实现"）。仅当**剩余未知问题以 B 类为主**时才允许进入实际开发。

**推进阈值**：进入技术选型/实现的唯一条件 = **顶层所有域的结构决策均已冻结（"整版原理图"完成）**。域内细节（枚举/格式/算法/UX 交互）显式登记为 Gate 项（选型后/实现期/UX 原型解决），不属于设计阶段义务；但不得以"细节未定"为由回避该域的**结构决策**。

**电路设计类比（用户提供）**：
- 可接受：接口定义完成后的外围模块变更；核心整版设计完成后的 IO 位置调整。
- **不可接受**：最小系统完成即 layout，再边加外设边 layout——引发系统结构性失配。
- 推论：顶层 = 整版原理图；选型 = 器件选型；实现 = layout。**原理图未完成不 layout**；不得以"用代码验证设计"为由提前进入实现。

**执行纪律**：
1. 评审**逐条裁决**（不打包默认）。
2. 所有正式裁决记录为 **ADR**（完整审计链）。
3. AC 判据在本阶段给出**纸面验证路径**；实证发生在实现阶段并回写设计文档。
4. 实现中暴露的残余 A 类问题必须**回写设计文档**（活清单），不得由代码静默拍板。

### 1.3 推进原则（批次级）

1. 自上而下、分批设计、分批审核、分批冻结。
2. 一个批次只有在**评审通过并冻结**后，才进入下一批次。
3. 后一批不得推翻前一批已冻结结论；若确需推翻，必须走 ADR（Superseded/Deprecated）并经人工决策。
4. 每批的产出物 = 该批的裁决问题清单 + 冻结结论 + 主文档相应章节更新。
5. 技术选型（Gate）之前，任何批次不得以具体技术（语言/框架/DLL/进程模型）反向决定顶层结论。

### 1.2 层级推进协议（域内四步 · 批次 1 经验沉淀）

**问题**：主题批次内混有多层问题（图景/概念/机制/结构/细节）。"下一层在上一层未稳时被裁决"会引发回溯——批次 1 已多次发生（对象细节 → 概念重构 → 框架三梁 → 运行机制），每次回溯都需"完成修正才能继续"。

**协议**：任何主题域（或域内裁决包）一律按四步子阶段推进，前一步未冻结不进下一步：

1. **图景描述**：先写/叙该域"是什么"（面向用户心智与类比），并做**"类比→抽象→边界"显式转换、经用户校验**——不直接形式化用户类比（教训：电路/工厂/仿真框架类比曾被误读/过度形式化）。
2. **概念与支点裁决**：立该域的"梁"（对象全集、边界、所有权、保存语义等支柱决策）。**支点信号**：若多点悬空答不上 → 判定缺上层支点，停止点状裁决，先向上补支点。
3. **机制/结构**：支点之上再裁该域内部结构问题。
4. **细节 Gate**：格式/编号/分类枚举/调度等 B 类与确定性设计 → 登记 Gate，不裁决。

**三条守护规则**：
- **层级定位检查**：每个待裁决问题先回答"这是哪层的问题？上层是否已冻结？"——下层未冻结则先补上层或转 Gate。
- **转写校验门**：用户以自由文本/类比给出的裁决，Agent 必须转写为**命题清单**请用户"确认即冻结"，不得直接扩写为架构结论。
- **逆例自检**：每次拟冻结措辞对照跨层不变式（P）/反模式（E）/判据（AC）自查（案例：批次 1 曾出现"Core 中转数据"表述与 P2 冲突未被自查拦截）。
