### 9.5 非 ASCII 编码：T12 的决策依据（**已裁 = UTF-8**）

**先把两个决策点分开**（它们**必须一致**才能往返）：

| 决策点 | 内容 | 落在哪 |
|---|---|---|
| **A** | `RawBytes.data` 这个**字节区**里放什么编码（发送方把「文本」变「字节」） | 本模块（`text-sender`），以及任何发文本的模块 |
| **B** | 读这个字节区时按什么编码**理解**（尤其 HEX ↔ 字符串转换、数据显示） | `hyw/hex-string-converter` · `hyw/data-monitor` |

| 维度 | **ASCII-only**（原约定） | **UTF-8** | **UTF-16（码点拆 1–2 个 16 位 / 代理对）** |
|---|---|---|---|
| **「不丢信息」** | 非 ASCII **直接不支持**（要丢） | ✅ **不丢** | ✅ **不丢** |
| **ASCII 字符的字节** | 1 字节 | **1 字节（与现在完全一致）** | **2 字节，且必带一个 `0x00`** |
| **中文（BMP 内）/ 补充平面** | ✗ | 3 字节 / 4 字节 | 2 字节（更省）/ 4 字节（**代理对**） |
| **`0x00` 的出现频率** | 只在真正的 NUL | 只在真正的 NUL | **每个 ASCII 字符都带一个** |
| **与 T10 的期望是否冲突** | 否 | **否** | ⚠ **严重冲突**：下位机/第三方工具**普遍**把 `0x00` 当字符串结束（即使我们规定「按 `len` 切片」，**别人不一定遵守**）⇒ UTF-16 的报文在对方看来是「每两个字节就截断一次」 |
| **HEX 可读性**（每字节 2 位 hex） | 直观 | 直观（中文 = 6 个 hex 字符） | 直观但**混**：一个汉字 4 个 hex 字符、一个字母也是 4 个（`41 00`）⇒ 分不清「这是宽字符还是数据」 |
| **变长截断风险**（1472 上限处切一刀） | 无（等长） | ⚠ 可能切在多字节字符中间 ⇒ 需**整字符对齐**规则 | ⚠ 可能切在代理对中间（同理） |
| **行业惯例（串口 / 嵌入式文本）** | 老设备 | **主流**（与 ASCII 兼容是决定性优势） | 见于 Windows API / C# 内部 / 某些 LCD 字库与老协议 |

**结论（已裁）**：✅ **采纳 UTF-8**。用户原话：「**T12 可能是我对 UTF8 理解有误，按你的建议和判断做**」。

具体口径：

| 项 | 约定 |
|---|---|
| **编码** | **UTF-8**（无 BOM）——ASCII 字符 1 字节（**与现行 ASCII-only 场景字节完全一致**）· 中文 3 字节 · 补充平面 4 字节 |
| **`len` 的口径** | **字节数**（不是字符数）⇒ 1472 字节上限 ≈ 最多 1472 个 ASCII 字符 / 约 490 个汉字 |
| **拆包对齐**（T13 的实现约束） | **必须按字符边界切**，绝不把多字节序列切两半（否则两包都解不出）——同「整字符对齐」要求 |
| **非法字节序列** | 字符串方向**明确报错**（不静默替换成 `�`）；十六进制方向**永不丢**（显示原始字节）⇒ 这是「不丢信息」的真实落点 |
| **`0x00`** | 与 T10 一致：**合法数据、不是终止符**（UTF-8 下 `0x00` 只出现在真正的 NUL 字符） |

> **回改清单（已执行）**：`decisions.md` **7.22⑦**（`ASCII` → **`UTF-8`**）与 **7.25**（本次裁定登记）。

### 9.6 字节口径与下位机（C）的一致性（**已裁：甲方案 · 「与 C 里面的约定对齐即可」**）

> 用户诉求：「这关系到一致性问题，我希望上位机的逻辑更接近下位机」。结论 = **上位机按字节思考，与 C 的字符串/字节口径对齐**；**下位机的字库与寻址不归上位机管**（「怎么处理字库和寻址是单片机自己的事情」）。

**下位机侧的事实（C 语言）**：

| 问题 | 事实 |
|---|---|
| 下位机怎么存中文 | `char[]` 里存的**永远是字节** —— C 没有「字符」概念；源文件是 UTF-8 时，`"你好"` = `E4 BD A0 E5 A5 BD 00`（6 字节 + 1 个 NUL 终止符） |
| 怎么区分 1 字节 / 3 字节字符 | **靠 UTF-8 的「自同步」**（首字节的高位模式标出该字符占几个字节）⇒ 任意位置都能判断「这是新字符开头还是要跳过的续字节」，**逐字节扫描即可，全程不必知道整串长度** |
| 是不是补 0 | **不补**（除末尾那一个 NUL 终止符）；`strlen` 返回**字节数**（`"你好"` = 6，不是 2） |

**上位机的对应口径**：

| 下位机（C） | 上位机（本模块 / `RawBytes`） | 一致？ |
|---|---|---|
| `char[]` 存字节 | `data` 存**字节** | ✅ |
| `strlen` = 字节数 | **`len` = 字节数**（不是字符数） | ✅ |
| 显示时才查字库/解码 | **协议层不碰字符**，显示时才 UTF-8 解码 | ✅ |
| 不补 0（除末尾 NUL） | 尾部补零**只是定长容器填充**；**`0x00` 是合法数据**（T10） | ⚠ **有意不同** —— 我们更安全（能传含 `0x00` 的数据） |

**唯一那处差异的正确接法**（对接文档口径）：我们的报文是 **`len` + 数据**（长度前缀），C 字符串是 **NUL 终止** ⇒ 下位机**不能**直接 `printf("%s", data)`（会在第一个 `0x00` 处停 —— 那 0 可能是填充、也可能是数据），必须**按 `len` 处理**：

```c
for (int i = 0; i < len; i++) putchar(data[i]);   // ✅ 按长度处理
// 或 printf("%.*s", (int)len, data);
```

这本身就是嵌入式协议最常见的形态（TLV / length-prefixed）⇒ **方案② 天然贴近下位机**。

**场景确认（用户）**：下位机 = **(甲) 只把串口字节原样转发/存储**，显示由上位机或串口助手负责 ⇒ **传输口径与 UTF-8 完全对齐，无需额外约定**；(乙)「下位机自己驱动 LCD/串口屏显示中文」**不纳入本约定范围**（字库索引与寻址属单片机内部事务）。

**对后续模块的约束**（`hyw/data-monitor` 等）：**按 `len` 切片后做 UTF-8 解码**，**禁止 NUL 截断**；非法/被截断序列**明确标出**（不静默显示乱码）—— 这样「上位机显示」与「下位机打印」才对得上。
