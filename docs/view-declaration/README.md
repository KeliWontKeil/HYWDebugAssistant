# 模块界面声明：文档入口

> 这三份文档回答三个不同的问题。**先看自己是哪一类问题，再翻对应的那一份。**

| 你在做什么 | 看哪一份 | 它是什么 |
|---|---|---|
| 想知道 **有哪些控件、每个控件认哪些键** | [控件目录.md](控件目录.md) | **由 schema 生成**，不会与实现走散 |
| 要**写 / 改一份 `view.json`** | [声明标准.md](声明标准.md) | 文件形态、键的顺序、几何怎么落地、不许写什么 |
| 遇到"**控件被压扁 / 看不见 / 文字位置不对**" | [排布与坐标.md](排布与坐标.md) | 框架怎么算空间、坐标从哪算起、放不下时唯一的出口 |

## 为什么分成三份

**键表可以生成，规则不能。** 「有哪些键、缺省是什么」是数据 —— 它由
`src/Hosting/Packages/schema/view.schema.json` 一处登记，文档是它的投影。
投影由用例（`ViewDeclarationDocTests`）在每次测试时核对，两边不一致就失败。
所以控件目录**不需要人维护**，也就不会腐烂。

「键的顺序为什么这么定」「一排按钮该给固定像素还是 `auto`」「最后一行为什么会被压成 0 高」
——这些要求人做判断，生成不出来，所以是手写的，并且**只写一处**。

## 这三份文档与代码的约定

| 约定 | 判据 |
|---|---|
| 控件目录 = schema 的投影 | `控件目录必须与声明面schema逐键一致`（改了 schema 不重新生成 ⇒ 红） |
| 每个模块的文本面把它的键显式写出来 | `模块声明里的文本面_必须显式写出它自己的键` |
| 每个模块的每个元素显式声明两个轴 | `模块声明里的每个元素_必须显式写出两个轴的口径` |
| 声明的固定像素高必须真的兑现 | 各模块的"内容必须放得下"快照用例 |

> **"声明键有没有消费者"今天是人工判据。** 从前有一条用例做这件事，但它的判据是
> "**源码里出现过** `Node.<键名>`"，与"这个键真的生效"无关，而且只遍历**目录**登记的键 ——
> `textAlign` 与目录漏登记的那几个键正是这么漏过去的。要恢复自动化时，对账的基准取 **schema**，
> 不取目录（登记与实现的欠账见 [`../TODO.md`](../TODO.md) §4）。

重新生成控件目录（改了 schema 之后）：

```powershell

dotnet test tests\HYWDebugAssistant.Tests.Reference\HYWDebugAssistant.Tests.Reference.csproj `
  -c Debug --filter "FullyQualifiedName~控件目录"
Remove-Item Env:HYW_WRITE_DOCS
```

## 一句话回顾这套机制

模块界面由**三层**决定，每一层只负责一件事：

| 层 | 在哪 | 负责 |
|---|---|---|
| **词汇 + 缺省** | `view.schema.json` | 有哪些 kind、每个 kind 认哪些键、不写时取什么值 |
| **这一份界面** | 模块的 `view.json` | 用哪些元素、怎么摆、多大、绑哪条数据 |
| **外观** | 主题（`Theme/*.axaml`） | 画成什么样：颜色、字号、边框、间距 |

**模块声明里不许出现外观数值**；**控件代码里不许出现该由声明决定的行为参数**。
这两条各自有一个方向：前者保住"换主题不用改模块"，后者保住"声明写了就生效"。
