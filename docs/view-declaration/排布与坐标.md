# 排布与坐标

> **这一页讲"框架怎么算"**：谁给谁多少空间、坐标从哪算起、文字摆在控件的哪儿。
> 键怎么写看[声明标准](声明标准.md)，有哪些键看[控件目录](控件目录.md)。
>
> 写这一页的理由：模块作者遇到"控件被压扁 / 后面那排看不见 / 文字跑到框中间"时，
> 必须能自己判断**是声明给错了还是框架算错了**。没有这套规则，只能靠试。

---

## 1. 三个原点，不要混

| 坐标系 | 原点在哪 | 谁在用 |
|---|---|---|
| **窗口坐标** | 模块窗口内容区的左上角（**不含**端口标记预留带与内缩） | 模块作者真正关心的一层 |
| **面板坐标** | 当前容器分给它的那一块区域的左上角 | 排布引擎内部；子元素的 `x`/`y` 相对它 |
| **控件坐标** | 控件自己的左上角 | 控件内部摆零件（标题、正文、状态角） |

**内容区的实际可用范围**：窗口尺寸减去四周的**内缩带**（主题给的 `SurfaceContentInset*`，
默认上 22 / 左右 20 / 下 24）。这条预留带在 `ScrollViewer` **之外**，所以内容不会被它盖住。

> 所以「声明窗口 420×560」的实际可用是 **380×514**，不是 420×560。
> 排内容时按可用范围算，不是按窗口尺寸算。

## 1.1 放置键**随父容器变**，不随元素自己变

同一个元素在 panel 里和在 grid 里，读的是**两组不同的键** —— 判据是"**父层是谁**"，不是"我是谁"：

| 父层是 | 元素写什么 | 由谁读 |
|---|---|---|
| `flow` | 什么都不写（顺序即位置） | 排布面板按顺序排 |
| `grid` | `column` + `row`（+ `columnSpan`/`rowSpan`），以及 `align` / `verticalAlign` | 网格分支按格子摆 |
| `panel` | `x` + `y`，且两轴必须 `pixels` | panel 分支按坐标摆 |
| `absolute` | 两轴 `pixels`，可选 `scaleWithWindow` | 绝对坐标分支 |

**两条容易踩的**：

1. **放置键只有一种写法：`column` + `row`**（+ `columnSpan`/`rowSpan`）。**都不写 = 按声明顺序落位**
   —— 与流式同一套直觉。**没有**"写个标志就自动放"这回事：排布只按声明顺序补空位。
   （`columnSpan`/`rowSpan` 必须跟着 `column`/`row`：只给跨度不给起点，跨度没有意义 ⇒ 硬伤。）
2. **`align` / `verticalAlign` 只在 grid 里被读**：元素在格子里"贴左 / 居中 / 拉伸"靠它。
   在 panel 里想调位置只能用 `x`/`y`（panel 不给对齐键，写了是硬伤）。

## 1.2 消息那一块为什么不会挤占别人

四个模块都把模块的消息放在**一块固定高的 `label`** 上（绑一条 `status` 源），
所以"消息出现 / 消失"**不改变任何尺寸** —— 它占的那一行**一直在**，只是内容从空变成一句话。

**要腾位置就改声明里的坐标，那是一次性的**：`flow` 里加一块元素，下面的自动顺延；
`panel` 里则要自己把后面的 `y` 往后挪（panel 的坐标是绝对的，框架**不会**替你重排 ——
这正是"整组挪位而不重排"那条语义）。

## 1.3 **框 = 内容**：元素的外框就是它看得见的那一块

声明面只回答两件事：**这个元素的外框多大**（`width` / `height`）· **放在哪儿**（`x` / `y`，或格子/流）。
**它不回答、也不需要作者回答**"可见件（墨迹）在外框里从哪一点开始" —— 那是**控件自己的事**：
控件的内容必须**严丝合缝**地填满这个外框，中间只允许**框线那 1–2 px**。

### 标准（对所有已开发 / 未开发的控件都成立）

1. **S1 框即内容**：内容矩形 = 外框 − 框线（**≤2 px**）。**不存在"隐形留白"** ——
   内容不许因为"居中 / 贴顶"而在框里留下作者看不见、也算不出来的空隙。
2. **S2 三类内容，各有唯一的填法**：
   - **区域型**（`textBox` 编辑器、`curve` 绘图区、`commandButton` 的面、容器的内容面板、`tabs` 页内容）⇒ **拉伸吃满**；
   - **文字型**（`label` 正文、`numeric` 读数、任何说明文字）⇒ **在内容矩形里居中**（这一轴声明了固定像素时，行盒直接取那个值 ⇒ 视觉中心 = 框中心）；
   - **图形型**（`toggleSwitch` 方框、`toggleSlider` 轨道）⇒ **独占轴吃满、共享轴按固有尺寸**（滑块的轨道：高吃满、宽仍 36 —— 那一行的其余宽度留给说明文字）。
3. **S3 说明 + 主体**：说明与脚注各占一行 `Auto`，**主体那一行 `1*`（吃满剩下那块）**。
   "主体按内容高、余量留底"的第二条路**已经删掉**：它让同一个 kind 在"有说明 / 没说明"两条路上落在不同位置。
4. **S4 内容下限要可见**：控件的内容固有下限（例：曲线绘图区 64）**不许静默** —— 声明比它还矮时要有话说。
5. **S5 落点在代码里**：内容怎么填由**控件自己**在构造处决定（基类 `BuildChrome` 给默认：主体吃满、文字居中），
   **不加任何声明键**。

**推论（作者要记住的一条）**：既然框 = 内容，那么**"看起来对齐"就是"框对齐"**。
`panel` 里让同一行的件视觉对齐 = 让它们的**框中心**对齐（写法见 §1.3.3）。

### 1.3.1 框架层：框里有什么、怎么排（四条规则）

| 情形 | 框里怎么排 | 证据 |
|---|---|---|
| 没有说明文字、也没有脚注 | **元素的框 = 主体控件的框**（不加任何布局层） | `SurfaceElementControl.cs:186-189` |
| `textPlacement` 是 `left`/`right`，且主体自带文字槽（勾选框 / 开关） | 说明塞进控件自己的内容槽，**不加布局层** | `:148-152` |
| `textPlacement` 是 `left`/`right`（普通主体） | 同一行盒：声明了 `height.pixels` 时**说明的行高 = 框高**，`textAnchor` 定顶/中/底，主体 Stretch | `:313-331` |
| `above`/`below`，或只有说明 / 脚注 | **说明与脚注各 `Auto`、主体 `1*`**（主体吃满剩下那块） | `BuildChrome` |
| 主体是文字（`TextBlock`） | **在内容矩形里居中**；这一轴声明了固定像素 ⇒ 行盒取那个值 | `FitTextToContent` |

### 1.3.2 逐 kind：框是什么 · 内容怎么填 · 该动哪个键

| kind | 声明的框 | 内容怎么填 | 内容顶 − 框顶 | 想"看起来对齐"动哪个键 |
|---|---|---|---|---|
| `container` | 外框；内容盒 = 框 − `padding` | 区域型：子项从内容盒左上开始 | `padding` | `y`（或 `padding`） |
| `group` | 外框（1 px 边 + 圆角）；有 `title` 时另有标题带 | 区域型 | `1`；有标题 = `1 + 标题行 + 2` | `y`；标题那截只能改 `title`/`padding` |
| `collapsible` | 外框（Fluent `Expander`），头部行是主题常数 | 区域型 | `头部行高 + padding`（头高是主题项） | `y`；头高动不了（欠账见 [TODO](../TODO.md) G40） |
| `tabs` | 页签条 + 页内容，两者高度由 `tabs.rows` 分 | 区域型：条内文字居中、页内容贴第 1 行顶 | 条：`(第 0 行高 − 文字行高)/2`；页内容：第 0 行高 | **`rows`**（tabs 没有 `y`） |
| `textBox` | 内容区（1 px 边框是**叠加层**，不占内容矩形） | 区域型：**吃满** | 编辑器内边距（`window` 档 `4,2` / `native` 档 `4,1`），属**内容内部** | `y` |
| `label` | 内容区（纯文字，无边框无内边距） | 文字型：**居中**（声明像素高 ⇒ 行盒 = 框高） | `(框高 − 行盒)/2`（行盒 = 框高时即 `0`） | `y` |
| `numeric` | 内容区（无边框） | 文字型（读数）：**居中** | 同上 | `y` |
| `curve` | 绘图区（1 px 框 + `SurfacePlotInset` = 1） | 区域型：**吃满** | `2`（1 框线 + 1 内缩） | `y`；框高另有内容下限（主题 `SurfaceCurveMinHeight`） |
| `commandButton` | 按钮本体（面 + 边） | 区域型：面吃满，字在面内居中 | `0`（字居中属内容内部） | `y`（框高另有 `MinHeight` 地板） |
| `toggleSwitch` | 整格命中区（方框 + 文字） | 图形型（方框）+ 文字在同行 | 方框 `0`（吃满高） | `y`；方框与文字两个墨迹的残余差见 [TODO](../TODO.md) G40 |
| `toggleSlider` | **整块命中区**，不是轨道 | 图形型：轨道**高吃满、宽固有 36**；圆钮 = 轨道高 − 上下内缩各一（**没有算式**，内缩是常量） | `0` | `y`（轨道高 = 框高，不再有居中留白） |
| 未渲染的 5 种（`statusLight` / `table` / `image` / `enumSelector` / `configurationEditor`） | 占位块 | 区域型（占位文字贴顶贴左） | `0` | `y` |

### 1.3.3 对齐的写法（`panel` 里手工排布时）

**居中类**（同一行里高度不同的件，例：18 的滑块与 28 的按钮）：取这一行的**共同中心** `C`
（= 行内最高那件的框中心），其余每件写 **`y = C − 框高 / 2`** ⇒ 等价于常用的 **`y = (行高 − 框高) / 2`**。
四个模块里手写的那些 `y` 正是这个公式（`toggleSlider` 18 与 `commandButton` 24 同行 ⇒ 按钮 `y = 4`）。

**吃满类 / 贴顶类**（`textBox`、`curve`、占位块）：`y = 0` 就是对齐（它们的内容顶 = 框顶）。

**同一块里两个 `fill` 件要等高 ⇒ 它们的 `min` 必须相等。** `fill` 拿到的高度 = **自己的 `min` + 均分到的余量**
（例：两个 `fill`、余量 100 ⇒ 各拿 50，谁都不会因为"余量够多"就自动跟另一件看齐）。
所以**"把 `min` 调小"不是"只留一条兜底、不影响排版"**：它把那一件的**基线**一起降下来了，两件于是等高不了
（实测：两个文本框 `min` 都给 30，看起来"30 很小、根本不到限制"，实际渲染出来一个 42、一个 20）。

页签那一层还要多算一笔：**页签条是从"页内容"那一格的高度里扣掉的**（`tabs.rows` 第 0 行），
所以想让页里的框与旁边的输出框等高，`tabs` 的 `min` 必须写成
**`页内容框的 min + 页签条高`**（例：内容框 `min` 30、条 22 ⇒ `tabs.min = 52`；写成 30 就差 22）。

> **维护约定**：这张表要与**控件构造处**一一对应（基类 `BuildChrome` 给默认、控件自己决定内部零件）。
> 改控件时改那句话，并同步本表 —— 否则"框 ↔ 内容"又会变成两处口径。

## 2. 流式（`layout: "flow"`，缺省）

单列、自上而下。**宽 = 满宽**（除非声明了宽度）；高按内容。

余量的去向：**只给"填满型"**（`height: { fill: true }`）。

| 情况 | 结果 |
|---|---|
| 有 1 个填满型 | 它吃掉"容器可用高 − 其它元素的内容高 − 间距" |
| 有 N 个填满型 | 余量**等分**给它们 |
| 没有填满型 | 余量留在底部（内容按内容高排，不硬撑） |
| 内容比容器高 | 外层滚动条接手（见 §5） |

**`fill` 在流式里对宽度没有意义**（流式本来就满宽）；它有意义的是**高度**。

### 2.1 地板（`height.min`）只有声明一个来源

**一个元素最少要多高，只看它自己的 `height.min`**（不写 = 0）：

- 容器内部的结构高度（页签条那一行的固定像素、标题行）与**子项的地板**，**不会**自动变成容器在外层分配里的下限 ——
  框架不替作者"猜"这一块内部要多少；
- 所以"默认窗口就放得下"这件事，必须由作者把这几笔**自己算进去**：写进相关的 `height.min`，
  或把 `frame.window` 调够。

**为什么这么定**：框架替作者猜，会让"放不下"变成**静默压内部** —— 容器里的东西被压扁一两个像素、
里面的滚动条冒出来，而外面看不出任何异常。今天宁可让缺口表现为"外层那根条"（看得见、能解释），
也不要它变成"里面的东西莫名其妙被切掉"。

> 反过来说：**容器的滚动条不是缺陷**。它只说明"这一块的外部给的比内部的少"——
> 该改的是声明里的数字（`min` / `frame.window`），不是去压里面的东西。

## 3. 网格（`layout: "grid"`）

按 `columns` / `rows` 分格，每个直接子节点**要么给 `column`+`row`（可带跨度），要么都不写**
（都不写 ⇒ 按声明顺序落位；**同一容器里两种写法不能混用**）。

### 3.1 轨道形式

| 写法 | 含义 |
|---|---|
| `"*"` | 等分剩余空间 |
| `"2*"` | 按权重分（这里是 2 份） |
| `"auto"` | 按内容 |
| `120` | 固定 120 DIP |

### 3.2 算账顺序（这一条决定了"为什么后面那排看不见"）

```
① 固定轨道先拿它的像素
② 非固定轨道的**下限**：`adaptive` 元素按内容量一遍，`pixels` / `fill` 元素只按**声明**（这就是流式那一套口径）
③ `*` 轨道分余量：可用空间 − 固定轨道 − `auto` 轨道内容高 − 全部轨道间距
④ 定案后再量一遍，然后摆
```

**第 ② 步的"内容"只对 `adaptive` 成立**：同一个声明在流式与网格里必须是**同一个地板** ——
`fill` 元素不会因为"它的内容更高"就把轨道顶高（要让轨道跟着内容走，元素该写 `adaptive`，那是 `auto` 轨道的定义）。

**`*` 只吃"扣掉其它轨道之后剩下的"**。这一条是硬约束：让 `*` 直接吃"可用空间"，
它会把 `auto` 轨道的份额也吃掉，网格总高超出可用高，**排在最后的那几行被推到视口外、
一个像素都看不见**（而屏幕上不报任何错）。

### 3.3 格子边界 = 跨度内轨道之和

跨列的格子宽度 = **跨度内各轨道之和 + 跨度内的列间距**。

- 不能按"轨道之和 + 全部间距"：那会把跨度之后那条间距也算进去（跨到最后一列时就排出面板）。
- 不能按"面板边"：最后一行上会算出**比行本身还小**的高度
  （实测：行高 30、行顶 444、面板高 454 ⇒ 格子只剩 10，声明 30 高的开关被压成 10）。

### 3.4 元素不许超出自己的格子

声明尺寸是"我想要多大"，格子是"这一层真的分给我多大" —— 两者冲突时**以格子为准**
（面板自己会裁掉超出的部分）。所以声明 96 宽的元素放进 90 宽的格子，实得 90。

> **`pixels` 档例外**：作者写死的尺寸就是唯一事实源。格子比它窄时**如实按声明摆**、溢出交给外层滚动条
> —— 夹了就等于静默改声明（声明 96 的元素在 90 的格子里实得 90，界面上看不出是声明失效）。

## 4. 面板（`layout: "panel"`）—— 相对坐标 + 整块挪位

**它跟 `flow`/`grid` 不是一类东西**：那两者描述**元素之间的关系**（随窗口重排），panel 描述**组内事实**
（坐标相对面板原点、恒定）。窗口变化时，行列式会动"元素之间"，panel 只动"整块在哪"。

### 4.1 四级尺寸（panel 最容易被混起来的地方）

```
① 格子（slot）      父层分给这个 panel 的空间
② 面板框（box）     panel 实际占据的矩形 ← 由 panel 自己的 width/height 定
③ 设计框（design box）所有孩子 (x, y, x+宽, y+高) 的包围盒 ← 只由坐标决定
④ 孩子             放在 (设计框停靠偏移 + 孩子.x, + 孩子.y)
```

| panel 自己的 `width` / `height` | ② 面板框 |
|---|---|
| `pixels` | 那个像素（与格子冲突时以格子为准） |
| `fill` | **= 格子**（于是有余量给 ③ 挪位 —— **这是 panel 的主要用法**） |
| `adaptive` / 不写 | **= ③ 设计框**（严丝合缝，没有余量可挪） |

### 4.2 键

| 键 | 取值 | 作用 |
|---|---|---|
| `anchor` | `left`(缺省) / `center` / `right` | **③ 在 ② 里横向停靠** |
| `valign` | `top`(缺省) / `center` / `bottom` | **③ 在 ② 里纵向停靠** |
| `overflow` | `scroll` / `clip` | ③ 比 ② 大时：交给外层滚动 / 裁剪。建议 `clip`（坐标写错时"看不见"比"顶大整块内容区"安全） |
| `spacing` / `padding` | —— | **不参与**（panel 的间距与留白一律由坐标给；写了给警告，避免两个来源） |

### 4.3 孩子（违反 = 硬伤）

| 规则 | 理由 |
|---|---|
| `x` / `y` **必写**（可为负） | 坐标是唯一事实源；省略会让"忘了写"静默堆到左上角 |
| 两轴**必须 `pixels`** | panel 不缩放尺寸 |
| 不许 `fill` / `adaptive` | 孩子的 `fill` 会随格子铺开 ⇒ 它内部的容器重排 ⇒ 破坏"内部不变" |
| 不许 `scaleWithWindow` | panel 不缩放 |
| 不许 `column`/`row`/`auto`/跨格/`align`/`verticalAlign` | 不是行列容器；停靠是**容器级**的 `anchor`/`valign` |
| **允许重叠** | 层级 = 声明顺序（后画的在上面） |

### 4.4 与别的容器组合

| 情形 | 规则 |
|---|---|
| panel 放进 `flow` / `grid` | 该元素必须给两轴 `pixels`（同 `absolute` 的既有规则），panel 在那一块里铺开 |
| panel 就是模块根 | 通常写 `width: fill` ⇒ 面板框 = 视口，内容块按 `anchor` 停靠 |
| **panel 里放 `flow`/`grid` 容器** | 容器必须写两轴 `pixels`（panel 给它的是死数）⇒ 它内部照旧自适应。**自适应的边界就在这一层**：panel 决定"这一块在哪、多大"，容器决定"里面怎么排" |

### 4.5 说明文字与主体并排时，行高从主体导出

`textPlacement: left` / `right` 让说明文字与主体**同一行盒**。让"方框的中线 = 文字的中线"
成立的不是 `VerticalAlignment = Center` 一条，而是两条一起：

1. **两者高度一致**：文字的行高取**主体的声明高**（`height.pixels`）。主题里写一个定值会与声明漂移
   （实测：主题常量 20 遇上声明 28 的勾选框，中线差 4 像素）；
2. **并排时不给下边距**：那条 `0,0,0,2` 的边距只在**堆叠**（`above`/`below`）时给，
   由 `BuildLabel` 按方位就地决定（`SurfaceElementControl.cs:234-255`），并排时是 `default`。
   **类名只有一个**（`surface-title`）—— 历史文档与测试文案里写的 `surface-inline-title` **全仓不存在**，别去找它。

**为什么不能只靠居中对齐**：字体缺省的行盒比控件矮，居中的只是"行盒"而不是"眼睛看到的字" ——
布局、溢出、声明兑现**全都合格**，只有眼睛看得出不对（实测差 2–3 像素）。

### 4.6 与 `absolute` 的分工

| | `absolute`（绝对坐标） | `panel`（相对坐标） |
|---|---|---|
| 坐标基准 | 父层/窗口坐标系 | **panel 原点** |
| 缩放 | 可选 `scaleWithWindow`（元素级，按比例散开） | **不缩放** |
| 窗口变大 | 元素按比例散开 / 原地不动 | **整块挪位**，内部不动 |
| 未写几何的孩子 | 流式接在设计框之下（兜底："漏写不隐形"） | **硬伤** |

## 5. 文本怎么摆（`textBox` / `label`）

**输入面与输出面是同一块文本面，同一套摆法。** 下面每一条对两者同等生效：

| 参数 | 键 | 行为 |
|---|---|---|
| 文字从哪开始 | —— | **左上**。文本面不吃 `TextBox` 的纵向居中缺省（那会让多行时每行漂在框中间）。 |
| 长行折不折 | `wrap` | `true`（缺省）：按宽度折行。`false`：一行到底，横向滚。 |
| 行末 `↵` 画不画 | `showNewlineMark` | `true`（缺省）：在**数据里真的有换行字符**的地方画。通道换行不是字符，不画。 |
| 横向对齐 | `textAlign` | `default` / `left` / `center` / `right`。**落在内层编辑器上**（它是排版文字的那一层）。 |
| 文本层滚哪一套 | `scrollBar` | **必写**：`window` = 自建竖条 + 分页窗口（尾部跟随，日志用）；`native` = 文本框自己的滚动条（光标在哪滚到哪，输入面用）。两档互斥。 |
| 文本内部最小高 | `minEditorHeight` | `0`（缺省）= 不设。它是**文本层**的最小高，不是元素高。 |

**这三条是纪律，不是建议**：

1. **控件代码不许按"这是输入还是输出"替参数做决定。** 声明面写了就得生效 ——
   静默覆盖比"没这个参数"更难查（用户改了 json，界面纹丝不动，还以为是 json 写错了）。
2. **属性要么在[控件目录](控件目录.md)里，要么在主题里。** 两头都不在的"参数"，
   等于一个模块作者永远调不了的决定。
3. **文本面的两个轴都由约束决定，不由内容决定。** 这是上述两条之外的第三条，也是最容易漏的一条：
   会折行的控件在**约束为无穷**时按内容报尺寸（`TextBox` 就是如此）——
   宽度上表现为**文字冲出框被外层裁掉**（被裁的是字，不是框，所以从框的尺寸上看不出异常），
   高度上表现得更隐蔽：**控件把自己撑高 ⇒ 排布层以为内容真要那么高 ⇒ 内容区与视口一起被撑大
   ⇒ 它的视口与滚动范围永远一样大 ⇒ 滚动条永远不出现**（用户看到的说法是"没得可滚"）。
   所以两个轴都必须夹回实得的尺寸：文字在框内折行、超出就在框内滚。

**那一圈边框是叠加层**：常态 1px、聚焦 / 标红 2px，**厚度完全不进内容矩形** ——
否则一聚焦内容区就缩 2px，文字跟着动。**状态只改颜色与叠加层，不改任何布局矩形。**

## 6. 放不下的时候：两级溢出

**先分清是哪一级** —— 两级的处理者不同，混起来就会得到"滚动条时有时无"：

| 级 | 事实 | 谁处理 |
|---|---|---|
| **元素层** | 元素比它**分到的格子 / 行**高或宽 | **该层容器**按 `overflow` 决定：`scroll`（缺省）= 如实上报内容高，**外层滚动条**接手；`clip` = 裁掉且不外报。**对每个控件一律成立。** |
| **文本层** | 文本比文本面的**内容区**高 | **文本面自己**：按 `scrollBar` 那一档滚（`window` / `native`）。**只改文本面内部排布，不改变元素矩形。** |

| 情况 | 谁处理 |
|---|---|
| 一块内容比容器高/宽 | 元素层：该层 `overflow`（`scroll` ⇒ 外层滚动条） |
| 页面比页签视口高 | 元素层：页签自己那一层的滚动条（每一页独立滚） |
| 窗口比内容小 | 同上，滚动。**这是允许的**，不是缺陷 |
| 一块文本面里的文本比它自己高 | 文本层：那一档自己的条（框不动、字在里面滚） |

**元素层不替内容做妥协**：不把声明 96 宽的元素算成 90 就当作"放下了"，也不把最后一行压成 0 高。
那两种做法的共同后果是"屏幕上看不见，但没有任何报错"。

**条的隐现只有一条规则**：有得滚就常驻（可见性由"范围 > 视口"决定），不靠悬停去试。
同一个文本面**只可能有一根看得见的条** —— 两档互斥。

**什么时候该调窗口**：模块声明的固定像素轨道（或固定高度元素）之和超过可用范围时，
正常做法是**把自己的 `frame.window` 调够**，让默认打开就放得下；滚动条是给"用户把窗口拖小"兜底的。

## 7. 自查表（改完声明先过一遍）

| 症状 | 九成是 |
|---|---|
| 某个控件整块看不见（0 宽或 0 高） | 它的轨道被挤没了 —— 检查 `*` 轨道是不是吃太多、`rows`/`columns` 是不是漏声明 |
| 控件只有上半部分 | 元素分到的高度小于它自己内部三层（说明 / 主体 / 脚注）之和 —— 给足 `height` |
| 后面那排被盖住 | 前面某个元素的声明高之和已经超过容器可用高 —— 调窗口或压前面的元素 |
| 文字跑到框中间 | 那是全局 `TextBox` 缺省在起作用 —— 文本面自己压掉了它；若仍居中，是主题被改过 |
| 一排控件宽度参差 | 用了 `auto` 宽 —— 给固定像素（见[声明标准](声明标准.md) §3 的表） |
| 同一个界面里出现两根竖条 | 元素层与文本层混了：文本层那一档要按 `scrollBar` 显式选一个（`window` / `native`） |
| 聚焦时文字跳一下 | 有东西用"状态"改了布局矩形（边框只许画在叠加层上） |
