# 模块界面声明（`view.json`）标准写法

> **这一页讲"怎么写"**：文件形态、键的顺序、几何怎么落地、哪些东西不许写。
> **"有哪些键"看[控件目录](控件目录.md)**（由 schema 生成，不会与实现走散）；
> **"排布怎么算"看[排布与坐标](排布与坐标.md)**。
>
> 三份文档的分工是刻意的：**键表可以生成，规则不能**。规则写在这里，因为它要求人做判断。

---

## 1. 一份声明由四段组成

```jsonc
{
  "version": 1,                    // 声明格式版本（不是模块版本）
  "frame": { "window": { … }, "ports": [ … ] },   // 框架级个性化：窗口尺寸、口的位置
  "sources": [ … ],                // 数据源：模块里流动的每条数据都在这儿登记
  "views": [ { "title": "", "root": { … } } ]     // 控件树（只渲染第 0 个视图）
}
```

| 段 | 必填 | 一句话 |
|---|---|---|
| `version` | ✔ | 固定 `1`。缺失或不等于 1 = 硬伤。 |
| `frame.window` | | 模块窗口的尺寸与上下限。不写取框架缺省（320×220）。 |
| `frame.ports` | | **每个数据面口都要有一条**，且 `edge` 必填 —— 声明是"这个口在哪条边"的唯一来源。 |
| `sources` | ✔ | 数据源表。元素通过 `data` / `input` / `command` 引用它们。 |
| `views` | ✔ | 只渲染第 0 个；其余按警告忽略。 |

---

## 2. 键的顺序（强制，判据在用）

同一份文件里，每个节点的键按这个顺序写。**不是审美**：顺序固定之后，
"两个模块的同一个控件差在哪"一眼就能看出来；顺序乱了，diff 里全是噪声。

```jsonc
{
  "kind": "…",          // ① 是什么
  "title": "…",         // ② 说明文字（按钮用 text —— 见 §4）
  "data" | "input" | "command": "…",   // ③ 绑定：只写一个
  "stateKey": "…",      // ④ 运行时状态（折叠态 / 选中页）
  "column" | "auto": …, "row": …, "columnSpan": …, "rowSpan": …,   // ⑤ 摆在哪儿（仅 grid）
  "width": { … }, "height": { … },     // ⑥ 多大
  "children": [ … ]     // ⑦ 子项（仅容器）
}
```

**kind 专有的键**（`multiline` / `capacity` / `wrap` / `showNewlineMark` / `fileMode` …）
写在 ③ 与 ⑤ 之间。

## 3. 几何：**逐元素显式声明两轴**

**每个会渲染的元素都写 `width` 与 `height`，一个都不省 —— 漏写是硬伤（整份声明作废）。**
几何**没有缺省口径**：模块作者看自己的声明就得看出"这块要多宽"，
界面一旦不符预期才说得清是声明的问题还是框架的问题。

每个轴**只写一个口径**：`pixels` / `fill` / `adaptive`。
**同时写两个 = 硬伤**（读取器拒绝加载）—— 那正是"声明了却没按声明来"的另一种来源。
`min` / `max` 可与任一口径同时写（`min` 是这一块在窗口压小时的地板，**地板只有声明这一个来源**）。

**怎么选**（这张表是判断，不是规则，拿不准按它来）：

| 这一块是什么 | 宽度 | 高度 |
|---|---|---|
| 一整块文本面（日志、结果区） | `fill` | 想让它跟着窗口长 ⇒ `fill`；想让它固定 ⇒ `pixels` |
| 输入框 / 下拉 / 文件选择 | `fill` | 单行 `pixels`（28–32）；多行 `pixels`（120 上下）或 `fill` |
| 按钮 | `pixels`（80–140） | `pixels`（28–34） |
| 勾选框 / 开关 | `auto` 或 `pixels`（文字要放得下） | `pixels`（28 上下） |
| 数值读数 / 标签 | `fill` | `adaptive` 或 `pixels`（24–32） |
| 分页容器（`tabs`） | `fill` | `pixels`（按页里内容给够）或 `fill` |
| 分组框（`group`） | `fill` | `adaptive`（它由内容撑开） |

**为什么按钮与勾选框给 `pixels` 而不是 `auto`**：`auto` 的宽度由**文字**决定，
换一套主题、换一种字体，一排控件的对齐就散了。固定像素让"这一排按钮一样宽"成为事实。

### 3.1 先选容器：四种排布的分工

**选错容器比写错尺寸更贵**：行列式容器动的是"元素之间"，用越多的格子去逼近坐标，
那些"算出来的间距"就越难解释、越难微调。

| 需求 | `flow` | `grid` | `absolute` | **`panel`** |
|---|---|---|---|---|
| 位置随窗口重排 | ✅ | ✅ | ❌ | ❌ |
| 余量给某一项（吃满） | ✅ | ✅ | ❌ | ❌ |
| 二维对齐（标签列 / 控件列） | ❌ | ✅ | ❌ | ❌（自己对齐坐标） |
| 逐元素像素级微调 | ❌ | ❌ | ✅ | ✅ 本质 |
| 一对控件单独间距 | ❌ | ❌ | ✅（算坐标） | ✅ |
| 重叠 / 层叠 | ❌ | ❌ | ✅ | ✅ |
| 窗口变大时**整组挪位**（内部不动） | — | — | ❌ | ✅ |
| 窗口变大时**整组等比** | — | — | ✅ | ❌ |
| 声明量 | 少 | 中 | 多 | **最多** |
| 改窗口后要不要重看排布 | 不用 | 不用 | 要 | **要** |

**一句话**：`flow`/`grid` 描述**关系**（随容器变），`absolute` 描述**窗口坐标**（可缩放），
`panel` 描述**组内事实**（恒定，整块挪）。

**选 panel 的典型场景**：一排控件的位置需要按像素调（按钮宽 84、下一个从 92 开始、标签在 210……），
而这些"间距"是你**特意留**出来的、不希望窗口一变就被重新分配。写法见
[排布与坐标](排布与坐标.md) §4。

**不要**把 panel 当成"更精确的 grid"到处用：它每个孩子都要写四个数，且窗口一变就得重看。
只有在"这一组的位置就是设计决定"时才用。

## 4. 说明文字：`textPlacement` 决定摆哪

控件的说明文字取 `title`，**摆在哪由 `textPlacement` 决定**（缺省见下表，写在 schema 的
`defaultText` 段里，代码零默认）：

| `textPlacement` | 文字在哪 | 副轴可调 |
|---|---|---|
| `none`（多数控件的缺省） | **不画** | —— |
| `above` / `below` | 主体的上 / 下方各占一行 | **横向**：`textAnchor` = `start` / `center` / `end` |
| `left` / `right` | 与主体**并排**（同一行盒，中线严格对齐） | **纵向**：`textAnchor` = `start` / `center` / `end` |

**`textAnchor` 只作用于副轴**：方位已经决定了另一轴，"文字在上方"再写"顶对齐"是自相矛盾，
写了不会有任何可见效果 ⇒ 读取器按方位报硬伤。

**各 kind 的缺省**（保持历史行为，改声明面不改变任何现有模块的渲染）：

| 控件 | 缺省 | 备注 |
|---|---|---|
| `textBox` | `above` | 只在**可编辑**面？不 —— 见下条 |
| `toggleSwitch` / `toggleSlider` | `right` | 勾选框在左、文字在右（WinForms 的固有预期） |
| `label` | `none` | 它自己的字在 `text` 里 |
| 其余（`numeric` / `curve` / `button` / …） | `none` | 不画 |

### 4.1 **只读与"有没有说明文字"是两件事**

`readonly` 管的是"这块文本面能不能编辑"，与它**有没有**一行说明**互不干扰**。
以前只读面被一条 `if (ReadOnly)` 静默吃掉说明文字 —— 那是隐式特例，作者看不出也改不了。
现在：只读面写 `"title"` 就按 `textPlacement` 画；不想要就显式写 `"textPlacement": "none"`。

### 4.2 `title` 不是所有控件的"说明文字"

| 控件 | `title` 的真实用途 |
|---|---|
| `commandButton` | **不许写**（写了是硬伤）。按钮的字用 `"text"`。 |
| `enumSelector` | 下拉的**水印**（占位提示），不是标签。 |

这两处的 `title` **不吃** `textPlacement`：它们不是"说明文字槽"。
需要一段自由摆放的说明时用 `label` —— 那是"描述性文本"该有的位置。

**理由**：`title` 在别处一律是"这个元素的说明文字"，而按钮上的字**就是按钮本身**。
同一个键承担两种语义，界面上就会出现双份文案（按钮上真的会写两个「发送」）。

### 4.2b 文件选择**不是一种控件**

"让用户指一个文件路径"是**模块能力**，不是界面元素：

```csharp
// 模块在自己的命令处理里发起；用户选定后，路径**经输入通道投回**（与用户自己敲进去同一条路）
context.Files.Request(new FilePickRequest(
    "savePath", FilePickMode.Save, "文本文件 (*.txt)|*.txt", "savetext1.txt"));
```

理由：过滤串 / 预填名 / 三种模式是**宿主对话的配置**，不是界面事实；把它做成一个按钮型控件，
声明面就得去描述"对话框怎么配"，还会让同一个路径值有两个存放处（元素自己的文本 + 模块）。
能力与 `ModuleCapability.File` 这条声明对齐（"文件读写，限制在用户选择的路径内"）。
界面那一侧只是一个普通的 `commandButton`，点它让**模块**去请求对话框。

### 4.3 要像素级微调就写 `none` + 自己摆 `label`

`left` / `right` 只保证"并排 + 中线严格对齐"，间距与列宽不开放。要自己定位置：

```json
{ "kind": "toggleSwitch", "input": "flag", "title": "连续发送", "textPlacement": "none" },
{ "kind": "label", "text": "连续发送", "nowrap": true, "x": 12, "y": 4, "width": {"pixels": 80}, "height": {"pixels": 20} }
```

代价是**对齐要你自己保证**：独立 `label` 是另一个元素，框架不知道它跟谁成对。
`flow` 下靠"两个元素**同高**"；`panel` 下靠你给的坐标。

**你只需要记住一条**：**声明的框就是看得见的那一块**（内容严丝合缝地吃满它，只留框线那 1–2 px）——
所以"看起来对齐"就是"框对齐"：`panel` 里让同一行的件的**框中心**落在同一个 `y + 框高/2` 上即可
（写法与逐 kind 表见 [排布与坐标](排布与坐标.md) §1.3）。文字类内容由控件自己在框内居中，不必你补差。

### 4.4 **消息不是控件能力**：模块写文本，控件按声明显示

**任何控件都不带"角"**，也没有"成功 / 失败"这种元素级结果。要给用户看一句话，走这条路：

```csharp
// 模块侧：把这句话写进一条源（替换语义 —— 连写两次只看到后一句）
context.Display.SetText("status", $"已保存：{name}（{lines} 行）");

// 要标出"是哪一格不对"就再给它一个颜色：
// **框架不认识"红 = 失败"** —— 红绿蓝由模块自己挑，这才是"外观是基础能力、不限定功能"。
context.Appearance.SetOutlineColor("interval", 0xFFD32F2F);
```

界面上由**声明**决定这句话长在哪儿，两种载体都行：

| 载体 | 写法 | 什么时候用 |
|---|---|---|
| **`label` 绑源** | `{ "kind": "label", "data": "status", "height": {"pixels": 18}, ... }` | 要一块**只有这句话**的地方（消息、状态） |
| **只读 `textBox` 绑源** | `{ "kind": "textBox", "data": "status", "readonly": true, ... }` | 这句话要多行 / 要能选中复制 |

**为什么不做成"每个控件自带一块结果区"**：那会把"显示消息"变成控件的固定本事 ——
每个控件都长出一块角、文字散在各处，而"这类消息该显示在哪儿"本该是**模块的排布选择**。
同理，`label` 绑了 `data` 就是"会变的文字"，不必为了显示一句话去借只读文本框。

消息的源**可以没有界面实体**：它出现在 `sources` 段就是接线了（判定见 §5.1）。
### 4.5 颜色的边界：主题给基线与色板，声明给初始值，C# 给"什么时候变"

| 归**主题** | 归**声明** | 归**模块的 C# 逻辑** |
|---|---|---|
| 字体族、字号档位、边框样式与圆角、控件底色、状态色**本身**（成功绿 / 危险红的色值） | 一块文字自己的字号与颜色（`fontSize` / `textColor` / `titleFontSize` / `titleColor`，见 §5.5） | 什么时候把某个元素的边框 / 文字设成什么颜色（`IViewAppearanceAccess`） |

这三档**互不干扰**：主题管"长什么样"的基线与色板；声明管"出来瞬间是什么样"；
运行时那一次变化归模块。**声明永不写死"成功/失败该是什么色"** —— 那是模块在运行时选的。

## 5. 每个节点该写哪些键（**按"谁读它"判**）

**判据只有一条**：这个键**有没有消费者**。有消费者 ⇒ **写全**（不许省，省了就是静默）；
没消费者 ⇒ **不许写**（写了没有任何效果，是最坏的一类"以为配好了"）。

「消费者」不看推演，看 [控件目录](控件目录.md) 的**「适用」列** —— 那一列就是这个键的消费条件。

### 5.1 通用键：随**父容器**与 **kind** 变

| 键 | 什么时候写 |
|---|---|
| `kind` / `width` / `height` | **每个节点都写**（几何见 §3） |
| `x` / `y` | **只在父层是 `panel` 时**写（panel 的孩子两轴必须 `pixels`） |
| `column` / `row` / `columnSpan` / `rowSpan` | **只在父层是 `grid` 时**写 |
| `align` / `verticalAlign` | **只在父层是 `grid` 时**写 —— 元素在格子里靠哪边就靠它（想"贴左"就写 `left`，别指望别的键） |
| `scaleWithWindow` | **只在父层是 `absolute` 时**写（四个基础模块没人用 `absolute` ⇒ 一律不写） |
| `textPlacement` / `textAnchor` | **有 `title` 的节点都写**（见 §4；`numeric` 这类不画说明文字的也要**显式写 `none`**） |
| `readonly` | **只给 `textBox` 写** |
| `stateKey` | 容器（页签 / 折叠）与输入控件写；其它节点不写 |
| `title` | 画说明文字、当页签名 / 分组标题 / 折叠头的节点写；`commandButton` 用 `text`（写 `title` 是硬伤） |
| `data` | `textBox`（输出）/ `label`（会变的文字）/ `numeric` 写。**`label` 的 `data` 可以省略** —— 不绑就是一块写死的说明（schema 里 `roleKeysOptional`） |
| `textColor` / `fontSize` | **这块控件"主文字"的颜色 / 字号**（`label` 正文、`textBox` 的输入文本、`numeric`/`curve` 的读数、`commandButton` 按钮上的字）。**必填**：不写 = 硬伤；写 `""` / `0` = 用主题那一档 |
| `titleColor` / `titleFontSize` | **这块控件"说明文字"（`title` 那一块）的颜色 / 字号**。只有声明了 `textPlacement`（≠`none`）才有实体，但**键仍必填**。`toggleSlider` 只有说明文字 ⇒ 它只登记这两个（没有 `fontSize`/`textColor`） |
| **`auto`** / **`icon`** / **`inputKind`** / **`capacity`** | **已从声明面删除**（都没有消费者）。落位只有 `column`+`row` 一种写法（都不写 ⇒ 按声明顺序）；字符级合法性归**模块**判 |

### 5.2 本 kind 的专有键：**一律写全**

`textBox` 为例：`multiline` / `textAlign` / `wrap` / `showNewlineMark` / `minEditorHeight`
/ `scrollBar` / `readonly` —— **一个都不省**（其中 `scrollBar` 是**必写键**：文本层用哪一套滚动
不由框架按 `readonly` 替你推）。
它们的缺省（`true` / `"default"` …）是 schema 里的**兜底**，不是"作者可以不管"：
省了之后，读者无法从声明文件看出"这一格折不折行、能不能编辑、滚哪一套"。

### 5.3 容器专有键：也写全

`layout` / `overflow` / `padding` / `spacing`（+ `grid` 的 `columns` / `rows` / `columnSpacing` / `rowSpacing`、
+ `panel` 的 `anchor` / `valign`）。**panel 不写 `padding` / `spacing`**（它俩在 panel 里被忽略）。

### 5.4 「提交」不是用户能感知的行为

上一节那条判据（**按"谁读它"判**）在这里有一个容易走错的推论：把"用户填的这一格没提交"当成缺陷去补一条"失焦提交"或"回车提交"。**它为什么是错的**：

| | 用户可感知的 | 只该是实现机制 |
|---|---|---|
| 动作的**触发点** | 点按钮、勾开关、滑滑块 | 「提交」这个动词本身 |
| 值的**去向** | 屏幕上"我填的东西生效了" | 模块从**视图状态**读（逐键实时更新） |

于是有两条硬规则：

1. **模块读值一律从视图状态读**（`IViewStateReader.GetInputText`），**不依赖任何提交动作** ——
   用户在框里打字，值就一直在那儿；模块每拍看一眼、变了才处理。文本框**不提交**、
   `Enter` **不提交**、"失焦"更不提交。
2. **动作不成立时，把它复原**（`IViewAppearanceAccess.ResetInteraction`）：勾了「连续发送」却发不出去
   ⇒ 勾选框被**拨回去**，用户看到的是"这个操作没成立，它自己退回去了"，而不是"我勾了但它没反应"。

**"提交"为什么会把界面弄坏**：发送器的页内文本也在同一条通道上 —— 一旦编辑即提交，
"打完字点一下别处"就会**发出一条报文**。这是实际发生过的缺陷，不是推演。

### 5.5 文字外观：**一块文字一条键**（且必填）

一块控件可能有两块文字：**主文字**（它显示的内容）与**说明文字**（`title` 那一块）。两者**各由自己的键**描述：

| 键 | 描述谁 | 谁要写 |
|---|---|---|
| `fontSize` / `textColor` | 这个控件的**主文字** | 有主文字的 kind：`label` / `textBox` / `numeric` / `curve` / `commandButton` |
| `titleFontSize` / `titleColor` | 这个控件的**说明文字** | 任何带 `title` 且可能画它的原子控件（含 `toggleSlider`） |

三条口径：

1. **必填**：四个键都**不许缺省**（schema 里 `required` 且没有缺省值）。不写 = **硬伤**；
   要"跟主题"就**显式写** `0`（数字）/ `""`（颜色）—— 与枚举键的 `default` / `none` 同一个意思。
   理由：缺省即静默，作者改了 json 却看不出"到底生效没有"。
2. **声明是初值，逻辑说了算**：主文字可被运行期 `IViewAppearanceAccess` 覆盖；清空 ⇒ 回到声明；
   两者都没有 ⇒ 交还**主题**（主题的类选择器是"缺省那一档"的唯一来源）。说明文字没有运行期通道。
3. **不设跨控件标准**：同一行里别的控件长什么样，与本控件**无关** —— 想统一就自己把值写成一样，
   框架不会替你"对齐同行文字"（那是排版，不是机制）。

> **落地位置**：字号/颜色必须写到**真正显示文字的那个元素**上（`TextBlock` / 内层编辑器 / 按钮本身），
> 不能靠外层元素继承 —— 主题的类选择器会在那个元素自身上设字号/前景，而**样式值压过继承**。
> 曾经因此出现过两类静默：`label` 声明了 `fontSize` 不生效、文本框的 `textColor` 与运行期设色不生效。

## 6. 不许写的东西

| 不许 | 为什么 | 该怎么写 |
|---|---|---|
| **没消费者的键**（`auto` / `icon` / `inputKind` / `capacity` …） | 写了也没人读 —— 最坏的一类"以为配好了" | 见 [控件目录](控件目录.md) 的「适用」列；**判据是"谁读它"** |
| 字体 / 边框样式 / 圆角 / 控件底色 | 那是**主题**的基线与色板；写进声明，换主题就换不动 | 什么都不写，主题会给。**例外**：**这块文字自己的外观**（`fontSize` / `textColor` / `titleFontSize` / `titleColor`）是**内容语义**，见 §5.5 |
| 把"成功 / 失败"写进声明 | 颜色与它何时变是模块的逻辑；声明写死就等于规定"失败必须长这样" | 声明给初始值，运行时由 `IViewAppearanceAccess` 设 |
| `title` 写在 `commandButton` 上 | 见 §4 | `text` |
| 一个轴写两个口径 | 只会取前一个，另一个静默失效 | 只留一个 |
| 一个元素写两个绑定键 | 硬伤（`data` / `input` / `command` 只能一个） | 只留一个 |
| grid 里只写 `columnSpan` / `rowSpan` 却不给 `column` / `row` | 硬伤：跨度没有起点 | 连 `column`+`row` 一起写，或都不写（顺序即位置） |
| `rows` / `columns` 没声明就用 `row` / `column` 索引 | 硬伤：索引越界 | 把用到的轨道声明出来 |
| 非 grid 容器写 `columns` / `rows` / `row` / `column` | 警告后忽略 | 删掉 |
| panel 里写 `align` / `verticalAlign` | 硬伤：panel 的停靠是**容器级**的 `anchor` / `valign` | 用 `x` / `y` 定位，容器级停靠写在容器上 |
| 页载体（`tabs` 的直接子节点）写 `width` / `height` | 硬伤：载体自己不生成控件，页内容的尺寸由**页签那一层**决定（`tabs.rows` 分出页签条与页内容，页内容再按自己的下限占位）—— 写在这里没有消费者 | 什么都不写；页里元素的尺寸写在**页里的元素**上 |

> **未渲染的 kind**（`statusLight` / `table` / `image` / `enumSelector`）**可以写**：
> 加载不报错、界面给一块写明"尚未渲染"的占位，另给一条警告。这是设计，不是缺陷 ——
> 比"画一个看起来能用、其实什么都不做的壳"诚实。

## 8. 一件事只有一个地方说

写声明时如果发现"同一个数值要在两处保持一致"，那是**声明面缺一个键**，不是"两边都记得改就行"。
已知的这类坑与它们的处理：

| 坑 | 处理 |
|---|---|
| 窗口高度放不下自己声明的内容 | 调 `frame.window`，不是缩内容（见[排布与坐标](排布与坐标.md) §5） |
| 一排控件各写各的宽，改了字体就散了 | 给固定像素（§3 的表） |
| 页里内容超过页高 | 那是**要滚一下**，不是缺陷（元素层由外层滚动条接手）；真正的缺陷是控件被排到视口外、或声明的高没兑现 |
