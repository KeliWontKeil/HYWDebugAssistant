### 1.2 声明表

| 项 | 内容 | 依据 |
|---|---|---|
| **数据类型** | **`RawBytes`@v1**（**D1 中性化**：原名 `NormalText`，改名理由见 §9.8）：形状 = `StructShape(("len", u16), ("data", BytesShape(1472)))` —— **【已裁 T1】** 方案②（长度 + 定长字节块），**N = 1472**（一个完整 UDP 载荷）；框架字节块上限已由 256 放宽到 **4096**（见 §5）。**契约尺寸 = 2 + 1472 = 1474 字节**（定长，`SizeInBytes` 编译期可算） | `03-data-protocol-and-typing`（形状即契约；**v1 只定长** ⇒ 字符串由"定长数组 **+ 长度字段**"自行表达 —— C3-5） |
| **`len` 的语义** | **有效字节数**（0–1472），**且它是唯一的"到哪结束"判据**。**【已裁 T10】**：`data` 尾部**补零**，但 **`0x00` 是合法数据、绝不是终止符** ⇒ 收方**必须按 `len` 切片**，**禁止**"遇到 0 就停"（C 字符串式的 NUL 截断）。用户原话："我有时会写 `00` 这种十六进制字符，它有时候在字符串中会有一定的意义（特别是对于我开发单片机来说，每个值都是有意义的）" | `03`（形状是机械结构；**"怎么解读"属模块语义**） |
| **数据角色（层②）** | `text-send`：**一种数据类型**（上表）+ **输出口** `out`（**无输入口** ⇒ 纯源角色） | `02-module-sdk`「角色声明」 |
| **角色顺序** | **不声明**：单角色模块无需 `DeclareFlow` | `02-module-sdk` |
| **端口** | `输出`：`out`（角色 `text-send`，方向 `Send`，契约 = `RawBytes`@v1） | `02-module-sdk`「口声明」 |
| **兼容要求** | 与**形状完全一致**的口可连（`05` §4：形状不完全一致即不连，**不自动转换**）；**不需要**显式强连确认 | `decisions.md` 4.5 · `05-network-semantics` §4 |

| 需要的能力 | 现状 | 请求状态 |

| **定长字节块 > 256 字节** | ✅ **已放宽（2026-09）**：`BytesShape.MaxLength` **256 → 4096**（`Sdk/Contracts/ContractShape.cs`，**只增/放宽**）。引用点只有 `Sdk` 构造校验 · `Sdk.Testing.ModuleContract` · `TestModuleContext` ⇒ **自动跟随**；**当时**由 grep 全仓取证：**无一处参考模块引用该常量** ⇒ 豁免"重编全部模块 + T3"（例外登记见 `decisions.md` **7.23**）。**该载体已于 2026-09 按用户裁定删除**，取证结论保留为历史证据 | **已完成**；`roadmap.md` §3 第 17 项 |

| 其他 | 长度字段 / 结构体组合 / 多行输入 / 输入失败红框 **均已具备** | — |

> **放宽上限的影响面（已取证）**：`BytesShape.MaxLength` 仅被 ① 构造校验 ② `ModuleContract` 的长度校验 ③ `TestModuleContext` 的"按长度推断形状"（`Math.Clamp(..., MaxLength)`）引用 ⇒ **改常量即可，三处自动跟随**；`ArrayShape.MaxLength` 是**独立常量**，方案②不用它，可不动。
> **代价（必须知情）**：v1 契约**只定长** ⇒ **每个数据单元的搬运字节 = 契约尺寸**（投递校验只拒"过短"，缓冲按 `layout.SizeInBytes` 租用 ⇒ 发 1 个字符也搬满 N 字节）。N 越大 ⇒ 单元速率相同时**字节速率与队列内存越高**（池化按需借用，最坏情况 = 积压满 1024 单元）。**这正是"长度字段"存在的意义**：下游据 `len` 取真实内容，不据搬运尺寸。

## 8. 已知限制

- **单条长度 = 1472（定长契约的硬约束）**：v1 只支持定长、不引入变长、不分片（`03` §2 · `05`「明确不做」）⇒ 单元**永远搬 1474 字节**（见 §5 的代价说明）。**超过 1472 的文本由模块拆成多个数据包发送**（**【已裁 T13】**；**契约不上调** —— "数据传输契约不会允许超过 1472 字节"），但**接收侧会表现为多条**（框架不做跨包重组 ⇒ **【已裁 T14a】**：完全接受，"这是可预期可复现的特性"）。
- **`0x00` 不是终止符**（**【已裁 T10】**）：尾部**补零**只是填充；`data` 里的 `0x00` 是**合法数据**（单片机场景下每个值都有意义）⇒ 收方**必须按 `len` 切片**，**禁止 NUL 截断**。任何接收侧模块（如 `hyw/data-monitor`）都必须守这条。
- **空内容静默不发**（**【已裁 T11】**）：输入为空 ⇒ 点「发送」**什么都不做**，**不报错、不提示**（"空"在各层意义一致）。
- **没有配置、不落盘**：本模块所有可调项都是运行期状态 ⇒ **重启后回到默认**（这是【已裁 T8】的意图：重启不该自动发数据）。
- **不做行尾加工**（**【已裁 T2】**）：发送内容**原样**进载荷，"最重要的是还原而不是格式"；要换行就在文本里写换行（多行输入框里回车即换行 —— **所见即所发**，`02-module-sdk`「不自动折行」）。
- **响应粒度约一个定时器刻度**：见 §4；「间隔」上下限见 §4 的范围说明。
- **编码**（**T12 已裁 = UTF-8**）：ASCII 字符 1 字节（**与原先"仅支持 ASCII"场景字节完全一致**）· 中文 3 字节 · 补充平面 4 字节；**非法字节序列**字符串方向明确报错（不静默替换 `�`），十六进制方向永不丢 ⇒ 详见 §9.5。**字节口径与下位机（C）的对齐关系**见 §9.6（`len` = 字节数 ≡ `strlen`；协议层不碰字符）。

### 9.5 非 ASCII 编码：三方案分析（**T12 的决策依据** —— 用户要求评审"32 位拆 2 个 16 位"的想法）

**先把两个决策点分开**（它们**必须一致**才能往返）：

| 决策点 | 内容 | 落在哪 |
|---|---|---|
| **A** | `RawBytes.data` 这个**字节区**里放什么编码（发送方把"文本"变"字节"） | 本模块（`text-sender`），以及任何发文本的模块 |
| **B** | 读这个字节区时按什么编码**理解**（尤其 HEX ↔ 字符串转换、数据显示） | `hyw/hex-string-converter` · `hyw/data-monitor`（**均未起草** ⇒ 现在定成本最低） |

| 维度 | **ASCII-only**（现行约定） | **UTF-8** | **UTF-16（码点拆 1–2 个 16 位 / 代理对）** |
|---|---|---|---|
| **"不丢信息"** | 非 ASCII **直接不支持**（要丢） | ✅ **不丢** | ✅ **不丢** |
| **ASCII 字符的字节** | 1 字节 | **1 字节（与现在完全一致）** | **2 字节，且必带一个 `0x00`** |
| **中文（BMP 内）** | ✗ | 3 字节 | 2 字节（更省） |
| **补充平面（emoji 等）** | ✗ | 4 字节 | 4 字节（**代理对** = 2×16 位，正是你说的"32 位拆 2 个 16 位"） |
| **`0x00` 的出现频率** | 只在真正的 NUL | 只在真正的 NUL | **每个 ASCII 字符都带一个** |
| **与 T10 的期望是否冲突** | 否 | **否** | ⚠ **严重冲突**：下位机/第三方工具**普遍**把 `0x00` 当字符串结束（即使我们规定"按 `len` 切片"，**别人不一定遵守**）⇒ UTF-16 的报文在对方看来是"每两个字节就截断一次" |
| **HEX 可读性**（每字节 2 位 hex） | 直观 | 直观（中文 = 6 个 hex 字符） | 直观但**混**：一个汉字 4 个 hex 字符、一个字母也是 4 个（`41 00`）⇒ 分不清"这是宽字符还是数据" |
| **变长截断风险**（1472 上限处切一刀） | 无（等长） | ⚠ 可能切在多字节字符中间 ⇒ 需**整字符对齐**规则 | ⚠ 可能切在代理对中间（同理） |
| **行业惯例（串口 / 嵌入式文本）** | 老设备 | **主流**（与 ASCII 兼容是决定性优势） | 见于 Windows API / C# 内部 / 某些 LCD 字库与老协议 |

**结论（2026-09 已裁）**：✅ **采纳 UTF-8**。用户原话："**T12 可能是我对 UTF8 理解有误，按你的建议和判断做**"；"32 位拆 2 个 16 位"是**不准确的比方**，**以 UTF-8 的处理方式为准**。

具体口径：

| 项 | 约定 |
|---|---|
| **编码** | **UTF-8**（无 BOM）——ASCII 字符 1 字节（**与现行 ASCII-only 场景字节完全一致**）· 中文 3 字节 · 补充平面 4 字节 |
| **`len` 的口径** | **字节数**（不是字符数）⇒ 1472 字节上限 ≈ 最多 1472 个 ASCII 字符 / 约 490 个汉字 |
| **拆包对齐**（T13 的实现约束） | **必须按字符边界切**，绝不把多字节序列切两半（否则两包都解不出）——同"整字符对齐"要求 |
| **非法字节序列** | 字符串方向**明确报错**（不静默替换成 `�`）；十六进制方向**永不丢**（显示原始字节）⇒ 这是"不丢信息"的真实落点 |
| **`0x00`** | 与 T10 一致：**合法数据、不是终止符**（UTF-8 下 `0x00` 只出现在真正的 NUL 字符） |

### 9.6 字节口径与下位机（C）的一致性（**2026-09 用户裁定：甲方案 · "与 C 里面的约定对齐即可"**）

> 用户诉求："这关系到一致性问题，我希望上位机的逻辑更接近下位机"。结论 = **上位机按字节思考，与 C 的字符串/字节口径对齐**；**下位机的字库与寻址不归上位机管**（"怎么处理字库和寻址是单片机自己的事情"）。

**下位机侧的事实（C 语言）**：

| 问题 | 事实 |
|---|---|
| 下位机怎么存中文 | `char[]` 里存的**永远是字节** —— C 没有"字符"概念；源文件是 UTF-8 时，`"你好"` = `E4 BD A0 E5 A5 BD 00`（6 字节 + 1 个 NUL 终止符） |
| 怎么区分 1 字节 / 3 字节字符 | **靠 UTF-8 的"自同步"**（不需要长度前缀、也不需要补 0 分隔）：<br>`0xxxxxxx` = ASCII 单字节 · `110xxxxx`+1×`10xxxxxx` = 2 字节 · `1110xxxx`+2×`10xxxxxx` = **3 字节（中文）** · `11110xxx`+3×`10xxxxxx` = 4 字节<br>⇒ 任意位置都能判断"这是新字符开头还是要跳过的续字节"，**逐字节扫描即可，全程不必知道整串长度** |
| 是不是补 0 | **不补**（除末尾那一个 NUL 终止符）；`strlen` 返回**字节数**（`"你好"` = 6，不是 2） |

**上位机的对应口径**：

| 下位机（C） | 上位机（本模块 / `RawBytes`） | 一致？ |
|---|---|---|
| `char[]` 存字节 | `data` 存**字节** | ✅ |
| `strlen` = 字节数 | **`len` = 字节数**（不是字符数） | ✅ |
| 显示时才查字库/解码 | **协议层不碰字符**，显示时才 UTF-8 解码 | ✅ |
| 不补 0（除末尾 NUL） | 尾部补零**只是定长容器填充**；**`0x00` 是合法数据**（T10） | ⚠ **有意不同** —— 我们更安全（能传含 `0x00` 的数据） |

**唯一那处差异的正确接法**（必须写进对接文档）：我们的报文是 **`len` + 数据**（长度前缀），C 字符串是 **NUL 终止** ⇒ 下位机**不能**直接 `printf("%s", data)`（会在第一个 `0x00` 处停 —— 那 0 可能是填充、也可能是数据），必须**按 `len` 处理**：

```c
for (int i = 0; i < len; i++) putchar(data[i]);   // ✅ 按长度处理
// 或 printf("%.*s", (int)len, data);
```

这本身就是嵌入式协议最常见的形态（TLV / length-prefixed）⇒ **方案② 天然贴近下位机**。

**场景确认（用户 2026-09）**：下位机 = **(甲) 只把串口字节原样转发/存储**，显示由上位机或串口助手负责 ⇒ **传输口径与 UTF-8 完全对齐，无需额外约定**；(乙)"下位机自己驱动 LCD/串口屏显示中文"**不纳入本约定范围**（字库索引与寻址属单片机内部事务）。

**对后续模块的约束**（`hyw/data-monitor` 等）：**按 `len` 切片后做 UTF-8 解码**，**禁止 NUL 截断**；非法/被截断序列**明确标出**（不静默显示乱码）—— 这样"上位机显示"与"下位机打印"才对得上。
