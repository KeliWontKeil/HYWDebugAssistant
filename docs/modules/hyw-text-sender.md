### 1.1 功能角色与数据角色构成（四层视角的 ①② —— `implementation/06` §A.1）

| 层 | 内容 |

- [x] **α**：本角色**只有输出口**（纯源）⇒ 输入口/输出口同型**天然满足**；**无类型转换** ⇒ **不拆角色**

### 1.2 声明表

| 项 | 内容 | 依据 |
|---|---|---|
| **数据类型** | **`RawBytes`@v1**（**D1 中性化**：原名 `NormalText`，改名理由见 `../journal/modules-rulings-and-progress.md` §9.8）：形状 = `StructShape(("len", u16), ("data", BytesShape(1472)))` —— **【已裁 T1】** 方案②（长度 + 定长字节块），**N = 1472**（一个完整 UDP 载荷）；框架字节块上限已由 256 放宽到 **4096**（见 §5）。**契约尺寸 = 2 + 1472 = 1474 字节**（定长，`SizeInBytes` 编译期可算） | `03-data-protocol-and-typing`（形状即契约；**v1 只定长** ⇒ 字符串由「定长数组 **+ 长度字段**」自行表达） |
| **`len` 的语义** | **有效字节数**（0–1472），**且它是唯一的「到哪结束」判据**。**【已裁 T10】**：`data` 尾部**补零**，但 **`0x00` 是合法数据、绝不是终止符** ⇒ 收方**必须按 `len` 切片**，**禁止**「遇到 0 就停」（C 字符串式的 NUL 截断）。用户原话：「我有时会写 `00` 这种十六进制字符，它有时候在字符串中会有一定的意义（特别是对于我开发单片机来说，每个值都是有意义的）」 | `03`（形状是机械结构；**「怎么解读」属模块语义**） |
| **数据角色（层②）** | `text-send`：**一种数据类型**（上表）+ **输出口** `out`（**无输入口** ⇒ 纯源角色） | `02-module-sdk`「角色声明」 |
| **角色顺序** | **不声明**：单角色模块无需 `DeclareFlow` | `02-module-sdk` |
| **端口** | `输出`：`out`（角色 `text-send`，方向 `Send`，契约 = `RawBytes`@v1） | `02-module-sdk`「口声明」 |
| **兼容要求** | 与**形状完全一致**的口可连（`05` §4：形状不完全一致即不连，**不自动转换**）；**不需要**显式强连确认 | `decisions.md` 4.5 · `05-network-semantics` §4 |

**阶段 1 通过判据复核**（`implementation/06` §E 阶段 1）：

- [x] **与 `02` / `03` 一致**：形状只在字母表内组合（原语 + 定长字节块 + 结构，深度 2 ≤ 4）；长度为 `u16`（1472 < 65535 ✓）
- [x] **每个口 / 数据源的类型引用都能在本模块解析**：`RawBytes` 由**本模块自己声明**（不是引用外部类型）⇒ 必然可解析
- [x] **角色里的口与口声明一一对上**：角色 `text-send` 的出口 = `out` = 唯一的 `PortDeclaration`（1:1）

**两条必过的自检**（`implementation/06` §B.1-b）：

- [x] **一个角色只有一种数据类型** ⇒ 本模块只有一种类型在流动（`RawBytes`）⇒ 恰好一个角色
- [x] **角色的输入口与输出口同型（α）** ⇒ 本角色**只有输出口**（纯源）⇒ α 天然满足；**无类型转换** ⇒ 不需要拆角色

> **代价（必须知情）**：v1 契约**只定长** ⇒ **每个数据单元的搬运字节 = 契约尺寸**（投递校验只拒「过短」，缓冲按契约尺寸租用 ⇒ 发 1 个字符也搬满 N 字节）。N 越大 ⇒ 单元速率相同时**字节速率与队列内存越高**（池化按需借用，最坏情况 = 积压满 1024 单元）。**这正是「长度字段」存在的意义**：下游据 `len` 取真实内容，不据搬运尺寸。

## 8. 已知限制

- **单条长度 = 1472（定长契约的硬约束）**：v1 只支持定长、不引入变长、不分片（`03` §2 · `05`「明确不做」）⇒ 单元**永远搬 1474 字节**（见 §5 的代价说明）。**超过 1472 的文本由模块拆成多个数据包发送**（**【已裁 T13】**；**契约不上调** —— 「数据传输契约不会允许超过 1472 字节」），但**接收侧会表现为多条**（框架不做跨包重组 ⇒ **【已裁 T14a】**：完全接受，「这是可预期可复现的特性」）。
- **`0x00` 不是终止符**（**【已裁 T10】**）：尾部**补零**只是填充；`data` 里的 `0x00` 是**合法数据**（单片机场景下每个值都有意义）⇒ 收方**必须按 `len` 切片**，**禁止 NUL 截断**。任何接收侧模块（如 `hyw/data-monitor`）都必须守这条。
- **空内容静默不发**（**【已裁 T11】**）：输入为空 ⇒ 点「发送」**什么都不做**，**不报错、不提示**（「空」在各层意义一致）。
- **没有配置、不落盘**：本模块所有可调项都是运行期状态 ⇒ **重启后回到默认**（这是【已裁 T8】的意图：重启不该自动发数据）。
- **不做行尾加工**（**【已裁 T2】**）：发送内容**原样**进载荷，「最重要的是还原而不是格式」；要换行就在文本里写换行（多行输入框里回车即换行 —— **所见即所发**，`02-module-sdk`「不自动折行」）。
- **响应粒度约一个定时器刻度**：见 §4；「间隔」上下限见 §4 的范围说明。
- **编码**（**T12 已裁 = UTF-8**）：ASCII 字符 1 字节（**与原先「仅支持 ASCII」场景字节完全一致**）· 中文 3 字节 · 补充平面 4 字节；**非法字节序列**字符串方向明确报错（不静默替换 `�`），十六进制方向永不丢 ⇒ 详见 `../journal/modules-rulings-and-progress.md` §9.5。**字节口径与下位机（C）的对齐关系**见同文件 §9.6（`len` = 字节数 ≡ `strlen`；协议层不碰字符）。
