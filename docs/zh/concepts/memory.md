# 内存构成与释放

这页回答三个问题：界面上的内存数字由什么组成、为什么"清空/关闭"看起来不回落、哪些行为是可优化的实现而不是框架限制。

## 读数字：工作集不是"活对象"

面板里的 `MEM` 是**工作集**（`WorkingSet64`），它同时包含：

| 组成 | 归属 | 会不会随"清空/关闭"回落 |
|---|---|---|
| 托管活对象（缓冲、视图、撤销栈…） | 我们的代码 + Avalonia | 会，但要等 GC 回收 |
| 托管堆的已提交段（gen0/gen2/LOH） | CLR GC | 不会立即；GC 在压力下才会收缩 |
| 已加载的模块程序集 | 默认 `AssemblyLoadContext` | **不会**（进程生命周期） |
| 字体/字形与格式化缓存 | Skia / HarfBuzz / Avalonia 静态池 | 不会（有上限） |
| 原生分配（窗口、渲染） | Avalonia / Windows | 随窗口关闭回收，但不保证立刻归还操作系统 |

因此"清空一大段文本后 `MEM` 只降不到 1 MB"和"关掉模块只降一半"都不等于泄漏：活对象很快变成垃圾，但**已提交段**要等 GC 收缩，程序集与原生缓存本来就不随实例走。判断是否泄漏要看**强制 GC 后的活对象**，而不是工作集。

## 文本在内存里有几份

一条数据从字节到屏幕，经过：模块把字节渲染成文本 → 显示缓冲持有 → 视图显示。

- **显示缓冲**（`DisplayBuffer`）是唯一权威：按行保存字符串，受 `DefaultCapacity`（20 000 行）与 `DefaultMaxChars`（1 048 576 字符）两个独立上限约束，取先到者。
- **视图**（`IncrementalTextView`）只持有布局需要的结构；视觉行按**区间**记录（`StartInLine + Length`），只有可见窗口内的行才物化字符串并建 `TextLayout`，滚出窗口即释放。
- **输入端**（`ModuleTextSurface` 的编辑面）另有一份 `TextBox` 文本与 Avalonia 的撤销栈：撤销每个状态保存**整段文本**（默认上限 10 个）。这是可编辑输入的合理特性；**只读面不启用撤销**，也不该为它留这份内存。
- 保存/复制时才会把行拼成完整字符串（一次 O(总字符) 的复制），不是每帧。

## 分配热点与已做的收敛

高频（1 ms）发送时，真正把 GC 打满的不是"文本本身"，而是**每包/每帧的临时对象**。已收敛的几条：

| 位置 | 旧行为 | 现在 |
|---|---|---|
| 文本发送器拆包 | 逐字符 `ToString()+GetBytes()`，1 KB 文本约 40 KB 垃圾/包 | 先量字节数、再一次编码进池化载荷（≈0） |
| 显示器格式化 | 每包一个 `StringBuilder` + `string` | 目标缓冲复用；"不换行"的包按 tick 合并成一次追加 |
| 视图视觉行 | 每个视觉行一个 `Substring` | 只记区间，可见时才物化 |
| 视图布局块 | 每 512 字符一个 `TextLayout` | 每 8 192 字符一个（对象数降一个数量级） |
| 状态消息 | 连续发送每拍写一次状态源 | 文案没变不写（避免状态缓冲版本号每拍变） |

**没做的**：不强制 GC、不加"释放内存"按钮、不限制可编辑输入的撤销深度——这些要么是绕开 GC，要么改的是合理特性。

## 测量方法与基线

用无头端到端夹具（真实 `TextSender` → 承载 → `DataMonitor` → UI 帧）测 `GC.GetTotalAllocatedBytes()`，1 ms × 1 KB 连续发送、连接显示器：

| 场景 | 改前 | 改后 |
|---|---|---|
| 只发送（模块线程） | 约 40.5 MB/s | 约 5.1 MB/s |
| 只显示（UI 管线） | 约 27.1 MB/s | 约 23.7 MB/s |
| 发送 + 显示 | 约 77.5 MB/s | 约 29.7 MB/s |

gen0 次数随之从约 5.2/s 降到约 1.5/s（Debug、无头、60 Hz 帧节拍；绝对值随机器与负载变化，比较同一台机器的前后值才有意义）。

显示侧剩余的分配主要是**把新文本排成视觉行**（`TextLayout` 与字形位置），它与"1 秒 100 万字符、且要按控件宽度折行"这一事实同阶；再往下走需要"只排可见窗口"的虚拟化，那是另一项功能，不在本次范围。

## 边界（特性，不是缺陷）

- 每块显示缓冲的字符/行上限固定，满了丢最旧并只提示"缓冲已满"，不计数。
- 实例存活期间其显示缓冲一直保留（关窗口 ≠ 移除模块）；移除实例后由 GC 回收。
- 模块程序集加载在默认 ALC，**不卸载**；重复加入实例不会重复加载程序集。
- 只读文本面关闭撤销；可编辑输入保留 Avalonia 默认撤销（10 步）。

## 什么时候需要调 GC

只有在测量表明"分配速率已经合理、但 gen0 预算过小导致 GC 过频"时，才考虑显式放大 gen0 预算（`System.GC.Gen0Size`），并记录"内存↑、GC 次数↓"的权衡。**不要**用定时强制 GC 或 `Conserve` 把问题藏起来：前者制造不可预期的停顿，后者会把 GC 次数推得更高。
