# 文档体系

文档站按读者分层，每层只回答一类问题；同一事实只有一个家，其余位置只放链接。

## 六层归属

| 层 | 写什么 | 位置 |
|---|---|---|
| 开始使用 | 从零到第一条数据 | `docs/zh/start/` |
| 使用指南 | 每个可操作功能；每个模块一册 | `docs/zh/guides/` |
| 深入理解 | 机制、文件结构、可手工改的范围 | `docs/zh/concepts/` |
| 模块开发 | 外部作者：流程、声明面、接口参考、打包与排障 | `docs/zh/module-dev/` |
| 项目开发 | 仓库：结构、构建、版本、测试、文档规则 | `docs/zh/project/` |
| 关于 | 定位、许可、更新日志 | `docs/zh/about/` |

代码与仓库约束、开发工作流、状态与验收留在仓库的 `dev/`，不进站点；历史材料在 `dev/archive/`，不作现行依据。

## 页面类型

| 类型 | 结构 | 用于 |
|---|---|---|
| 层首页 | 读者 / 回答 / 不写 + 页面表（回答什么、状态） | 六层的 `index.md` |
| 教程 | 完成什么、前置、步骤、结果、下一步 | 开始使用 |
| 任务指南 | 适用场景、步骤、验证、相关 | 使用指南 |
| 模块册 | 界面、典型用法、状态与提示 | 使用指南/模块 |
| 解释 | 解决什么问题、机制、边界、相关 | 深入理解 |
| 开发 | 目标、步骤、约束、验证 | 模块开发 |
| 仓库 | 事实、命令与位置、相关 | 项目开发 |
| 骨架 | 读者 / 回答 / 不写 / 事实来源 | 尚未写的页面 |

模板即上表：按页面类型照该结构写，不另建模板文件。

## 写法

- 专业书面语，步骤用动词开头；不用口语、拟人化与感叹号。
- 一页回答一个问题；能一页说清就不拆，规格表与矩阵允许同页分段。
- 先写做什么、怎么做，再写为什么；机制解释放在深入理解层。
- 面向用户的页面不出现类名、方法名、内部状态名与代码路径。
- 版本号、模块清单与更新日志手写：仓库不生成文档正文，三者与源码保持一致靠人工同步。
- 不把界面文案写成规范：不写“某条提示应该是……”“某字段的格式必须是……”“状态行提示‘……’”，只写这条文本表示什么。具体措辞由文本表与开发者调整，文档不得把文案钉死。控件名称可以按当前界面引用；状态、错误、格式提示不抄原文。此条与“版本号、模块清单不手写”同级。
- 术语首次出现给一句定义，全站保持一致；定义集中在深入理解的术语页。
- 不写“以前是 X，现在是 Y”；历史留在版本库与更新日志里。

## 页面内容全部手写

正文、模块目录、更新日志与首页的版本提示都由人写，仓库里没有生成文档正文的脚本。这样文档只有一种工作方式：改 Markdown 就是改站点。

需要与源码同步的清单类事实，用**指向事实源**的方式维护：模块目录页的表格与 `src/Modules/Business/*/module.json` 和各模块的 `zh-Hans.json` 保持一致；新增模块时同时改代码、导航与表格三处。更新日志记录每个交付版本的用户可见改动，版本号从 `version.props` 抄写。

`docs/requirements.txt` 列出 mkdocs 与主题版本；`docs\build.ps1` 只调用 mkdocs 建站与结构检查，不注入内容。

## 结构检查

`docs\build.ps1 -Mode Check` 做严格构建与结构检查：

- 导航里的每个页面都存在；磁盘上的每个页面都登记在导航里。
- 目录只能是六层之一，每个目录都有 `index.md`。
- 中文站顶层导航固定为 7 项（首页 + 六层）。
- 英文站页面不得多于中文源页（未翻译只提示）。
- 构建产物存在首页与搜索索引。

检查只回答“页面在不在、有没有登记、产物有没有生成”，不判断措辞与内容质量。

## 新增页面

1. 在对应层目录新建页面，按上表该页面类型的结构填写读者、回答、不写与事实来源。
2. 在 `docs/mkdocs.yml` 的 `nav` 里登记。
3. 补正文，删掉用不上的骨架段落。
4. 运行 `docs\build.ps1 -Mode Check`，通过后提交。

英文页面放在 `docs/en/` 下相同路径，并在 `docs/mkdocs.en.yml` 中登记。
