# Skill：自上而下设计 + 人类专家协作式架构评审方法论

> 本文件是可复用方法论（非具体项目内容）。用于：从零设计可扩展平台/系统、Agent 与领域专家用户协同推进架构设计、评审驱动式设计会话。

---

## name / 用途

- **名称**：top-down-design-with-human-expert-review
- **一句话**：在"领域专家用户逐条评审拍板"的协作下，用"层序正确、支点先行、Gate 推迟、类比受控、逆例自检"的协议把系统从零设计到可进入实现，避免方向性返工。
- **何时使用**：① 从零设计可扩展/平台化系统；② 与"懂领域、不懂形式化建模"的人类专家逐条确认架构；③ 文档将作为后续开发验收唯一事实源的长周期设计。

---

## 0. 核心理念

1. **两类不确定性**：设计消除 A 类（"什么东西应该是什么"——语义/结构决策）；实现消除 B 类（"已确定的东西怎么实现"）。**进入实现的判据 = 剩余未知以 B 类为主，且残余 A 类已显式登记为活清单**（实现中暴露的新 A 类必须回写设计文档，不得由代码静默拍板）。
2. **整版原理图先于 layout**：所有域的结构决策冻结前不得进入技术选型/实现；允许"外围在接口定稿后并行"，禁止"边实现边补外设"引发结构性失配。
3. **推进单元是"层"而非"主题"**：主题（领域模型/接口/运行时…）是工作分区；真正的顺序约束在层（图景→概念→机制→结构→细节）。主题批内必须再按层序走，否则必然回溯。

---

## 1. 域内四步协议（任何主题域/裁决包）

```
① 图景描述（域"是什么"）
      ↓ 冻结
② 概念与支点裁决（对象全集/边界/所有权/保存语义等"梁"）
      ↓ 冻结
③ 机制/结构（支点之上的内部结构）
      ↓ 冻结
④ 细节 Gate（B 类：格式/编号/分类枚举/调度/线程…→登记推迟）
```

- 每步产出：裁决问题清单 → 用户逐条确认 → ADR 记录 → 回写主文档。
- **支点信号**：一批点状问题全都"答不上/悬空" = 缺少上层支点定义。立即停止点状裁决，先向上立支点。
- **层级定位检查**：每个待裁决问题先自问"这是哪层的问题？上层冻结了吗？"下层未冻结：先补上层或转 Gate。

---

## 2. 类比处理协议（与领域专家协作的关键）

专家用户常用类比表达核心思想（电路/工厂蓝图/仿真框架/mod…）。类比是**需求信号**，不是架构结论；直接形式化必然失真。

1. **记录**：完整记录类比原话与场景，不加工。
2. **映射表**：提出"类比元素 → 架构抽象"映射，**显式标注采纳/不采纳及边界**。
3. **用户校验**：请专家确认映射（"你的意思是 X 吗"），确认后才冻结为文档表述。

---

## 3. 守护规则

- **层级定位检查**（见 §1）。
- **转写校验门**：专家以自由文本给出的裁决/倾向，必须转写为**编号命题清单**请其"确认即冻结"，不得把倾向扩写为结论。
- **逆例自检**：拟冻结措辞先对照既有不变式/反模式清单/验收判据自检。
- **逐条裁决、全 ADR**：不打包默认、不代答；Accepted 需含背景/候选/放弃方案/影响；推翻已冻结必须 Superseded 文档化。
- **不预设程序行为**：顶层只定"应该是什么"；"怎么分类/怎么调度/怎么跑"若无顶层语义支撑即属实现属性 → Gate。

---

## 4. 反模式自查清单

1. 无图景先裁内部结构。
2. 主题批内层序颠倒（下层在上层未冻结时被裁决）。
3. 把 B 类当 A 类提问（涉及格式/编号/分类/调度 → 先判层）。
4. 直接形式化用户类比（必须走映射表 + 校验）。
5. 缺少逆例自检（新表述与既有原则冲突未被发现）。
6. 过早冻结递归/嵌套/机制规则。
7. 用"写代码验证设计"绕过结构冻结。
8. 文档治理机制超出收益（批/ADR/编号/徽标按需使用）。

---

## 5. 拟冻结前检查清单

- [ ] 该问题属于哪一层？上层是否已冻结？
- [ ] 是否 B 类/确定性设计？（是 → Gate）
- [ ] 用户类比是否已走"映射表 + 用户校验"？
- [ ] 自由文本裁决是否已命题化并经回执？
- [ ] 措辞对照不变式/反模式/判据自检通过？
- [ ] 与已冻结章节无重叠、无一物多主、无循环依赖？
- [ ] 若产生新对象/新原则：是否真属本层？

---

## 6. 与领域专家用户协作的纪律

- 专家心智模型（类比、蓝图、直觉）是最重要的需求输入，也最容易被 Agent 自作主张"补全"——每次补全都先命题化再请求确认。
- 专家说"感觉缺了点什么/无法定夺"= 强信号：停止当前裁决，先做元分析（通常是缺上层支点或层序颠倒）。
- 专家直接否决时，先确认理解再修改，不以"方案 B 其实类似"绕回。
- 评审节奏由专家控制：宁慢勿错。

---

## 7. 实战案例（供对照自检）

| 案例 | 教训 | 准则 |
|---|---|---|
| 写出"框架提供数据收发通道"（暗示 Core 中转数据，违背"Core 不做中央交换机"） | 拟冻结措辞必须对照不变式/反模式/判据自检 | 逆例自检 |
| 把"电路类比"读成运行语义（通电/保险丝）；把"组合件"列为模块定义来源；预设"活动方式二分" | 专家类比与倾向必须"命题化 → 确认即冻结"，不得扩写 | 转写校验门 |
| 在"模块如何被框架运行"未描述时先裁模块内部结构（Definition 组成/ID 格式） | 先立支点再裁点状；多点悬空 = 缺上层支点 | 层级定位检查 / 支点信号 |
| 把抽象概念（工作区）实体化为容器/文档/多开 | 抽象概念不得被机制化表述污染 | 抽象优先原则 |
| 想以"最小系统即 layout"提前切片验证 | 整版原理图先于实现 | 推进阈值 |
| 文档中长期并存"被取代的旧表述"与"生效结论" | 失效信息必须与生效事实分离（搬家而非删除） | 文档治理 |
| 交叉审查发现 10 项高危，全部是"历史结论未随新 ADR 收敛" | 每次裁决后立即回写并清理全部受影响表述 | 回写与收敛 |

**经验总结**：A 类问题必须在动手实现前清零或显式登记；每次裁决都要问"它替代了什么、哪些表述必须同步改"；专家的直觉是需求信号，须经命题化校验后再形式化。
