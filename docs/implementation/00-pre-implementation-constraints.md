# 实现前置约束：三条验证边界纪律（00）

> 状态：**现行**
> 本文件只保留**用户确立的三条验证边界纪律 C1–C3**（"实现前必须守住的边界"）。它们是长期纪律，被 `docs/architecture/09-test-and-gate.md` 以"**纪律 C1 / C2 / C3**"回指（§6 测试与验证纪律、§10.2 推进方式）。

## C1｜验证方式 = 模块验证 + 组合验证

| 项 | 内容 |
|---|---|
| **是什么** | 框架的正确性由**模块级验证**（模块契约自检，T6）与**组合级验证**（参考组合 = 模块/桩模块搭出的真实链路，T1）证明。**不用"MCU 式单元测试经验"套用框架本身**。 |
| **为什么** | 框架的风险在**接缝**（登记 / 绑定 / 投递 / 重建 / 持久化），单函数级用例覆盖不到；参考组合是 AC-1~AC-6 的**实证载体**（**现行载体 = 四个正式模块 + 判据项目内测试桩**，见 `docs/architecture/09-test-and-gate.md` §2）。 |
| **违反的后果** | 用例全绿但机制不通；"设计这么定、实现做反了"只能靠用户手工发现——问题被推迟到验收现场。 |
| **怎么自查** | 改了 Core 机制 ⇒ 有没有一条**参考组合级**用例（数据源 → 变换 → 记录/判据汇）？只加了单函数用例 = **未验证**。 |
| **现行落点** | `docs/architecture/09-test-and-gate.md` §1（AC-1~AC-6）· §2（判据落地与现行判据载体表）· §3（T1/T6 与承载项目）。 |

## C2｜最小可验证形态才可开始验证

| 项 | 内容 |
|---|---|
| **是什么** | 需要"**框架完全就绪 + 最小可验证模块完成搭建**"才具备验证条件；**不做"半成品早期验证"**。 |
| **为什么** | 半成品上的验证结论不可用（形态还会变），却会消耗大量往返；且会把"还没做"误读成"做错了"。 |
| **违反的后果** | 验证结论随形态变动而作废；验收判据反复重写；用户看到的"问题"其实只是未完成。 |
| **怎么自查** | 准备跑验证前先问：框架机制是否已就绪？最小可验证模块（**现行 = 四个正式模块 + 判据项目内测试桩**）是否已搭起？两者缺一 ⇒ **先搭，不验**。 |
| **现行落点** | `docs/architecture/09-test-and-gate.md` §10.2（推进方式 = 垂直切片，"符合纪律 C2"）· §10.3 M1 步骤的交付边界。 |

## C3｜禁止把简易原型并入工程

| 项 | 内容 |
|---|---|
| **是什么** | 不把原型代码并入工程（避免技术债）；如确需原型，**必须独立搭建**（独立目录 / 独立方案，**不参与主构建、不被工程引用**）。 |
| **为什么** | 原型是"为验证一个想法而写"，没有边界与契约约束；一旦并入，它就变成必须维护的第二套实现。 |
| **违反的后果** | 工程里长期存在两套行为（原型与实现），改动要改两处、观感各不相同——典型技术债。 |
| **怎么自查** | 这段代码是否参与 `build.ps1` 主构建、是否被产品项目引用？是 ⇒ 它就不是原型，必须按正式标准写。 |
| **现行落点** | `docs/architecture/09-test-and-gate.md` §6（"**不做一次性原型**（纪律 C3）：测试代码属常备基础设施，不是原型"）· §9 Gate C（UX 原型时点在 M1 之后、M2 之前，**独立进行**）。 |
