## A. 图景：这个平台里的"模块"是什么（先对齐心智，再裁结构）

### A.1 **四层视角**：同一个模块，四层不同的东西（**本节的层号在全文通用**）

> 用户 2026-09：**"一个功能究竟该成为什么，这个问题不能从代码层面去回答"** —— "功能""角色"都建立在**用户感知层**上。所以第一步必须把**视角**分开。

| 层 | 名字 | 单位 / 数量 | 谁拥有 | 判据 | 框架参与判定？ |
|---|---|---|---|---|---|
| **①** | **功能层**（用户感知） | **模块** = **1 个功能角色** | 用户 / 需求 | 用户会不会用**一个名字**指代它 | ❌ 只作目录展示（`DisplayName` / `Description` / `Tags`），**框架不分类** |
| **②** | **角色层**（模块内部结构；叠加层画方块 ⇒ 用户仍看得见） | **数据角色**（可多个） | **模块自己声明**（框架**不派生、不发明**） | **一种数据类型 = 一个角色**；**两侧同型** | ❌ 只呈现 |
| **③** | **接口层**（对外数据端点） | **口 + 数据类型** | 模块声明；框架机械校验 | 需要被连 / 被观测的数据端点 | ✅ 建网 / 兼容 / 停流 / 投递 / 计量 |
| **④** | **实现层**（代码） | 类 / 文件 / 算法 / 控件 / 串口 / TCP | 实现方 | **无判据、不分类**（登记即可） | ❌ |

**一句话记法**：**层①给用户看名字 · 层②给用户看结构 · 层③给框架用 · 层④谁也不看**（只决定你写得多累）。

- **层①与层②都在用户感知层**（主文档 §4.10 ③「角色分层」）；**层③是框架唯一的判定输入**；**层④不参与任何一层**。
- **术语对齐（2026-09 已裁）**：层① = 主文档已有的「**功能角色**」；层② = 「**数据角色**」（SDK 载体 `RoleDeclaration`，代码里就叫 Role）；「**模块族**」= 功能角色的**分类维度**（开发约定，**非框架概念**）。详见 §B.2。

**另外两个视角**（同一件事的另外两种说法，用于对齐心智）：

| 视角 | "模块"是什么 | 判据 |
|---|---|---|
| **平台** | **一个可独立发布、独立版本、独立装卸的功能单元**；框架对它的全部了解只来自**声明** | "**只靠声明**能不能知道它要什么" |
| **开发者** | **一个只引 `Sdk` 的类库项目 + 一份 `module.json` + 一个实现 `IModule` 的类** | 编译期不依赖框架内部、不依赖别的模块 |

**一句话**：模块是**声明驱动的功能单元** —— 它对框架说清"我有哪些口、什么类型、哪些配置、想画什么"，其余（承载线程、投递、建网、渲染、持久化）**全部由框架做**。

### A.2 已经冻结的边界（**不用再裁**，只列指针）

| 边界 | 内容 | 指针 |
|---|---|---|
| 基数 | **1 包 = 1 Definition = 1 实现**（不允许一包多模块） | `02`「模块包与发现」 |
| 引用面 | 模块**只引 `Sdk`**；不引 UI 框架、不引别的模块、不引框架内部 | `../architecture/01-layering-and-projects.md` §2（AR-1/AR-2/AR-9） |
| 声明面 | 特性六项 + `IModuleDeclaration`（类型 / 口 / 角色 / 顺序 / 视图）+ 配置类型（`[ConfigurationField]`） | `02` |
| 生命周期 | 六个钩子（`Registered → Active ⇄ Disabled → Removed`） | `02`「实现基元」 |
| 线程 | **模块不自建线程 / 定时器**；需要自发活动就实现 `IActivitySource`，线程由框架给 | `02`「线程与投递」 |
| 视图 | **模块不提供 View 类型**；只能从**预置元素目录**选元素 + 绑数据源；框架照声明渲染 | `02`「视图」 |
| 数据 | 定长契约、形状即契约、兼容 = 形状完全一致；**单位 / 时序语义归模块** | `03` |
| 连线 | **建网由用户在 UI 声明、由 L4 执行；模块不参与、不可见** | `02`「框架服务面」 |
| 交付 | 改代码 → `build`（包自动归拢到 `artifacts\modules\`）→ **重启应用**；**无热重载** | `02`「开发期行为」 |

### A.3 从声明面直接读出的**硬推论**（后文多处用到）

> **模块不得假定"一定有人连着它"。**
> 框架既不告诉模块"谁连着我"，也不告诉它"现在有没有上游"。
> ⇒ 每个模块都必须能在**未连 / 停流 / 被禁用**状态下正常存活：不空转、不报错、不刷 Issue、不假定数据一定会来。

## B. 支点裁决

> 本节是本文的核心。**B1 与 B2 已由用户 2026-09 裁定**；仍未决的项在 §I 汇总，未裁决前不进入实现（`.dsh/skills/human-ai-collaborative-design-review`（仓库根） §2 域内四步协议）。

### B.1 模块粒度：**分三层回答**（**已裁 · 用户 2026-09**）

> 用户判据（原话）：**"一个功能究竟该成为什么，这个问题不能从代码层面去回答"** —— "功能""角色"都建立在**用户感知层**上。
> ⇒ **B1 不是一个问题，是三个问题，每层一个**（层号见 §A.1）。本文上一版的"四问"把**层①与层③混在一起**，已按此改写。

#### B.1-a｜层①：一个"功能"该成为一个独立模块吗？

判据分三档：**主判据（感知）· 硬约束（必须合）· 拆分倾向 + 一条否证**。

| 档 | 判据 | 说明 / 例子 |
|---|---|---|
| **主判据（感知）** | **用户会不会用同一个名字指代这些能力？** | 会 ⇒ 一个模块（"串口助手"能收能发 = **一个**模块）。**这是唯一的主判据** —— 因为层①本来就是用户感知的 |
| **硬约束（必须合）** | **共享独占资源或不可分割的状态**：串口句柄 / TCP 会话 / 文件句柄 / 同一份采样缓存 | 框架**禁止模块间共享**（AR-2）⇒ **只能同一个模块**。这是**框架限制，不是设计偏好** |
| **拆分倾向**（任一条成立 ⇒ 考虑拆，但**不必然拆**） | ① 用户可能**只要其中一块** ② 两块需要**各自的配置界面** ③ 两块可能接到**不同的上游 / 下游** ④ 需要**独立版本或独立复用** | 四条都只给"倾向"，不是判据 |
| **否证**（拆错了的样子） | 拆出来的模块**只有一条固定连线、零配置、只在一种场景用** | ⇒ 那不该是模块，应是同模块内的**另一个角色** |

#### B.1-b｜层②：一个模块该有几个角色？—— 由**数据类型**机械决定

**硬约束①（已被 ADR-0052 Q2 冻结）**：**一个角色只有一种数据类型**（`RoleDeclaration` 只有一个 `Type`）。
⇒ **推论（你的直觉的正式化）**：

> **一个模块里有几种数据类型在流动，就至少有几种角色。**

**硬约束②（B2‴ · 2026-09 补充裁定 α）**：**一个角色的输入口与输出口承载同一种数据类型**（= 该角色的 `Type`）。
⇒ **类型转换 = 两个数据角色**（"收 A" + "发 B"）+ `DeclareFlow` 表达先后；叠加层上表现为**两个方块**、各按自己的类型色。
⇒ **推论**：同一路输入要喂给两个角色 ⇒ **需要两个接收口**，由上游一个发送口按 **1→N 广播**（主文档 §6.3 ①）。

**反过来不成立**：同一种数据类型也可能有多个角色，此时用"**是不是一件事**"判：

| 情形 | 结论 | 依据 |
|---|---|---|
| **一件事**（"两路合成一路"） | **1 个角色**（2 入 1 出） | ADR-0052 §8 的 `Fuser` 声明即此写法 |
| **两件事**（"先滤波再限幅"） | **2 个角色** + `DeclareFlow` | `02`「声明载体」 |

- SDK 自检已为此给了 **`Advisories`**（角色 >2 口给一条**可忽略**的建议，不进 `Problems`）。
- **α 的可执行检查已实施**（2026-09）：① **SDK 自检** —— `ModuleContract.CheckRoles` ⇒ 进 **`Problems`**（空 = 合法）；② **加载期** —— `ModuleInstanceFactory.BuildRoles` ⇒ **Issue + 忽略该条**（与其余结构非法同处置）。**口未声明 `Type`（旧模块形态）⇒ 跳过不报**。约束全文与正反写法见 `02`「角色两侧同型（α）」。

#### B.1-c｜层④：实现层**不设判据、不分类**

要什么能力就写什么代码（怎么解析数据、怎么显示、提供哪些控件、怎么连接串口、怎么做 TCP）—— 这一层**没有"该成为什么"的问题**。
**唯一纪律**：框架**给不了**的能力 ⇒ **停止实现**，走契约扩展通道（`05` §2），**不得自造第二套机制**。

#### B.1-d｜"从功能解析角色" 与 "角色由模块自己声明" **不矛盾**

两个**时点**的事，别混：

| 时点 | 谁做 | 做什么 |
|---|---|---|
| **设计期** | **人 / AI**（**不是框架**） | 从**层①的功能**往下**推导**层②的角色 —— 这就是"根据功能解析角色" |
| **声明期** | **模块自己**（`DeclareRole`） | 把推导结果**声明**出来；框架**推不出来**（"这块把两路合成一路"是**设计信息**，不是机械组合） |
| **运行期** | **框架** | **只校验结构、只投影**；**不派生、不发明角色**（ADR-0052 红线） |

⇒ **"角色必须模块自己声明"，恰恰是因为"从功能解析角色"只能由设计者做。** 这两句话是同一件事的两面。

### B.2 层①的名字 = 「功能角色」；「模块族」= 它的分类维度（**已裁**；分类维度【待评估】）

> **术语纪律**：本平台已有冻结术语 **「角色」= 模块内的功能分块**（`RoleDeclaration`）与主文档 §4.10 ③ 的「**功能角色 / 数据角色**」两层。**不再引入新的同层术语**（`.dsh/skills/…-design-review`（仓库根） §4 单一事实源）。

**裁决（已裁 · 用户 2026-09）**：

| # | 项 | 结论 |
|---|---|---|
| ① | **层①的名字** | **用主文档已有的「功能角色」** —— **不动主文档**，零新增术语 |
| ② | **「模块族」的定位** | **降为"功能角色的一个分类维度"**（**开发约定用语，不是框架概念**）—— 用于选模板 / 写模块页 / 检索 |
| ③ | **粒度关系** | 功能角色是**实例级**（"这个模块是什么"）；模块族是**类级**（"它属于哪一类"） |

> **⚠ 更正登记（2026-09 · 本文上一版的疏漏）**：主文档 **§4.10 ③**（`../../上位机架构设计.md`）**早已有一层"角色分层"**：**功能角色**（这个模块是什么/干什么 → 模块清单 / 模块自身 UI / 帮助）· **数据角色**（怎么处理数据、几种、从哪到哪 → 叠加层与拓扑）。
> 本文上一版提出「模块族」时**没有发现这一层已存在**，另造了一个同层的词 —— 已按上面①收敛。

> **约束（已冻结，不受命名影响）**：主文档 §4.3 —— "功能/结构"仅作**用户侧角色描述**，**不构成框架机制**，**框架不维护业务分类**。
> ⇒ 无论叫什么，都**不进框架、不进 `module.json` 的框架字段**；只出现在**模块页与开发约定**里。载体 = `DisplayName` / `Description` / `Tags`（仅供检索）。

**分类维度（【待评估】· 用户保留意见）**：用户 2026-09：

> "当前分类有些过细了，暂时不这样分类，且这种分类命名方式**与实际代码实现的分类冲突**，需要保留意见；可以具体分类需要评估。"

因此**不冻结任何族表**，只登记两个候选维度供评估；**评估时点 = 第一批基础模块开发完成之后**（用户：先做几个基础可验证模块，完成后再回来修框架与补标准）。

#### 候选维度 A：按**口形态**（本文原提议，**已降为候选**）

按 (入数, 出数) 分七族：源 0/N · 汇 N/0 · 变换 1/1 · 融合 N/1 · 分流 1/N · 桥接 N/M · 面板 0/0。
**已知问题**：① 对多数模块**过细**（"分流"与"桥接"、"汇"与"面板"在实践中界限模糊）；② **与代码已有的分类并列而非派生** —— 代码里模块内的功能分块已由 `RoleDeclaration` 的三态表达（见候选 B），另立一套 (入,出) 说法等于**同一件事两处定义**（`.dsh/skills/…-design-review`（仓库根） §4 反模式）。

#### 候选维度 B：**从角色派生**（**与代码一致，倾向此路**）

`RoleDeclaration` 已给出模块内功能分块的官方三态（`Sdk/Contracts/RoleDeclaration.cs`）：`Input`（纯汇分块）· `Output`（纯源分块）· `Both`（处理分块）。**分类由"该模块声明了哪些角色"派生**，不另立一套术语：

| 模块角色构成 | 归类 | 语义 |
|---|---|---|
| 只有 `Input` 角色 | **汇** | 消费数据（显示 / 记录 / 存盘） |
| 只有 `Output` 角色 | **源** | 产生数据（采集 / 接收 / 回放 / 仿真） |
| 只有 `Both` 角色（1 入 1 出，**两侧同型**） | **处理** | 滤波 / 限幅 / 换算（**不做类型转换**） |
| N 入 1 出（同类型） | **融合** | 多源合并 |
| 1 入 N 出（同类型） | **分流** | 条件分发 / 协议路由 |
| **同时有 `Input` 与 `Output` 角色**（**α 后的转换类**） | **转换** | 收 A / 发 B（**两个角色**，见 B.1-b） |
| 有数据口 + 独占外部资源 | **桥接** | 内部数据 ↔ 外部世界（串口 / TCP / UDP / 文件） |
| 无任何数据口（0 口 ⇒ 0 角色） | **面板 / 工具** | 只有人机面（命令 / 输入），如"HEX ↔ 字符串转换器" |

**优点**：① 唯一事实源 —— 归类从**已声明的角色**推出，不新增人工归类；② 与叠加层画法（角色方块，ADR-0052）**同一份数据**；③ 可由声明**机械判定**，能写成自检。
**待评估点**：**"转换"与"处理"的界限**（α 之后"1 入 1 出同型 = 处理"与"收 A/发 B = 转换"是两件事，边界清楚，但命名待定）；"汇 vs 面板"、"处理 vs 桥接"是否需要在名字前加限定词；以及**是否需要"族"这一层抽象**（也可能"角色构成"本身已足够描述，族只是检索用的 `Tags`）。

#### 三条正交轴（同样【待评估】，不是族）

| 轴 | 取值 | 载体 |
|---|---|---|
| **人机面** | 无 / 命令 / 输入 | `ViewCommand` · `TextInput` · `ToggleSlider` |
| **外部资源** | 无 / 串口 / 网络 / 文件 / 进程 | `ModuleCapability` |
| **活动形态** | **被动**（只收不产，`SetReceiveHandler`）/ **主动**（`IActivitySource`） | `Sdk/Lifecycle/IModule.cs` |

> **【待评估 B2】** ① 分类维度采纳候选 B（从角色派生）还是其他？② 是否需要"族"这一层，还是直接用**角色构成 + 三条正交轴**描述即可？③ **评估时点 = 第一批基础模块完成之后**。

### B.3 一个模块可以有几个数据角色？

**裁决（已裁 · 用户 2026-09，随 B1 一并接受）**：**可以有多个，但必须显式**。多角色时模块页必须写明"**为什么这些块必须住在一个包里**"（用 B.1-a 的主判据回答：用户用**一个名字**指代它们；或用硬约束回答：**共享同一个独占资源或同一份状态**）。
**反例警戒**：把"顺便还能干点别的"塞进一个包 ⇒ 应拆。

### B.4 模块的"可选能力面"【**已裁 · 用户 2026-09**】

| 面 | 声明方式 | 模块作者的义务 |
|---|---|---|
| **能力**（资源） | `[ModuleDefinition(Capabilities = …)]` | 声明了就要真的**只**碰这类资源；**加载时透明提示、不拦截** ⇒ **靠自觉** |
| **依赖** | `[ModuleDefinition(DependsOn = …)]` | 缺失 ⇒ Issue，**不静默降级**；依赖是**标识三元组**，不是"引用程序集" |
| **框架兼容** | `FrameworkCompatibility` | 区间外**拒绝注册** |
| **参与数据活动** | `ParticipatesInDataFlow` | 无数据活动的模块可标 `false` |

**B4 裁决（选项 a）**：**"凡碰外部资源必须声明 `Capabilities`" = 模块页必填字段 + 本文件 §F.2 的提交检查项**；
**框架不做校验、不做启发式扫描** —— 依据：`Sdk/ModuleCapability.cs` 的注释已写明"该枚举**只用于告知用户**模块会触碰什么资源；v1 **不做权限拦截、不做沙箱**"，而启发式（扫代码里有没有 `SerialPort`/`Tcp`/`File` 关键字）**成本高、必然误报**（`02`「安全一致性」的透明模型）。
⇒ 落地形式：**模块页 §「能力 / 依赖 / 活动形态」一行写清**；提交前逐条过 §F.2 检查表。

## C. 组织结构

### C.1 目录与文件（建议形态）

```text
src/Modules/Business/<Name>/                     ← 一个模块 = 一个目录 = 一个包
├─ HYWDebugAssistant.Modules.<Name>.csproj       ← 只引 Sdk；显式声明 <ModulePackageName>
├─ module.json                                   ← 清单（id / entryAssembly / entryType / 依赖 / 资源）
├─ <Name>Module.cs                               ← 入口：特性 + IModule(+IActivitySource) + 声明 + 钩子 + 接线
├─ <Name>Config.cs                               ← 配置类型（公有可读写属性 + [ConfigurationField]）
├─ <Name>Types.cs                                ← 数据类型声明（标识 / 版本 / 形状 / 解码器）  [按需]
├─ <Name>Codec.cs                                ← 编解码 / 成帧 / 校验（纯函数，可单测）        [按需]
└─ <Name>State.cs                                ← 运行期状态与内部结构                        [按需]
tests/HYWDebugAssistant.Modules.Tests/           ← 契约自检 + 模块测试                        【待裁 C3】
docs/modules/<模块标识>.md                        ← 模块页（一模块一页；模板 `../modules/_模板.md`）
```

- **`ModulePackageName` 必须显式写**：默认取项目名最后一个点段（`src/Modules/Directory.Build.targets`），容易得到 `Scope` 这种与用户无关的名字；**包目录名 = 用户看到的名字**。
- 包产出与发现规则不在本文重复（`02`「模块包与发现」）。

### C.2 模块主类的**固定四段**（结构约定，比行数更重要）

| 段 | 内容 | **不应出现** |
|---|---|---|
| **① 标识与常量** | `[ModuleDefinition]` 特性；口名 / 数据源名 / 命令名的 `const` | 业务数值（入配置） |
| **② 声明块** | `OnRegistered`：`DeclareDataType` → `DeclarePort` → `DeclareRole`（→ `DeclareFlow`）→ `DeclareView` → `SetReceiveHandler` | 业务计算、IO |
| **③ 钩子块** | `OnActivated` / `OnDisabled` / `OnEnabled` / `OnConfigurationChanged` / `OnRemoved` | 绕开框架的替代实现 |
| **④ 接线与业务** | 接收处理 / 活动体 / 收件箱消费 → **调辅助类** | 超过 ~80 行的算法与协议细节（搬 `Codec.cs`） |

**C.2′ 视图声明**按控件分块**（**2026-09 用户裁定**，四个基础模块已按此重排）**：

用户原话："**不行就只在代码中将默认属性按控件分块呈现，便于符合直觉的修改，不用到处翻，最轻量完全不动任何逻辑，只动文本结构。**"

| 规则 | 说明 |
|---|---|
| **一个控件一段** | `DeclareView` 之前用局部变量逐控件声明：`var xxx = new ViewElement(...)`，每段自带它的**默认属性**（`InputKind`/`Alignment`/`Multiline`/`FileMode`…）；段与段之间空一行 |
| **紧邻它的数据源** | 该控件的 `ViewDataSource`（含 `unit`）写在**同一段**里 —— 改"单位/类型"不必跳到 `dataSources:` 列表里找 |
| **段序 = 界面自上而下** | 用户看到什么顺序，代码就什么顺序；对称结构（如转换器两组）按组重复同一形状 |
| **汇总处只做汇总** | 最后 `DeclareView(new ViewDeclaration([控件1, 控件2, …], dataSources: [源1, 源2, …], …) { PreferredWidth/Height })` **只列名字**，不再写内联的控件构造 |
| **不许改变行为** | 这是**纯文本结构**重排：控件集合、源集合、顺序、属性值都必须**逐一对应**（`Declaration` 的公开面自检与模块测试即是回归网） |

| 对象 | 规则 |
|---|---|
| 模块 ID | `hyw/<kebab-name>/<semver>`（`02`「标识：结构化三元组」） |
| 包名 / 目录名 | 同上 `<kebab-name>`（**用户可见**） |
| 项目名 | `HYWDebugAssistant.Modules.<Name>`（PascalCase） |

## D. 大小约定【**已裁 · 用户 2026-09：全采纳 §D.1 数值**】

### D.1 现行数值（口径：含 XML 注释）

| 项 | 建议值 | 校准依据（实测） |

| **模块主类行数** | 目标 **≤ 300** / 上限 **450** | 现行四个基础模块：`TextSender` **405** · `HexSender` · `DataMonitor` · `HexStringConverter`（另有判据项目内的测试桩 `FusionStub`/`RateSourceStub`/`JudgementSinkStub`）。**历史对照**（已删除的 6 个参考模块）：**255–428 行** —— `DataGenerator` 255 · `Monitor` 327 · `Asserter` 330 · `ManualSender` 351 · `Recorder` 391 · `Fuser` 428（`Fuser` = 2 入 1 出 + 三种合并策略，属"确实复杂"的例子，已贴近上限） |

| 声明的数据类型 | ≤ 5 | — |
| 角色数 | ≤ 4 | 超过 ⇒ 模块可能在干两件事 |
| 配置字段 | ≤ 20（**一屏能配完**） | 配置表单由框架按 Schema 自动生成，字段多了没人配 |
| 视图元素 | **不设数量上限**（2026-09 用户裁定："**12 个太少了，建议不设上限（或是性能极限上限），无意义的约束不符合逻辑**"）；只留**软指引**「一窗能看完」 | 默认窗口 320×220；现行四个模块的声明值见 `02` |
| 视图数据源 | **不设数量上限**（同上裁定；数据源多了只影响订阅缓冲数量，属性能问题，不是合法性约束） | — |

### D.2 超限的正确反应（**不是"写着就行"**）

1. **先问 B.1-a 判据** —— 多数超限意味着"这里面住了两个模块"；
2. 不是模块边界问题 ⇒ **抽辅助类 / 抽文件**（算法、协议、状态各自成文件）；
3. 确实都合理 ⇒ 在模块页「已知限制」登记**为什么**，并作为下一次复盘的输入。

### D.3 主类里**不该出现**的东西（硬清单）

- `new Thread` / `System.Timers.Timer` / `Task.Run` 起常驻循环（**框架的线程纪律**，`02`）
- 自己重造框架该管的事：自建队列 / 自建调度 / 自己解析包类型标签
- 直接引用 UI 类型，或 `Core` / `Core.Api` / `Hosting` / `DataPlane` / `Infrastructure`
- 引用**另一个模块的实现**（只能通过**数据类型标识**复用契约，`03` §6）
- 静态可变状态（除常量与不可变对象）
- 绕过 `IModuleContext` 的日志 / 上报（`Console.WriteLine`、直接引日志库）
- 热路径上的 LINQ / 装箱 / 每单元 `new` / 字符串插值（`01` §3）

### E.1 阶段 0 之前必须先做的一件事：**契约扩展预判**

写第一行代码前，逐项对照**现有 SDK 面**问："这件事框架让我做吗？"

| 想问框架要 | 判定 | 动作 |
|---|---|---|
| 线程 / 定时 / 调度 | ❌ 框架独占 | 用 `IActivitySource` |
| 主动"等数据"（不占核的微秒级唤醒） | ❌ **尚无**（`WaitForData` 属后续扩展项） | 改用**被动接收**（`02`「接收模式」） |
| 自定义 UI 元素 | ❌ 目录封死 | 等框架升级，或**换一个能被渲染的元素**（见 H.1） |
| 读写配置 / 发数据 / 收数据 / 上报 | ✅ 有 | 直接用 |
| 串口 / 网络 / 文件 | ✅ 语言层可做，**但依赖与"谁占线程"要守规矩**（H.2 / E.2） | 声明 `Capabilities` + 在**活动体内同步 IO** |

**需要框架没有的能力 ⇒ 停止实现，走 `05` §2 契约扩展通道**（登记请求 → 用户裁决 → 只增不改 → 重编全部模块 + T3）。**禁止在模块里偷偷绕过去。**

### E.2 外部 IO 的**唯一推荐写法**（本文新增）

模块**不能自建线程**，而串口 / 网络的"数据到达事件"发生在**别人的线程**上。因此：

```text
✅ 唯一推荐：把外部 IO 收进活动体，用「同步阻塞 + 短超时」自己驱动
   void RunActivity(IModuleContext ctx) {
       while (!ctx.StopSignal.IsStopRequested) {
           从设备读一帧（带超时；超时返回 0 字节）;
           有帧 ⇒ 解码 ⇒ ctx.Ports.TrySend(口名, payload);
       }
   }

❌ 禁止：在 DataReceived / 异步 IO 回调里直接改模块状态或投递
   （跨线程 + 绕过框架投递语义 + 停止协议失效）
```

**代价与取舍**（写进模块页）：活动间隔**直接决定命令响应延迟**。现行 `TextSender` / `HexSender` / `DataMonitor` 用 **20 ms** 周期轮询收件箱，而 Windows 定时器分辨率约 **15.6 ms** ⇒ 响应粒度约等于该值。**"点一下发一条"够用；高频控制不适用。**

> **【已裁 E · 用户 2026-09：选项 a = 强制】** E.2 是**强制写法** —— 违反必须在违规处写 `// ARCH-EXCEPTION: <原因> · <复查条件>` **并**登记到 `../decisions.md` §3（与"模块不得自建线程"同一强度）。
> 为什么强制：模块**不能自建线程**（ADR-0013 / ADR-0029），而在异步 IO 回调里改模块状态会**同时**破坏三件事 —— 跨线程访问模块内部状态、绕过框架投递语义（计数/丢弃/顺序全部失真）、停止协议失效（活动体不知道要退出）。

### E.3 每阶段共同的三条纪律（不重复，只指）

1. **验证层按需选**：`09` §5 选择表 + `DEVELOPMENT.md` §1；**模块轨不跑 T3**，一批模块做完再跑一次（`05` §5）。
2. **提交纪律**：一个模块 = 一次提交；提交消息写**跑了哪一层**（T0/T1/T2/T3）；**框架轨改动不与模块轨混在一个提交**（`05` §5）。
3. **文档与代码同一次改动**：模块页 / `modules/README.md` / `roadmap.md`（`05` §4）。
