## 3. 实施与验证

### 3.1 实施纪律（本文件保留的部分）

1. **分层约束优先于便利**：不得为了让代码跑通而新增反向依赖 —— `01-layering-and-projects` §2 的依赖链是**穷举的**；
2. **参数先入设置模型再使用**：框架行为的可调参数 → `08-application-settings` §2 的字段 + 默认值，**不在代码里写魔法数字**；
3. **热路径代码先想分配**：数据面路径（产生 / 传递 / 解析 / 缓冲 / 绑定）按 `implementation/01` §3 写，改完给出分配数据；
4. **模块相关改动**：先看 `02-module-sdk` —— 模块作者只引 `Sdk`，不得依赖 UI 框架、不得引用其他模块；
5. **UI 相关改动**：模块视图只能由**声明**表达（元素目录见 `02-module-sdk`「视图」），模块不提供 View；UI 一律经 `Core.Api` 读写；观感取值见 `07-overlay-and-visual-baseline`「取值纪律」；
6. **一次改动一个主题**：重构与功能不混在同一提交；
7. **提交与分支**：单人直提 `main`（开关 S4）、Conventional Commits、构建产物不入库 → **见 `DEVELOPMENT.md` §6**。

## 5. 质量门禁

### 5.1 通过条件（必须全部满足）

1. `build.ps1` 全绿：**0 error、0 warning**（`TreatWarningsAsErrors=true`；局部 `NoWarn` 须注明原因）；
2. **AR-0~AR-16 全绿**（依赖类走程序集元数据 + 源码类走源码扫描；**目标程序集缺失即失败**，禁止"无对象则跳过"）—— 规则集正文见 `09-test-and-gate` §4；
3. 依赖许可 ∈ {MIT, Apache-2.0, BSD}，**含传递依赖**（许可审计门禁，见 `10-delivery-and-ops` §3）；
4. 热路径改动**给出分配数据**（`GC.GetAllocatedBytesForCurrentThread()` 或基准）；
5. 机制改动有**组合级验证**（参考组合：四个正式模块 + 判据项目内测试桩，见 `09-test-and-gate` §2）；
6. 关键约束可映射到**可执行检查**（检索 / 构建 / 测试 / 架构规则），而不是只写在文档里；
7. 文档与代码**同次同步**（见 §4）。

### 5.2 拒收条件（出现即打回）

1. 同一结构事实在多个文档并行维护（双份漂移）；
2. 为兼容旧结构新增"跳转壳"文档或空壳层；
3. 新增反向依赖，或绕过 AR 规则的"临时通道"；
4. 关键路径出现无收益的重复拷贝 / 转换 / 绕路中转（违背"数据直通"）；
5. 引入降低可读性的冗余中间抽象（"为了模式而模式"）；
6. 静默吞异常、静默降级、静默丢数据（必须转为 Issue 或诊断计数）；
7. 未登记的架构例外（`// ARCH-EXCEPTION` 写了但未进 `docs/decisions.md` §3）。

## 6. 例外申报与登记纪律

- **申报格式**（写在违规处的代码注释）：`// ARCH-EXCEPTION: <原因> · <复查条件>`；
- **登记处唯一**：`docs/decisions.md` **§3（架构例外登记，追加式）**；代码注释只是索引，**不构成登记**；
- **缺登记 = 门禁失败**；禁止静默绕过；禁止为了让门禁变绿而放宽规则、删规则或改白名单 —— 要么换依赖 / 改代码，要么走登记；
- 每条登记须含：日期 · 约束编号 · 位置 · 原因 · 复查条件 · 处置人 · 状态；
- **复查**：每个里程碑收尾复查一次；过期例外须**关闭或续期**（状态改「已关闭」并注明日期，**不删行**）；
- 架构测试对**已登记的例外按显式白名单放行** —— 放行靠登记，不靠改测试。

## 7. 交付与报告纪律

1. **说清跑了哪一层**：报告必须区分 T0 / T1 / T2 / T3 与手工验证，**不得把 T0/T1 的通过说成"全量通过"**（`DEVELOPMENT.md` §1 纪律 4）；
2. **给可复现步骤**：交付 / 回写时给出别人能照着重跑的命令与预期输出（T3 与手工验收尤其如此）；
3. **归因只报证据**：只写"看到什么 + 原始输出 / 日志 / 截图"；确需推测必须标明是推测，并给出验证它的下一步；
4. **失败要给最小复现**：报失败时给复现步骤 + 原始报错文本，不转述、不省略关键字；
5. **不擅自改规则**：架构规则 / 门禁报错先确认是否真违规；确属误报**走 §6 登记**，不自行改规则或用 `NoWarn` 了事；
6. **不做一次性原型**（纪律 C3）：临时脚本 / 试验代码不得留在仓库；测试与桩模块属**常备基础设施**；
7. **会话压缩或切换后**，继续改动前**重读关键分册**（至少 `01-layering-and-projects` + `04-runtime-mechanisms`）。

### 8.1 类型与成员默认值

| 项 | 约定 |
|---|---|
| 默认封闭 | 类型默认 `sealed`；**例外**：`Sdk` 中面向模块作者的抽象接口（抽象基类一律不用） |
| 不可变优先 | 框架内部元数据（Definition / 契约形状 / 设置快照）一律**不可变**（`readonly` / `init` / `record`）；运行期只读共享 |
| 可见性最小 | 默认 `internal`；仅 `Sdk` / `Core.Api` 的公开面用 `public`；跨程序集内部可见用 `InternalsVisibleTo`（**并登记原因**） |
| 值与引用 | 数据单元用**结构体**；跨层传递的描述 / 元数据用不可变 `record`；**热路径不 new 类** |
| 集合 | 对外暴露 `IReadOnlyList<T>` / `ReadOnlySpan<T>`；内部用数组 / 池化；不用 `List<T>` 作长期容器 |
| 常量与枚举 | 魔法数字入具名常量或设置项；**枚举显式编号**（序列化稳定性） |
| 可空 | `<Nullable>enable</Nullable>` 全程开启；`!` 仅用于已证明非空处并加注释；公开 API 入参校验用 `ArgumentNullException.ThrowIfNull`（非热路径） |

### 8.2 异步与并发（本项目最重要的一节）

| 项 | 约定 |
|---|---|
| 数据面不用 async | 投递路径**同步**（线程已专属）；`async` 只用于 UI / IO 等待，**禁出现在热路径** |
| 线程归属 | **框架为每个 `Active` 实例分配专属线程**（`04-runtime-mechanisms`「线程、队列与停止协议」）；模块可阻塞；**任何代码不得自建 `Thread` / `Timer`**（除 `DataPlane` 的承载设施） |
| 共享状态 | 跨线程共享**只经**：① 不可变快照 + 原子替换（绑定集合、设置快照）② 有界队列（投递）③ 订阅缓冲（UI 读取）——**不引入 `lock` 保护热路径** |
| UI 线程 | UI 只碰 UI 对象，经订阅缓冲 / `Core.Api` 与后台交互；**不阻塞 UI 线程**，也不用 `Task.Run` 把框架逻辑丢到池上 |
| 停止协作 | 长循环必须检查**停止信号**；模块活动体入口由框架包裹异常边界（超时路径的资源处置见 `04-runtime-mechanisms`「超时路径的资源处置规则」） |

### 8.3 异常与错误

| 场景 | 约定 |
|---|---|
| 模块异常 | **不逸出边界**：框架在活动体入口捕获 → Issue（归属实例）+ 该模块活动停止 |
| 框架内部 | 不做防御性 `catch` 掩盖；框架缺陷必须暴露给开发者 |
| 可预期失败 | 用返回值 / Try 模式（解析失败、契约不匹配、口不存在），**不用异常作控制流** |
| 上报路径 | 内部**不抛**：上报失败只记诊断计数 |
| 错误分类 | 一律映射到 Issue 七类（主文档 §8.2）+ 归属对象；**不用自定义错误码体系**（v1 明确不做） |
| 禁止 | `catch (Exception) { }`、`catch` 后仅 `Debug.WriteLine`、静默降级 |

### 8.4 日志与上报

| 层 | 方式 |
|---|---|
| 框架 | 内置极简日志 sink（**自研**，决策见 `docs/decisions.md` 类 7 · 原文 `docs/archive/adr/ADR-0024`）；结构化字段：时间 / 层级 / 对象 / 事件 |
| 模块 | **只经 `Sdk` 上下文**上报（Issue / 日志 / 业务状态）；**不直接引用日志库** |
| 级别 | `Trace/Debug/Info/Warn/Error`；`Info` 及以上进日志文件，`Trace/Debug` 只在诊断开关打开时 |
| 禁止 | 热路径逐单元打日志（改为**计数 + 定时汇总**）；日志里拼字符串（用结构化参数） |

（观测分层、日志文件策略、诊断信息去向见 `10-delivery-and-ops` §4。）

### 8.5 DI 与生命周期

- 容器：`Microsoft.Extensions.DependencyInjection`；**注册集中在 `App`（唯一白名单组合根）**，各层不自行 `ServiceLocator`（见 `01-layering-and-projects` §6）；
- 框架内部对象由构造注入；**不用静态可变单例**（除 `ArrayPool<T>.Shared` 这类 BCL 池）；
- `Core.Api` 的实现随 Core 生命周期；UI 侧不持有 Core 内部对象（只持接口）。

### 8.6 热路径的缓冲归还（其余见 `implementation/01` §3）

```text
✅ 结构体 + Span/ReadOnlySpan + ArrayPool 租还 + 批量处理（一次搬 N 个单元）+ 固定容量环形缓冲
✅ 返回值表达失败（Try 模式）
❌ LINQ / 装箱 / 闭包 / 每单元 new / 字符串插值 / 异常控制流 / async
```

**缓冲归还**：池化缓冲的所有权必须明确（谁租谁还）；跨线程移交时**由接收方归还**；调试构建下断言双重归还。

## 9. 构建与调试（只留别处没有的）

> 构建命令、常见错误与规避、命令速查 → `DEVELOPMENT.md` §3 / §5 · `implementation/02` §2 / §3（`P##` 踩坑表）· `09-test-and-gate` §5.5 · `10-delivery-and-ops` §2。

1. **数据面问题先看诊断**（投递数 / 丢弃数 / 最后数据时间 / 队列深度），不要一上来打断点 —— 多线程下断点会改变时序；
2. **模块卡住** → 看是否 `Removed` 后线程超时（Issue + 孤儿标记，见 `04-runtime-mechanisms`「超时路径的资源处置规则」）；
3. **UI 卡顿 ≠ 数据面卡顿**：看订阅缓冲丢弃计数；数据面**不应**受 UI 影响（受影响即违反主文档 §13.1，属架构级缺陷）；
4. **无 Accelerate 许可键时的遥测提示不影响构建**，可用 `AVALONIA_TELEMETRY_OPTOUT=1` 抑制上报。
