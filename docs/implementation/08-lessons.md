## 一、UI 开发方式（**最重要的一条经验**）

1. **尺寸归 XAML，代码不算布局。**
   *错误做法（我做过）*：按"元素类型 → 高度/宽度表"在运行时算窗口尺寸。
   *后果*：布局被写死在 C# 里——用户在设计器/XAML 里看不到也改不了；加一种元素就要改代码；信息量一变化外层容器就变形。
   *正确做法*：**外层容器尺寸固定**（默认/最小尺寸写在该视图的 axaml 里），**子区排不下就出滚动条**；代码只在三处介入：
   ① 恢复**用户拖过的**几何（那是用户的布局）；② 应用**设置里选的**比例/主题；③ 绘制**领域标准件**（端口标记/连线/参考线）。

2. **设计时数据 = 用户能不能自己调 UI 的前提。**
   视图没有 `d:DataContext` → 设计器里是空壳 → 用户只能描述现象、不能在 XAML 里直接改。
   做法：design-only 的样例数据类（`Ui/Design/DesignData.cs`、`FrameworkUi/Design/ShellDesignData.cs`）+ 设计时替身运行时返回**样例数据**（不是空集合）+ 每个视图挂 `d:DataContext` / `d:DesignWidth/Height`（`d:` 运行时被忽略）。
   **交付 UI 相关改动时，必须同时说明"这个视图在设计器里能不能预览"。**

3. **文字信息只有三种写法**（用户反复提"信息过多/教程式描述"）：
   | 内容 | 写法 |
   |---|---|
   | 短语（≤12 字） | 直接显示 |
   | 一句话解释 | `ToolTip.Tip`（悬停才出现） |
   | 多句/教程 | **小问号按钮 + `Flyout` 弹窗**（点外部关闭）——**绝不就地展开**（就地展开会改变布局，用户明确反对） |

4. **区域要有边框、帮助按钮要小且对齐。**
   列表/分区加 1 px 边框（`ListBox` 全局样式、`Border.pane`）；帮助按钮 16×16 带边框、**放右侧/右下角**、各分区**右边距一致（X 对齐）**；帮助弹窗里**只放文字**。

5. **区域尺寸不随内容变化。**
   模块列表这类"选择区"必须放在 `*` 行/固定高度里并内部滚动；标签/按钮**固定宽度** → 切换分类、搜索、数量变化**都不推动其它控件**（用户报过"切换分类影响整体排版"）。

6. **沟通用"段位"。**
   把页面切成编号区段（①②③…）并写进代码注释与 UI 指南 → 用户只需回"④ 应该紧贴 ③"这样一句话；**只改被点名的那一段**，不动已认可的部分。同理：**不要过度解读用户的手绘原型**（原型里的文字标签、比例、缺项往往只是"画起来方便"）。

## 二、交互与命中的经验

7. **层级决定可用性**（固定为：内容 → 交互带/手柄 → **口标记层** → 叠加信息层 → 按钮簇）。
   手柄"垂直居中"与端口标记"垂直居中"必然重叠 → 双击被吃掉（用户报"改不了网络标签"）。
   规则：**手柄只在选中/可交互时才可命中**；"唯一入口"类控件必须在**最上层**。

8. **"看得见"是功能的一部分。**
   端口标记曾因为底色对比度≈1.02 + 字号 10 + 被拖动带压掉 5 px，用户**以为功能不存在**。现在的标准件：20×114、贴外框、强边框、字号 11、四段固定槽位。

9. **绝不允许静默失败。**
   - 提交路径拿不到控制器/依赖 → **就地报错**，不要"默默取消"；
   - 校验失败 → **保持弹窗打开 + 框内显示原因 + 不清空输入**；
   - **死开关**（可改可存但没人消费）是最坏的一类缺陷（P27）→ 新增开关时必须能指出"谁读它"。

## 三、框架与平台陷阱

10. **XAML 编译通过 ≠ 运行时安全**：资源类型写错（`x:Double` → `CornerRadius`）只在**运行时**抛异常（P20）。
11. **Avalonia 资源查找顺序** 主题字典 → 自身 → 合并字典（P21）。
12. **无头 UI 测试**：用 `HeadlessUnitTestSession`（不绑 xunit v3）+ `DisableParallelization` 集合 + `ForceRenderTimerTick()`（P22）。
13. **自绘要换算坐标系**：屏幕物理像素 ÷ `RenderScaling`，原点取 `PointToScreen(0,0)`，根容器 `ClipToBounds`（P23）。
14. **装饰窗口** `Position` 是外框、`Bounds` 是客户区 → 要客户区矩形就用 `PointToScreen(0,0)` + `ClientSize`（P24）。
15. **"零尺寸矩形"会被几何校验过滤** → 线要用"参照线"通道而不是零宽矩形（P25）。
16. **图标方案**：Avalonia 12 无 `SymbolIcon`；系统图标字体（Segoe Fluent Icons / MDL2 码位）零依赖且 Windows 原生；引第三方图标包前先核对它依赖的 Avalonia 大版本（P26）。
17. **SDK 的"只增不改"要看签名**：给构造器加**可选参数**会改方法签名 → 已编译的第三方模块加载即 `MissingMethodException`（P30，本项目实测 3 个参考模块当场失败）。**SDK 新增可选声明一律用 `init` 属性**；改 SDK 后**必须重编全部模块**。
18. **"清空"不等于"还原"**：把配置对象清掉会让"按登记对象生成"的表单失去来源（用户看到空表单）；正确做法是**替换为同类型的新默认实例**（P16 的"读即登记"同一道理：凡"框架按对象取数据"的接缝，都要保证对象始终存在）。
19. **吸附必须"双向阈值 + 粘滞"**：只有一个容差、每帧重新比大小 ⇒ 边界处 1px 抖动就换来多像素回跳（P31）。进阶：候选要**分级**（贴合 > 端口/标签中心 > 模块中心 > 边缘），跨级不比较；同级顶替还要"明显更近"。
20. **像素几何只有一个量化口径**：模型存小数、窗口只能整数时，两条边的"贴合"会各自取整成 0/1px 的缝或叠（P32）。**在一处取整**（`ScreenPixels`），并且**只驱动者写模型**（被指针带着走的成员不要被窗口回写）。
21. **判定要用"事件发生前"的几何**：用移动后的坐标去判"谁贴着谁"，会把判定条件悄悄变成"位移足够小才成立"（P33：外壳跟随退化成 ≤2px 才生效 ⇒ 快速拖动永久拉脱）。**这条在"外壳纳入拼图图"时又犯过一次**：用移动后的外壳矩形判"谁与外壳相连" ⇒ "贴上了"被判成"没贴上"，模块完全不跟随（P33 第②例）——**写成参数显式传进去**（`TranslateShellGroup(dx, dy, preMoveShell)`）就不会再忘。
22. **别拿"被自己移动的对象"当输入基准**：拖动时用"窗口位置 + 窗口内局部坐标"算屏幕指针，两个来源**不是同一次采样**（前者是我们自己刚设进去的）⇒ 指针读数误差 = 窗口位移量 ⇒ **正回授振荡**；表现为"**只沿拖动方向抖**"（P34）。指针取**系统光标**最稳。**推论**：这类自反馈问题里，"只在一个方向出现"往往就是线索 —— 那个方向正是我们自己动过的方向。
23. **贴边画的东西会被自己的裁剪吃掉 —— 而且根因常常是"判断"而不是"裁剪"**：对齐参考线画在窗口内部，父级 `Frame` 是 1px 边框 ⇒ **自绘控件被四周内缩**，坐标却按"客户区原点"算 ⇒ 下/右贴边的线落在"范围 + 2"，被 `position <= extent` 的**可见性判断直接否掉（根本不画）**；上/左落在 0 所以看得见（P37）。我第一轮只加了"收进半个线宽"（改的是"怎么画"），**没改判断**（"画不画"）⇒ 用户复验"还是没有"。**两条一起改**：可见性判据容忍贴边超出（并保留"排除离得远的线"），绘制时按"线宽/2"内缩。**教训：报"看不到"时，先分清是"没画"还是"画了看不见"。**
24. **凡"内存领先于落盘"的成员，刷新一律让路**：整体平移为了省开销做成"只改内存 + 防抖落盘"，而刷新是 **60Hz** 的，`SyncModules` 用"已落盘的旧布局"回写 ⇒ 模块被一帧帧拉回原位，表现为"**移动主窗口时模块跟不动**"（P36）。凡是"交互中先改内存、稍后再提交"的路径，都要在刷新里**显式跳过**这些成员。
25. **模板里"两套分支"不要用同名 `Name`**：端口标记模板为竖排/横排各写一套内容、靠 `IsVisible` 互斥，我按"被测试定位"给两边都写了 `Name="TypeStrip"` ⇒ **首次布局时**（模板实例化）抛 `ArgumentException: Control with the name 'TypeStrip' already registered.`——**T0 编译完全看不到，只有无头 UI 测试/真机跑到布局才炸**（P38）。模板是**一个命名域**，"不可见的那套也算"。**模板内需要被定位/被样式命中的元素一律用 `Classes`**（`portMarker` 本就是此做法）。

## 四、流程与验证纪律

26. **分层验证**：T0 单项目编译 → T1 单类测试 → T2 单测试项目 → T3 完整门禁。
    · **纯 UI（XAML/样式/文案/间距/颜色）**：只 **T0 + `-Mode Run` 眼睛看**，**不跑测试、不跑门禁**；
    · **连带逻辑**（视图模型/命令/数据结构）：只跑**受影响的测试类**（T1）；
    · **T3** 只在：交给用户手工验收之前 / 改了公开面或文件格式或依赖 / 宣布某步骤完成时。
27. **报告必须区分"我跑了哪一层"**，不得把 T0/T1 的通过说成"全量通过"。
28. **文档先行**：ADR（设计冻结）→ 主文档回写 → 实现；**作废要"移动/标注"不删除**；发现漂移立即修（本轮修过 3 处）。
29. **回归网要用真实窗口**：无头 UI 测试（真实 App 资源 + 真实 `ModuleWindow`/`MainWindow`）已经**抓到过我自己的三处疏忽**（活动栏按钮计数、标记被手柄压住、资源类型崩溃）——它是视图层性价比最高的兜底。**本轮又抓到一次**（模板同名 `Name`，见 25）。
30. **不要用 PowerShell 改源码**（P14）；批量替换测试断言后**必须逐条核对**（本轮替换后仍残留 2 处硬编码坐标，被迫二次修）。
31. **应用运行会锁 `src/App/bin` 输出**：UI 改动时用 `-SkipAppRebuild` 跑测试，或先关应用；**不要**为了跑门禁擅自 `-StopApp` 杀掉用户正在看的实例（会丢现场，先问）。
32. **如实承认错误归因**：曾把"改不了网络标签"断言为"控制器交接为空是唯一原因"，被用户截图（状态栏显示成功消息）推翻——**只报证据支持的结论**，并在文档里更正归因。
33. **"手感"问题先做数值实验再改**：吸附振荡这类主观描述，先用**纯几何的临时测试**把"1px 指针位移 → 位置跳几像素"打出来（本轮实测 +10px），再定方案；改完把该实验**转正为回归断言**，手感就不再靠嘴说。
34. **"扫描通过"不等于"问题解决"**：用户报"还是抖"，我把判据写严、扫了 1446 组几何全绿 —— 结论只能是"**决策层没问题**"，**不能**是"没问题了"。要接着问"**剩下的差异在哪一层**"（本轮答案是输入层/交互层）。**先证伪一层，再往下一层走**，不要在被排除的层里继续加机制。
35. **"更好的做法"往往是把新对象并入既有那条规则**：主窗口与模块"整体运动"一开始被我做成"外壳移动 → 所有模块无条件跟随"（新规则），用户指出这不符合直觉 —— 正确做法是**让外壳成为拼图图里的一个节点**，于是"单侧吸附 → 同组 → 移动谁都是整组动"这套**既有逻辑**直接覆盖了它（`docs/architecture/07-overlay-and-visual-baseline` 的「拼图组、外壳跟随与平移落盘」）。**遇到"两种东西要一起动"时，先问"能不能把它们放进同一张图"，而不是再写一条联动**。
36. **"死绘制路径 + 死属性"编译器看不见，只有断言拦得住**：`ConnectionOverlay.DrawArrow` 建好 `StreamGeometry` 后**没有 `DrawGeometry`** ⇒ 叠加层的**流向箭头从来没显示过**；配套的 `ArrowBrush` 属性从定义到 XAML 传参一路齐全，`Render` 里却**从未读取**（还有一处：控件**缺 `AffectsRender`** ⇒ 改画刷不重绘）。编译器不会报"几何被丢弃""属性没人用""参数没用到"，**验收项写着"带流向箭头"也没人验**（P39）。**通用规则**：① 自绘路径必须有断言证明"**真的画出来了**"（本轮起因就是用户一句"叠加层太潦草"）；② 每个公开属性都要有消费者，否则删掉；③ 会画东西的控件必须显式声明 `AffectsRender`。
37. **自绘连线/图形的起止点要落在"语义锚点"上，不要落在"中间层"**：连线原本从**端口标记中心**画到窗口边缘 —— 标记本来就在 20px 边带里 ⇒ 线长 = `Band/2` = **10 px**，用户看到的是"两小段残线"，判断为"**像出了 bug**"（`docs/decisions.md`）。**通用规则**：画连接线时先问"这条线的两端在语义上分别锚在哪里"——**模块中心 ↔ 窗口边界**才是锚点；**中间的装饰件（标记、手柄、边带）不是几何锚点**。**推论**：用户说"看起来像 bug / 不清晰"时，先量几何（线长、层级、颜色），别急着调颜色与粗细。
38. **显示名不能当唯一键 —— 身份必须由框架给出**：诊断/网络视图只暴露 `NetworkName`，视图层就拿它 `ToDictionary`；而**匿名网络（自动建网）的名字是空串** ⇒ 出现**第二条**自动建网链路时抛 `An item with the same key has already been added. Key: `（**空键**）——而且它在**60Hz 刷新路径**里，界面当场废掉；只有一条匿名网络时**不报错但张冠李戴**（两条网络显示同一组数字）。**同款写法仓库里有第二处**（拓扑页），说明这不是手误而是**建模缺口**（P40）。**通用规则**：① 任何"配对/索引/去重"都用框架给的**身份键**（本例 = "源 → 宿集合"），**显示名（可空、可重复）永远不能当键**；② 高频刷新路径里**一律不抛**（`TryAdd` 之类"宁可少显示"）；③ 修一处后**全仓搜同款写法**（grep `ToDictionary` 的键选择）。

39. **"标志"与"成员"不能各说一套 —— 可由集合推导的状态一律派生，不要另存**：`Network.IsStalled` 曾被存成独立布尔量，而"**哪些源在场**"在模型里根本没有位置 ⇒ 两者随时可能矛盾（标志说停流、成员却在场）。改成 **`IsStalled ⇔ Sources.Count == 0`** 后，不一致**在结构上不可能**。**通用规则**：写"状态字段"前先问"它能不能由已有集合算出来"——能，就别存。
40. **"同一个值"不等于"同一个事实"**：加载期的**源字面量** `g2.out` 与**锚定后的成员** `g2.out` **取值完全相同** ⇒ 用一个集合表达时**无法区分"这个源在场"与"这个源只是声明"**。后果很隐蔽：重锚用成员比较判断"有没有变化"，结论永远是"**没变**"⇒ **锚定成功了却不建绑定**（无报错、界面只是"没数据"）。**通用规则**：用 `Equals`/`SequenceEqual` 判断"状态是否变化"之前，先确认**被比较的对象真的携带了那个差异**；携带不了就**把差异显式建模**（源分 `Sources`/`UnresolvedSources` 两个集合），**不要**用标志位或时间戳去补救。**对称性检查**：宿侧早就分了两态（`Targets`/`UnresolvedMembers`），源侧没分——**一处有、一处没有的对称结构，通常就是缺的那半**。
41. **同一语义写两遍必然分叉 —— 抽成唯一实现**：组合件**加载**与**占位补齐后重锚**各写了一套"字面量 → 网络"的换算，重锚那套只认**单源** ⇒ 多源网络被**悄悄打回单源**，而且没有任何报错（结果"看起来正常"）。修法 = 抽 `AnchorNetwork` 一个实现，两处都调它。**通用规则**：同一语义出现两次就抽出来；**"看起来正常"的静默数据损失是最贵的一类缺陷**——它不会进 Issue 中心，只会让用户困惑。
42. **格式迁移 = "读旧写新 + 清旧字段 + 升版号"**：v1 的 `source`（字符串）与 v2 的 `sources`（数组）**绝不能同时留在文件里**（同一事实两个字段 = 第二事实源）。做法：**解析期归一**（读到旧字段就写进新模型）、**写回时移除旧字段**、`schemaVersion` 升格；两个字段同时存在时**以新字段为准并报警**，不猜测、不静默取旧值。迁移前**先写"旧文件加载"用例**。

43. **`bool` 结果会把两种不同的原因挤成一个 `false`**：`TryEnqueue` 原本返回 `bool`，而"队列满（best-effort 丢弃，正常）"与"目标口根本不存在（无承载，配置/模型问题）"**都表现为 `false`** ⇒ 调用方只能把它记成同一种丢弃。**通用规则**：只要一个"成功/失败"背后有**性质不同的原因**（可重试 vs 不可重试、正常 vs 异常），返回值就应该是**枚举**（`Accepted/QueueFull/NoCarrier/Stopped`），让调用方按原因分别计数与提示。**代价极低（改一次签名），收益是诊断从此说得清。**
44. **"提示"可以不可靠，但**不能**把它当正确性的依据**：每口一条队列后，投递循环要跳过空口。为了不每轮对 N 个口各取一次锁，用了一个"该口有数据"的位图提示。**关键是写清它只是提示**：入队成功**必** `Release` 信号量、消费侧 `Wait` 是 Acquire 栅栏 ⇒ 即使位图读到陈旧值，也只是"多一次空探测 / 最多等一个 `IdleWait`"，**不会漏数据**。**通用规则**：任何优化用的"捷径状态"必须能回答"它读错了会怎样"，且答案是"只慢不错"；答不上来就别加。

45. **"旁路元数据"落地时必须同时给出消费者，否则它就是死数据**：Q6(c) 批了"多源网络带薄旁路头（源标识+序号+接收时刻）"，但如果只是"生产侧把它挂上去"而没有读的人，就会重演上一条的坑（几何建了不画、属性传了不读）。**做法**：把头交给**观测面**（承载诊断：带头发起数 / 最近序号 / 接收时刻），于是"**单源网络 `Headered == 0`**"直接变成"**零附加**"这条设计承诺的**可断言证据**——一个消费者同时兑现了两件事（有用 + 可验证）。**通用规则：新增任何"旁路/附加"数据，同一次改动里就必须有它的读取方与断言。**
46. **同一个数字不要有两种含义**：`Delivered` 是"**按宿**计的投递次数"（多播会放大），如果拿它当"发布序号"，多播一次序号就跳 N —— 序号立刻失去意义。**做法**：为"**每个数据报一次**"单列 `Published`（按源、不被多播放大），并明确它同时是"单元速率（按源计）"的分母。**通用规则：落地一个新语义（序号/速率/计数）时，先问"它的分母到底是什么"，然后为之单列计数器——不要复用语义不同的既有计数。**

47. **"默认不兼容"这种规则必须问"用户的确认存在哪里"**：`docs/decisions.md` 说"**不同标识**的数据类型**默认不兼容 + 用户显式确认可强连**"。我第一版只在**建连那一刻**校验里放行 —— 结果连接建立了，**绑定却建不出来**：绑定构建路径会**再判一次**兼容，而那里没有"用户确认"这个信息。**修法**：把确认**存到连接本身上**（`Network.AllowUnverifiedTypeMatch`，且它是**用户决定**而非派生事实 ⇒ **随组合件持久化**，否则重载后连接莫名失效）。**通用规则**：凡"需要用户显式确认才能成立"的规则，落地时要追问**确认在哪个对象上、谁能再看到它**——只放在一次性的校验函数里，等于没存。
48. **"投递成功"不等于"真的到达"——记账要跟着事实走，不能跟着返回值走**：队满且策略是**丢旧**时，`TryEnqueue` 返回"成功"（新单元确实入队了），但同时**挤掉了一个更旧的单元**——那个旧单元**永远不会被消费**，可它早先已被记成"投递"。于是"投递数"里混着从未到达的数据。**修法**：把这个状态**如实说出来**（`CarrierEnqueueResult.QueueFullEvicted`），调用方据此"**新单元记投递 + 旧单元记队列满丢弃**"。**通用规则**：计数器要跟**事实**对齐，而不是跟**函数的返回值**对齐；凡是"成功但仍损失了什么"的操作，返回值里必须带出那份损失。

49. **静态/共享的 Avalonia 画刷必须用"不可变画刷"，否则整套 UI 测试会"一起跑就红、单独跑全绿"**：`PacketTypePalette.Placeholder`（静态单例）与 `ThemeApplier` 的覆盖项（进应用级资源字典）原先都用 `SolidColorBrush` —— 它是 `AvaloniaObject`，**有线程亲和性**；只要它在**非 UI 线程**上被首次创建（测试并行、后台刷新），渲染线程读它（`Brush.get_Transform`）就抛 `The calling thread cannot access this object because a different thread owns it`。症状极具迷惑性：**单独跑该测试类 16/16 全绿，整项目一起跑就固定红 9 项**（T3 因此被挡）。**修法**：一律 `Avalonia.Media.Immutable.ImmutableSolidColorBrush`（无亲和性、可跨线程共享）。**通用规则**：凡"静态 / 单例 / 进资源字典"的 `IBrush`/`Pen`/几何，都当作**跨线程共享**处理；"测试单独跑绿、一起跑红"先怀疑**共享可变状态**（线程亲和、静态缓存、单例），而不是测试本身。
50. **"一个成功/失败"背后的原因不同时，别把它挤进一个布尔值**（P45 同源）：`RateMeter` 的首个观察没有"上一时刻" ⇒ 必须返回 0 而**不是**猜一个速率；丢旧策略下"新单元已入队但挤掉旧单元" ⇒ 必须**如实说出那份损失**（`QueueFullEvicted`）。**通用规则**：凡是"看起来成功、但其实丢了点什么"的操作，返回值里必须带出损失；凡是"还没有基准"的度量，宁可返回 0/未知，也不要估算——**估算出来的数字一旦进了界面，就再也没人知道它是猜的**。

51. **"兼容"不等于"能按自己的契约整块读"—— 声明层通过 ≠ 运行期安全**：契约兼容判的是"**接收方声明的字段集覆盖发送方**"，但**到达的数据报长度 = 发送方的契约尺寸**（框架不投影、不补零、不截断）。于是"尾部追加 = 兼容"的版本升级路径上，新版本接收方拿到的仍是**旧版本那么长**的数据报，**尾部字段根本不在** —— 用**自己的**契约 `new PayloadReader(payload, myLayout)` 直接抛 `数据单元过小`。**更糟的是后果**：异常从投递回调逸出 ⇒ 该实例的**投递循环整体退出**（再发也无反应、计数不再增长），只留一条写着"**活动体**异常"的 Issue（文案还不对）⇒ 现场表现是"**模块莫名不再收数**"，极难定位。**实测还发现**：多源同名标签把**不同版本**的发布者连到**同一个口**时，同一口上会**混着两种长度**的数据报（这是被允许的配置）。**修法与纪律**：① 接收方**按到达长度读**（`PayloadReader.TryCreate` 长度不足返回 false 不抛），只读"**发送方一定存在**的公共前缀字段"；② **声明层没拒绝 ≠ 运行期安全** —— 凡是"上层判定通过、下层按假设硬取"的地方，都要在下层加**边界检查 + 可见的失败信号**（丢弃 + 计数 + 首次 Issue），而不是让它抛。**通用规则：兼容性/类型检查只解决"能不能连"，不解决"连上以后怎么读"；这两件事必须分别写下规则。**
52. **"能跑"与"正确"要分开回答**：用户问"不用融合器直接用标签连线也能跑，是巧合还是正确？"—— 正确答案不是"能跑就行"，而是**分形态回答**：**1 源 → N 宿 = 广播**（每宿一份独立拷贝，**根本没有"合并"这回事**）⇒ 正确且非巧合；**N 源 → 同一宿口 = 匿名多路复用**（按到达写同一条 FIFO，不排序/不去重/不仲裁/**不告知来源**）⇒ **语义正确但不是合并**，需要语义合并时必须由模块承担（**一源一口**是推荐形态）。**通用规则**：回答"这样行不行"时，先**把形态拆开**（谁对谁、几个源、几个宿、同口还是分口），再对每种形态说清"框架做了什么"与"应用必须自己做什么"——**含混地说"可以"或"不行"都是不负责任的**。

53. **"宽松的兼容规则"会把两个问题绑成一个**：旧规则"接收契约 ⊇ 发送契约"（子集）允许接收方字段更多，于是**到达的数据报可能短于本口契约** ⇒ 接收方按自己的契约读就抛异常 ⇒ **一个坏数据报让整个模块再也不收数**。**规则宽松 = 责任转移给每个模块作者**（每人都得记住"兼容 ≠ 能按自己契约读"）。用户一句话点到要害："**大版本往往是破坏性调整，无需考虑兼容**" ⇒ 改成**形状完全一致**后，"**能连**"与"**能安全读**"重新成为同一件事，规则从三层降到一句话。**通用规则：当一条"宽松规则"需要配套一整套纪律去兜底时，先问"把规则收紧会不会更简单"——纪律靠人记，规则靠框架执行。**
54. **record 的默认相等不是"结构相等"**：`ContractShape` 是 record，我一度直接写 `sender == receiver` 判"形状是否一致"；但结构形状的**字段集合**是 `ReadOnlyCollection`，record 生成的相等对它做的是**引用比较** ⇒ "两个模块各自 new 出的同一形状"会被判**不相等**（隐形陷阱：只有引用同一个静态实例才连得上，测试里恰好都是同一实例所以全绿）。**修法**：写真正的逐字段结构比较（`ContractShape.AreSame`）并**专门加一条"各自构造的同形状必须兼容"的用例**。**通用规则：凡是"值语义"类型里含集合/数组/字典，record 的 `==` 都不可靠；需要值语义就自己写比较，并**为它写一条专门用例**——否则它会一直靠巧合通过。**
55. **值元组/值类型放进字典后，取出来的是"副本"—— 计数改了等于没改，而且**引用成员会替你掩盖它****（v1.59 实测）：`GetRolePairs` 的角色对聚合写成 `Dictionary<键, (int Count, List<string> Networks)>`，循环里 `TryGetValue` 拿到 `entry` 后 `entry.Count++` —— **改的是副本**，条数**恒为 0**。它之所以没被立刻发现，是因为**同一个元组里的 `Networks` 是 `List`（引用类型）**：`entry.Networks.Add(...)` **真的生效了**（列表有内容），让人误以为"这个 entry 是活的"。**修法**：累加后**写回** `pairs[key] = entry;`（或直接把累加器写成 `class`）。**通用规则**：① 值类型（`struct`/`ValueTuple`/`record struct`）**从集合取出后一律视为只读副本**，任何修改都要写回；② 一个"半引用半值"的复合类型最危险 —— **部分字段生效会掩盖另一部分失效**，所以**判据不能只断言"看得见的那部分"**：本条的用例正是靠"**条数**"（而不是"网络列表非空"）把它抓出来的；③ 新增聚合/累加逻辑时，**同时写一条断言"计数正确"的用例**，别只断言集合内容。

56. **新增一个公开面字段时，"定义"不等于"接线"—— 同一次改动里必须同时有生产者与消费者**（v1.61 实测）：P3 给 `PortView` 加了 `TypeKey`（颜色映射的键），但 `RuntimeServices.ToView` 里**没有赋值** ⇒ 它恒为 `null` ⇒ 色板永远回落到占位色（**代码里"有这个能力"，跑起来却完全没生效**）。它是被"窄色条的颜色必须等于 `PacketTypePalette.For(TypeKey)`"这条用例抓出来的 —— 关键在于**断言的是"取自哪里"而不是"是某种颜色"**（后者在"恒为占位色"时也会通过）。**通用规则**：① 加字段的同一笔改动里，**写完生产者再写消费者**，并让产消两端**共用同一来源**（此处 = `DescribePortTypeKey`，与角色键同源 ⇒ 端口标记与角色方块颜色天然一致，不会两处漂移）；② 测试要断言**来源/一致性**，而不是断言"某个具体值"；③ 与第 45 条（旁路数据必须有消费者）同源：**没有消费者的数据、没有生产者的字段，都是死代码**。

57. **"留白"是几何参数，不是审美偏好 —— 留得太少会把线退化成"坏掉的样子"**（v1.61 实测）：角色方块第一版放在"离窗口边缘留 `Gutter(24)`"的位置，默认窗口（320 宽）下从方块画到窗口边界的线只有 **24 px** —— 与 20 px 的端口标记带同量级，看起来**又像上一版被用户投诉的"10 px 残段"**。改成 `RoleColumnInset = 46`（并保证**不越过窗口中线**）后线长约 **46 px**。**通用规则**：① 凡"从 X 画到 Y"的线，**先算最坏情况下它的实际长度**，再决定 X 的留白；② 把这条写进**几何用例**（"线长必须显著大于标记带"），否则后人调布局时会悄悄改回去；③ 极窄尺寸要有**明确的退化策略**（此处 = 单列居中，保证不重叠），别指望"把参数调小一点就行"。

58. **连线的几何 = "两点 + 一裁"，别拿业务推断去补几何**（v1.62 · 用户直接点出来的）：我第一版用两套**推断**决定端点——"该角色下各口在边缘上的**平均位置**"（`BoundaryOffset`）与"对端在**上下左右**哪一侧"（`PeerSide` 分类 + 回退），再按方位分别算端点。结果：同一个角色对在不同布局下**端点跳来跳去**、线还横穿模块，用户一眼判定"**四不像**"，并给出一句话的正确形态："**通过核心的坐标和是否连接即可计算连线的长度和角度**"。改成 **起点 = 方块中心、终点 = 对端窗口中心、两点连线被本窗裁一刀** 之后，长度/角度/箭头朝向**全部自然成立**，连"箭头往哪指"都不再需要判断（沿这条线即可），代码与用例同时变短。**通用规则**：① **画线就是"两点之间"** —— 想把端点"修正得更聪明"之前，先问"这个修正是不是在弥补一个本不该存在的假设"；② 需要**方位分类**（上/下/左/右 + 特判）通常说明几何没选对（两点定线天然与方位无关）；③ 一条几何规则若要用**两套推断**才能说清，它就不是"简单规则"。

59. **"分区域 + 按字号分层"是信息设计，不是排版细节**（v1.62）：`docs/decisions.md` 早就定了"一眼级信息 **12 / 11 / 10 px**"，我实现时却把身份、结构、指标、未连接数**拼成一行 10px** 贴在右下角 —— 字都在，但**重要度全被压平**（用户："你似乎忘记了我之前说的'分区域和根据字号大小显示不同的信息'"）。改法：**每块只放一种信息**（左上身份 12 · 左上结构 10 · 右下指标 11 · 右下速率 10 · 方块两行 · 线上标签），三档字号**对应重要度**。**通用规则**：① 信息**不是凑齐就行**，要按"一眼看到什么 → 再看什么"分层：主指标用大一号字，事实/细节用小一号字；② **别把并列关系硬塞进一行** —— 一行里混三种语义，等于没有层次；③ 面积紧张时先问"这块信息该不该出现在这里"（我原先放左下的结构文字与模块自有的运行指示**叠字**，是渲染快照抓出来的）。

60. **"指标来源唯一"要落到"只有一个写入点"，否则两处会在某些状态下互相打脸**（v1.62 · 用户裁定"所有数据指标必须保证来源唯一"）：`PortInstance.IsStalled` **从来没有写入方**（恒 `false`）却被读进 `PortView.IsStalled`；`PortInstance.IsConnected` 同病（上一轮已删）；而 `PortView.IsConnected` 走**绑定**、UI 走**网络**，在**停流网络**（不建绑定）上给出**相反**的答案。清理原则：① **谁的事实谁派生** —— "连上了吗/停流吗"的唯一来源是**网络成员关系**（`Network.Members` / `Network.IsStalled`），实例对象只回答"我是谁"；② **同一条事实只允许一个写入点** —— 标记的连接状态曾由 `SyncPorts` 与 `RefreshMarkerStatus` **各写一次**（"谁最后跑谁赢"），删掉一处后反而暴露出"要等 0.5 秒节拍"的响应问题 ⇒ 再用**结构签名**把刷新提前到"变化当帧"；③ **只被测试使用的实现等于死代码**（`PortAnchorCalculator` 与 `PortMarkerPanel` 是同一份等分规则的两份实现）——删掉它，规则才真正唯一。**通用规则：删第二来源时，顺手检查"它是不是还承担了刷新时机/口径统一"这两件事**，否则删完会出现"状态不更新"或"两个角看到不同数字"。

61. **自绘 UI 必须有"真的出像素"的自检手段**（v1.62）：无头测试默认是**空绘制**（`UseHeadlessDrawing = true`）—— `context.DrawGeometry(...)` 忘了调用、文字画到窗外、两块字**叠在一起**，**断言全都看不见**（P39 的"箭头从来没画出来"就是这么漏的）。做法：另起一个**独立测试项目**（`HYWDebugAssistant.VisualSnapshots`）用真实渲染栈（`UseHeadless(new AvaloniaHeadlessPlatformOptions { UseHeadlessDrawing = false }).UseSkia()`）把窗口 `RenderTargetBitmap.Render(window)` 成 PNG。**必须独立进程**：`AvaloniaHeadlessPlatform` 的配置是**进程级**的，同一个进程里混用两种会话会把主测试项目的无头会话一起弄坏（实测 13 项集体失败）。收益立竿见影：本轮两处观感缺陷（结构文字与左下角运行指示**叠字**、`未连` 压进端口标记带）**都是在 PNG 里一眼看出来的**，而它们此前通过了所有单元断言。**通用规则：凡是"自己算坐标画出来"的东西，都要有一条能把它渲染成图片的路径** —— 否则你只能在用户截图里发现 bug。

62. **"世界坐标"与"画布坐标"是两个坐标系，跨窗几何必须经显式换算**（v1.63 实测）：新叠加层的 `ClipSegment(window, from, to)` 要求 `window` 是本窗的**局部矩形**（每窗画布原点恒为 0,0），世界原点**只用于把对端锚点换算进本窗**。我写几何用例时把 B 窗的**世界矩形**（`x=320`）直接传进去裁 B 窗的点（点在 B 的**局部**坐标里）⇒ 裁剪判定"整段在窗外"⇒ 用例报"两段端点差 **48 px**"。**这不是实现错了，而是用例把两个坐标系混用了** —— 但它和用户说的"**看起来连不上**"是同一类错误，所以更值得记住。**通用规则**：① 几何函数**要么全用世界坐标、要么全用局部坐标**，并在签名/注释里写死；② 跨窗一律经**显式换算函数**（`ToLocal(point, fromOrigin, toOrigin)`），不许"看起来对"就算；③ 几何用例失败时，**先怀疑输入坐标的口径**，再怀疑算法。

63. **"建议"不能混进"问题清单"—— 一个会在自家正确样例上报警的检查，先怀疑检查本身**（v1.63 实测）：`ModuleContract.CheckRoles` 把"角色口数 &gt; 2 ⇒ 建议拆成两个角色"写进 `Problems`，而 `Problems` 的语义是"**空 = 合法**"（`IsValid`、`CheckAll`、参考模块门禁用例都按它写）。于是这条提示在**自家参考融合器**（2 入 1 出，用户已裁定的合法范例）上必然触发 ⇒ 门禁用例直接失败；运行期也报 Warning 时，用户会在正确模块的 Issue 中心里产生"模块写错了"的错觉。**修法**：**分通道** —— SDK 自检把建议放进**独立列表**（`ContractProbeResult.Advisories`，不计入 `Problems`、不影响 `IsValid`/`CheckAll`），文本里明说"若是一件事（多路合成一路）则**不必拆**"；**运行期不产生**这条提示。**通用规则**：① 诊断分级要与消费方的语义一致 —— "建议"要么单独一个通道，要么别做；② 任何"可能会误报"的检查，**先在自家参考实现上跑一遍**：如果它报警了，要么检查错了，要么参考实现错了（二者必居其一，不能"将就"）；③ 别把"能跑但有话说"和"不合法"挤进同一个布尔。

64. **"设计意图"只能声明，不能猜 —— 猜出来的图会把作者的设计说反**（v1.63 · 用户第三十三轮重新定义"角色"）：`docs/archive/adr/ADR-0048-module-data-role-model.md` 让角色 =（方向 × 类型身份）**派生**，于是多源融合器（`in1`+`in2`+`out`，同类型）被画成"**一个接收方块 + 一个发送方块**"，看起来像**两进两出的转发器**，而真实语义是**一块"两路合一"的功能**；同理"采集 → 计算 → 输出"会被画成两个互不相干的方块，**丢掉"链"**。用户的原话是"**角色是模块的子功能分块表达……这一点为模块自身声明**"。**修法**：角色改为**模块声明的功能分块**（一种类型 + 输入/输出口），框架只**投影**；（同时按他的裁定**不做兼容回退**）—— 因为"**两套角色模型并存**"才是真正的技术债。**通用规则**：① 凡"设计意图"（功能怎么分解、块之间什么顺序、哪个口属于哪件事），框架一律**问模块**，不要**从结构反推**；② **派生只适合"确实是结构属性"的东西**（比如"连了几个对端角色"这种能从网络成员关系算出来的量）；③ 判断标准很简单 —— **它能否被结构唯一确定？** 不能，就必须声明。

65. **"底层同源"不等于"同一个信息维度"**（v1.64 · 用户直接点出来的）：叠加层把速率/投递/丢弃画成**线旁边的一个信息卡**，理由是"这些数取自同一条网络的绑定诊断"；但用户看到的是"**这条通路**搬运得多快"，而他要的是"**这块功能**自己跑得多快" —— **同一个数字、两个表达对象**。用户原话："**可能实际底层实现读取与叠加层的信息相同，但是用户感知到的不是一个维度的信息**" ⇒ 拆成两处：**角色维度**（角色方块上方/周围的纯文字）与**通路维度**（端口标记上的通路速率），且**视觉权重也要分开**（角色块明亮、接口层降权不高亮）。**通用规则**：① 设计信息呈现时先问"**这个数字是在说谁**"（哪块功能 / 哪条通路 / 哪个实例），而不是"它从哪读的"；② **一处只讲一个维度** —— 两个维度的数字塞进同一个控件，用户必然读成同一个意思；③ 维度分开之后**权重必须跟着分开**（否则等于没分）；④ "文档写了但界面没落实"要当成缺陷处理（用户第三十四轮原话："可能文档写明了，但是似乎并没有落实"）。

66. **`DashStyle.Offset` 的单位是"笔宽倍数"，方向约定也要实测**（v1.64）：改叠加层虚线流向时，我先按注释推演（以为偏移单位是 DIP），结果方向与实际相反（用户实测反馈："输入/输出均为中心块向外"）。改法：写一条**真实渲染**的探针 —— 画一条水平虚线，量"**第二段**虚线的起点"随偏移如何移动 ⇒ 一次拿到两个事实：**偏移增大 ⇒ 图案朝几何起点移动**、**单位是笔宽倍数**（笔宽 2、偏移 +2 ⇒ 实测位移 **4 DIP**）。于是修法确定：**两侧共用 `-相位 ÷ 线宽`**（线的几何恒按数据流方向绘制 ⇒ 发送向外、接收向内）。**通用规则**：① 凡"依赖渲染引擎语义"的东西（虚线相位、渐变端点、字体度量、像素对齐），**先写能测量的探针**再改业务代码；② 量**单调可测的量**（"第二段起点"），不要量"第一段"（可能被相位吃掉或推到线外，不单调）；③ 探针留在测试里（`OverlaySnapshotTests`）—— 它同时是**文档**：下次谁再改方向，用例会告诉他单位与符号。

67. **"块太大"的根因是"尺寸写死"，不是"设计不好看"**（v1.64）：角色方块第一版固定 128×42，两字功能名（`发送`）也占一大块，用户："**中心块太大了**观感不好，建议使用**文本自适应宽度**"。改成按文本估算宽度（夹在 [64,176]）后，块自然贴住文字；同时**删掉"缩方块"这一档降级**（文字自适应后它已无意义）。**通用规则**：① 自绘控件的尺寸**能由内容推出的就由内容推**（写死只是"现在看着还行"）；② 尺寸函数若**两端共用**（本窗画块、对端算锚点），必须是**确定性纯函数**（不能依赖渲染期排版结果，否则两端算出不同宽度 ⇒ 线又错位）；③ 内容驱动尺寸之后，**回头检查那些"为适配固定尺寸而生"的降级档** —— 多半可以删掉（复杂度常是跟着写死的尺寸长出来的）。

68. **"观测型指标"必须**可重复读**——同一个刷新里的多个消费者要拿到同一个数**（v1.65 实测）：`RateMeter.Observe` 每次调用都重算"自上次观察以来"的增量并**改写基准**，而一次 UI 刷新会**对每个模块各读一遍诊断**（端口标记 / 角色信息 / 角色连线…）⇒ 第一遍之后增量恒为 0 ⇒ **除第一个消费者外，所有人读到的都是 0**。现场表现极具迷惑性：不是"没数据"，而是"**只有一个模块显示速率，其它全是占位符**"（用户实测："角色本身速率无法显示，一直是 `---`"）。**修法**：给速率计加**最小重算间隔**（`MinIntervalSeconds = 0.1`）——间隔过短的重复观察**直接返回上次速率**，不重算、不换基准。**通用规则**：① 区分**事件**（消费一次就没了）与**观测**（可以被任意多个消费者读，且必须一致）：前者用队列，后者必须**幂等**；② 只要一个指标是"读的时候算出来的"，就要问一句"**同一次刷新里被读两次会怎样**"；③ 修这类 bug 时，**同时**检查"读取路径上还有几处会写状态"（本例：诊断列表被 UI 多处调用）。

69. **两套键空间是"静默归零"的高发现场**（v1.65 实测）：同一份诊断同时带 **`Key`**（逐源键 `源 → 宿子集`）与 **`NetworkKey`**（网络键）；我在 `GetRoles` 里按前者建表、却用后者查 ⇒ **永远查不到** ⇒ 角色的速率/投递恒为 0（界面恒显示占位符，且**不报错**）。同一条路径上还有第二处：端口标记按"逐源键前缀"回退，宿口查不到时**静默保持旧值**。**通用规则**：① 一个查询面里出现两个"看起来都像键"的字符串时，**先用一条端到端断言把数值钉住**（本例：真实链路里角色的速率必须 > 0）；② **查不到 ≠ 数值为 0**：聚合查询要把"没查到"与"查到 0"分开表达，否则界面无从分辨；③ 注释里把**每个键的含义与生产者**写清楚（"逐源键 vs 网络键"这类差异，写下来只要一行，猜错要一整天）。

70. **"相对尺寸"是错位之源：同一个东西只能有一个尺寸来源**（v1.65 实测）：叠加层控件挂在 `Frame` 边框**之内** ⇒ 它的 `Bounds` 比窗口小 **2 DIP**；而"对端方块在哪"是**另一侧**用 `LayoutRoles(peer.Roles, peer.Width, peer.Height)` 算的 ⇒ 两端喂进**不同尺寸**、算出**不同位置** ⇒ 连线**系统性错位**（用户："仍然没有对齐……多套坐标系相互冲突，请确定唯一事实源"）。**修法**：画布尺寸统一到 `ModuleViewViewModel.Width/Height`（叠加层经 `CanvasWidth/CanvasHeight` 接收并在 `Render` 里使用，`Bounds` 仅兜底）。**通用规则**：① 凡"两端各算一半、拼起来要对得上"的几何，**尺寸/坐标必须来自同一个变量**（哪怕只差 2px，也会被眼睛抓到）；② `Bounds`（布局结果）与 VM 尺寸（意图）**不是一回事**，别混用；③ 把这条写成一个**跨窗口**的用例（"本窗算的对端方块中心 = 对端实际画出来的那个"），它是这类 bug 的**唯一**回归网。

71. **周期性刷新**重建集合**会把用户正在交互的控件拆掉**（v1.66 实测）：颜色映射表原先每 0.5 s 把 `Rows` 整体重建一次（"刷新"写成了"重新构造"）⇒ 用户把鼠标停在色块上、或正打开弹窗时，**目标控件被换成新的** ⇒ 现场表现为"**鼠标指到色块上时不停闪烁**"（不是样式问题，是**对象身份**问题）。**修法**：行对象**只在类型集合增删时变动**，其余情况一律**就地改值**（`DataTypeColorRowViewModel.Update`）。**通用规则**：① 区分"**刷新数据**"与"**重建视图**"——前者改属性，后者动集合；② 有悬停/展开/弹窗等**跨帧状态**的列表，一律不许在刷新里重建；③ 排这类 bug 的第一问是"**这个控件还是刚才那个对象吗**"（绑定目标被替换时，任何 `IsMouseOver`/`Flyout` 状态都会归零）。

72. **"能选任意颜色"是一次能力升级，不是换个控件 —— 要顺势把入口收敛成一个**（v1.66 · 用户裁定："我希望内置一个**调色板窗口**……**可被所有颜色选择相关位置复用**……建议做精简"）：此前 5 个取色点各自内联"预设色片 + 十六进制输入框"，能力上限是**只能输十六进制或挑内置色**，且观感/行为各不相同。**做法**：抽出一个可复用窗口（`ColorPickerDialog`，官方 MIT `ColorView`：色板 + 色相 + 分量 + 十六进制），**精简**（一排推荐色、不做自定义色格、不带透明度），**5 处全改走它**并删除内联 Flyout 与只服务它们的命令。**通用规则**：① 同一类交互出现**第二遍**时就抽公共件（第二遍是最便宜的时机，第三遍就开始抄歪）；② 抽公共件要**顺手删掉旧路径**（否则留下两套行为，用户会在不同页面看到不同本事）；③ "精简"是公共件的**准入条件**：功能面越大越要划边界（本例：不要透明度、不要自定义色格）；④ 用户说"**建议做精简**"时，他是在批准**删**，不是批准**加**。

73. **第三方控件的"自带模板"不会自动生效；而"没画出来"只能靠真渲染看见**（v1.66 实测）：调色板窗口接好后，用户点开看到的是"**一个复位提示**——不仅没法选，字还是错位的"（截图里只有标题 + 提示 + 三个按钮）。**根因**：`Avalonia.Controls.ColorPicker` 的 `ColorView` 模板在**它自己的程序集**里，`FluentTheme` **不含**它 ⇒ 必须显式 `<StyleInclude Source="avares://Avalonia.Controls.ColorPicker/Themes/Fluent/Fluent.xaml" />`；**没有模板的控件不报错、不抛异常，只是什么都不画**（`SizeToContent="Height"` 于是把窗口压成"三行字"那么高）。**"字错位"**是同一场景的次生现象：去掉内容后，提示文字与三个按钮挤在同一行、超出固定窗宽被裁。**修法**：挂样式 + 提示换行 + 按钮独占一行右对齐；并**加一条渲染冒烟**（真实 Skia 渲染 + 数"不同颜色数"，色相条一个人就能给出上百种色；空白窗口只有个位数）。**通用规则**：① 引入第三方控件的第一件事是查"**它的模板/样式从哪来**"（自带 ≠ 自动生效）；② "控件在界面上不出现"的排查顺序：**有没有模板 → 有没有尺寸 → 有没有被裁/被盖**；③ 给每个自绘/第三方控件留一条**出像素**的判据（P39、P62 的老账：断言看不见"没画出来"）；④ 同进程里开两个无头渲染会话会互相破坏 —— 这类测试要**串行**（xunit 同一个 `Collection`）。

## 五、给"下一个我"的三句话

1. **先想"用户能不能自己在 XAML 里改"，再决定这段逻辑放哪**——放不进 XAML 的外观逻辑，几乎都是错的。
2. **任何"看起来没反应"的功能，先查三件事**：命中的是谁（层级）、开关有没有接线、失败有没有提示。
3. **改动范围 = 用户点名的范围 + 必要的连带**；其余一律不动，改完按分层验证跑最小必要一层。
