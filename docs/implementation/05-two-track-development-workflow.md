# 双轨开发工作流（模块轨 / 框架轨）+ 契约扩展通道

> 状态：**现行**（2026-09 用户裁定：框架已基本完成，开发方式随阶段变更 —— 从"从零搭框架"转为"业务模块 + 框架维护"两条轨道）
> 适用范围：**接下来所有开发**。它只管"怎么开发"：跑哪一层验证看 `architecture/09-test-and-gate.md`、怎么写代码看 `01-coding-style-and-dev-conventions.md`、踩坑基线看 `02-engineering-baseline.md`、到哪了看 `roadmap.md`。
> 与主文档的关系：主文档 `上位机架构设计.md` 是验收唯一事实源；本文是实现期的**流程纪律**，冲突时以主文档为准。

## 0. 为什么要分轨（判据，不是偏好）

| 维度 | **模块轨**（插件） | **框架轨** |
|---|---|---|
| 依赖面 | 只依赖 `Sdk`（测试用 `Sdk.Testing`） | L0–L5 全部内部实现 |
| 与契约的关系 | 契约的**消费者**（只能遵守） | 契约的**所有者**（受"只增不改"约束） |
| 影响面 | 单个模块包，**可枚举** | **不可枚举**（契约 / 文件格式 / 依赖 / AR 规则） |
| 验证代价 | T0 + 模块契约测试（秒级） | 按性质选层；触及契约/格式/依赖/AR ⇒ **必须 T3** |
| 出错后果 | 换包即可回滚 | 需迁移/兼容判断，可能让**所有模块**重编 |
| 文档改动 | 模块自己一页（`docs/modules/`） | 分册 + `decisions.md` + **回写主文档** |

**一句话判据**：这次改动会不会让**任何模块作者需要重新编译或重新理解**？
- 会 ⇒ **框架轨**（哪怕只改一行）
- 不会 ⇒ **模块轨**
- "模块需要框架还没有的能力" ⇒ **第三条通道**（§2 契约扩展通道）

## 1. 两轨的循环

### 1.1 模块轨（写一个模块 = 4 步）

> **展开版（七阶段、每阶段有进入条件与通过判据）见 `06-module-standard-and-development-process.md` §E**；下表是它的压缩版，两处冲突时以 `06` 为准。

| 步 | 做什么 | 产出 / 校验 |
|---|---|---|
| **1 声明设计** | 数据类型（`DeclareDataType`）→ 端口（`DeclarePort`，带 `DataTypeRef`）→ 角色（`DeclareRole`：**一种数据类型** + 输入/输出口）→ 角色顺序（`DeclareFlow`，**只有多块模块才需要**）→ 配置字段（`ConfigurationFieldAttribute`；注意"**读即登记**"语义）→ 视图声明（元素 + 写入通道） | 声明与 `02-module-sdk.md` 一致；模块页写清"职责一句话 + 这几个声明" |
| **2 契约测试** | 用 `Sdk.Testing` 写 T6：形状/兼容/钩子/配置往返 | 模块**自证**（不是等框架验） |
| **3 本地验证** | `.\tools\dev.ps1 -Mode Build -Project <模块>` → `-Mode Test -Filter <该模块测试类>` | T0 + T1/T2，**不跑 T3** |
| **4 现场确认** | 装入 `modules\`，人工确认"能连 / 能投递 / 能显示" | 结果写进模块页（含未确认项） |

**模块轨的纪律**：模块内**不得**自造第二套机制（自己起线程、自己解析包、自己造调度）；需要就提契约扩展请求（§2）。

### 1.2 框架轨（每次改动 = 5 步）

| 步 | 做什么 |
|---|---|
| **1 分类** | ① **缺陷修复**（可在 `02` 的 P 表登记）② **落地缺口**（`roadmap.md` §4 的 `Gx`）③ **新能力**（SDK / 机制）④ **结构调整**（分层 / AR 规则） |
| **2 判定文档动作** | ①③ ⇒ 更新 `decisions.md` + **回写主文档**（修订记录 +1）；② ⇒ 只更新 `roadmap.md` 状态与缺口；④ ⇒ 更新 `01-layering-and-projects` / `09-test-and-gate` |
| **3 实现 + 最小验证** | 跑哪一层查 `architecture/09` §5 的选择表（**别为一行改动跑全量，也别让有风险的改动溜过去**） |
| **4 文档同步** | 按 `architecture/00-architecture-index.md` §4 的"改动同步表"逐条勾 |
| **5 收尾** | `roadmap.md` 状态/缺口归零；触及契约或文件格式 ⇒ 跑一次 T3 |

### 1.3 两条铁律（交汇面 = `Sdk`）

- **模块侧**：不得为绕开框架缺失而自造机制；能力缺失走 §2。
- **框架侧**：不得为单个模块特化（禁止"如果模块是 X 就…"）。若某个能力只有一两个业务模块需要，**先考虑它是不是应该由模块自己用现有面组合出来**。

## 2. 契约扩展通道（模块需要框架没有的能力时）

这是最容易乱的地方：模块想干的事框架给不了，就会诱发"在模块里偷偷绕过去"。固定成 5 步：

| 步 | 内容 |
|---|---|
| **1 登记请求** | 在 `roadmap.md`（或模块页）登记一条 **契约扩展请求**：**要什么 / 为什么现有面做不到 / 影响哪些模块** |
| **2 用户裁决** | 判据：**≥2 个模块需要**，或它**本质只能由框架做**（线程、调度、持久化、拓扑）。否则答复"用现有面组合" |
| **3 只增不改** | 新增类型/成员/`init` 属性；**禁止**：改既有签名、构造器可选参数（= 二进制破坏）、改既有语义（要改语义 ⇒ 走框架轨③ 并回写文档） |
| **4 重编 + 门禁** | 改完**重编全部模块**（二进制兼容判据）+ 跑一次 **T3**（`.\build.ps1`） |

> **例外登记（现行 1 条）**：**G3 的 SDK 只增扩展豁免"跑一次 T3"** —— 用户 2026-09 裁定"旧模块是临时产物、后续测试均用新模块"（`decisions.md` **7.17**）。
> **豁免边界**：被豁免的只是**额外那次完整门禁**；**"重编全部模块"照常发生**（**当时** 6 个参考模块仍在解决方案里，任何构建都会编它们 ⇒ 二进制兼容仍被验证；**该载体已于 2026-09 按用户裁定删除**，现行模块 = `src/Modules/Business/` 下的 **4 个正式模块**）。
> **注意（事实更新 · 2026-09）**：`src/Modules/Reference/` **已按用户裁定删除**（原 6 个参考模块包）；`tests/HYWDebugAssistant.Tests.Reference` **项目名未变**（"Reference" 现指"**判据参考实现**"，**41** 条），`build.ps1` 的模块包校验现为 **4 个正式模块包**。删除的**硬前置 = AC-1~AC-6 判据已由新模块接管** ⇒ **已满足**（见 `06` §G.3）。
| **5 文档** | 更新 `02-module-sdk`（声明面）+ `03-data-protocol-and-typing`（若涉契约）+ `decisions.md`（若动了决定） |

**已挂账的契约待办**（下一轮复盘用，取自 `roadmap.md`）：`WaitForData`（主动接收原语）· `ParticipatesInAutoNetwork`（实现或删除）· `EnumSelector`(B4) 渲染分支 · 命令合并语义 · 池化包装对象（40 B/单元 → 0）· 波形/FFT 依赖引入 · **输入元素的「处理结果」反馈通道**（`roadmap.md` §3 **第 15 项**；G3 的前置 —— 模块需把"某次输入/命令的处理结果"回报到**对应元素**以渲染失败态，现有面做不到，取证见该条）。

## 4. 模块文档（一模块一页）

| 项 | 规定 |
|---|---|
| 位置 | `docs/modules/<模块标识>.md`；清单页 `docs/modules/README.md` |
| 模板 | `docs/modules/_模板.md`（复制即用） |
| 写什么 | **只写模块自己的事**：职责一句话 · 声明面（类型/端口/角色/顺序）· 配置键 · 视图元素 · 用到的契约扩展 · 验收点（引 `implementation/04` 编号）· 已知限制 |
| 不写什么 | 框架契约、机制细节 —— **一律引用分册**，不复制（避免两处漂移） |
| 何时更新 | 与模块代码**同一次改动**；模块状态变化时同步改清单页与 `roadmap.md` |
| 与 roadmap 的分工 | 模块页 = "这个模块是什么"；`roadmap.md` = "做到哪了"（状态唯一源） |

## 5. 验证与提交节奏

| 轨道 | 跑哪一层 | 说明 |
|---|---|---|
| 模块轨 | T0 + 模块测试 | **不跑 T3**；一批模块做完再跑一次 T3 |
| 框架轨 | 按 `09` §5 表 | 纯观感改动仍只需 T0 + 眼睛看；触及契约/格式/依赖/AR ⇒ **T3** |
| 跨轨（契约扩展） | **必须 T3** + 重编全部模块 | 见 §2 第 4 步 |

**提交纪律**：
1. **一次提交 = 一个可独立回滚的意图**（一个模块 / 一个缺陷 / 一个能力）；
2. 提交消息里写**跑了哪一层验证**（T0/T1/T2/T3 与结果），"通过"必须有确定含义；
3. **框架轨改动与模块轨改动不混在一个提交**（回滚粒度不同）；
4. 文档与代码同一次提交（模块页、roadmap 状态、`decisions.md` 视 §1.2 第 2 步）。
