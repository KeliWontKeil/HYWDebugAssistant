# 外部接入：顶层定义（v2 · 按评审收敛 · 待你确认）

> **状态：草稿。** v1（"外部接口能力：标准与顶层设计"）的通道层 / 组帧铁律 / 数据流图 / 四模块同形 / `WaitForData` / "端点即数据面接口"等**均已被评审推翻**，其要点压缩在 §9 沿革。
> 本文只写**顶层**：概念位置 · 机制 · 交付物形状 · 标准化的边界。**不含实现细节，不含参数值。**
> 待你确认的只剩名字（§7）。

---

## 1. 已裁的顶层（六条定义）

| # | 定义 | 形状（只定形状，不定协议） |
|---|---|---|
| 1 | **声明** | 模块在注册钩子里声明**外部接入**：模块内唯一的名字 + 适配件（懂外部标准的实现）+ 参数类型。与数据类型 / 口 / 角色同级；**声明期一次性、运行期不重读** |
| 2 | **实例化与驱动** | 框架按声明开 N 个**会话**；**等待与轮询由框架做**；模块**不为 IO 建活动体** |
| 3 | **交付** | 框架向模块递三样，且只有三样：**应用标准的数据单元** · **会话状态** · **计量**；**协议语义不进交付面** |
| 4 | **生命周期** | 会话的 open / close 由框架随实例状态驱动（Active / Disabled / Removed）；失败与断开按 Issue 类别归属到会话 |
| 5 | **实现分离** | 懂外部标准的是**适配件**；框架只认**中性契约**（开 / 关 / 读 / 写 / 就绪 + 请求面）；协议词与第三方依赖全部关在适配件里 |
| 6 | **连接操作链** | **用户**在模块窗口点〔打开 / 关闭〕→ **模块只发起请求**（自己也不操作连接）→ **框架执行并持有会话**。缺了这条链就是失败设计：用户既不知道何时会连上，也看不到"参数改了一半"的中间态行为 |

## 2. 概念与层次

| 概念 | 层次 | 谁持有 / 实现 | 对外形态 | 与谁同级 |
|---|---|---|---|---|
| 模块 | 用户可感知的功能单元 | 作者写、框架加载 | 有（窗口 + 包内声明） | — |
| 角色 | **抽象描述**（模块内部功能分块） | 模块声明、框架只呈现 | 只在叠加层 | 与"部件"不同层 |
| **口** | **网络**的端点（模块 ↔ 模块） | 框架机制 + 模块数据 | 有（端口标记 / 网络名 / 拓扑） | 与接入同级（都是模块的数据部件） |
| **外部接入** | **框架与模块之间的接触面**（外部标准 → 应用） | 框架持有会话；模块拿到标准数据 | **无形态**（纯逻辑） | 同上；但**口入网、接入不入网** |
| 适配件 | 实现件：懂某个外部标准 | 随模块包 | 无 | 不是模块、不是接入 |
| 实例 | **实现机制**（承载 / 线程 / 生命周期） | 框架 | — | **不是架构角色** |

**三层互不推导**：实例 ↛ 接入 · 角色 ↛ 口 · 口 ↛ 接入。

### 2.1 一句话把数据面切成两半（这是全部标准化的着力点）

> **数据面 = ① 网络模型 + ② 投递机制**
> ① 网络模型（口 · 源 / 宿 · 绑定 · 建网 · 拓扑 · 逐对兼容）→ **只有模块 ↔ 模块**用。
> ② 投递机制（有界队列 · 投递回调 · 丢弃策略与计数 · 停流 · 停止协议 · 计量）→ 模块间通信**与外部接入共用**。

由此：
- **源 / 宿不需要取消，也不需要泛化** —— 它们属于①；外部接入**不进①**（不是源、不是宿、不入网）。
- 外部接入**只用②** ⇒ 模块消费数据的代码，无论来自口还是来自外部接入，**是同一个形状**。

## 3. 机制（最简：一个信号 + 多个工作源）

```
适配件（懂外部标准）  ⇄  中性契约（开/关/读/写/就绪）  ⇄  L3 承载（实例线程 + 一个"有活干"信号）
                                                            │
                         应用标准单元 ──▶ 每会话有界队列 ──▶ 回调 或 读取面 ──▶ 模块逻辑 ──▶ 口 ──▶ 网络
```

1. **等待在框架**：L3 的实例循环只等**它自己的"有活干"信号**（今天 `ModuleCarrier` 里就是那个信号量）。适配件的"就绪"**投进同一个信号** —— 不需要 `WaitAny`、不需要第二套同步原语。
2. **醒来试两个来源**：口队列（出队 → 交给模块）· 会话（读 → 入队 → 交给模块）。多一个来源，不加一类线程。
3. **框架侧是信号驱动，不是节拍驱动**：有数据即醒。⇒ 你直觉里那条"模块有轮询时间限制、框架没有"在这里落地：**模块侧零轮询、零等待、零 IO 线程**。
4. **就绪的实现差异关在适配件里**：串口实际要靠自带泵（线程或 `DataReceived` 事件），套接字是原生异步；框架只等信号，不关心来源。

### 3.1 交付面（我做的决定）

| 交付物 | 形状 | 为什么 |
|---|---|---|
| **数据单元** | **每会话一条有界队列 + 可选回调**：设了回调 ⇒ 框架出队后在实例线程上交给它；没设 ⇒ 单元留在队列里由模块取 | 流是"会丢的东西" ⇒ 队列 + 丢弃分类计数；与口的投递**同形状**，模块只有一个写法 |
| **状态** | **可读快照**（会话状态 + 最近错误文本） | 状态是"当前事实" ⇒ 不做事件面：少一个接口、少一处"事件与快照不同步" |
| **计量** | **可读快照**（收 / 发单元数 · 按类丢弃 · 最后数据时刻） | 与口诊断同口径；呈现由**模块自己的控件**决定（接入无形态） |
| **参数** | **复用模块配置面**：框架把适配件的参数类型登记进该实例的配置快照 ⇒ 配置表单自动出现该协议的参数（枚举出下拉）、随组合件**原样持久化**（零格式改动）、模块**零代码** | 参数域无法统一 ⇒ 让每个适配件自带参数类型；框架只反射出表单，不理解含义 |

### 3.2 `IActivitySource` 的定位（我做的决定）

- **收窄为"非 IO 的周期活动"**（周期采样、定时发送、批处理）。
- **硬规则**：模块**自带活动体**时实例线程归它 ⇒ 框架**不投递回调**，该模块用**读取面**在自己的循环里取；模块**不声明活动体**时由框架驱动，回调生效。
- 于是"两种消费方式"不是风格选择，而由"有没有活动体"唯一决定 —— 不存在同时有两个消费者。

## 4. 生命周期与失败

- **open / close 由框架执行**，三条触发：① 模块收到用户的〔打开 / 关闭〕后**发起请求**；② 实例状态（Active / Disabled / Removed）；③ 参数变更（框架已知配置变更事件）。**执行与持有始终在框架** —— 模块不碰连接本身。
- **框架不自动重试**（既有纪律）；**重连策略属适配件**（它有参数、懂协议），框架只观测状态并上报。
- **失败隔离**：适配件异常不得逸出 ⇒ 框架在边界捕获、转 Issue（Communication / Runtime），会话状态置故障；模块本身继续活着。
- **停止协议覆盖会话**：关闭有界等待；超时 ⇒ 孤儿线程（与今天同一条纪律），登记进验收。
- **线程规模**：会话**不给模块加线程**；适配件可自带泵线程（串口），套接字不需要。

## 5. 标准化的边界（什么被标准化，什么不被）

| 标准化（框架执行，唯一执行者） | 不标准化（适配件 / 模块自决） |
|---|---|
| **声明的形状**：具名接入 = 适配件 + 参数类型 | **参数域**：COM 口 / 波特率 / IP / 组播 / 校验 …… |
| **交付的形状**：定长单元 + 有效长度 · 状态 · 计量 | **协议语义与帧边界**：一帧从哪到哪 · 粘包分包 · 校验 |
| **生命的形状**：开 / 关 / 重开的**触发链**（用户或模块 → 请求 → 框架执行）与失败归类 | **连接策略**：何时自动重连、退避怎么算（模块 / 适配件自决） |

**一句判据**：标准化的是**接口形状与生命周期**，不是**协议语义**。标准要有约束力 ⇒ 必须有**唯一执行者** —— 这正是把能力交给框架、而不是交给各模块自带库的理由。

## 6. 为什么这条路线"最干净 + 实现最简"

1. **与口同形**：模块消费外部数据与消费模块间数据是同一个写法（队列 + 回调 / 读取 + 丢弃计数），不必学第二套模型。
2. **复用配置面**：参数类型由适配件给 ⇒ 配置表单、持久化、恢复默认**全部复用**，零新机制。
3. **不动网络模型**：口仍是唯一建网单位；源 / 宿、兼容判定、建网、拓扑、端口标记**一行不改**。
4. **标准有唯一执行者**：驱动在框架 ⇒ "标准"是被执行的，不是被约定的。
5. **框架层仍无协议词**：中性契约在 L1；协议词与第三方依赖只在适配件里（AR-13 不破）。

## 7. 名字（只剩这一件要你拍）

| 位置 | 候选 | 说明 |
|---|---|---|
| 这一层 | **外部接入层** | 与"网络"并列；"接入" = 外部标准接入应用 |
| 模块声明的东西 | **一条外部接入**（具名） | 与"口 / 角色 / 数据类型"并列 |
| 框架实例化的东西 | **会话** | 有生命周期 / 状态 / 计量 |
| 模块侧那个接口 | **接入接口** | 框架往它上面递数据与状态 |

避开的词：**能力**（`ModuleCapability` 已占用，那是资源族声明）· **口 / 表面**（撞现有词）· **端点**（被 v1 用脏，且 TCP 里另有含义）。

## 8. 待实现 / 未验（不是"代价"，是待办）

1. **参数表单**：v2 依赖"配置表单"接线（今天 `configurationEditor` 是欠账）—— **这是前置项**。
2. **原生资产**：适配件带的第三方原生依赖（`System.IO.Ports` 依赖 `runtime.native.System.IO.Ports`）能否被插件进程解析 —— 需一次探针；框架可能要统一解决一次。
3. **串口就绪**：托管层没有真正的异步等待 ⇒ 适配件自带泵（[dotnet/runtime#28968](https://github.com/dotnet/runtime/issues/28968)）。
4. **中性契约的字段**：开 / 关 / 读 / 写 / 就绪 五项的最小签名，待与 L3 承载的实现一起定。
5. **配置变更与会话参数**：参数改了之后"重开"的时机与失败回滚口径。

---

## 9. 沿革（v1 被推翻的要点，压缩存档）

1. 把**口**说成"设备→框架 / 框架→设备"的接口 —— 错：口是网络端点，方向 = 网络中的源 / 宿。
2. 把组帧写成"四模块共用" —— 应升格为**字节流接入的应用标准**；且**帧边界识别**归适配件，别混。
3. 数据流图**跨过模块本身** —— 错：外部标准 → 接入 → 模块逻辑 → 口 → 网络。
4. 说**四个模块"同形"** —— 错：**同骨架、不同参数域与界面**。
5. 主张给模块加 `WaitForData` —— 错：等待与复用属框架机制。
6. 主张**端点 = 一个实例 + 一个角色 + 一进一出两个口** —— 错：把四个不同层级的概念绑成一个。
7. 主张**端点是数据面的一类源** —— 错：源 / 宿属网络模型，外部接入不入网。
8. 在 (1) 与 (2) 之间摇摆（模块自驱的库 + 框架托管的生命周期）—— 两个所有权并存，不可共存；已定为 **(2) 家族：框架托管、实现由适配件给**。
