# 人机协作的设计与决策流程

> 本技能是**可复用方法论**：不依赖任何具体项目、模块、技术栈。括号里的"例：…"只提示该条通常来自哪一类经历，不构成前提。

## 0. 角色与裁决边界（先定这个，否则后面全部返工）

- **人类 = 需求信号与裁决的唯一来源；AI = 扩散、形式化、实现、取证。** AI 不产出"结论"，只产出"待裁决的命题 + 证据 + 影响面"。
- **按"两分法"划边界**：
  - 属于人的（必须逐条裁决）：语义是什么、边界在哪、谁拥有、默认值是什么含义、命名与术语、用户可见行为的取舍。
  - 属于实现方的（结构冻结后可自行定，但必须登记）：格式、编号规则、分类枚举、调度策略、线程模型、序列化细节。
- **常见失败模式**：把人的倾向"扩写"成架构结论；替人做默认选择（"不打包默认"）；把实现属性当设计问题反复追问，消耗裁决带宽。
- **可执行判据**：每一条拟冻结的措辞，都必须能回答两个问题 ——「**它替代了什么**」「**哪些下游表述必须同步改**」。答不出，就还没到冻结条件。

## 1. 两类不确定性与"进入实现"的阈值

- **A 类**＝"什么东西应该是什么"（语义/结构决策）；**B 类**＝"已确定的东西怎么实现"。
- **进入实现的判据**：剩余未知**以 B 类为主**，且**残余 A 类已显式登记为活清单**（不是"没有了"，是"列出来了"）。
- **实现中暴露的 A 类必须回写设计文档**，不得由代码静默拍板。可执行的落法：实现期一旦发现"应该是什么"未定 → **停止实现** → 登记为待决项 → 人裁决 → 回写文档 → 再继续。
- **常见失败模式**：以"写代码验证设计"为名提前进入实现（等于用不可回退的成本去试探结构）；把"细节未定"当作"结构未定"的借口，或反过来用"细节未定"回避结构决策。
- **判据**：能画出一张"整版原理图"（所有域的结构决策已冻结）才允许做技术选型与实现；**原理图未完成不做 layout**。

## 2. 推进单元是"层"，不是"主题"

- 主题（领域模型/接口/运行时/呈现…）只是**工作分区**；真正的顺序约束在**层**。
- **域内四步协议**（任何主题域或裁决包都适用，前一步未冻结不进下一步）：
  1. **图景描述** —— 先写"这个域是什么"（面向人的心智与类比）。
  2. **概念与支点裁决** —— 立"梁"：对象全集、边界、所有权、保存语义。
  3. **机制 / 结构** —— 支点之上再裁内部结构。
  4. **细节 Gate** —— 格式/编号/分类/调度 → **登记推迟**，不裁决。
- **支点信号**：一批点状问题**全都答不上或悬空** = 缺少上层支点 → **立即停止点状裁决，先向上立支点**。
- **层级定位检查**：每个待裁决问题先自问「**这是哪层的问题？上层冻结了吗？**」下层未冻结时，先补上层或转为 Gate。
- **常见失败模式**：主题批内层序颠倒（下层在上层未冻结时被裁决）—— 这是**回溯的唯一结构性来源**；过早冻结递归/嵌套/机制规则。
- **判据**：一次裁决里若出现"要改上层才能回答"，说明层序错了，回到协议第 1 步。

## 3. 处理人的输入（类比、直觉、自由文本）

- **类比是需求信号，不是架构结论**。三步协议：
  1. **记录原话与场景**，不加工；
  2. 提出「**类比元素 → 抽象**」映射表，**显式标注采纳/不采纳及其边界**；
  3. **请人确认映射**（"你的意思是 X 吗"），确认后才冻结为文档表述。
  - 失败模式：直接把类比形式化（必然失真）；把类比里的修辞读成运行语义。
- **转写校验门**：人用自由文本给出的裁决/倾向，**必须转写为编号命题清单**请其"确认即冻结"；**不得把倾向扩写为结论**。
- **强信号识别**：人说"**感觉缺了点什么 / 无法定夺 / 说不上来**" = **停止当前裁决，先做元分析**（通常是缺上层支点或层序颠倒），而不是继续追问该点。
- **人说"不"时**：先确认理解，再修改；**不要**用"方案 B 其实和 A 类似"绕回原方案。
- **沟通降本技巧**：把页面/方案切成**编号区段**（①②③…）写进说明与代码注释，人只需回"④ 应该紧贴 ③"；**只改被点名的那一段**，不动已认可的部分。
- **不过度解读人的手绘原型**：原型里的文字标签、比例、缺项往往只是"画起来方便"。
- **节奏由人控制**：宁慢勿错；不要为了"推进"而合并裁决。

## 4. 单一事实源与文档治理

- **结论只在一处定义，其他文档一律引用而不复述**（复述必然漂移）。**这条对"数量/编号区间/条目数/版本号"尤其致命**——入口文件里写死区间，几乎必然过期。
- **状态唯一**：进度状态只在一个地方维护；正文不重复声明进度。
- **变更纪律**：改已冻结的结论 → 走新的决策记录（标注取代关系）+ 回写主文档 + 登记修订；只改措辞 → 登记修订即可。
- **失效信息必须搬家，不能并存**：被取代的表述要么删除、要么移入归档区，**绝不与生效结论并排**。
- **裁决后立即回写并清理全部受影响表述**；把"哪些表述必须同步改"当作裁决的一部分来做（否则下一次交叉审查会集中报出"历史结论未随新决策收敛"）。
- **反模式清单**：双份维护同一事实；为兼容旧结构新增"跳转壳"文档或空壳层；只在文档里约定的关键约束（没有可执行检查）。
- **可执行判据**：随机抽 3 条结论，问"它在几处被定义？"；答案必须都是 1。

### 4.5 注释预算（注释不是回写目标）

- **注释只写三类**：为什么这么做（动机与取舍）、不变量与前置条件、反直觉的坑（不写会再踩）。
- **禁止写进注释**：日期与版本号、裁决/决定编号、用户原话、历史叙述（"原先 / 曾经 / 旧实现 / 之前"）、复述下一行代码就能表达的内容、测试读数、文件与改动清单。
- **当前布局取值也不进注释**：坐标 / 尺寸 / 间距 / 像素值描述的是"现在正好是多少"，改布局就会过期；注释写**意图与关系**（谁跟谁对齐、为什么这样排、哪里会踩坑），具体值指到唯一来源（声明文件 / 主题 token / 控件属性）。
- **回写目标只有文档**：决定与过程进文档，且只落一处（§4.6）；代码里最多留**一条**指向该处的指针。**同一个事实已在文档里 ⇒ 注释里删掉它。**
- **注释与代码不一致时删注释**，不要"顺手把注释改新"——改注释等于维护第二份事实源，它必然再次过期。
- **可执行检查**：用一条检索或规则扫源码注释里的日期、决定编号、用户字样、历史叙述词与**当前布局数值**（坐标 / 尺寸 / 像素值），命中即失败；确有必要保留的走**例外登记**（代码标记 + 唯一登记处 + 复查条件）。
- **反模式**：把"回写文档"执行成"回写注释" —— 同一事实在代码与文档各存一份，代码那份必然过期，且抬高每一次阅读的成本。

### 4.6 文档预算（落点与频率）

- **一次裁决只落两处**：决定记录**一条**（决定了什么 + 为什么 + 取代了谁）+ **受影响的唯一一个**下游正文；其余位置**只留指针**（引决定编号，不复述）。
- **状态与读数各自单点**：进度只在一个文件里维护；实测读数/基线只在一处维护，别处引用它。
- **回写频率 = 每批次一次**，在该批次收尾时做；进行中不写文档、不写注释。
- **按体裁分配内容**：决定记录写"决定了什么 + 为什么"；正文写"现在是什么样"；对外契约只写对外部分。**过程叙述、评审对话、测试统计、实现细节（类名/行号）不进任何文档。**
- **写进表格单元格的内容必须转义**：裸露的分隔符会把表格撑坏——表格错位属于"事实源被破坏"，不是排版小事。
- **判断一次回写是否必要**：问「**它替代了什么**」「**哪些下游表述必须同步改**」；只答得出前者的，通常一条追加即可，不必扩散。

## 5. 先证伪假设，再改代码

- **报"看起来坏了"时的查序**：先查**是否真的存在**（有没有画出来 / 有没有接线 / 有没有被盖住），再查**参数是否合适**。先动参数会掩盖真正的根因，并产生"改了还是老样子"的循环。
- **主观描述 → 数值实验**：把"抖 / 不跟手 / 卡 / 错位"这类描述**先做成纯计算的最小实验**，把量打出来（多少像素、在什么区间、单向还是双向），再定方案；**实验做完只把机制不变量转正为断言**（"次数翻倍不新增""缓冲借还平衡"这类），**"手感/观感"本身不写断言、事故现象也不留回归用例**；根因是结构问题的**用设计消灭**，之后靠截图 + 人眼复核。
- **"扫描通过"≠"问题解决"**：判据全绿只说明**被排除的那一层**没问题。**接着问"剩下的差异在哪一层"**，逐层证伪；**不要在被排除的层里继续加机制**。
- **"更好的做法"常常是把新对象并进既有那条规则**：遇到"两种东西要一起动"，先问「**能不能把它们放进同一张图/同一条规则**」，而不是再写一条联动规则。
- **归因纪律**：只报证据支持的结论；被推翻时**在文档里更正归因**并留下更正记录。
- **常见失败模式**：把"能跑"当作"正确"（"这样行不行"要先**把形态拆开**：几个源、几个宿、同口还是分口，再对每种形态说清"框架做了什么、应用必须自己做什么"——含混地说"可以"或"不行"都不负责任）。

## 6. 落地与验收的节奏

- **固定循环**：设计冻结 → 实现 → 自证（分层验证）→ **人手工验收** → 回写文档。
- **验收是一次性的，不是长期资产**：每个功能完成后当场跑一遍、看一遍；要看的现象写在当次回复或提交说明里，验收完即失效。确实需要落成文件时，按「**编号 ｜ 操作 ｜ 可观察预期 ｜ 结果**」写，且只在当期存在——**不要维护跨功能、跨里程碑的验收清单**，它会迅速膨胀成第二份状态文档。
- **验收前置要写进清单**（例：先跑一次完整门禁、先关闭正在运行的实例），因为这些顺序错了会产生假的失败。
- **交付纪律**：① 报告必须区分"我跑了哪一层"，**不得把局部通过说成全量通过**；② 给出**可复现的验证步骤**；③ 明确"哪部分没验、由谁验"。
