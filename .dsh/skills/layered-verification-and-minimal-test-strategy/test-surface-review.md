# 测试面评审表与破坏性重整步骤

> 配套 [`SKILL.md`](./SKILL.md) 的 §0.1 / §0.2 / §0.3。用于**决定一条测试的去留**，以及**一次性重整**整个测试面。
> 本文件是**配附件**：约束正文在 `SKILL.md`；这里只是可照抄的表格。

## 一、单条用例判据（照表勾）

| # | 问 | 答不上来/答"否"的后果 |
|---|---|---|
| 1 | 它失败时，**用户会看到什么坏结果**？（必须是一句"人能观察到的现象"） | 删 |
| 2 | 这个坏结果**有没有更靠外的一层已经兜住**？（如：端到端用例已覆盖、架构规则已覆盖） | 删 |
| 3 | 它断言的是**来源 / 一致性 / 结构 / 边界**，而不是某个字面值（含**用户可改的资源名 / 资源数值 / 布局尺寸**）？ | 改成同一来源对照或关系/边界判据，或删 |
| 3b | 它没有把模块视图/窗口的**可调宽度、高度、最小尺寸、间距**抄成期望值？设计者改 `.axaml` 尺寸后仍应成立？ | 改成"视图声明 + 框架 chrome"或"至少填满内容区"这类来源/关系判据 |
| 4 | 它**不与既有用例重复**同一事实？ | 删（保有更靠外的那一条） |
| 5 | 它**不会因为与被测行为无关的重构而变红**？ | 删或改成结构判据 |
| 6 | 它构造被测对象时走的是**唯一夹具**，而不是手搭领域对象/声明树？ | 先改夹具，再留 |
| 7 | 它是不是在**钉某个已经修好的历史事故的样子**？（注释里常见"回归网/被钉住的缺陷/曾经炸"） | **删**；根因是结构问题的用设计消灭，不立台账 |
| 8 | 它是不是**交付物**？（判据文档、用法示范、留图/留文本给人看） | **删**；判据进文档，图片进截图工具 |

**1–4 问优先级最高**：答不上第 1 问的用例，其余全绿也是负债。

## 二、逐文件评审表（模板）

| 文件 | 用例数 | 它负责的"看不见的问题" | 判 | 理由 / 去向 |
|---|---|---|---|---|
| `XxxWindowVisualTests.cs` | 50 | 无（呈现） | 删 | 呈现走"截图 + 人眼" |
| `XxxContractTests.cs` | 6 | 契约面（模块与框架的约定） | 留 | 人眼不可及，且失败会让模块静默不可用 |
| `XxxStressTests.cs` | 12 | 真实负载下的时序 | 移出 | 按需跑（开发期临时测试）；功能收尾登记可删 |
| `XxxSnapshotTool.cs` | 3 | 无（出 PNG） | 改为工具 | 不写断言、不进自动化门禁 |
| `…` | | | | |

判 = **留 / 删 / 合并 / 移出 / 改为工具**（合并要写明并入哪个文件或哪条参数化用例）。

## 三、破坏性重整步骤（一次做完，不许改一个跑一个）

```
① 清点：各测试项目、各文件的用例数（一条命令产表，不逐个打开文件）
② 评审：照 §一/§二 填表，先把"删 / 移出 / 改为工具"的清单列全（一次列全，不边删边想）
③ 落清单：
   · 整文件删除优先（代价最小、不牵动编译面）
   · 呈现类：删断言；需要给人看画面的，改成截图工具（无断言、独立进程、输出图片）
   · 压力/性能类：加类别标记后移出门禁，门禁提供 -Include* 开关
   · 需要保留的契约面用例：按新口径一次性改完（夹具 + 断言）
   · 删掉只被删掉用例使用的夹具/桩（否则会留下死代码与警告）
   · 历史事故若暴露结构问题：用设计消灭根因（改接口 / 改唯一来源 / 改约束），不立台账
④ 门禁与脚本：默认过滤按需类别；加"0 用例即失败"守卫；打印每个项目的耗时
⑤ 一次整体验证：构建（受影响测试项目 + 被测库项目）→ 全量测试一次（含按需类各一次）
⑥ 报告：重整前/后条数、删掉/移出/工具化的类别、留下的类别各自兜住什么、
   门禁逐段读数（构建 / 各测试项目 / 测试小计）
```

**纪律**：

- 不做"删一条 → 编译 → 再删一条"。中间态**不要求全绿**，也不看中间态颜色。
- `TreatWarningsAsErrors`、全量测试、门禁只在 **⑤** 这一次要求。
- 删除的判据写在报告里（哪一类被删），但**删除本身不需要逐条自证**——版本控制就是安全网。
- 重整后仍要有一个**显式的程序集预算**：写清"每个测试项目最多留多少条、它负责哪些看不见的问题"。超预算新增一条 ⇒ 先删一条。
- **不要用新用例补偿删掉的旧用例**：机制不变量已在保留面里；事故现象不入用例，根因靠设计消灭。

## 四、常见误判

| 现象 | 错误结论 | 正确动作 |
|---|---|---|
| 契约面一改，几十条测试编译不过 | "先把测试改绿再动产品" | 先让产品定稿；测试面此时应被**重整**（该删的删、该经夹具的经夹具） |
| 布局/外观改完，一批断言变红 | "断言写得不够细" | 把"当前取值"换成**同一来源对照**或**关系/边界**；用户可改的资源名 / 数值 / 视图尺寸本来就不该当判据 |
| 用例数量多、跑得久 | "测试很扎实" | 看它覆盖的是"看不见的问题"还是"内部形状/呈现" |
| 某条用例很难维护 | "再改改它" | 按 §一 判据定去留；维护成本本身就是删除的理由 |
| 删了历史缺陷用例，担心复发 | "补一条更细的回归断言" | 用设计消灭根因，不用断言兜住现象；不立待办台账 |
| 删了 UI 断言，担心界面坏了没人发现 | "加回出像素/像素比对" | 改 UI 就走"编译 + 截图 + 人眼"；自动化只保留行为链路 |
| 删测试后没人发现问题 | "不该删" | 记录这一类问题的**人工观察点**；若确实再次发生，补一条**端到端行为**用例，而不是补一串形状断言 |
| 门禁变慢 | "少跑几条" | 先量分步耗时：最大单项常常不是测试（许可/依赖检查、打包、文档站）；再按类别把压力/性能/截图移出门禁 |
| 用户说"我自己跑一遍没发现问题" | "那测试就不用跑了" | 人工观察覆盖的是"看得见"的那一层；**看不见的那一层仍需一次整体验证** |
