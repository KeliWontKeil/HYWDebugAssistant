# 分层验证与最小工作量的测试策略

> 本技能是**可复用方法论**：不依赖具体语言、框架或项目。括号里的"例：…"只提示该条通常来自哪一类经历。

## 0. 先把"层"定义清楚，并给出代价

分层的目的不是"少跑测试"，而是**让每次验证的代价与这次改动真实的风险相称**。

| 层 | 做什么 | 首次能发现什么 | 量级 |
|---|---|---|---|
| **T0 单项目编译** | 只编译本次改动的项目（含其下游） | 语法、类型、分析器/风格规则、可见性 | 秒级 |
| **T1 单类测试** | 只跑匹配的测试（按名称/类名过滤） | 该逻辑分支的行为回归 | 数秒 |
| **T2 单测试项目** | 一个增量收尾时跑整个测试项目 | 跨类耦合、共享状态冲突 | 十秒级 |
| **T3 完整门禁** | 还原 + 构建（0 错误 0 警告）+ 依赖/许可/架构规则检查 + 全部测试 | 契约/格式/依赖/架构违规 | 几十秒 |
| **表现层通道** | 只编译 + 把应用跑起来用眼睛看 | 布局、间距、颜色、文案、观感 | 秒级 |

**必要的基础设施**：把这一切做成**一个入口脚本**，并把已知的"环境摩擦"内置进去（清理会污染构建的环境变量、停掉会锁定输出产物的进程、检测"目标程序在跑"并**快速失败**而不是让构建重试十次）。**纪律写进工具，比写在文档里可靠**。

## 0.1 第一序位：人工可感知优先（谁的问题配得到验证资源）

**验证资源的第一顺位是"人能直接感知的问题"**，不是"能写断言的问题"。

| 问题类别 | 谁验 | 理由 |
|---|---|---|
| **人能直接看到的**（功能有没有出来、界面有没有、窗口是不是空的、按钮点不点得动、明显报错） | **由人跑起来看**；AI 只负责"能出包"（T0 编译通过） | 人一次观察就覆盖掉的结论，写成几十条断言是把人力换成机器噪声 |
| **看不见、难手动触碰的**（嵌入资源的可解析性、边界拒绝、并发/缓冲/生命周期、持久化一致性、格式/契约面、架构分层） | **才写测试** | 人眼不可及，且失败代价高 |
| **纯观感**（间距、颜色、文案、像素位置） | 只编译 + 人眼验收，**不写测试** | "对错"不客观，写进断言等于把每次微调变成测试维护 |

**判定一条测试该不该存在的三问**（任一问答不上来 ⇒ 删）：
1. 它失败时，**用户/使用者会看到什么坏结果**？（答"某个内部字段不对"不算）
2. 这个坏结果**有没有更靠外的一层已经兜住**？（被兜住 ⇒ 删）
3. 它会不会**随着与被测行为无关的重构而无意义地变红**？（会 ⇒ 改成结构/来源判据，或删）

**测试不是交付物**：测试的价值只在于"替人看那些看不到的地方"。当"让测试通过"开始吃掉开发时间、并且改动的是测试自己的形状而不是产品行为时，已经进入**测试漩涡**——此时的正解是**治理测试面**，不是继续追绿。

## 0.2 测试面预算：越小越好（准入 + 删除 + 重整）

**总原则：测试面越小越好；删除没有代价（历史在版本控制里），保留有代价（每次契约面改动都要跟着改）。**

**准入（新增一条测试必须同时满足）**：
1. 拦得住**一类已发生过的**缺陷（不是"以防万一"的想象）；
2. **不与既有用例重复断言同一事实**（同一事实只许有一处断言，跨测试项目重复尤其要删）；
3. 断言**来源 / 一致性 / 结构 / 边界**，而不是钉住某个字面值（像素、`Margin`、内部字段名、私有形状）；
4. 能通过 0.1 的三问。

达不到 ⇒ 写成**临时探针**，定位完即删（探针不是测试）。

**构造纪律（防止一次载体改动引发百处改写）**：
- **禁止测试直接手搭领域对象/声明树/配置树**：必须经**唯一夹具入口**（一个函数/一个工厂）构造被测对象。载体、字段名、缺省值一变，只改夹具一处。
- **禁止"复制粘贴一个既有用例改个值"**：重复形状的用例合并成 `[Theory]`/参数化，或删掉——它们提供的信息量与一条相同。
- **禁止把实现内部形状当契约**：断言"排成两行三列、同宽同高"这类**用户可感知的结构**可以；断言"宽 128、高 30、`Margin=4,0,5,0`"不行。

**程序集预算**：每个测试程序集维护一个**显式预算**（用例条数上限 + 它负责的"看不见的问题"清单）。超预算新增一条，必须**同时删掉/合并一条**，或者写明"它替掉了哪一条的覆盖"。

**破坏性重整（一次性做完，不许改一个跑一个）**：
1. 逐文件列清单，按 0.1 的三问给判据：留 / 删 / 合并；
2. **一次删完、一次改完**（允许大段删除整文件）；
3. 然后**只做一次**整体构建 + 一次全量测试，最后再报告；
4. 重整期间**不看中间态颜色**（不要求"每删一个还全绿"）。

## 1. 按改动范围选层（判据表）

| 改动性质 | 跑哪层 | 判据 |
|---|---|---|
| **纯表现层**（样式/文案/间距/颜色/布局字面值） | T0 + 跑起来看 | **不跑测试、不跑门禁**。这类改动没有可自动判定的"对错"，跑测试是空转 |
| **连带逻辑**（视图模型 / 命令 / 数据结构 / 校验） | T1 只跑**受影响的那个测试类** | 只跑被改动的逻辑面 |
| **契约 / 公开面 / 文件格式 / 依赖清单 / 架构规则** | **必须 T3**，但**在一个契约面改完、而不是每改一处** | 影响面不可枚举 |
| **机制类改动**（并发、缓冲、生命周期、持久化） | T3 + **组合级验证** | 只有端到端组合能证明 |
| **交给人类手工验证之前** | **只要求 T0**（能出包、能被跑起来） | 人的观察本身就是这一层的验收；自证交给下一轮 |
| **宣布某个步骤/里程碑完成时** | **必须 T3**（并与文档回写同时发生） | 状态回写必须有事实支撑 |
| **测试面自身重整** | **一次做完后 T2/T3 各一次** | 见 0.2 |

**执行纪律**：
1. **批量改完再编译**——不要"改一行编一次"（编译是最便宜的层，但它的价值在于"尽早发现"，而不是"高频触发"）。
2. **完整门禁不是收尾仪式**：只在上面表里那三种时点跑。频繁跑全量会让人开始"为了快而跳过"，反而降低纪律。
3. **例外要有裁决**：若有人明确要求"某阶段一律不跑全量门禁"（例：表现层还在大规模调整期），把这条**写成带触发条件的例外**（"直到 X 就绪后恢复"），而不是变成默契。
4. **跳过重编 = 使用旧产物**：只重编测试项目而不重编被改动的库项目，测试跑的是旧产物，会让人误判"改了没生效"。**这条必须写在工具注释或验证表第一行**，因为它太容易被踩。
5. **同一改动、同一层只跑一次**：重复跑不增加信息，只增加成本。改动集合变了，按新集合重新选层，而不是把旧层再跑一遍"确认一下"。
6. **并行工作单元不得跑全量**：交给子代理/并行分支的验证只到"**改动工程的编译 + 受影响的那一个测试类**"；**T2/T3 由主流程按批次跑一次**，避免同一批改动被并行地验多遍。
7. **新增用例的准入**：见 0.2（四条同时满足才加）；达不到就写成临时探针，定位完即删。
8. **纯表现层不新增用例**：样式/文案/间距/布局字面值走"编译 + 人眼验收"。
9. **禁止"改一个验证一个"**：契约面/载体/机制类改动期间，**先把改动集合做完**（产品 → 夹具 → 断言），再选层验证一次。中间态不要求全绿；`TreatWarningsAsErrors`、全量测试只在**收尾**这一次要求。发现自己"改一处 → 编译 → 跑测试 → 再改一处"地循环时，停下来，把剩余改动列成清单一次做完。
10. **治理优先于修复**：一旦判断问题出在流程/测试面本身，**暂停其他修复与架构调整**，先把治理落成"可执行的约束"（写进技能/工具/门禁），再做一次彻底重整。顺手修一修会造成治理不彻底，把"治理半成品"和"产品半成品"混在一起，比问题本身更贵。

## 2. 报告纪律：让"通过"有确定的含义

- **必须区分"我跑了哪一层"**，例如"T0 + 受影响的 T1"，**不得把局部通过说成全量通过**。
- **过滤词没匹配到任何测试 ≠ 失败**：工具应单独识别并提示"换个过滤词或去掉过滤跑整项目"。把这种情况当失败会浪费人的时间，当成功则会掩盖漏测。
- **报告"通过"时给出**：跑的命令、范围、耗时量级、以及**没覆盖的部分由谁验**。
- **不要为了跑验证而杀掉别人正在使用的实例**（会丢失现场）：先问；需要时用"应急模式"（只重编测试项目、不碰被引用应用的输出），或在提示里明确"会丢现场"。
- **报告"测试面重整"时给出**：重整前后的用例条数、删掉了哪一类、留下了哪一类"看不见的问题"、以及**留下的测试各自兜住什么**。

## 3. 让缺陷可复现：探针与回归

- **主观/时序类缺陷先做探针，不先改代码**：
  - 记录关键量（输入、输出、差值、状态前后、几何前后）；
  - 只在异常条件成立时**落盘最近 N 帧**，并在界面上把落盘路径告诉人；
  - **定位完成即删除探针**，并把其中稳定的判据**转正为回归断言**。
- **断言要断言"来源/一致性"，不要断言"某个具体值"**：断言具体值在"功能恒回落到占位值"时也会通过，等于没测。
- **对"恒定噪声"的断言要写成与次数无关的形式**：例如分配/调用类断言，写成"**次数翻倍不新增**"，而不是"等于 0"——后者会被首次调用的一次性开销污染成偶发失败。
- **几类高价值的固定断言模式**（可直接照搬）：
  - **反向断言**：数据未变时，对象引用必须相同（抓"刷新即重建"）。
  - **幂等断言**：同一次刷新里读两次，必须得到同一个数（抓不可重复读的指标）。
  - **来源断言**：颜色的来源必须等于某个键，而不是"是某种颜色"。
  - **唯一性断言**：键必须唯一且一一对应（抓"显示名当键"）。
  - **边界拒绝断言**：越界/版本过新/形状不符必须被拒绝且原文件不被改写。
  - **数值钉住断言**：端到端跑真实链路，断言"这个数必须 > 0"（抓静默归零）。
  - **资源可解析断言**：随程序集嵌入/随包发布的资源（schema、声明文件、模板、清单）必须**真的能被解析**——构建期不校验它们，这是"编译通过却带病出货"的高发区。
- **先假设自己可能改错**：用户说"还是老样子"时，先确认**我的改动真的被加载了**（产物是否重编、是否被缓存、是否被另一条实现路径覆盖），再去改代码。

## 4. 验证真正跑不动时：排查顺序

### 4.1 "单独跑绿、一起跑红"

**先怀疑共享可变状态，再怀疑测试本身**，顺序：
1. **静态 / 单例 / 进全局资源字典的可变对象**（尤其有线程亲和性、有缓存、有懒初始化的）；
2. **进程级配置**（渲染模式、环境变量、全局开关）——不同配置的测试会话**必须拆进程**，同进程混用会把两边的会话一起弄坏；
3. **需要专属线程/专属资源的测试**：放进"禁止并行"的集合，或串行执行；
4. 最后才怀疑测试自身的写法。

### 4.2 构建/测试被环境挡住

| 症状 | 常见根因 | 规避 |
|---|---|---|
| 构建配置解析失败 | 外部环境变量污染 | 工具启动即清理/固定；并建议在系统层删除 |
| 输出文件被占用 | 运行中的实例 / 设计器宿主 | 工具先检测并**快速失败**给可操作提示；必要时提供"停掉它"开关（并提示会丢现场） |
| 重试十次才失败 | 同上（没做前置检测） | 前置检测必须在构建之前 |
| 测试"改了没生效" | 跳过了被改动项目的重编 | 应急模式的前提写清楚：**先编改动的项目** |
| 输出刷屏无法定位 | 未降级日志级别 | 平时用静默模式；失败时再加过滤定位单个测试 |

## 5. 验证的边界：明确"不做什么"

- **不设覆盖率硬性百分比**：以"机制改动必须有组合级验证"替代。
- **自动化只覆盖主要问题，不追求全覆盖**；**不可自动化的应用层行为交给人类手工验收清单**（并保持"清单只写人能观察到的现象"）。
- **基准/性能测试不进常规门禁**（按需运行）；但**热路径改动要给出分配或吞吐数据**。
- **架构/规则类检查必须"目标缺失即失败"**，不允许"没有对象就跳过"——**规则的静默失效比误报危险得多**。
- **规则报错时先确认真违规还是误报**；确属误报走**例外登记**（代码注释 + 唯一登记处 + 复查条件），**不擅自改规则或关规则**。
- **关键约束必须能映射到可执行检查**（检索/构建/测试/规则），只写在文档里的约束等于不存在。
- **不静默降级**：未做到的事必须登记为待办或例外，不能"暂不实现"就算完成。
- **不许用测试替代使用**：测试通过不等于功能可用；"人跑起来看"是不可省略的一环。
