# 同一文件一次改完（批量编辑纪律）

> 本技能是**可复用方法论**：不依赖具体语言、工具或项目。它约束的是"怎么下笔"，不是"写什么"。

## 0. 一条规则与它的理由

**规则**：同一个文件在一次任务里**只编辑一次**——编辑前先把该文件**所有**要改的位置找齐并一次落盘；禁止对同一文件连续做"改一行、再改一行"的微改。

**为什么**（代价是线性的，不是风格问题）：

| 逐行微改的代价 | 说明 |
|---|---|
| 重复传输 | 每次编辑都要把该文件的相关上下文（常常是整段、甚至整个文件）重发一遍；改 N 处 ⇒ 同一份内容被传 N 次 |
| 缓存失效 | 每次写盘都会让"已读到的文件内容"作废 ⇒ 下一次编辑前往往要重读，读与写互相触发 |
| 中间态 | 任务中途失败/被打断时，文件停在"改了一半"的状态；阅读者无法判断哪些是旧口径、哪些是新口径 |
| 噪声评审 | 评审者看到的是一串碎片化改动，而不是"这一处结论是什么" |
| 校验空转 | 每改一行跑一次校验，等于把同一份构建/审计跑 N 次 |

**判据**：如果两次编辑之间**没有**发生"需要读取外部结果才能决定下一处怎么改"的事，那两次编辑就该合并成一次。

## 1. 允许分次的三种例外

1. **后一处的内容取决于前一处的结果**：例如先编译/跑测试/跑脚本，再按它的输出决定下一处怎么改。
2. **工具报错需要重试**：编辑被拒绝（未命中、越权、文件被锁）后再试一次，不算违约。
3. **文件大到无法一次重写**：按**逻辑段**分次，但每一段在同一次任务里只碰一次；分段的边界要选在"这一段内部的所有改动都能一次说清"的地方。

除以上三种，**不要**用"先改一处看看效果"当理由。

## 2. 操作配方（五步）

1. **先找齐**：用搜索把该文件里**所有**待改点列出来（关键词、行号、每处的一句话理由），不要一边找一边改。
2. **取够上下文**：为每个待改点读到足够的上下文（整段/整行/相邻行），确认"改哪里、改成什么"已经确定。
3. **选形态**：
   - 改动跨多处、且分布零散 ⇒ **整文件重写**（先读全文，再一次写回同一内容 + 全部改动）。
   - 改动集中在少数连续区块 ⇒ **少量大块替换**（每次替换覆盖一个完整逻辑段，而不是一行）。
4. **一次落盘**：把这一批改动一次提交。
5. **一次校验**：整批落盘后再跑校验（编译/测试/审计/格式检查）**一次**；通过即结束。只有在"校验结果会改变后续改法"时，才允许把校验插在中间。

## 3. 同批多文件的做法

- 每个文件各自**一次**完成；一个文件在同一轮里不出现第二次编辑。
- 读取阶段可以并行（把要读的文件一次性并行读掉），把往返次数压到最低。
- 若两个文件必须"同进同出"（互相引用、契约对齐），先把两边的改动都定稿，再分别一次落盘。

## 4. 校验节奏

| 情形 | 校验时机 |
|---|---|
| 同一文件的一批改动 | 全部落盘后跑一次 |
| 纯字面/文案/样式类改动 | 编译或渲染检查一次即可，不必每处都跑 |
| 会改变后续改法的校验（例如"下一步要按错误输出决定"） | 允许插在中间，但要把"因此分次"写进报告 |
| 一次任务收尾 | 跑一次该范围的完整校验，并在报告里写明跑了哪一层 |

## 5. 反例与正例

| 反例 | 正例 |
|---|---|
| 同一文件改了 6 次，每次一行 | 一次读完，改 6 处，写回 1 次 |
| 每改一处就跑一次审计/编译 | 改完一批，跑一次审计/编译 |
| "先改这处，看看对不对，再改下一处" | 先把该文件所有待改点定稿，再一次落盘 |
| 用多次"插入一行/删除一行"拼出一段新文字 | 用一次"整段替换"把旧段换成新段 |
| 中途被打断，文件停在半新半旧 | 一次落盘 ⇒ 要么全旧，要么全新 |

## 6. 自检清单

- [ ] 我在这个文件上**只**编辑了一次吗？
- [ ] 两次编辑之间，是否真的存在"必须等外部结果"的依赖？
- [ ] 每个待改点是否在编辑前就**列出来**了（而不是边改边发现）？
- [ ] 校验是否放在整批落盘之后（而不是每处之后）？
- [ ] 若确实分了次，我在报告里写明了**为什么**必须分次吗？
